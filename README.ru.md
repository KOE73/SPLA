## Что важно в SPLA

**Только .NET.** Агент, его инструменты и все плагины — это C# и .NET: никакого Python-рантайма,
никакого Node-процесса, никаких инструментов на подпроцессах в пути исполнения агента. Один
инструментарий для сборки, отладки и поставки — значит одна поверхность отказов, а не три. Это
жёсткое ограничение для ядра и плагинов, а не лозунг: плагин, которому для *запуска* инструментов
агента нужен Python или Node, здесь не приживётся. Web-клиент — единственное осознанное исключение:
это браузерный UI (Vue/TypeScript), а не часть рантайма агента, и он обращается к сервису так же,
как любой другой клиент.

**Проектность.** Всё поведение агента заточено на файл проекта `.spla` — рабочую область,
инструкции, LLM-эндпоинт, плагины, роли, разрешения. Это не конфиг для галочки: файл — единственная
точка входа что для UI, что для CLI, что для стороннего кода, который встраивает агента (см. ниже).

**Компонентность.** Агент — не только приложение, но и библиотека. Чат — обычный объект: можно
подключить `SPLA.Runtime` в свой C#-код, открыть тот же файл `.spla` и получить полноценного агента
без CLI, сервиса и UI:

```csharp
var settings = ConfigLoader.LoadAndResolve("my.spla");
using var runtime = new AgentRuntime(settings, loggerFactory);
var chat = new ChatRegistry(runtime).CreateNew("my task");
await chat.SendAsync(text, callbacks, permission, clarify, ct, images);
```

Это не гипотетический сценарий — в [`demo/workers/`](demo/workers/) лежат реально работающие
примеры такого встраивания: [VisionAgent](demo/workers/VisionAgent/README.md) (анализ кадров с
камеры моделью), [LogSentry](demo/workers/LogSentry/README.md) (триаж лог-файла) и
[Summarizer](demo/workers/Summarizer/README.md) (прогон документа по матрице промптов и моделей).

**Модульность.** Модульность работает в обе стороны:

- «голову» (модель) можно менять, не трогая остальное — сменить эндпоинт LLM в `.spla`, или вовсе
  прогнать один и тот же промпт через несколько локальных моделей подряд;
- а можно, наоборот, отдать *свои* инструменты внешней голове: SPLA поднимает `/mcp` на своём
  сервисе и работает как MCP-сервер, так что большая внешняя модель (например, в другом чате или
  другом продукте) получает руки — доступ к локальным файлам, shell, плагинам SPLA — через
  стандартный MCP, а не через копипасту.

**Роли.** Роль — это набор инструкций и разрешений, который назначается чату, а не проекту в целом:
в одном проекте у разных чатов могут быть разные роли. А чаты — не изолированные острова: для
переписки между ними есть отдельный инструмент, `agent_correspond`, так что несколько чатов с
разными ролями можно свести в команду агентов, которая общается друг с другом напрямую — вплоть
до спора нескольких точек зрения на одну задачу — а не координируется вручную через человека.

## Основные возможности

1. **Локальные LLM.** SPLA рассчитан на локальные модели и OpenAI-compatible API. Конфигурация по умолчанию - LM Studio по адресу `http://127.0.0.1:1234/v1`, но можно использовать другой совместимый runtime.
2. **Расширяемая система инструментов.** Инструменты регистрируются через MCP-хост и плагины; отдельный MCP-клиент позволяет агенту звать инструменты внешних MCP-серверов, а сама SPLA может выступать MCP-сервером для внешней модели (см. выше).
3. **Организация проектов.** Проект SPLA описывается файлом `.spla` в рабочей директории. В нем задаются рабочая область, режим агента, инструкции, документация, игнорируемые пути, LLM endpoint, плагины, роли и разрешения. Файл можно связать с приложением и открывать как отдельную рабочую область.
4. **Безопасность через режимы, роли и зоны.** Пять режимов агента (`Chat`, `Research`, `Inspect`, `Edit`, `Agent`) по-прежнему задают верхнюю границу автономности чата. Поверх них разрешения переходят на модель зон и грантов на ребро между ними, а роли собирают набор инструкций и разрешений для конкретного чата. Подробнее — в разделе [«Безопасность»](#безопасность).

## Архитектура

Внутри система разложена по слоям — от понятий, не знающих ни про протокол, ни про ОС, до окон,
через которые с агентом разговаривают:

| Слой | Что это |
|---|---|
| Домен (`SPLA.Domain`) | понятия и контракты, не знающие ни про протокол, ни про провайдера, ни про операционную систему |
| Конвейер инструментов (`SPLA.MCP.Core`) | путь вызова от имени, названного моделью, до исполнения, и сборка контекста, из которого модель это имя узнала |
| Рантайм чата (`SPLA.Runtime` / `SPLA.Agent`) | живое состояние разговора и сам цикл хода |
| Провайдеры LLM (`src/llm`) | интеграции с теми, кто на самом деле отвечает на запрос |
| Сервис и протокол (`src/service`) | агент за проводом, клиенты подключаются снаружи |
| Плагины и инструменты | то, что агент умеет делать руками |
| Клиенты (web / CLI / Avalonia) | окна, через которые с агентом разговаривают |

По сути, агент — это `SPLA.CLI` и рантайм под ним; у CLI много режимов запуска, и разные способы
достучаться до агента — это его разные грани, а не разные продукта:

- `spla chat open` — интерактивный REPL, чат в терминале;
- `spla chat run` — безголовый одноразовый/пакетный запуск: один или несколько промптов на одну или
  несколько моделей, вывод на экран или в файлы — режим для скриптов и автоматизации;
- `spla serve` — тот же рантайм, поднятый как сервис за WebSocket-протоколом, к которому
  подключаются другие клиенты;
- `spla` в MCP-режиме — CLI сам говорит по MCP через stdio с внешней головой (см. «Модульность» выше);
- `spla start` / `spla stop` / `spla ps` — поднять агента на проекте и оставить работать в фоне,
  остановить, посмотреть, что уже запущено.

Отдельно от CLI, `SPLA.Runtime` можно подключить напрямую в свой C#-код (см. «Компонентность» выше)
— это ещё один способ получить агента, вообще без CLI, сервиса и UI.

Что до графических клиентов — web-клиент (`web/`, Vue 3 + TypeScript + Vite) является фактическим
рендерером: файловый браузер, редактор кода/Markdown, настройки проекта и ролей, панели плагинов —
всё это Vue-код, говорящий с сервисом по WebSocket. Этот же web-клиент можно открыть напрямую в
обычном браузере, без Avalonia и без установки — достаточно, чтобы где-то был поднят `spla serve`
(или embedded-сервис) и до него был сетевой доступ. Desktop-приложение на Avalonia
(`SPLA.UI.Avalonia`) сейчас не отдельный UI, а тонкая оболочка: нативная оконная рамка + иконка в
трее вокруг `WebView`, который показывает тот же web-клиент. Своих нативных экранов чата или
настроек в Avalonia больше нет.

У каждого проекта свои чаты и состояние агента; один сервис может обслуживать несколько проектов и
клиентов одновременно.

## Инструменты

Возможности агента складываются из двух уровней: встроенных инструментов, которые образуют базовую рабочую среду SPLA, и подключаемых плагинов для специализированных задач.
Такой подход сохраняет основной набор компактным, а дополнительные возможности позволяет добавлять только там, где они действительно нужны проекту.

### Встроенные инструменты

- **Проект и окружение:** получение текущего контекста проекта, рабочей директории, даты и времени.
- **Файлы и изображения:** просмотр каталогов, чтение, создание, запись, точечное изменение и удаление файлов; поиск файлов и текста; просмотр изображений.
- **Командная строка:** выполнение команд в рабочей области, включая постоянные интерактивные shell-сессии, которым агент может дослать ввод и к которым может вернуться. В пределах выданных разрешений агент может, в частности, запускать сборку, тесты и другие утилиты проекта.
- **Веб-доступ:** получение содержимого веб-страниц по указанному адресу.
- **Рабочая память:** двухуровневое key-value хранилище — заметки текущего чата или общие для проекта — которое агент читает, пишет, перечисляет и очищает.
- **Контроль длинных задач:** контрольные точки контекста и именованные отметки, к которым агент может вернуться при необходимости.
- **Субагенты:** запуск одного или нескольких субагентов на подзадачу и переписка с ними, пока они работают.
- **MCP-клиент:** вызов инструментов внешних MCP-серверов, подключённых к проекту.
- **Организация работы:** справка по доступным инструментам, активация навыков и уточняющие вопросы.

Конкретный набор доступных инструментов зависит от настроек проекта, активированных возможностей и выбранного режима безопасности.

### Плагины

Плагины поставляются отдельно от базового набора и могут включаться для конкретного проекта.
Плагины располагаются рядом с опубликованным приложением в директории `plugins/`.
У каждого плагина есть собственный `meta.yaml`; плагин может добавлять инструменты, prompt-инструкции, команды интерфейса, настройки и собственные интерактивные панели.
Правила именования инструментов и metadata плагинов описаны в [plugins.md](agents/plugins.md).

Реализованные плагины, которые добавляют инструменты агенту:

#### Browser

Управляет полноценным браузером семейства Chromium через Playwright: открывает сайты, исполняет JavaScript, работает с вкладками и элементами страницы, делает снимки и собирает диагностические сообщения.

Это не второй вариант встроенного `web_fetch`. Встроенный инструмент выполняет обычный HTTP-запрос и извлекает текст страницы без браузерного интерфейса, JavaScript и пользовательского профиля. Browser-плагин запускает настоящий Microsoft Edge, Google Chrome или управляемый экземпляр Chromium — все три варианта используют Chromium-движок.

Для браузера можно выбрать один из трех типов профиля:

- новый временный профиль без сохраненных данных, состояние которого не сохраняется после закрытия браузера;
- постоянный профиль проекта, сохраняющий авторизацию, файлы cookie и другое состояние между запусками;
- существующий профиль Edge или Chrome пользователя с его сохраненной авторизацией и файлами cookie — доступ к нему агент получает только после явного выбора.

Инструменты:

- жизненный цикл: `browser_start`, `browser_stop`, `browser_status`, `browser_list_profiles`;
- вкладки и навигация: `browser_tabs`, `browser_new_tab`, `browser_switch_tab`, `browser_close_tab`, `browser_navigate`, `browser_wait_navigation`;
- анализ страницы: `browser_snapshot`, `browser_inspect`, `browser_get_text`, `browser_screenshot`;
- действия: `browser_click`, `browser_fill`, `browser_press`, `browser_select`, `browser_scroll`, `browser_wait_element`, `browser_upload`;
- диагностика: `browser_console`, `browser_page_errors`.

#### Browser Screencast

Отдельный экспериментальный плагин интерактивного браузера. Он независимо от Browser-плагина запускает собственный headless-браузер, передает его изображение в панель Browser Lab и принимает от пользователя ввод мышью и клавиатурой.

Browser Screencast не использует сессию или профили Browser-плагина и не заменяет его инструменты автоматизации. Именно изображение страницы передается в интерфейс как поток кадров в памяти; сам браузер при этом остается полноценным отдельным экземпляром Chromium.

Инструмент: `browser_screencast_info` — сообщает о назначении и экспериментальном статусе панели.

#### Network

Предназначен для сетевой диагностики, инвентаризации локальной сети и проверки сетевых сервисов.

Инструменты:

- хост и маршруты: `network_get_host_info`, `network_ping_host`, `network_ping_host_stats`, `network_trace_route`, `network_get_routes`, `network_get_arp_cache`;
- DNS и WHOIS: `network_resolve_host`, `network_query_dns`, `network_reverse_dns`, `network_check_dns_propagation`, `network_lookup_whois`;
- HTTP и TLS: `network_http_get`, `network_http_head`, `network_http_post`, `network_check_http_redirects`, `network_check_tls`;
- поиск и проверка узлов: `network_discover_hosts`, `network_scan_tcp_ports`, `network_check_tcp_port`, `network_probe_tcp`, `network_probe_udp`, `network_probe_smtp`, `network_wake_host`.

#### Roslyn

Компилирует и выполняет C#-код, а также собирает, запускает и тестирует реальные .NET-проекты.

Инструменты: `roslyn_compile_check`, `roslyn_script_run`, `roslyn_project_build`, `roslyn_project_run`, `roslyn_project_test`.

#### SQL

Работает с настроенными подключениями к базам данных: исследует схему, выполняет безопасные запросы, анализирует планы и контролируемо изменяет данные.

Инструменты: `sql_connections`, `sql_test_connection`, `sql_schema`, `sql_query`, `sql_query_plan`, `sql_execute`, `sql_verify_context`.

#### SSH

Выполняет команды на удаленных хостах и работает с постоянными интерактивными SSH-сессиями, видимыми пользователю.

Инструменты: `ssh_list_hosts`, `ssh_run`, `ssh_sessions`, `ssh_session_exec`, `ssh_session_wait`, `ssh_session_send`, `ssh_session_close`.

#### 1C

Индексирует исходники конфигурации 1С и помогает исследовать объекты, ссылки и зависимости.

Инструменты: `onec_build_index`, `onec_find_object`, `onec_get_object`, `onec_explain_object`, `onec_find_references`, `onec_find_readers`, `onec_find_writers`, `onec_get_dependencies`, `onec_get_reverse_dependencies`.

#### Documents

Читает Word-документы по смыслу, а не как сырой XML, и работает со строками таблиц по заголовкам
столбцов, а не по адресу ячейки.

Инструменты: `document_extract`, `spreadsheet_inspect`, `spreadsheet_read_rows`, `spreadsheet_append_rows`.

#### Test

Служебный плагин для проверки механизма загрузки плагинов.

Инструмент: `test_ping_host` — возвращает тестовый ответ, подтверждающий, что плагин загружен и доступен агенту.

Дополнительный модуль `sql_avalonia` предназначен для интеграции SQL-плагина с пользовательским интерфейсом.

## Быстрый старт и сборка из исходников

Готовые сборки публикуются на [странице релизов](https://github.com/KOE73/SPLA/releases) в виде
`SPLA.zip` с версией вида `v0.<minor>.<build>`. Сборка из исходников нужна, если требуется текущее
состояние разработки, а не последний релиз.

Требования:
- для сборки: .NET 10 SDK.
- для запуска: .NET 10 Runtime и доступный OpenAI-compatible endpoint, например локальный LM Studio.

1. Соберите desktop app, CLI, плагины и ZIP-пакет общим скриптом:

```powershell
.\PublishAll.cmd
```

Готовая папка приложения создается в `.publish/work/`. Ее можно перенести в другое место и запускать SPLA оттуда. ZIP-архив создается в `.publish/zip/SPLA.zip`.

2. Запустите LM Studio или другой локальный OpenAI-compatible endpoint либо убедитесь, что у вас есть доступ к нему.
3. Запустите desktop UI из `.publish/work/` и укажите путь к вашему LLM endpoint.

Также можно запустить CLI-версию из `.publish/work/`, чтобы работать через терминал.

Экран настроек содержит краткое описание. Проект можно создать в любой папке. На практике это файл `*.spla` с настройками, который можно открыть через UI или CLI. Проект определяет разрешения, инструкции, документацию, игнорируемые пути, плагины и связанные настройки.

Между проектами можно переключаться через список проектов в интерфейсе или открыть несколько окон. У каждого проекта собственные настройки, чаты и состояние агента, при этом проекты могут использовать одни и те же плагины и инструменты.

## Безопасность

SPLA по-прежнему использует 5 режимов агента — они задают верхнюю границу того, что чат вправе
делать, независимо от всего остального: от «только обсуждение» до автономного многошагового
выполнения:

| Режим | Назначение |
|--------|--------|
| Chat | Только обсуждение |
| Research | Чтение и анализ |
| Inspect | Диагностика и инспекция |
| Edit | Изменение файлов проекта |
| Agent | Автономное многошаговое выполнение |

Под этим слоем модель разрешений переходит на зоны: именованные области (проект, локальная
файловая система, интернет, shell, ...) и гранты не на инструмент, а на ребро между зонами — вместо
одного плоского списка разрешений на каждый вызов. Роли собирают набор грантов и инструкций и
назначаются конкретному чату (см. выше). Это активно развивающееся направление, а не готовая
гарантия — воспринимайте его как курс, которым движется модель разрешений SPLA, а не как
устоявшийся факт.


## Схемы архитектуры (альфа)

Побочный вспомогательный подпроект рядом с основным — [`docs/diagrams/`](docs/diagrams/README_RU.md)
и редактор [`tools/spla-diagram`](tools/spla-diagram/). Цель у него двусторонняя.

**Туда:** показать внутренние структуры проекта так, чтобы их было легче понять — не пересказом в
тексте, а схемой, на которую можно смотреть.

**Обратно:** по нарисованной архитектуре смысл легче даётся и агенту. Схема перестаёт быть
картинкой к тексту и становится входом: модель читает её как источник структуры и намерения, а
владелец правит архитектуру на холсте, а не в переписке.

Именно из обратного направления растёт всё остальное устройство — рисовалки для этого мало. Если
схему читает модель, то:

- схема должна нести **причины**, а не только топологию, иначе разговор словами не сокращается;
- текст должен быть **проверяемым на актуальность**, иначе модель уверенно соврёт по устаревшему
  описанию — поэтому у каждого текстового поля записано собственное происхождение, а базового языка
  нет: русский и английский равноправны;
- каждый элемент картинки должен иметь **однозначное прочтение**, иначе модель домысливает —
  поэтому вложенность блока в рамку не оформление, а утверждение, и вид обязан объявить свою **ось**:
  что именно эта вложенность классифицирует.

Отсюда и виды: одна и та же кодовая база раскладывается по-разному, и это выбор вопроса, а не стиля
— «хребет хода» (от ящика до возврата к модели), смысловой атлас подсистем, зоны безопасности,
процессы.

```powershell
.\ViewArchitecture.cmd
```

## Ответственное использование

Сетевые инструменты SPLA предназначены для исследований, диагностики, инвентаризации и обычной работы сетевых администраторов с системами и сетями, которыми они владеют, управляют или которые им явно разрешено проверять.

Не используйте SPLA для несанкционированного сканирования, probing, попыток доступа, нарушения работы или любых действий против сторонних сетей без разрешения.
