# `spla-atlas` — инструкция для агента-исполнителя

Здесь **пока нет кода**. Папка подготовлена, писать будет другой агент — то есть,
скорее всего, ты. Этот файл говорит, что именно построить.

**Контракт — v3.** Формы полей: [`CONTRACT.md`](../spla-diagram/docs/CONTRACT.md).
**Решение и обоснование:** [`ADR_20260828_diagrams_model-contract-v2`](../../docs/adr/ADR_20260828_diagrams_model-contract-v2.md),
развит [`ADR_20260831`](../../docs/adr/ADR_20260831_diagrams_text-provenance-and-view-axes.md).

> Пока утилиты нет, реестры (`entities.json`, `relations.json`) ведутся руками
> или разовым скриптом. Go-предшественник `tools/spla-arch` выведен из обращения:
> файлы, которые он собирал, удалены. Сверки с кодом сейчас нет вообще — это и
> есть главная причина писать эту утилиту.

## 1. Что это

Утилита, которая ведёт **реестр архитектурной модели SPLA**: извлекает сущности
из C# через Roslyn и сверяет их с тем, что уже записано.

Она **не рисует схемы и не расставляет координаты.** Схемы собирает человек в
редакторе `tools/spla-diagram`. Утилита поставляет базу, из которой он выбирает.

### Три жёстких запрета

1. **Никогда не писать в `docs/diagrams/projects/*/views/`.** Ни при каких
   обстоятельствах, ни «для восстановления», ни при миграции. Там лежит ручная
   работа человека. Однажды её уже потеряли — вся конструкция v2 существует
   ради того, чтобы это стало невозможным, а не маловероятным.
2. **Не трогать `tools/spla-arch`** (старая Go-версия). Она продолжает работать
   до конца переезда. Читать её как референс — можно и нужно; править — нет.
3. **Не трогать `src/plugins/SPLA.Plugins.Roslyn`.** Это другой замысел, не
   имеющий отношения к этой утилите, несмотря на общий Roslyn.

### Автономность

Утилита **не является частью решения SPLA**:

- собственное решение `SplaAtlas.sln` внутри `tools/spla-atlas/`;
- **не добавляется в `SPLA.slnx`**;
- **не ссылается** ни на один проект из `src/`;
- зависимости — только NuGet (Roslyn, `System.CommandLine` или аналог).

**Засада с `Directory.Build.props`.** В корне репозитория лежит
[`Directory.Build.props`](../../Directory.Build.props), и MSBuild подтягивает его
во **все** проекты ниже по дереву, включая эту папку. Тогда утилита унаследует
версию продукта (`VersionMajor/Minor/Build`) и поедет за любой её правкой — то
есть автономность будет только на словах.

Разорвать цепочку: положить собственный `tools/spla-atlas/Directory.Build.props`,
который **не импортирует родительский**, и задать в нём свои
`TargetFramework` (`net10.0`, как в репозитории), `Nullable`, `ImplicitUsings` и
собственную версию.

## 2. Что построить

```
tools/spla-atlas/
  SplaAtlas.sln
  src/
    SplaAtlas.Model/          контракт v3: типы реестров, чтение/запись JSON
    SplaAtlas.Extraction/     Roslyn: код → сущности, структурные связи, кандидаты
    SplaAtlas.Sync/           сверка реестров с извлечённым, находки
    SplaAtlas.Cli/            точка входа, вывод отчёта
  tests/
    SplaAtlas.Tests/
```

Целевой фреймворк — как в основном репозитории (`net10.0`). Utility-класс на
каждый чих не заводить: `Model` и `Sync` должны быть покрыты тестами, `Cli` —
тонкий.

### Команды

```bash
spla-atlas sync --project docs/diagrams/projects/core            # сверить и записать
spla-atlas sync --project docs/diagrams/projects/core --dry-run  # только отчёт, выход 1 если есть находки
```

Отдельной «генерации» нет. `sync` — единственная операция; первый прогон
отличается лишь тем, что реестр пуст.

## 3. Контракт данных

Полные формы файлов — в [`docs/diagrams/projects/AGENTS.md`](../../docs/diagrams/projects/AGENTS.md).
Здесь то, что должна соблюдать именно утилита.

### 3.1 Идентификаторы — самое важное

`entities.json` **долговечен**. Утилита его сверяет, а не пересоздаёт.

| Событие | Что делает утилита |
|---|---|
| в коде появился тип, которого нет в реестре | добавляет запись, выдаёт id **один раз** |
| тип есть и в коде, и в реестре | обновляет `namespace`, `codeRef`, `members`; **id и `name` не трогает, если имя совпало** |
| запись есть, типа в коде нет | ставит `"status": "gone"`, **не удаляет** |
| пропал X и появился Y в том же файле того же вида | **не решает сама** — печатает как кандидата на переименование |

Правило id: `e_` + имя типа в нижнем регистре, коллизия разрешается суффиксом
`_2`, `_3`. **После выдачи id не меняется никогда**, даже если тип переименован.
Расхождение id и `name` после переименования — норма, а не рассинхрон.

Переименование выполняет человек или агент: правит `name`, оставляет `id`. Всё,
что ссылается на id — тексты, связи, размещения на видах — переживает это без
изменений. Утилита такую правку принимает молча и перестаёт считать тип
пропавшим.

### 3.2 `origin`

У сущности и у связи:

- `"code"` — ведёт утилита, сверяет с кодом, помечает пропавшее;
- `"authored"` — ведёт человек, утилита **не трогает вообще**, включая `status`.

**В v3 значение `manual` переименовано в `authored`.** Встретив `manual` в старом
файле, читать как `authored` и записывать уже новым именем.

`origin: "authored"` у сущности нужен для того, чего нет в C#: внешний API, СУБД,
чужой сервис. Извлечение обязано их не затирать и не помечать пропавшими.

### 3.3 Связи

Идентификатор выводится **из id сущностей**, не из имён:
`r_<fromId без префикса>_<toId без префикса>_<type>`.

Все места вызова `A → B` схлопываются в **один** факт «A вызывает B» — иначе
коллизии id и бессмысленный объём. Рукописная связь получает явный авторский id
и им и остаётся.

Тип связи — **открытая строка**, но с v3 у типов есть авторский словарь
`relation-types.json`. Структурные (`extends`, `implements`, `composes`) утилита
ставит сама и заводит в словаре, если их там нет. Потоки (`call`, `data-flow`,
`event`, `security`, `storage` и любые новые) заводит человек — **в чужие записи
словаря утилита не пишет и ничего оттуда не удаляет.**

Подписи связи в `relations.json` нет: поле `label` в v3 удалено, весь текст живёт
в каталогах текстов под id связи.

Свидетельство (`evidence`) проверяемо: если файл или символ исчезли, это находка
вида `лишнее`, а не тихое удаление.

### 3.35 Чего утилита не касается никогда

Три вещи в v3 принадлежат человеку целиком, и запись в них — дефект утилиты, а не
удобство:

- **`text.<lang>.json`.** Каждое значение несёт происхождение (`origin`, `at`,
  `from`, `fromHash`). Утилита не пишет тексты и не переставляет штампы: значение,
  которого она не переводила, она не вправе называть ни `authored`, ни
  `translated`. Появление сущности в реестре текста для неё не создаёт — дыра в
  переводе должна быть видна.
- **`views/*.view.json`.** Ни координат, ни осей, ни `edges`. Ни при каких
  обстоятельствах, включая «восстановление».
- **`relation-types.json`** в части авторских типов (см. 3.3).

### 3.4 Контейнеры

`containers.json` ведёт человек. Утилита:

- применяет `match` (`name` → `nameRegex` → `path`, длиннейший префикс, затем
  сосед по файлу) и вычисляет предполагаемую принадлежность;
- **уважает `overrides`**: явное назначение человека всегда бьёт правило;
- сообщает о правилах, которые ни во что не попали (гниль в правилах);
- **ничего не размещает.** Принадлежность — подсказка для панели базы в
  редакторе и для отчёта. На геометрию видов она не влияет никак.

Уникальность принадлежности **не требуется**. Одна сущность может состоять в
нескольких контейнерах — это не ошибка и не находка.

## 4. Извлечение (Roslyn)

Нужны **разрешённые символы**, а не разбор текста: `MSBuildWorkspace`, а не
`CSharpSyntaxTree.ParseText` по отдельным файлам.

**Засада с форматом решения.** В репозитории только `SPLA.slnx` — `.sln` нет
вовсе. Поддержка `.slnx` в `MSBuildWorkspace.OpenSolutionAsync` зависит от версии
MSBuild и может отсутствовать. **Не закладываться на неё:** перечислять `*.csproj`
под путями из `project.json` → `sources.include` (их 37) и открывать каждый через
`OpenProjectAsync`, складывая в одно `Workspace`. Фильтрация по путям всё равно
нужна — решение целиком нам и не требуется.

Если `OpenSolutionAsync` на `.slnx` внезапно заработает — это удобство, а не
основание менять подход: перечисление проектов не зависит от формата решения и
не сломается при следующем обновлении SDK.

**Обязательный минимум первой волны:**

| Что | Зачем |
|---|---|
| тип: kind, имя, namespace, путь файла | база; сейчас namespace объявлен и никогда не заполняется |
| `partial` собирается в один тип | сейчас даёт дубли |
| базовые типы и интерфейсы → `extends` / `implements` | структурные связи |
| **значения `enum`** | главный запрос: «есть enum, содержимого нет» |
| публичные методы интерфейсов: имя + сигнатура | сюда смотрят при чтении схемы |
| свойства: имя, тип, **ссылка на id сущности**, если тип свой | `composes` перестаёт быть догадкой |

Не архитектура, пропускать: `private`/`protected` вложенные типы, `bin/`, `obj/`,
`*.g.cs`, `*.Designer.cs`, `AssemblyInfo`, `GlobalUsings`.

**Кандидаты связей — вторая волна, не первая.** Когда дойдёт: извлекать только
вызовы, где **оба конца уже есть в реестре**, и подавать их отчётом, а не
записью в `relations.json`. Порог не замерен — см. открытый вопрос 1 в ADR.

## 6. Отчёт

Находки трёх видов, как в v1 — формулировки оттуда можно взять:

| Вид | Что значит |
|---|---|
| `сломано` | реестр сам себе противоречит: связь в никуда, дубль id, ссылка на несуществующую сущность |
| `лишнее` | в реестре есть то, чего нет в коде: `status: gone`, протухшее свидетельство, правило в пустоту |
| `не хватает` | код есть, реестра нет: новый тип; новая связь между показанными сущностями, которую ни один вид не показывает |

**Чего в отчёте больше нет** (было в v1, отменено ADR):

- «узел вне своей зоны» — на виде это законное решение автора;
- всё, связанное с зоной `НЕ РАЗМЕЩЕНО` — её не существует.

`--dry-run` при непустом отчёте — выход `1`.

## 10. Незакрытое

Не изобретать в одиночку — поднять вопрос, если упрёшься:

1. **Объём кандидатов связей.** Неизвестен до замера на живом коде. Если счёт
   пойдёт на тысячи — останавливаться и обсуждать порог, а не сваливать всё в
   отчёт.
2. **Гранулярность членов.** `enum` — точно. Методы интерфейсов — вероятно.
   Свойства всех 428 классов — под вопросом; если объём `entities.json`
   переваливает за пару мегабайт, это сигнал остановиться.
3. **Имя утилиты.** `spla-atlas` взято по образцу соседей. Версия живёт в
   `contractVersion: 3`, а не в имени папки. Переименование тривиально, пока нет
   кода, — если у владельца есть другое имя, лучше сменить сейчас.

Язык: коммиты, ветки и PR — по-английски; документы и обсуждение — по-русски.
