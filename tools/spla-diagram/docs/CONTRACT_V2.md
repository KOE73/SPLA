# Контракт модели: стоит ли менять формат

**Статус:** открытый вопрос, решение не принято. Разбор для обсуждения.
**Когда:** после переноса (проход 1) и после починки дефектов (проход 2).
**Язык:** внутренний разбор, по-русски. Формальная спецификация —
[`REQUIREMENTS.md`](REQUIREMENTS.md), она двуязычная.

## 1. Что заставляет вернуться к этому вопросу

Не эстетика. У текущего формата **два источника истины о вложенности, и они
расходятся при редактировании**.

- `R-CONT-01`: родитель узла — это `node.zone`, а если его нет, то геометрия.
- `R-EDIT-06`: при перетаскивании узла в зону редактор **записывает** `node.zone`.
- `R-CONT-02`: вложенность зоны в зону не выражается вообще ничем, кроме геометрии.
- `D-04`: когда геометрия срабатывает, победитель определяется порядком в массиве.

Отсюда следствия, которые видны уже сейчас:

1. Файл, который поредактировали в редакторе, постепенно обрастает полями `zone`,
   которых не было у сгенерированной модели. Никто не сверяет их с геометрией.
2. Сдвинул узел на 20 пикселей за край зоны — он молча сменил подсистему, хотя
   поле `zone` осталось прежним. Что победит при следующей загрузке, зависит от
   того, какое из двух правил сработает первым.
3. Генератор `spla-arch`, чтобы выразить «этот класс принадлежит этой роли»,
   обязан **подобрать координаты** — то есть выражать смысл через геометрию,
   хотя смысл ему известен точно.

Это не дефект реализации, это свойство формата. Ни один из пунктов не чинится в
коде — только в контракте или ценой вечного соглашения «пишем оба поля и следим
руками».

## 2. Три варианта

### A. Оставить v1 как есть

Дерево строится в памяти выводом: `node.zone`, дальше геометрия.

**За:** нулевая работа. `spla-arch` не трогается, пять существующих моделей не
трогаются, история git по моделям остаётся сравнимой.

**Против:** всё из раздела 1 остаётся. Вложенность зон остаётся невыразимой.
Вывод остаётся лоссовым: два разных смысла (логическая принадлежность и
физическое размещение) схлопываются в одну догадку.

### B. v1 + явный родитель, массивы остаются плоскими

Ко всем зонам и узлам добавляется `parent: string | null`. Геометрия перестаёт
что-либо значить для принадлежности и становится чисто визуальной.

**За:**

- Диф минимальный: одно новое поле, структура файла не меняется.
- Совместимость в обе стороны: у файла без `parent` работает старый вывод, так
  что переход можно делать по одной модели за раз.
- Вложенность зон наконец выразима.
- `spla-arch` пишет одно поле вместо подбора координат.

**Против:**

- Два массива с почти одинаковой формой остаются: `zones` и `nodes` отличаются
  по сути только полями `name`/`label` и наличием `style`.
- Родитель как ссылка — это список смежности, значит циклы представимы и их
  придётся проверять валидатором.

### C. v2: единое дерево, вложенные `children`

Один массив `elements`, у элемента есть `kind` и `children`.

**За:** одна форма вместо двух, дублирование исчезает, циклы непредставимы по
построению, различие зона/узел сводится к наличию детей.

**Против — и здесь главное возражение, которое неочевидно:**

- **Вложенный JSON хуже для дифов.** Перенос узла между зонами перемещает целый
  блок текста вместо изменения одного поля. На `model-core-full.json` (246
  сущностей, вложенность 2 уровня) ревью становится нечитаемым.
- **Вложенный JSON хуже для детерминированной генерации.** У `spla-arch` есть
  `verify`, и смысл его в том, что прогон даёт побайтово тот же файл. С плоским
  массивом порядок задаётся одной сортировкой; с деревом порядок надо
  фиксировать на каждом уровне.
- Ломает все пять моделей и генератор разом.
- `views` ссылаются на `highlightZones` и `highlightNodes`. Если различие
  зона/узел размывается, эти два поля надо схлопывать в одно — ещё одна
  ломающая правка в тех же файлах.

Плоский массив с полем `parent` даёт структурную ясность **и** построчные дифы.
Дерево даёт только первое.

## 3. Отдельный вопрос: относительные координаты

Не обсуждался, но по выигрышу он крупнее, чем сама вложенность.

Сейчас все координаты абсолютны (`R-MODEL-07`). Следствие: перетаскивание зоны
переписывает координаты **всех** потомков (`R-EDIT-03`).

Если координаты ребёнка задать относительно родителя:

| | абсолютные (сейчас) | относительные |
|---|---|---|
| Сдвиг зоны на 10px | переписывает N+1 пар чисел | переписывает 1 пару |
| Диф в git | сотни строк | одна строка |
| Снимок отмены (`R-HIST-01`) | вся модель меняется | вся модель меняется, но содержательно — одно место |
| `R-EDIT-03` | цикл по потомкам | не нужен вовсе |
| Экспорт в drawio (`R-IO-07`) | конвертирует в относительные | конвертация исчезает |

То есть относительные координаты **упраздняют целое требование** и убирают шаг
из экспорта.

**Против:**

- Правка координаты руками требует знать начало отсчёта родителя.
- Ответ на вопрос «где эта штука на экране» требует пройти цепочку предков.
- Перенос узла между зонами меняет его координаты, хотя визуально он не двигался.

Первые два — цена, которую платит код, а не человек, и платит один раз в
функции `resolveAbsoluteRect`. Третий — реальный, но проявляется только при
ручной правке JSON.

## 4. Цена перехода

| Что | Объём |
|---|---|
| Конвертер v1 → v2 | ~50 строк, разовый прогон |
| Пять моделей в `docs/diagrams/` | один коммит-переформатирование |
| `spla-arch`: запись `parent` вместо подбора координат | упрощение, а не усложнение |
| `spla-arch verify` | правка сравнения |
| `mapping/*.map.json` | не трогается, правила про смысл, а не про формат |
| Внешние потребители | их нет — drawio-экспорт и viewer внутренние |

Смягчается полем `metadata.contractVersion`: загрузчик читает и v1, и v2, пишет
всегда v2. Тогда переход не обязан быть атомарным.

## 5. Предварительный вывод

Менять стоит, но не в форме C.

1. **`parent` на каждом элементе** — снимает раздвоение источника истины,
   делает вложенность зон выразимой, освобождает генератор от выражения смысла
   через координаты.
2. **Координаты относительно родителя** — упраздняет `R-EDIT-03`, убирает шаг из
   экспорта, превращает перенос зоны из дифа на сотни строк в диф на одну.
3. **Массивы остаются плоскими** — ради построчных дифов и детерминированной
   генерации.
4. `name` у зон и `label` у узлов сводятся к одному полю; `kind` остаётся
   отдельным полем, а не выражается принадлежностью к массиву — чтобы возможное
   слияние `zones` и `nodes` в будущем не потребовало третьего ломающего
   изменения.

## 6. Почему это правильно отложить

Перенос (проход 1) строит **разделение «формат на проводе» ↔ «дерево в
памяти»**. Канвас, интеракции, инспектор, история и экспорт работают с деревом и
про JSON не знают ничего.

Значит переход на v2 позже трогает только слой загрузки и сохранения — те самые
~80 строк маппинга, — а не весь код. Отсрочка почти ничего не стоит.

Обратное неверно: если делать v2 **сейчас**, одновременно поедут структура,
поведение и формат, и стенд (`model-features.json`) перестанет что-либо
диагностировать — расхождение будет невозможно отнести ни к чему конкретному.

Порядок: перенос → дефекты → контракт.
