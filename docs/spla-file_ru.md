# Формат файла проекта `.spla`

Канонический файл: [`agents/spla-file.md`](../agents/spla-file.md). При расхождении приоритет у английской версии.

---

Файл `.spla` — точка входа в проект. Двойной клик по нему (или передача путём в аргументе) запускает
SPLA с полным контекстом проекта — режим, инструкции, разрешения.

**Корень проекта — это каталог, в котором лежит этот файл.** Это не настраивается, и поля для этого
нет: второе определение «где работает агент» сделало бы договорной любую границу, проведённую от
первого. Манифесты, всё ещё несущие старый ключ `workspace:`, загружаются нормально — он игнорируется.

## Пример

```yaml
version: 1

name: My Project

mounts:
  - name: AAA
    type: file-system
    path: ../AAA          # относительно каталога ЭТОГО файла
    access: read          # read (по умолчанию) | write
    trust: trusted        # trusted (по умолчанию) | untrusted
    description: справочные настройки Linux — эталонная копия, не редактировать

agent:
  mode: Edit
  instructions:
    - AGENTS.md

roles: [reviewer]

llm:
  provider: lmstudio
  endpoint: http://localhost:1234/v1
  model: auto

ui:
  theme: Emerald

permissions:
  read: allow
  write: ask
  shell: ask
  internet: allow

toolsets:
  ssh: agent_demand
  network: skill_demand
  roslyn: disabled

docs:
  - docs/

ignore:
  - bin/
  - obj/
  - .git/
  - node_modules/
```

## Поля

| Поле | Обязательно | Описание |
|-------|----------|-------------|
| `version` | Да | Версия формата. Сейчас `1`. |
| `name` | Нет | Человекочитаемое имя проекта. |
| `mounts` | Нет | Папки вне корня проекта, названные здесь и адресуемые как `mnt/<name>/...`. См. [Точки монтирования](#точки-монтирования). |
| `agent.mode` | Нет | Режим по умолчанию: `Chat`, `Research`, `Inspect`, `Edit`, `Agent`. |
| `agent.instructions` | Нет | Markdown-файлы, вставляемые в системный промпт. Пути относительно корня проекта. |
| `agent.capabilities` | Нет | Включённые встроенные возможности `core.*`. Отсутствует = все; `[]` = чистый чат без встроенных инструментов. |
| `agent.spawned_retention` | Нет | Сколько завершённых порождённых сессий держать на диске, от новых к старым (по умолчанию 200). `0` — не держать ни одной; отрицательное значение отключает подрезку вовсе. Никогда не трогает сессию с ещё идущим ходом. Только на уровне проекта — не поле роли: ретенция это дисковая политика проекта, а не поведение, которое роль сужает. См. [Роли](#роли). |
| `agent.peer_debounce_base` / `agent.peer_debounce_max` / `agent.peer_depth_ceiling` / `agent.peer_hard_cap` | Нет | Регулятор затухания переписки — как быстро замедляется обмен между двумя деятелями и где он обрывается. См. [Затухание переписки](#затухание-переписки). |
| `roles` | Нет | Имена ролей этого проекта, например `[reviewer, architect]`. Каждое имя связано с телом в `roles/<name>.yaml` рядом с манифестом. См. [Роли](#роли). |
| `llm.provider` | Нет | Провайдер LLM. Сейчас только `lmstudio`. |
| `llm.endpoint` | Нет | Базовый URL API. |
| `llm.model` | Нет | Имя модели. `auto` = использовать то, что загружено. |
| `connections` | Нет | Список именованных подключений (объединяется со значениями по умолчанию по `id`); поля записи: `id`, `name`, `provider`, `endpoint`, `api_key`, `model`, `context_length`, `lock_model`, `swap_model`. При отсутствии подключение по умолчанию синтезируется из `llm.*`. |
| `connections[].context_length` | Нет | Ручное переопределение размера контекстного окна в токенах. Не задано/0 = автоопределение у провайдера (нативный API LM Studio сообщает окно загруженного экземпляра; vLLM сообщает `max_model_len`). |
| `connections[].models[].reasoning_options` | Нет | Ручное объявление вариантов рассуждений модели, словами самого провайдера (`[off, low, medium, xhigh, on]`). Тот же приоритет, что у `context_length`: объявление побеждает то, что заявляет провайдер, и это единственный способ получить рычаг для сервера, который ничего не описывает — большинство OpenAI-совместимых эндпоинтов, LocalAI и простой vLLM в их числе. Не задано = верить слову провайдера или оставить рычаг недоступным. См. [ADR_20260817](adr/ADR_20260817_llm_reasoning-lever.md). |
| `connections[].models[].reasoning_default` | Нет | Вариант, который модель использует, когда её ни о чём не попросили. Читается только вместе с `reasoning_options`. |
| `llm.temperature` | Нет | Температура сэмплирования (по умолчанию `0.7`). Слои по умолчанию → проект → чат; собственное значение чата пишется в его YAML статус-баром. |
| `llm.reasoning_level` | Нет | Выбор рассуждений: пусто (собственное значение модели по умолчанию), `off`, `on`, слово усилия в словаре провайдера (`low`/`medium`/`xhigh`/…) или `budget:N` токенов. Ничего не отправляется провайдеру, который никогда не описывал канал рассуждений модели — почему это важно, см. в ADR выше. |
| `ui.theme` | Нет | Цветовая тема: `Dark`, `Light`, `Cream`, `Emerald`. |
| `ui.density` | Нет | Плотность интерфейса: `norm`, `mini`, `nano`, `max`. |
| `permissions.*` | Нет | Переопределения по эффектам: `allow`, `ask`, `deny`. Переопределяет матрицу режима по умолчанию. |
| `toolsets.<id>` | Нет | Насколько далеко набор инструментов раскрывается модели: `disabled`, `skill_demand`, `agent_demand`, `enabled`. Отсутствует = выводится из флага `plugins.<id>.enabled` поставщика, так что проекты, написанные до появления наборов инструментов, не затронуты. `on`/`off` отклоняются — YAML читает их как булевы значения. См. [Наборы инструментов](toolsets_ru.md). |
| `plugins.<id>.enabled` | Нет | Включает/выключает один плагин по id. Именованная запись всегда побеждает. |
| `plugins."*".enabled` | Нет | Включает/выключает каждый плагин, у которого нет своей записи. См. [Запись плагина `*`](#запись-плагина-). |
| `docs` | Нет | Каталоги документации для индексации. |
| `ignore` | Нет | Каталоги/файлы, которых агент никогда не коснётся. |

## Точки монтирования

Проекту иногда нужна папка вне его самого — общее дерево ссылок для нескольких экспериментов, каталог
развёртывания, папка-приёмник. Ни один из обычных способов её назвать не работает: относительный путь
в инструкции не имеет базы (относительно каталога процесса? корня проекта? файла, где написана
инструкция?), а абсолютный путь ломается на второй машине и вовсе невыразим на сервере.

Точка монтирования даёт такой папке имя. **Имя едет в git, цель — свойство машины** — это единственное
разделение, при котором адрес одновременно стабилен в инструкции и переносим между копиями.

```yaml
mounts:
  - name: AAA
    type: file-system
    path: ../AAA
    access: read
    trust: trusted
    description: справочные настройки Linux — эталонная копия, не редактировать
```

Дальше всё адресует её как `mnt/AAA/nginx/nginx.conf`, и файловые инструменты берут это в точности как
путь проекта. То же делает `sftp_upload`, ради которого точки монтирования и вводились.

| Ключ | Обязателен | Значение |
|-----|----------|---------|
| `name` | Да | Адресный сегмент. Один простой сегмент — без слэшей, без `..`. |
| `type` | Нет | Существует только `file-system`. Ключ здесь для того, чтобы второй вид стал добавлением, а не поломкой. |
| `path` | Да | Куда указывает. Относительные пути разрешаются относительно **каталога, содержащего этот манифест**, никогда относительно текущего каталога. |
| `access` | Нет | `read` (по умолчанию) или `write`. Только чтение, пока не включено явно — так же, как `allow_write` у SSH-хоста. |
| `trust` | Нет | `trusted` (по умолчанию) или `untrusted`. См. ниже. |
| `description` | Да | Для чего папка. Попадает в системный промпт. |

**`description` обязательно намеренно.** Это то, что модель читает рядом с адресом; без строки о том,
для чего папка, она откроет папку, чтобы выяснить.

**`trust: untrusted`** — для одной ситуации: папки, куда файлы кладут другие люди — общий дроп,
чей-то экспорт, папка загрузок. Чтение из такой папки поднимает флаг сомнения чата, что стоит один
переспрос, когда что-то позже уходит наружу, и ничего не стоит в остальных случаях. Всё, что настроили
вы сами, доверенное по умолчанию — точка монтирования это источник, который вы назвали, точно как
SSH-хост.

### `mnt` зарезервирован в корне проекта

Настоящая папка `mnt` в корне не даёт проекту открыться. Это проверяется независимо от того,
смонтировано ли что-нибудь, и в этом смысл: это одно условие на всю жизнь проекта, так что добавление
точки монтирования никогда не поднимает заново вопрос о том, что уже есть в дереве. Альтернатива —
проверка имени каждой точки монтирования по дереву при загрузке — падала бы в момент, который никто не
выбирал, в день, когда `git pull` принесёт папку с совпадающим именем.

### Чего точка монтирования не делает

- **Не работает в shell.** `system_run_shell`, `roslyn_script_run`, git и компиляторы берут путь от
  модели и никогда не проходят через файловые инструменты; ОС ничего не знает про `mnt/`. Дизайн
  ([ADR §7](adr/ADR_20260814_core_project-mounts.md)) указывает на `MapPathToHost` для этого, но
  **сегодня ни один инструмент не раскрывает это модели** — так что пока адрес `mnt/` работает только
  для инструментов, и промпт об этом говорит. Немонтируемые виды точек в любом случае никогда не
  заработали бы из shell; это следствие того, что такое shell, а не пробел.
- **Не изолирует.** Как всё остальное в модели зон, держится до первой команды shell.
- **Не делает общую папку согласованной.** Два проекта, пишущих в один каталог развёртывания —
  по-прежнему гонка; точка монтирования её называет, но не блокирует.
- **Отсутствующая цель — не ошибка при загрузке.** Проект открывается, а точка монтирования помечается
  недоступной; обращение внутрь неё тогда сообщает об этом по имени, а не как об отсутствующем файле.

Дизайн: [`ADR_20260814_core_project-mounts`](adr/ADR_20260814_core_project-mounts.md).

## Роли

Роль — это **именованный тип настроек деятеля** — тот же тип вещи, что уже есть `agent:` выше, по
[`ADR_20260827-2_core_roles`](adr/ADR_20260827-2_core_roles.md) §2.1. `agent:` — это роль проекта *по
умолчанию* — «роль ноль» — и не требует записи нигде; любая другая роль объявляется дважды, в двух
разных местах и по двум разным причинам:

1. **Манифест называет её**, под ключом `roles:`. Именно это делает роль *существующей* — манифест,
   никогда не упоминающий `reviewer`, не имеет роли `reviewer`, что бы ни лежало на диске.
2. **Файл хранит её тело**, в `roles/<name>.yaml`, рядом с манифестом. Он едет в git — в отличие от
   `.spla/`, которая закрыта целиком и не хранит ничего действующего.

```yaml
# project.spla
roles: [reviewer, architect]
```

```yaml
# roles/reviewer.yaml
mode: Research
instructions:
  - AGENTS.md
  - docs/review-checklist.md
capabilities:
  - core.read
model: fast-local
toolsets:
  roslyn: agent_demand
islands:
  - sql:staging-db
```

**Файл в `roles/`, которого манифест не назвал, не действует.** Это свойство безопасности, а не
аккуратности: файл роли, приехавший в чужом pull request, не должен становиться новым деятелем с
доступом в момент, когда он оказался на диске. Это ровно та же логика, что «нет подъёма по дереву» в
[Использовании](#использование) ниже — не действует то, чего никто не назвал.

**Тело роли имеет ту же форму, что `agent:`**, плюс три собственных поля:

| Поле | Значение |
|---|---|
| `mode`, `instructions`, `capabilities`, `custom_prompt`, `loop_guard*`, `unified_resources`, `ask_timeout_minutes`, `shell_timeout_seconds`, `trusted_domains`, `save_tool_calls`, `save_attempts`, `peer_debounce_base`, `peer_debounce_max`, `peer_depth_ceiling`, `peer_hard_cap` | То же значение, что у одноимённого поля `agent.*` выше. Отсутствует у роли = наследует собственное значение проекта, как и любое другое поле здесь. (`spawned_retention` — единственное исключение, только на уровне проекта, см. таблицу полей выше.) |
| `model` | На какой из моделей собственных `connections:` проекта работает эта роль. Роль не объявляет своё подключение — проект объявляет, что вообще достижимо, роль лишь выбирает из этого. |
| `toolsets` | Та же форма, что у верхнеуровневой секции `toolsets:`, объединяется с ней ключ за ключом — роль, упомянувшая один набор, сужает (или расширяет, в пределах того, что всё ещё разрешает гейт возможностей) только этот набор. |
| `islands` | Какие из уже достижимых островов проекта (база данных, хост, чужой сервер инструментов — см. `SPLA.Domain.Security.IslandIdentity`) упоминаются в промпте и поверхности инструментов этой роли. Это *выбор*, не грант: список сужает, что показывается, но никогда не расширяет, что реально достижимо — гейт возможностей остаётся единственным местом, где решается доступ. |

**Роль не является подмножеством прав проекта.** `capabilities` у роли *заменяет* список проекта для
этой роли целиком — роль может объявить возможность, которую `agent:` никогда не упоминал, и получить
её. Потолок того, что роль реально может достичь — корень каталога и гранты владельца, а не
объединение того, что объявил `agent:`. Требование «возможности всех ролей ⊆ возможностей `agent:`»
сделало бы сам проект максимально привилегированной сущностью — ровно та беда, что
[`ADR_20260819`](adr/ADR_20260819_core_project-entry.md) описывает для безпроектного режима.

**Роль не встаёт второй осью прав.** У неё нет собственного блока `permissions:`: она выбирает `mode`,
так же как это делает `agent:`, и сужает то, что работает внутри этого режима. Две перекрывающиеся
системы разрешений немедленно подняли бы вопрос «кто кого перебивает» — ADR это прямо отверг.

**Роль не самоназначается.** Владелец манифеста пишет `roles:` и каждый `roles/<name>.yaml`; ничто,
что агент может вычислить или сказать во время работы, это не заменяет. Нет ни инструмента, ни пути
конфигурации, который позволил бы работающему агенту сочинить роль или взять невыданную — ADR прямо
называет это «единственным настоящим инвариантом», всё остальное — вопрос грантов.

## Затухание переписки

[Переписка](../agents/composition.md#correspondents-are-deliberately-not-a-contributor) между двумя
деятелями (`agent_correspond` и открываемый им инструмент `reply_<роль>[_<тема>]` — см.
[`toolsets.md`](../agents/toolsets.md#virtual-reply-tools-are-outside-this-system)) — это внутренняя
циркуляция: ответ на ответ не требует, чтобы кто-то смотрел хоть в один из чатов, чтобы продолжаться,
и именно это делает неограниченный обмен возможным. Четыре настройки, все под `agent:` (и
переопределяемые для роли, наравне с любым другим полем `agent.*`, которое роль сужает — см.
[Роли](#роли) выше) — это регулятор, который не даёт одному обмену длиться вечно:

```yaml
agent:
  peer_debounce_base: 2      # секунды
  peer_debounce_max: 300     # секунды
  peer_depth_ceiling: 6
  peer_hard_cap: 24
```

| Поле | По умолчанию | Значение |
|---|---|---|
| `peer_debounce_base` | `2` | Секунды, которые памп ждёт перед тем как разбудить ход для первой реплики после внешней энергии (сообщение человека или завершённая фоновая задача сбрасывают счётчик в 0). |
| `peer_debounce_max` | `300` | Потолок ожидания снизу — удвоение никогда не ждёт дольше этого между входящей репликой и ходом, который она будит. |
| `peer_depth_ceiling` | `6` | Сколько подряд идущих реплик (с последнего сообщения человека или результата задачи) ещё способны поднять собственный ход. За этой глубиной реплика больше не будит ход — она остаётся в очереди и едет на ходе, случившемся по другой причине, так что обмен замедляется до темпа внешних событий, а не обрывается. |
| `peer_hard_cap` | `24` | Аварийный стоп — не должен срабатывать в нормальной работе, поскольку дебаунс и потолок глубины выше существуют именно для того, чтобы глубина никогда сюда не доходила. Срабатывание — дефект регулятора, а не нормальный исход, и отказывает реплике с уведомлением в чат вместо того, чтобы молча продолжать. |

Ожидание между репликами — `peer_debounce_base · 2^глубина`, снизу ограничено `peer_debounce_base`,
сверху `peer_debounce_max` — глубина 0 (реплика сразу после внешней энергии) всегда ждёт ровно базовое
значение, и ожидание растёт только когда переписка начинает циркулировать сама по себе. Реплика за
`peer_depth_ceiling` никогда не выбрасывается, только остаётся в очереди; по-настоящему отказывает
только `peer_hard_cap`. См. `docs/adr/ADR_20260827-2_core_roles.md` §2.4 и
`ChatPump.PeerWakePolicy`/`DecideWake` для самого регулятора.

## Профили запуска

Профиль — это **параметр CLI и шаблон, применяемый один раз, при создании.** Это не поле манифеста, и
ничто при загрузке не читает его обратно — поведение существующего проекта целиком определяется
обычными настройками, которые записал профиль (`agent.capabilities`, `plugins:`), никогда тем, «какой
профиль это создал». Хранение самого профиля добавило бы второй источник истины рядом с этими
настройками и подняло бы вопрос, какой из них побеждает; хранение только результата этого не может.

| Профиль | По умолчанию | Пишет | Значение |
|---|---|---|---|
| `minimal` | Да | `agent.capabilities: []` и подстановочную запись `plugins: { "*": { enabled: false } }` | Никаких встроенных возможностей `core.*` и никаких плагинов. Подключение LLM всё равно работает — это не возможность, и без него нечего запускать. |
| `standard` | Нет | Ничего | Намеренно пусто: отсутствующий ключ `agent.capabilities` уже означает «всё», а отсутствующая секция `plugins:` уже означает, что работает каждый плагин. Прописать это явно заморозило бы сегодняшний список функций в манифесте. |
| `inherit` | Нет | Манифеста вообще нет | Работает против `~/.spla/defaults.yaml` без проекта и без границы пути — историческое поведение, достижимое, но никогда не по умолчанию. |

Профиль задаётся через `spla init --profile <name> [--name <name>] [directory]`, либо через
`--init[=<name>]` перед любой другой командой, чтобы создать и сразу продолжить одним шагом
(`spla --init chat run "..."`, `spla --init=standard serve`). Один `--init` означает `minimal`.

Запуск в папке без манифеста больше не наследует молча настройки машины. Интерактивная сессия (REPL
без команды или `chat open`) спрашивает человека, что делать. Сценарный или headless-вызов
(`chat run`, `mcp`, `serve`) отказывает и называет `--init`, потому что запрос в процессе, за которым
никто не смотрит, просто зависает.

Манифесты, написанные до появления профилей, не затронуты: отсутствие маркера профиля означает ровно
то же, что означало всегда, поскольку его никогда и не было.

### Результат `minimal`

```yaml
version: 1

name: My Project

agent:
  capabilities: []

plugins:
  "*":
    enabled: false
```

## Запись плагина `*`

`IsPluginEnabled` разрешается в этом порядке: запись, называющая плагин, побеждает, если задаёт
`enabled`; иначе побеждает запись под ключом `"*"`, если задаёт `enabled`; иначе плагин включён.

```yaml
plugins:
  "*":
    enabled: false      # каждый плагин без своей записи выключен
  network:
    enabled: true        # именованная запись всё равно побеждает подстановочную
```

Подстановочная запись существует вместо сгенерированного списка всех установленных плагинов, потому
что манифест едет в git, а список плагинов одной машины — нет: вторая машина с другим набором плагинов
либо не досчиталась бы записей (молча наследуя «включено»), либо несла бы устаревшие записи для
плагинов, которых у неё никогда не было. `"*"` говорит «выключено, если не названо» без называния чего
бы то ни было — ровно то, что пишет профиль запуска `minimal`. `standard` не пишет здесь ничего по той
же причине, по которой не пишет ничего под `agent.capabilities`: отсутствующая секция `plugins:` уже
означает, что работает каждый плагин.

## Каскад настроек

```
Жёстко заданные значения по умолчанию  →  ~/.spla/defaults.yaml  →  project.spla  →  Runtime UI
```

Каждый слой переопределяет только те ключи, что явно задаёт. Отсутствующие ключи наследуются с
предыдущего слоя.

## Глобальные настройки по умолчанию

Находятся в `~/.spla/defaults.yaml`. Тот же формат YAML, но без полей, специфичных для проекта
(`instructions`, `docs`, `ignore`).

```yaml
version: 1

llm:
  provider: lmstudio
  endpoint: http://127.0.0.1:1234/v1
  api_key: lm-studio
  model: auto
  temperature: 0.7

agent:
  mode: Edit

ui:
  theme: Dark
```

## Персональное состояние — слой, не являющийся файлом настроек

Некоторые вещи принадлежат человеку, а не проекту или конфигурации машины, и их никогда нельзя
коммитить. Они живут как отдельные файлы в **персональном каталоге** — локально `~/.spla`, на сервере
`{server root}/users/{userKey}`, так что пользователи одного сервера ничего из этого не делят.

| Файл | Хранит | Пишется кем |
|---|---|---|
| `secrets.yaml` | значения учётных данных | UI секретов |
| `secrets.acl.yaml` | кто может использовать/управлять каждым секретом | UI секретов |
| `skills.yaml` | ветки скиллов, добавленные этим человеком | Настройки → Скиллы |
| `skills.acl.yaml` | папки, одобренные этим человеком, по ключу разрешённого пути | Настройки → Скиллы |

Паттерн одинаков в обеих парах, и его стоит сохранять: **список и разрешение над ним — это два файла,
никогда не один.** Список редактируется как данные; одобрение — это решение о безопасности, и один
документ для обоих — способ выдать себе что-то, отредактировав соседнее поле.

Это не слой настроек в смысле каскада — они хранят то, чего каскад хранить не может, а именно решение,
которое было бы неверно доставить каждому, кто клонирует репозиторий. `skills.yaml` действительно
сливается со списком источников как самый специфичный слой, что и позволяет панели выключить
унаследованную ветку, не трогая файл проекта.

## Использование

### CLI
```bash
# Явно
spla run my-project.spla

# Автоопределение (ищет *.spla только в текущем каталоге — без подъёма
# к родительским каталогам, и два манифеста в одном каталоге — отказ, а не жребий)
spla

# Веб-сервис; создать чат и отправить первое сообщение при подключении первого клиента
spla serve --new-chat "Introduce this project"
```

### GUI
Двойной клик по `my-project.spla` → SPLA открывается с полным контекстом.
