# SPLA.CLI — полный справочник по командам

[English](README_CLI.en.md)

> **Этот файл обязан отражать код.** Он описывает ВСЕ команды и флаги CLI. Меняешь разбор аргументов
> в `src/apps/SPLA.CLI/` — `Program.cs`, `Cli/CliBootstrap.cs`,
> `Cli/ServeCommand.cs`/`Cli/ServeCliCommand.cs`, `Cli/SecretCommands.cs`/`Cli/SecretCliCommand.cs`,
> `Cli/ChatCommands.cs`, `Cli/ReplCommand.cs`, `Batch/ChatRunCommand.cs`, `Cli/InteractiveRepl.cs` —
> правь оба справочника (`docs/README_CLI.ru.md` и `docs/README_CLI.en.md`) в том же коммите.
> Справочник, который врёт, хуже отсутствующего: по нему человек выполняет команду и получает
> `Scope is required` вместо результата.

Исполняемый файл называется **`SPLA.CLI.exe`**. Ниже он для краткости `spla` — как это устроить,
см. [Алиас в Windows](#алиас-в-windows).

Диспетчеризация — на [Spectre.Console.Cli](https://spectreconsole.net/cli/): каждая команда и
подкоманда ниже сама отвечает на `--help`/`-h` (`spla --help`, `spla chat --help`,
`spla chat run --help`, …), сгенерированный из тех же атрибутов, что управляют разбором — поэтому он
не может разойтись с тем, что реально принимается, как это бывает с текстом usage, написанным рукой.

## Как выбирается проект

Проект определяется ДО разбора команды, по первому аргументу:

| Запуск | Что берётся |
|--------|-------------|
| `spla <путь>.spla …` | именно этот файл; **если файла нет — он будет создан** (`ScaffoldIfNew`) |
| `spla chat …` | поиск `*.spla` вверх от текущего каталога |
| всё остальное, включая запуск без аргументов | поиск `*.spla` вверх от текущего каталога |

Если файл проекта не найден, CLI работает на глобальных настройках (`~/.spla/defaults.yaml`) — это
рабочий режим, а не ошибка. Когда проект найден, **рабочий каталог процесса меняется на `workspace`
проекта**, и относительные пути дальше считаются от него.

При старте печатается: файл проекта, имя проекта, workspace, endpoint модели, режим агента и число
зарегистрированных инструментов.

## Команды

### Без команды — интерактивный REPL

```
spla
spla myproject.spla
```

Создаёт новый чат и входит в цикл «строка → ход агента». Внутри REPL:

| Ввод | Действие |
|------|----------|
| `/skills` | список доступных скиллов: `[on]`/`[off]`, id, описание; плюс активный, если он есть |
| `/skills load <id>` | загрузить тело скилла в контекст текущего чата |
| `/skills unload` | завершить активный скилл, если модель не сделала это сама |
| `exit` / `quit` | выход |
| пустая строка | выход |

### `serve` — WebSocket-сервис

```
spla serve [--port <N>] [--bind <адрес>] [--token <строка>] [--repl] [--new-chat "<текст>"]
```

| Флаг | По умолчанию | Смысл |
|------|--------------|-------|
| `--port <N>` | `5050` | TCP-порт |
| `--bind <адрес>` | `127.0.0.1` | интерфейс |
| `--token <строка>` | нет | токен доступа к сокету |
| `--repl` | выкл | параллельная консольная сессия к тому же рантайму, что и у сокет-клиентов |
| `--new-chat "<текст>"` | нет | сообщение, с которого начинается первый чат |

Останов — Ctrl+C. С `--repl` слова `exit`/`quit` останавливают сервис; если stdin просто закрылся,
сервис продолжает работать.

Привязка не к loopback **без** `--token` выводит предупреждение и не блокируется: любой, кто достанет
до порта, управляет агентом. Это осознанное «предупреждаем, но не решаем за тебя» — но в сети так
делать не надо.

### `secret` — хранилище секретов

```
spla secret list                          --user | --project | --shared
spla secret set    <key> [--field <имя>]  --user | --project | --shared
spla secret delete <key> [--field <имя>]  --user | --project | --shared
```

Правила, из-за которых команда чаще всего не срабатывает с первого раза:

- **Флаг области обязателен и дефолта не имеет.** Так сделано намеренно: инструмент, выбирающий
  область сам, — это способ получить один ключ в двух хранилищах, где одно тихо затеняет другое.
- **`--field` учитывается только первый.** Одно поле за вызов; два поля — два вызова.
- **Значение вводится скрытым промптом**, в аргументах командной строки его передать нельзя — иначе
  оно осело бы в истории оболочки. По той же причине `list` печатает только ключи и имена полей,
  никогда — значения.
- `set` **дописывает** поле в существующую запись, не затирая соседние.
- `delete` с `--field` удаляет одно поле; без него — запись целиком. Удаление последнего поля удаляет
  запись.
- `--project` требует открытого проекта, иначе — отказ с подсказкой.

Область попадает в ссылку, которой на секрет ссылается конфиг: записанный с `--user` ключ
`my-host-ssh` адресуется как `secret:user:my-host-ssh`.

Поля, которые понимает SSH-плагин: `user`, `password`, либо `private_key` (+`passphrase`).

Коды возврата: `0` — успех, `1` — не найдено (при `delete`), `2` — ошибка в аргументах.

### `chat` — сохранённые чаты и пакетные запуски

```
spla chat list
spla chat open [id]
spla chat fork <id> [--model <имя>]
spla chat run  [--prompt "<текст>"]... [--prompt-file <путь>]... [--model <id>|all]...
               [--out <папка-или-файл>] [--out-name <шаблон>] [--overwrite]
               [--sys-prompt "<текст>"] [--md-clean] [--skill <id>]
               [--show-prompt] [--show-prompt-file <путь>]
               [--stream] [--temp <n>] [--reasoning <level>]
               [--timeout <секунды>] [--dry-run]
```

- `list` — id, заголовок, время изменения.
- `open [id]` — открыть чат и войти в REPL. Без id, или если id не найден, создаётся новый чат.
- `fork <id>` — копия чата, опционально с другой моделью (`--model`).
- `run` — пакетный headless-режим: каждый `--prompt`/`--prompt-file` × каждая `--model` идёт в своём
  свежем чате, без запросов разрешений на инструменты (каждый вызов инструмента отклоняется — спросить
  не у кого) и без clarify. Подробности ниже.

#### `chat run` — пакетный режим

Одна ячейка = один промпт × одна модель. `--model` можно повторять; `all` — прогнать все записи из
`connections:` проекта. `--prompt` — повторяемый текст прямо в командной строке (в именах файлов
получает имя `text1`, `text2`, …); `--prompt-file` тоже повторяем и сочетается с `--prompt` — именем
становится имя файла без расширения.

Куда уходит результат:

| `--out` | Поведение |
|---------|-----------|
| не задан | каждый результат печатается на экран отдельной панелью |
| папка (создаётся, если её нет) | один файл на ячейку, имя — по `--out-name` (по умолчанию `{timestamp} {label}`; плейсхолдеры `{timestamp}` `{prompt}` `{model}` `{label}`), при совпадении в одну секунду добавляется `(2)`, `(3)`, … |
| задан `--overwrite` | `--out` — один конкретный файл; **каждая ячейка его затирает** — годится для «только последний прогон», а не для матрицы из нескольких ячеек |

`--sys-prompt "<текст>"` и `--md-clean` **не трогают** `agent.custom_prompt` проекта — системный
промпт собирается из фиксированного именованного конвейера контрибьюторов (`mode` → `core.*` →
`instructions` → `custom-prompt` → `skills`/`toolsets`/`plugins`/`memory` — см. `spla chat run
--show-prompt` ниже), а добавки CLI едут отдельным контрибьютором `cli`, вставленным сразу после
`custom-prompt`: промпт проекта всегда на месте, без правок, текст прогона добавляется после него, а
не вместо. `--md-clean` просит у модели одно финальное сообщение чистым Markdown, без вступлений и
разговорных оговорок — расчёт на то, что файл после этого не нужно править руками.

`--skill <id>` выдаёт скилл каждой ячейке перед её промптом (тот же путь «выдал человек», которым
пользуется пикер скиллов в UI, а не трюк REPL-команды `/skills load` с подсовыванием сообщения) — если
скилл неизвестен, выключен или не хватает предпосылок, ячейка завершается ошибкой, а не запускается.

`--show-prompt` перед запуском печатает таблицу вкладчиков собранного системного промпта (кто что
добавил и сколько примерно токенов) — тот же вид, что вкладка «prompt» в отладочном инспекторе
контекста, чтобы видеть, куда именно легли `--sys-prompt`/`--md-clean` относительно `AGENTS.md` и
промпта проекта. `--show-prompt-file <путь>` вместо этого (или вместе с этим) пишет полный собранный
системный промпт в файл. `--dry-run` печатает план матрицы и будущие имена файлов, не вызывая ни одной
модели.

Код возврата — `1`, если хоть одна ячейка не удалась (таймаут/ошибка/пустой ответ/скилл), иначе `0`;
запись в `--out` — best-effort: неудавшаяся ячейка пропускается, не повторяется.

## Алиас в Windows

Копировать `SPLA.CLI.exe` в другое место **нельзя**: apphost ищет свою управляемую сборку рядом с
собой и в чужом каталоге просто не запустится. Переименование на месте работает, но каждая сборка
создаёт `SPLA.CLI.exe` заново, и переименование придётся повторять.

Рабочий вариант — шим `spla.cmd`. Он уже лежит в корне репозитория: добавь корень в `PATH` (или
скопируй файл в каталог, который там уже есть) — и `spla ...` работает откуда угодно.

Он сам ищет exe в порядке: переменная `SPLA_CLI` → `.publish\work` → `bin\Release` → `bin\Debug`,
поэтому переживает и пересборку, и публикацию. Если сборка лежит в стороне:

```bat
set SPLA_CLI=D:\где-то\SPLA.CLI.exe
```

Каталог шим не меняет намеренно: CLI ищет `*.spla` вверх от текущего каталога, и `cd` внутри шима
тихо подсунул бы не тот проект.

Альтернатива для PowerShell — строка в `$PROFILE`:

```powershell
Set-Alias spla 'C:\путь\к\SPLA.CLI.exe'
```

`doskey` не предлагаю: он живёт только внутри сессии `cmd` и в PowerShell не действует.
