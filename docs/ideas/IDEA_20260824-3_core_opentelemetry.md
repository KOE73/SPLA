## Два разных слоя, их нельзя путать

**Ошибка в чате — для человека.** Сбой вызова инструмента должен быть визуально first-class:
красная рамка, статус `Failed`, короткая причина, кнопки `Retry` / `Details`. Не заставлять
разбирать текст вызова, чтобы понять, что он упал.

**Trace — для системы.** Структурированный след для разбора harness: входные аргументы, какой
middleware что решил, фактический вызов, latency, exception / exit code / status, output, retry,
какой агент это инициировал, что сделал после ошибки, токены, checkpoint.

## Зачем trace на самом деле

Не для отладки. Для будущей автооптимизации. Без него утверждения вида «этот инструмент падает на
таких параметрах», «модель постоянно вызывает лишний инструмент», «после такого exception агент
делает бесполезный retry», «политика слишком строгая» остаются впечатлениями, а не измерением.

Это прямое продолжение уже принятого принципа «замерять на живых провайдерах».

## Что поднять и чем проверить

Поднять OTel Collector + backend (Jaeger/Tempo + Prometheus/Grafana) и прогнать SPLA end-to-end.
Один `run` должен давать связанный trace:

```text
agent run → model call → tool middleware → tool execution → error/retry → subagent
```

Приёмка не «traces видны в Jaeger», а: **от упавшего инструмента за один переход дойти до
конкретного prompt/run, агента и модели, и увидеть, что агент сделал после ошибки.**

Контрольные прогоны:

1. успешный вызов;
2. policy reject (см. приоритет 1);
3. упавший инструмент;
4. вызов с субагентом — проверить, что дерево прогресса и trace-дерево не разъезжаются.

Четвёртый добавлен сверх разговора: `ProgressScope`/`ProgressTree` уже строят своё дерево, и два
независимых дерева над одним вызовом — верный способ получить расхождение.
