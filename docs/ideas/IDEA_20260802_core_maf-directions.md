## 0. Workflow и playbooks — не рассматриваем

Решение владельца: «это нифига не агенты, а очередная выполнялка заданий». Согласен, и добавлю свой
довод: детерминированный граф в SPLA сейчас нечем кормить. Нет ни одной процедуры, которую гоняли бы
достаточно часто, чтобы окупить движок с исполнителями, рёбрами, контрольными точками и
возобновлением.

Единственное, что стоит **вынуть из этой темы и запомнить отдельно:** ценность была не в графах, а в
**инвариантах вокруг опасных операций** — «фиксация изменений только после подтверждения», «SQL на
запись только после предпросмотра», «число повторов ограничено». Это делается политиками и middleware
(блок 3), а не графом исполнения.

## 1. Единый механизм типизированных вкладов (`IAgentContributor`)

> **Сделано 2026-08-03** (этапы 1 и 2; этап 3 — вклад инструментами — остаётся за блоком 6).
> Решения и отличия от написанного ниже: [`ADR_20260803_agent_typed-contributions`](../adr/ADR_20260803_agent_typed-contributions.md),
> как это работает сейчас: [`agents/composition.md`](../../agents/composition.md).

**Суть.** Плагин, скилл, память, проект, режим, ядро — все они делают одно и то же: вносят вклад в
собираемую поверхность агента. Сегодня каждый вносит по-своему. Предлагается один интерфейс и один
типизированный результат:

```csharp
public interface IAgentContributor
{
    string Id { get; }
    ValueTask<AgentContribution> ContributeAsync(AgentContributionContext ctx, CancellationToken ct);
}

public sealed record AgentContribution
{
    IReadOnlyList<ContextItem>                  Context { get; init; }
    IReadOnlyList<ToolRegistration>             Tools { get; init; }
    IReadOnlyList<AgentMiddlewareRegistration>  AgentMiddleware { get; init; }
    IReadOnlyList<ToolMiddlewareRegistration>   ToolMiddleware { get; init; }
    IReadOnlyList<SkillDescriptor>              Skills { get; init; }
    IReadOnlyList<PolicyContribution>           Policies { get; init; }
    IReadOnlyList<UiContribution>               Ui { get; init; }
}
```

Ключевое ограничение — и оно важнее самой идеи: **механизм композиции единый, а виды вклада остаются
разными типами.** Иначе стирается различие между «это добавляет 800 токенов», «это запускает
PowerShell» и «это грузит сборку в процесс». На этом различии держатся доверие, разрешения и бюджет
контекста, поэтому терять его нельзя.

**Инструмент — не исключение из механизма, а вклад с двумя адресатами.** Формулировка «инструмент =
описание + реализация» не противопоставляет инструменты контексту: описание **и есть** вклад в
контекст. Один типизированный вклад несёт обе половины, а слой композиции разводит их по адресатам:

```
ToolRegistration = ContextItem (definition → в запрос модели)
                 + Handle      (implementation → в реестр исполнения)
```

Различие в доверии при этом никуда не девается — оно выражается не отдельным механизмом, а правом на
*вид* вклада: **недоверенный источник вправе внести `ContextItem`, но не вправе внести
`ToolRegistration`**. Одна проверка на типе вместо двух параллельных конвейеров.

Побочный продукт, который может оказаться ценнее самого интерфейса — **CompositionManifest**, отчёт
о том, из чего собрана текущая поверхность агента:

| Вопрос | Ответ, который должен давать манифест |
|---|---|
| Почему у агента есть этот инструмент? | набор `ssh` (плагин Ssh), уровень «по требованию скилла», включён скиллом `backup-docker-server` |
| Почему в промпте этот текст? | проектный скилл `coding-conventions`, версия 1.2, 840 токенов |
| Почему вызов заблокирован? | режим Inspect, правило `network.write` — запрет |

**Что уже есть — больше, чем кажется.** `SystemPromptBuilder` строит не строку, а список
`PromptSegment(Kind, Title, Body, Text)` с девятью источниками (режим, ядро, файлы инструкций,
пользовательский промпт, активный скилл, преднагруженные скиллы, индекс скиллов, промпты плагинов,
команды плагинов), и UI рисует те же сегменты цветными блоками. Это ровно половина будущего манифеста
— только по одной оси, контекстной, и с жёстко зашитым списком источников.

`IAgentFeature` связывает инструменты и prompt-фрагмент в одном объекте — тот же паттерн вклада, но
частный, только для core-фич. Он же становится ToolSet в блоке 6.

**Объём — большой, но дробится:**

| Этап | Что делаем | Объём | Что ломается |
|---|---|---|---|
| 1 | Обобщить `PromptSegment` до `ContextItem`: источник строкой вместо перечисления `PromptSegmentKind` | малый | только раскраска промпта в UI |
| 2 | Ввести `IAgentContributor` и перевести на него двух существующих поставщиков (core-фичи и плагины) | средний | `SystemPromptBuilder` из «знает всех» становится «складывает вклады» |
| 3 | Затянуть в тот же вклад инструменты | крупный | регистрация идёт через `PluginManager`/`McpHost` и завязана на `IsPluginEnabled` |

Этап 3 смыкается с блоком 6: типизированной единицей вклада становится ToolSet, поэтому отдельно от
блока 6 его делать не нужно.

**Вердикт: делать поэтапно, начиная с этапов 1 и 2.** Это самое сильное из всего обсуждения — не
потому, что красиво, а потому что снимает конкретную боль: сегодня на вопрос «почему у агента такой
промпт и такой набор инструментов» отвечает чтение кода в четырёх разных местах.

Но начинать я бы стал **не с интерфейса, а с манифеста** — с отчёта о том, кто что внёс, собранного
поверх сегодняшних источников. Он окупится сразу, при отладке, и заодно покажет, какие поля вклада
нужны на самом деле, а какие придуманы. Интерфейс, спроектированный до манифеста, почти наверняка
обзаведётся полями «на вырост».

**Одна правка к предложенному контракту:** `UiContribution` в одной записи с `Tools` — это
протаскивание UI в ядро. У нас UI уже отвязан: веб-панели общаются через `plugin.action` по границе
JSON. Поле `Ui` из `AgentContribution` надо убрать и оставить его в манифесте плагина, где ему и
место.

## 2. Поставщики контекста и токен-бюджет

> **Сделано 2026-08-03 частично.** Поставщики — да, вместе с блоком 1. **Бюджет — отвергнут:**
> локально резать контекст значит гадать, окно и занятость знает провайдер. Осталось измерение и
> атрибуция в манифесте. См. [`ADR_20260803_agent_typed-contributions`](../adr/ADR_20260803_agent_typed-contributions.md).

**Суть.** Вынести из `SystemPromptBuilder` динамические части в независимые поставщики: проект,
состояние git, активные скиллы, рабочая память, текущий файл, предпочтения пользователя, диагностика.
У каждого — собственный бюджет токенов.

**Что уже есть.** `SystemPromptBuilder`, `WorkingMemoryInjector` (38 строк) и `Features/CoreMemory`.
То есть поставщики фактически существуют, но зашиты внутрь построителя и вызываются в жёстко заданном
порядке.

**Объём.** Средний, и это фактически этап 2 из блока 1 — тот же самый код. Отдельно от блока 1 делать
не нужно.

**Вердикт: делать вместе с блоком 1.** Самостоятельная ценность здесь ровно одна, и она не
архитектурная — **бюджет токенов на каждого поставщика.** Сегодня, если скилл или память распухли,
они молча съедают окно контекста, и узнаёшь об этом по деградации ответов. Бюджет с усечением и
записью в манифест («контекст проекта обрезан: 4 000 из 6 000») — то, ради чего блок стоит делать
даже без остального.

Формулировку из переписки «и инструменты тоже через поставщика контекста» принимаю с уточнением из
блока 1: инструмент вносится тем же механизмом, но его вклад типизирован (`ToolRegistration`, а не
`ContextItem`), и право на этот вид вклада проверяется отдельно. Недоверенный источник по-прежнему не
сможет внести ничего, кроме текста, — но для этого не нужен второй конвейер.

## 3. Tool middleware (`IToolMiddleware`)

**Суть.** Обернуть вызов инструмента цепочкой: телеметрия → разрешение → проверка аргументов →
исполнение; далее по мере надобности таймаут, повтор, вычистка секретов, аудит, кеш, холостой прогон,
маршрутизация в песочницу.

**Что уже есть — и это главный аргумент «за».** `McpHost.ExecuteToolAsync` (`McpHost.cs:161–270`) уже
представляет собой такую цепочку, только развёрнутую руками в один метод:

```
плагин включён? → span → CheckPermission → PermissionScope.RequestAsync
  → ToolHostScope → ProgressScope → ExecuteAsync → RecordToolSuccess
```

Восемь независимых забот, зашитых последовательно, каждая со своим ранним `return "Error: ..."`.

И **образец, как это оформлять, у нас тоже уже есть**: `SPLA.Domain/Llm/ILlmMiddleware.cs` с
перечислением `LlmPipelineStage` (Trace → Policy → Content → Retry → Accounting → Transport), где
порядок задан типом, а не порядком регистрации, и часть стадий помечена как принадлежащая хосту и
закрытая для плагинов. Конвейер инструментов надо делать **по этому же шаблону** — тогда это не новая
абстракция, а второй экземпляр уже принятой.

**Объём.** Средний и локализованный: один класс `McpHost`, около 110 строк одного метода. Смысл кода
не меняется, существующая проверка разрешений просто становится первым настоящим middleware.

Главный риск — в типе результата. Сейчас инструмент возвращает `string`, и пока это так, middleware не
может отличить ошибку от текста, начинающегося со слова «Error». Придётся вводить `ToolResult`
(состояние + содержимое), а это затронет вызывающую сторону в `ConversationOrchestrator` и все места,
где результат складывается в сообщение.

**Вердикт: делать, вторым по счёту, после телеметрии.** Из четырёх предложенных в переписке конвейеров
(agent, turn, llm, tool) делать надо **только конвейер инструментов**. Конвейер LLM у нас уже есть и
проработан лучше описанного в переписке; уровни agent и turn пока нечем наполнить — не набралось
сквозных задач, ради которых стоило бы рвать `ConversationOrchestrator.RunAsync`. Универсальный
`IMiddleware<TContext>` не делать.

Что открывается сразу после введения конвейера — и ради чего он на самом деле нужен:

| Возможность | Почему без конвейера её нет |
|---|---|
| Таймаут на инструмент | сейчас его нет вовсе, зависший инструмент вешает весь turn |
| Вычистка секретов в аудите и телеметрии | иначе это надо повторять в каждом плагине |
| Холостой прогон («покажи, что сделаешь») | иначе надо править каждый инструмент по отдельности |
| Точка врезки песочницы (блок 7) | маршрутизация исполнения без переписывания инструментов |

## 4. OpenTelemetry — довести до сквозного трейса

**Суть.** Три интервала (span), связанные родитель-потомок:

```
spla.turn
├── spla.llm.call
├── spla.tool.call
├── spla.llm.call
└── spla.tool.call
```

Атрибуты — по стандарту `gen_ai.*` (провайдер, модель, входные и выходные токены) плюс свои
`spla.project.id`, `spla.chat.id`, `spla.mode`. Содержимое — промпты, аргументы, результаты, вывод
SSH, результаты SQL, содержимое файлов — по умолчанию **не писать**.

**Что уже есть.** Инфраструктура почти вся:

| Готово | Подробности |
|---|---|
| `ActivitySource` и `Meter` | оба с именем `SPLA`, в `SPLA.Observability` |
| Счётчики | `spla.tool.calls`, `spla.tool.errors`, `spla.tool.duration.ms`, `spla.tokens.prompt`, `spla.tokens.completion` |
| Автообогащение интервалов | `SplaTelemetryContext`: разговор, запрос, сообщение, вызов инструмента, проект, рабочая папка, пользователь |
| Экспорт по OTLP | ключ `--otlp-endpoint`, backend выбирается адресом |
| Локальная панель | `/stats`, без внешних систем |

**Чего не хватает — ровно одного, зато принципиального: интервалов почти нет.** По всему `src`
написан **один** вызов `StartActivity` — `mcp.tool.execute` в `McpHost.cs:171`. Ни `spla.turn`, ни
`spla.llm.call` не существует.

Значит, иерархии нет вообще: сегодня в Jaeger прилетит россыпь одиночных интервалов инструментов без
общего родителя. На вопрос «агент работал 47 секунд, почему» ответа не будет — не видно ни ожидания
провайдера, ни времени сборки контекста.

**Объём — малый, это самый дешёвый пункт из всех.** Два `using var activity`: один в
`ConversationOrchestrator.RunAsync`, второй в стадии `Trace` конвейера LLM, которая ровно для этого и
заведена. Плюс переименование `mcp.tool.execute` в `spla.tool.call` и атрибуты. Примерно полдня
работы вместе с ручной проверкой.

Чек-лист ручной проверки в Jaeger:

- два вызова инструментов попадают в один трейс с общим родителем;
- ошибка инструмента видна как ошибка;
- отказ по разрешению виден и отличим от ошибки;
- отмена (cancellation) не оставляет висящий интервал;
- параллельные подагенты не смешиваются в один трейс;
- в интервалы не утекли секреты, промпты, аргументы и содержимое файлов.

**Вердикт: делать первым.** Отдача максимальная при минимальном риске: ничего не ломается и ничего не
переписывается, а всё остальное — middleware, вклады, уровни — становится измеримым. После этого
любую переработку из документа можно оценивать по трейсу, а не по ощущениям.

## 5. Скиллы: совместимость с открытым форматом Agent Skills

**Суть.** Скилл — каталог с файлом `SKILL.md` (YAML-заголовок плюс текст процедуры) и необязательными
подпапками `references/`, `scripts/`, `assets/`. Раскрытие постепенное: агент изначально видит только
имена и описания, тело грузит по запросу, дополнительные материалы читает по необходимости.
Особенности SPLA кладутся в раздел `metadata:` или в отдельный файл рядом. Источников много:
каталог, проект, плагин, git, архив, **MCP**, реестр.

**Что уже есть — почти весь механизм:**

| Готово | Не хватает |
|---|---|
| `ISkillSource`: `Id`, `Label`, `Trust`, `Enumerate`, `Read` | скилл — один файл `.md`, а не каталог |
| `SkillSourceRegistry`, `DirectorySkillSource`, `PluginSkillSource` | нет дополнительных материалов и их ленивого чтения |
| `SkillManager`, `ISkillCapabilityProbe` | нет версий и совместимости |
| YAML-заголовок: `id`, `description`, `enabled`, `preloaded`, `requires`, `uses` | нет `McpSkillSource` |
| Проверка требований, закрытая по умолчанию при сомнении | |
| **Модель доверия на уровне источника** (`SkillTrust`) | |

Про доверие стоит сказать отдельно: в исходном предложении его нет вовсе, а вещь правильная. Тело
скилла попадает в системный промпт, поэтому недоверенный источник — это поверхность для внедрения
инструкций, и решать это надо на уровне источника, а не отдельной проверкой на каждой записи.

**Объём.** Малый для совместимости заголовка: наши поля ложатся в `metadata:`, а `name` и
`description` уже совпадают по смыслу. Средний для перехода «скилл = каталог»: придётся сменить смысл
`Ref` с «путь к файлу» на «путь к каталогу» и добавить чтение материалов через источник — контракт
это выдержит, поскольку `Ref` объявлен непрозрачным для ядра. `McpSkillSource` — отдельный средний
кусок работы.

**Вердикт: совместимость формата — делать; каталоги и материалы — позже; скрипты внутри скиллов — не
делать.** По пунктам:
- **Формат брать стоит, и это не «слямзить».** `SKILL.md` — открытая спецификация Agent Skills,
  Microsoft её реализует, а не владеет ею. Совместимость даёт переносимость скиллов в обе стороны и
  ничего не стоит. Своего несовместимого `skill.yaml` вместо `SKILL.md` изобретать не надо — только
  дополнительный файл рядом, если полей не хватит.
- **`McpSkillSource` — самая интересная часть.** MCP-сервер публикует не только тридцать инструментов,
  но и знание, как ими правильно пользоваться: ssh-плагин отдаёт `ssh_run`, `ssh_upload` и прочие
  **и вместе с ними** скиллы `backup-docker-server`, `deploy-compose-project`. У нас MCP и так
  центральный механизм инструментов, так что источник ложится естественно. Но делать его надо после
  блока 1, иначе это будет ещё один частный поставщик вклада.
- **Скилл должен ссылаться на набор, а не на плагин** (блок 6): `requires: [dns]` вместо
  `requires.plugins: [ad]`. Сегодня в `SkillRequirements` есть `Tools` и `Features` — с введением
  ToolSet эти два списка сливаются в один.
- **Скрипты внутри скилла — против.** Скилл есть текст из потенциально недоверенного источника, и
  исполняемый код в нём стирает границу между «попало в промпт» и «выполнилось». Для кода у нас есть
  плагины, для скриптов — Roslyn; смешивать не надо.
- **Режимы активации из предложения** (ручной, предложенный, автоматический, всегда включённый)
  частично уже есть: `enabled` и `preloaded` покрывают ручной и всегда включённый. Добавлять
  предложенный и автоматический стоит только тогда, когда скиллов станет столько, что ручной выбор
  начнёт мешать.

## 6. ToolSet: четыре уровня активации вместо флага «включён»

**Суть.** Сегодня единица включения — плагин, и у него два состояния. Предлагается две правки,
независимые друг от друга по смыслу, но полезные только вместе:

1. Единицей включения становится **ToolSet** — именованный набор инструментов. Плагин остаётся
   поставщиком кода и настроек и в активации не участвует.
2. У ToolSet не два состояния, а **четыре уровня**, различающиеся тем, сколько контекста набор
   занимает до того, как понадобился.

### 6.1. Две сущности: ToolSet и поставщик

**Проблема.** Плагин сейчас — «всё или ничего». Для ssh это нормально, для крупного плагина — нет.
Административный плагин Windows/AD естественно распадается на AD, DNS, DHCP, пользователей и
Hyper-V, и включать все шестьдесят инструментов ради правки одной DNS-записи бессмысленно. Резать
такой плагин на пять отдельных — тоже плохо: пять сборок ради пяти переключателей заставят
дублировать подключение, учётные данные и общий код.

**Отвергнутый вариант — вложенные группы.** Первым напрашивается «у плагина есть необязательные
группы, группа наследует уровень плагина с потолком». Это хуже, потому что уровень тогда несут две
сущности, и из этого немедленно вырастают правило наследования, «неявная группа» как частный случай
для плагинов без групп и правило обратной совместимости. Сложность добавляется ради случая, которого
в большинстве плагинов нет.

**Принятый вариант — снять ось, а не добавить.** Носитель уровня один, и он существует всегда, даже
когда набор в плагине единственный:

| | ToolSet | Плагин |
|---|---|---|
| Роль | единица **активации** | единица **поставки** |
| Владеет | id, объявление, уровень, `requires`, состав инструментов | сборка, версия, настройки, учётные данные, UI-панели |
| Участвует в решении «показать агенту» | да, целиком | нет |
| Роль в UI | то, что пользователь включает | группировка «эти наборы пришли из одного файла» |

Наследования нет, потолка из четырёх значений нет, частных случаев нет.

**Главный довод — так же уже устроены core-инструменты.** `IAgentFeature` сегодня и есть ToolSet:
набор инструментов плюс собственный prompt-фрагмент, включаемые одним объектом (`AgentRuntime.cs:231`,
`AgentFeatureCatalog`). То есть core-фичи и плагинные инструменты — два разных механизма для одного и
того же. При «ToolSet есть всегда» они сливаются в одну сущность с разным происхождением, а блок 1
получает готовую типизированную единицу вклада вместо выдуманной. Ради одного этого разделение стоит
делать, даже если крупного плагина вроде AD никогда не появится.

**Следствия:**

- **Именование упрощается.** Раз ToolSet самостоятелен, его id глобально уникален сам по себе и
  составной `ad.dns` не нужен. Скилл пишет `requires: [dns]`, а происхождение (`plugin: ad`) —
  атрибут для UI и диагностики.
- **Слово «домен» не годится.** Оно взрывается ровно на том примере, который его породил: в
  AD-плагине «домен» — это домен Active Directory. Комментарий `Expected tool name format:
  [pluginId].[domain].[action]` (`PluginManager.cs:273`) этой коллизии не видит и подлежит правке.
- **Загрузка сборки выводится механически:** сборка грузится, если хотя бы один её ToolSet стоит выше
  уровня «выключен». Отдельного решения это не требует.

### 6.2. Четыре уровня

Вопрос, который они решают: если инструменты набора не показаны агенту — знает ли он о его
существовании? Ответ не двоичный.

| Уровень | Что попадает в контекст | Кто включает | Цена |
|---|---|---|---|
| Выключен | ничего | никто | 0 |
| По требованию скилла | ничего | скилл, через `requires` в своей meta | 0 |
| По требованию агента | одна строка-объявление | агент сам, вызовом `toolset_activate` | ~20–40 токенов |
| Включён | полные definitions всех инструментов набора | — | сотни–тысячи |

Читается как «запрещено / разрешено, но только по заранее описанной надобности / разрешено, и агент
вправе позвать сам / всегда включено».

**Два средних уровня — не «больше и меньше одного и того же», а разные активаторы.** У скилла набор
прописан в его собственной meta заранее, поэтому объявлять набор агенту не нужно вовсе: активация
происходит механически при загрузке скилла и стоит ноль токенов. Агенту строка нужна именно потому,
что он выбирает сам, и эти 20–40 токенов — плата за непредусмотренный заранее случай.

Отсюда важное предупреждение на будущее: осей здесь две — **кто активирует** и **сколько контекста**,
— и в линейную лесенку они складываются случайно, потому что средние два уровня удачно упорядочились
по второй оси. Если когда-нибудь понадобится пятый уровень (скажем, «по требованию пользователя из
UI: без контекста заранее, но с полными definitions после»), лесенка разъедется и оси придётся
считать раздельно.

**Уровень ставится на набор, а не на отдельный инструмент.** Четыре уровня на каждый инструмент не
нужны: для этого достаточно точечного вкл/выкл, которое уже работает
(`PluginManager.IsToolEnabled`, `settings.Plugins[id].Tools[toolName]`). Им покрывается случай «набор
ssh по требованию агента, но `ssh_upload` выключен совсем».

**Уровень задаёт человек — и это же снимает вопрос об опасных наборах.** Агент вправе поднять только
то, что пользователь заранее поставил на «по требованию агента». Roslyn туда просто не ставят, и
никакого отдельного потолка для этого не требуется.

### 6.3. Объявление набора для уровня «по требованию агента»

Из существующей meta объявление выводится только наполовину. `PluginMeta` несёт `Id` и `Description`,
из них собирается строка «что это». Но агенту нужен ответ на другой вопрос — «когда меня звать», — и
он механически не выводится: его пишет автор набора.

```
ssh — 12 инструментов: подключение к удалённым хостам, живые сессии, передача файлов.
      Звать при: удалённый сервер, docker на хосте, разбор логов по ssh.
      toolset_activate("ssh")
```

Это ровно то же поле, что `description` у скилла в индексе, и работает по той же логике постепенного
раскрытия. То есть нужно одно новое поле в манифесте набора, а не новая механика.

**Оба нужных механизма в коде уже есть, и один из них не огорожен:**

- `PromptSegmentKind.SkillsIndex` (`SystemPromptBuilder.cs:208`) — индекс скиллов в промпте. Это
  работающий уровень «по требованию агента», только для скиллов; индекс наборов — тот же сегмент.
- `McpHost.GetToolHelp` (`McpHost.cs:88`) ищет в `_tools` напрямую и **не проверяет, включён ли
  плагин** — в отличие от `GetToolDefinitions` (`McpHost.cs:81`), где стоит `IsToolAvailable`. Значит,
  сегодня агент, угадавший имя `ssh_run` при выключенном ssh-плагине, получит полное описание и схему.

Второе — расхождение с заявленным поведением (по смыслу баг: выключенный плагин не должен быть
описуемым) и одновременно случайно написанный прототип отложенного раскрытия. При вводе уровней эта
же развилка становится границей:

| Уровень | `tool_help` | `execute` |
|---|---|---|
| Выключен | нет | нет |
| По требованию скилла | нет | нет до активации скиллом |
| По требованию агента | да | нет до `toolset_activate` |
| Включён | да | да |

### 6.4. Где живёт уровень и где живёт активация

Это разные вещи, и они хранятся в разных местах:

| | Уровень | Активация |
|---|---|---|
| Что это | «разрешено ли вообще» | «взведено ли прямо сейчас» |
| Кто задаёт | человек | скилл, агент или человек |
| Где живёт | настройки проекта (`.spla`) и пользователя | состояние чата (`ChatRuntime`) |
| Срок жизни | до изменения настройки | до конца чата |

**Сейчас так не получится, и это основной объём блока.** `McpHost` и `PluginManager` создаются в
`AgentRuntime` (`AgentRuntime.cs:138,161`) — они процессные. `SkillSession` создаётся в `ChatRuntime`
(`ChatRuntime.cs:29`) — он на чат. Скиллы этот путь уже прошли, плагины нет:
`PluginManager.IsPluginEnabled` читает глобальные настройки, то есть состояние ровно одно на процесс.

Следствие: «агент включил ssh в этом чате» без доработки протечёт во все параллельные чаты — а
параллельные чаты у нас поддерживаются намеренно, с раздельными областями разрешений и режимами.
Активация должна лечь в `ChatRuntime` рядом с `SkillSession`, а гейт в `McpHost`
(`IsToolAvailable`, `GetToolDefinitions`, `GetToolHelp`) — принимать её из окружения вызова, как
сейчас принимается `AgentMode`.

Работа здесь — в переносе области видимости, а не в объявлении перечисления на четыре значения.

> Записано по ходу обсуждения 2026-08-02, чтобы рассуждение не потерялось. **Это ещё не решение.**
> ADR пишется под принятое решение и после этого не правится, поэтому пока живёт здесь.

**Исходное намерение:** проектный вариант — один файл проекта, везде одни инструменты. Сетевой проект
означает сетевые инструменты и ssh во всех его чатах.

**Что с ним не так:** намерение верное, но один слой отвечает сразу на два разных вопроса —
«разрешено ли это вообще» и «показано ли модели прямо сейчас». Первое есть свойство проекта и решение
человека, оно устойчиво. Второе есть свойство чата и следствие конкретной задачи: в чате про правку
конфига ssh не нужен, а в соседнем чате того же проекта нужен. Склеенные, эти вопросы дают либо
раздутый контекст во всех чатах, либо протечку активации между параллельными чатами.

**К чему пришли:** два слоя вместо одного. Проект отвечает, что доступно; чат — что из доступного
взведено. Проект остаётся единственным местом, где человек настраивает состав, а чат ничего не
разрешает и только выбирает из уже разрешённого. Поэтому «агент включил ssh» никогда не расширяет
границу, заданную проектом, и не может протечь в соседний чат.

**Прецедент:** у скиллов это уже сделано и работает — источники и доступность процессные,
`SkillSession` на чат. Плагины отстали на один шаг.

**Чем платим:** состояние набора перестаёт быть одним флагом в настройках, появляется различие между
уровнем и активацией, и его придётся объяснять в UI. Иначе пользователь не поймёт, почему набор
«включён», а агент его не видит.

### 6.5. Что уже есть в коде

| Механизм | Состояние |
|---|---|
| `PluginManager.IsPluginEnabled` | двузначный флаг из настроек, процессный |
| `settings.Plugins[id].Tools[toolName]` | точечное вкл/выкл инструмента — работает |
| `IAgentFeature` / `AgentFeatureCatalog` | де-факто ToolSet для core-инструментов |
| `PluginMeta` | `Id`, `Version`, `DependsOn`, `Commands`, `Metadata` — понятия набора нет |
| `PluginMeta.DependsOn` | объявлен; используется ли при загрузке — **проверить** |
| `PluginLoadContext` / `PluginAssemblyLoader` | вынесены отдельно |
| `PromptSegmentKind.SkillsIndex` | работающий индекс-объявление, но только для скиллов |
| `GetToolDefinitions` | закрыт `IsToolAvailable` |
| `GetToolHelp` | **не закрыт** — расхождение, см. 6.3 |
| `SkillSession` в `ChatRuntime` | образец того, как должна храниться активация |

### 6.6. Объём и чем платим

**Объём — средний, при условии что физическая загрузка сборок не трогается.** Физических состояний
сборки по-прежнему два; четыре уровня различаются **раскрытием**, а не загрузкой:

| Уровень | Сборка | Вклады |
|---|---|---|
| Выключен | можно не грузить, достаточно дескриптора | нет |
| По требованию скилла | загружена | не активны |
| По требованию агента | загружена | не активны |
| Включён | загружена | активны |

Если попытаться делать отложенность через реальную выгрузку `AssemblyLoadContext`, упрёмся в
выгрузку, висящие ссылки, фоновые службы, UI-регистрации и native-библиотеки. Этот сорт боли уже
знаком по `roslyn-scripting-alc-globals`. Туда не ходить.

Точка контроля при этом остаётся прежней, на уровне инструмента (`IsToolAvailable` /
`IsToolEnabled`): ToolSet лишь задаёт, какие имена меняются вместе.

**Чем платим:**

- настройки меняют форму (`Plugins[id].Tools{}` → `ToolSets[id]`), нужна миграция существующих
  `.spla`;
- UI обязан показывать происхождение набора, иначе пользователь теряет связь «эти наборы из одного
  файла» и не понимает, почему у них общие учётные данные;
- появляется различие «уровень» и «активация», которое надо объяснить в интерфейсе.

### 6.7. Сценарии: какой уровень чему подходит

Разобрано на реальном составе плагинов репозитория. Ценность здесь не в раскладке по уровням, а в
третьем столбце: каждый сценарий вскрывает отдельное требование к механизму.

| Плагин / набор | Уровень | Что вскрывает |
|---|---|---|
| **Network** + `SPLA.Skills.Network` | по требованию скилла | Готовый эталон второго уровня: плагин уже поставляет скиллы. В контексте объявлен только скилл `diagnose-host`, набор втягивается его meta. На нём и проверять. |
| **Roslyn** | по требованию скилла либо явно включён | Опасные наборы регулируются тем, что человек просто не ставит их на «по требованию агента». Отдельный потолок для этого не нужен; открытым остаётся лишь вопрос умолчаний при обновлении — см. 6.8. |
| **OneC** | включён, но на проект | Уровень живёт в настройках проекта, а не только глобально. Приоритет как у скиллов: проект > пользователь > умолчание набора. |
| **Browser** + **Browser.Screencast** | по требованию агента | Зависимости между наборами должны разрешаться при активации, а не только при загрузке (`PluginMeta.DependsOn` объявлен — проверить, участвует ли он). Отдельно: у screencast активация даёт видимый побочный эффект (окно, запись), то есть «тихо активировать в середине turn'а» нельзя. |
| **Sql** | по требованию скилла | Активации мало: нужны выбранное соединение и секрет. `toolset_activate` должен уметь вернуть «активирован, но требуется выбор соединения» и поднять уточнение, а не молча преуспеть. Активация — операция с возможным запросом к человеку, а не флаг. |
| **Ssh** | по требованию агента | Тот случай, ради которого третий уровень и нужен: удалённый хост всплывает в разговоре непредсказуемо, заранее скиллом не покроешь. Требует поля «когда меня звать» в манифесте — из `Description` оно не выводится. |
| **Test** | выключен | «Выключен» обязано означать «не существует» для агента, включая `tool_help`. Сейчас это не так (см. 6.3). |

### 6.8. Открытые вопросы

**❓ Рубильник доверия у поставщика — нужен или лишний.**
**Не решено, требует отдельного разбора владельцем: принять или выкинуть.** На остальную модель не
влияет и её не блокирует.

Предложение: помимо четырёх уровней на наборах, у поставщика остаётся один двоичный переключатель
«доверен / нет», гасящий все его наборы разом.

- *За:* риск есть свойство кода, а не имени набора. Все наборы одной сборки исполняются одним кодом и
  делят процесс, память и права. Если Roslyn выставит наружу три набора с самостоятельными уровнями,
  действие «выключить Roslyn» перестанет быть одним действием: придётся погасить все три, а завтра в
  обновлении появится четвёртый.
- *Против:* это возвращает поставщика в модель управления доступом, из которой его только что убрали,
  — а ради этого разделения всё и затевалось.
- *Возможное решение без него:* правило умолчания «новый, ранее не виденный набор всегда выключен».
- *Вопрос, который закрывает тему:* бывает ли случай, когда пользователь хочет погасить именно
  поставщика, а не наборы? Если да — рубильник нужен. Если единственный сценарий это «не хочу
  сюрпризов при обновлении» — хватает правила умолчания, и рубильник выкидывается.

**❓ Что отвечать на вызов недоступного инструмента.** Агент зовёт `ssh_run`, набор стоит на «по
требованию скилла». Вариант «нет такого инструмента» честен по раскрытию, но заводит агента в тупик и
провоцирует переспрашивание. Вариант «есть, но включить может только скилл или пользователь» полезнее,
однако раскрывает существование набора, то есть частично откатывает ко второму уровню. Решение
продуктовое; склоняюсь ко второму варианту, потому что тупик дороже.

**❓ Срок жизни активации.** Набор включён на пятом turn'е, чат идёт ещё пятьдесят, инструменты висят
в контексте всё это время. Возможные области: turn, чат, проект, приложение. Начать стоит с «до конца
чата», постоянное включение оставить решением пользователя.

**❓ Активация в подагенте.** `SpawnedAgentRunner` получает `McpHost` родителя (`AgentRuntime.cs:168`),
то есть состояние сейчас общее. Правильное поведение: активация подагента живёт в его собственной
сессии и умирает вместе с ней, родителю не наследуется. Это придётся задать явно.

**Обязательное во всех случаях:** любая активация пишется строкой в `CompositionManifest` (блок 1) —
кто включил, на каком основании и когда. Иначе на вопрос «откуда в середине чата взялись двенадцать
новых инструментов» ответа не будет.

### Вердикт по блоку 6

**Делать, после блока 1.** Промежуточные уровни имеют смысл, когда есть кому активировать набор, то
есть когда скиллы умеют объявлять зависимость и что-то умеет её исполнить. Сейчас `requires.tools`
есть, а механизма активации нет: скилл, требующий выключенный плагин, просто недоступен.

Практическая польза не архитектурная, а прямая — **экономия контекста**. Каждый включённый набор
стоит своих definitions и своего prompt-фрагмента в каждом запросе; два промежуточных уровня
позволяют держать установленными десяток плагинов, не оплачивая их токенами постоянно.

## 7. Изоляция / sandbox — в отдельный репозиторий

**Суть.** Sandbox — самостоятельный слой, и начинать надо не с контейнеров, а с контракта:
`SandboxRequest`, `MountDefinition`, `NetworkPolicy`, `ProcessLimits`, `SandboxResult` плюс
клиентский интерфейс `ISandboxExecutor` в SPLA. Реализации приходят потом: `DirectExecutor`
(сегодняшнее поведение, без изоляции), затем отдельный процесс, Windows Sandbox, Docker, удалённый
исполнитель.

Изоляция задаётся набором возможностей, а не одним переключателем «безопасно», потому что разным
инструментам нужно разное:

| Что изолируем | Что для этого нужно |
|---|---|
| Файловая система | ограничение точек монтирования |
| Оболочка (shell) | процесс, файловая система и сеть одновременно |
| Браузер | отдельный профиль и сетевая политика |
| SQL | учётные данные и сетевые политики |
| SSH | изоляция учётных данных, но не файловой системы |

**Что уже есть.** Модель разрешений и возможностей (`PermissionManager`, `PermissionScope`, режимы
агента, отсечение по возможностям). Но это **контроль на уровне приложения, а не граница
безопасности**: при разрешённой оболочке процесс получает права текущего пользователя. Менеджер
разрешений запретит вызов инструмента, но не спасёт ни от ошибки внутри разрешённого инструмента, ни
от выхода за пределы рабочей папки, ни от вредоносного дочернего процесса, ни от уязвимого плагина.

**Объём.** Контракт, `DirectExecutor` и врезка — малый; если блок 3 сделан раньше, врезка становится
одним middleware и обходится почти бесплатно. Реальные изоляторы — большой отдельный проект.

**Вердикт: контракт делать, изоляторы — отдельный репозиторий и отдельная жизнь.**

Одно дополнение к решению владельца: **первым шагом должны быть не контейнеры, а честная формулировка
в документации.** Надо проверить `docs/readme_security*.md` на предмет обещаний, которых код не
выполняет; правильная формулировка — «в SPLA есть модель разрешений и возможностей, но нет изоляции
исполнения». Это не стоит ничего и закрывает главный риск темы — ложное ощущение защищённости.

## 8. Переименование `ConversationOrchestrator`

**Суть.** Класс на 323 строки занимается не «оркестрацией разговора», а циклом агента: строит запрос,
обрабатывает потоковый ответ, читает и исполняет вызовы инструментов, возвращает результаты модели,
повторяет, следит за защитой от зацикливания, работает с контрольными точками и памятью.

| Сейчас | Предложено |
|---|---|
| `ConversationOrchestrator` | `AgentLoop` |
| `SpawnedAgentRunner` | `SubagentRunner` |

**Объём.** Тривиальный: переименование по всему решению.

**Вердикт: под вопросом, склоняюсь к «сделать заодно».** Само по себе переименование не даёт ничего.
Единственный содержательный довод в переписке — «чтобы термин не столкнулся с будущим
`WorkflowRunner`», а workflow мы не делаем (блок 0), так что и срочности нет.

При этом `AgentLoop` точнее описывает содержимое класса, а `SubagentRunner` короче и яснее, чем
`SpawnedAgentRunner`. Если делать, то отдельным коммитом, чтобы не смешивать переименование с
содержательными правками. Удобный момент — перед блоком 3, когда этот файл и так будет тронут
из-за введения `ToolResult`.

## 9. Правило: что можно брать у чужих фреймворков

Вопрос возник по ходу обсуждения и закрыт; фиксирую, чтобы не возвращаться.

| Можно без оговорок | Требует проверки лицензии | Не стоит |
|---|---|---|
| архитектурный паттерн | копирование исходного кода | копировать сложность MAF, которая SPLA не нужна |
| общепринятые термины | перенос значительных фрагментов | повторять чужой API один в один без причины |
| реализация открытого формата | тесты и документация почти дословно | делать функцию только потому, что она есть у крупного фреймворка |
| изучение публичного API | форк библиотек | выдавать заимствованное название за совместимость |
| повторение удачного разделения ответственности | включение сторонних ресурсов | |
| поддержка стандартного протокола | | |

Для `SKILL.md` это даже не заимствование: спецификация Agent Skills открытая, Microsoft её реализует,
а не владеет ею. Поддержать её — значит не запереть свои скиллы в собственном формате.
