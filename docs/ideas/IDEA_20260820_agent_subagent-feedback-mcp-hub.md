## 1. Проблематика: зачем и почему нужна обратная связь

### Контекст
SPLA может использоваться не только как самостоятельное интерактивное приложение с родным интерфейсом, но и как **инструментальный бэкенд / MCP-сервер** для внешних крупных агентов (ChatGPT, Claude Code, Cursor, Windsurf, Antigravity и др.) через команду `spla mcp` или сетевой endpoint.

В этом сценарии внешний агент видит инструментальный стол SPLA, включая мета-инструменты делегирования: `agent_spawn` и `agent_spawn_batch`.

### В чём проблема («чёрный ящик»)
Когда внешний агент вызывает `agent_spawn`:
1. Задача уходит в изолированный рантайм `SpawnedAgentRunner`.
2. Подагент может работать от 20 секунд до нескольких минут: выполняет серию обращений к LLM, активирует скиллы, читает десятки файлов, сканирует порты, запускает скрипты и компиляторы.
3. Всё это время для вызывающего агента и для человека за экраном вызов выглядит как **глухое зависание**:
   - Нет индикации, жив ли процесс.
   - Не видно, на каком шаге находится агент.
   - Не видно промежуточных рассуждений (`reasoning`) и вызовов инструментов.
   - Невозможно понять, не застрял ли подагент в цикле повторных ошибок или галлюцинаций.
   - Нельзя вовремя прервать выполнение или скорректировать направление.
4. По завершении возвращается лишь одна финальная строка ответа ассистента.

**Цель:** Сделать работу подагента прозрачной и наблюдаемой «сверху» как в интерфейсе вызывающего агента (через протокол MCP), так и на стороне окружения SPLA (через веб-интерфейс, боковую панель или окно Хаба).

## 2. Стандартные механизмы в спецификации MCP (Model Context Protocol)

Спецификация MCP (JSON-RPC) предоставляет три различных механизма для передачи информации от сервера к клиенту.

```
                  ┌────────────────────────────────────────────────────────┐
                  │                    MCP Transport                       │
                  └───────┬────────────────────────┬───────────────┬───────┘
                          │                        │               │
            tools/call + _meta.progressToken   logging/setLevel  resources/read + subscribe
                          │                        │               │
                          ▼                        ▼               ▼
                 ┌─────────────────┐      ┌─────────────────┐ ┌─────────────────┐
                 │ Progress Tokens │      │   MCP Logging   │ │  MCP Resources  │
                 │ (notifications/ │      │ (notifications/ │ │ (notifications/ │
                 │    progress)    │      │    message)     │ │resources/updated│
                 └────────┬────────┘      └────────┬────────┘ └────────┬────────┘
                          │                        │                   │
                     К вызову инструмента    К серверу/сессии    К URI пассивных данных
```

### 2.1. Progress Tokens (`notifications/progress`)

*Основной инструмент оперативной обратной связи при длительных операциях.*

- **Привязка:** Строго к конкретному запросу (`tools/call`).
- **Инициатор:** Клиент. При отправке запроса на вызов инструмента клиент генерирует и передаёт уникальный токен в секции `_meta`:
  ```json
  {
    "jsonrpc": "2.0",
    "id": 101,
    "method": "tools/call",
    "params": {
      "name": "agent_spawn",
      "arguments": {
        "input": "Проведи аудит портов и обнови конфигурацию"
      },
      "_meta": {
        "progressToken": "spawn-task-789"
      }
    }
  }
  ```
- **Работа сервера:** Во время работы подагента сервер периодически шлёт JSON-RPC нотификации без `id`:
  ```json
  {
    "jsonrpc": "2.0",
    "method": "notifications/progress",
    "params": {
      "progressToken": "spawn-task-789",
      "progress": 3,
      "total": 8,
      "message": "Шаг 3/8: Запущен инструмент run_command (nmap scan)..."
    }
  }
  ```
- **Жизненный цикл:** Завершается в момент отправки финального ответа (`result` или `error`) на запрос `tools/call`.
- **Отображение в клиенте:** Отображается прямо в основном диалоге рядом с карточкой инструмента (прогресс-бар, анимированный спиннер, меняющийся статус-текст).

### 2.2. MCP Logging (`notifications/message` + `logging/setLevel`)

*Инструмент системной телеметрии и фонового аудита.*

- **Привязка:** К сессии подключения в целом, не зависит от конкретного `tools/call`.
- **Инициатор:** Сервер (при условии, что клиент настроил фильтр через `logging/setLevel`).
- **Работа сервера:** Сервер транслирует системные события разного уровня важности (`debug`, `info`, `notice`, `warning`, `error`, `critical`):
  ```json
  {
    "jsonrpc": "2.0",
    "method": "notifications/message",
    "params": {
      "level": "info",
      "logger": "spla.runtime.subagent",
      "data": {
        "event": "tool_executed",
        "tool": "fs_read",
        "durationMs": 42
      }
    }
  }
  ```
- **Жизненный цикл:** Непрерывный поток на протяжении всей жизни соединения.
- **Отображение в клиенте:** В системных журналах, консоли разработчика (Output / DevTools), не засоряя контекст диалога модели.

### 2.3. MCP Resources (`resources/list`, `resources/read`, `resources/subscribe`)

*Инструмент пассивного доступа к данным и состоянию по URI (аналог REST GET).*

- **Принцип:** Ресурсы представляют собой сущности только для чтения с уникальным URI (`spla://...`, `file:///...`) и MIME-типом.
- **Сценарии для подагентов:**
  1. **Живой транскрипт сессии:** Сервер объявляет динамический ресурс вида `spla://subagents/{instanceId}/transcript` (`text/markdown` или `application/jsonl`).
  2. **Подписка на обновления:** Клиент может подписаться на ресурс через `resources/subscribe`. При каждом новом сообщении или вызове инструмента сервер шлёт:
     ```json
     {
       "jsonrpc": "2.0",
       "method": "notifications/resources/updated",
       "params": {
         "uri": "spla://subagents/subagent-456/transcript"
       }
     }
     ```
  3. **Инспекция состояния проекта:** `spla://project/tasks` — список всех активных подагентов и их текущих статусов.

### 2.4. Границы и ограничения спецификации MCP
- В MCP **нет стандарта на встраиваемый интерактивный GUI** (нет механизма для передачи iframe, вебвью или вызова нативного UI).
- Запрос `tools/call` является блокирующим в рамках протокола: клиент ожидает итоговый `result` в конце работы.

## 3. Паттерны «Больших агентов» (Sidecar, Drawer, First-Class Tasks)

Ведущие агентские среды (Antigravity, Cursor, Claude Code, Devin, Windsurf) решают задачу наблюдения за подагентами через разделение уровней:

1. **Подагент как First-Class Conversation / Task:**
   - Подагент не является анонимной функцией в памяти. Каждому запуску присваивается полноценный `taskId` / `chatId`.
   - Полный транскрипт (системный промпт, мысли/reasoning, вызовы инструментов, ответы, ошибки) сохраняется на диск (например, `.spla/chats/{id}.json` или `transcript.jsonl`).
2. **Параллельная шина событий:**
   - Все события оркестратора (`turn.start`, `delta`, `tool.started`, `tool.result`, `assistant.message`) транслируются в локальную шину (WebSocket / EventBus).
3. **Боковое окно (Sidecar Panel / Drawer / Split View):**
   - В UI появляется боковая панель или вкладка «Фоновые задачи / Подагенты».
   - Клик по задаче открывает полнофункциональный чат, где в реальном времени стримится текст и отображается дерево выполнения инструментов.
4. **Deep Links / Ссылки в выводе:**
   - В основном чате или в промежуточном статусе выдаётся ссылка вида:
     `[Подагент task-123 запущен (открыть транскрипт)](http://localhost:5050/#/chat/task-123)`.

## 4. Текущее состояние SPLA и архитектурный разрыв

Анализ кодовой базы SPLA показал:

```
[Внешний клиент / ChatGPT]
       │ (JSON-RPC over Stdio)
       ▼
[McpStdioServer] ──(нет поддержки _meta.progressToken, нет notifications/progress)
       │
       ▼
[McpHost] ──(вызов agent_spawn)
       │
       ▼
[SpawnedAgentRunner] ──(создает Conversation чисто в памяти)
       │ ──(НЕ регистрирует чат в ChatRegistry)
       │ ──(НЕ публикует события в SplaServiceHost / ConnectionHub)
       │ ──(НЕ регистрирует участника в RegistryHub)
       ▼
[Результат]: Черный ящик. Возвращается только lastAssistantMessage.
```

### Ключевые разрывы:
1. `McpStdioServer.cs` не читает `_meta.progressToken` из входящего JSON и не умеет отправлять нотификации `notifications/progress` или `notifications/message`.
2. `SpawnedAgentRunner.cs` создаёт сессию `AgentSession` и `Conversation` на лету, не сохраняя её в `ChatRegistry`.
3. События `AgentCallbacks` (включая `OnToolProgress` и `OnProgressTree`) у подагента не подключены к `ConnectionHub`, поэтому подключённые веб-клиенты и окна Avalonia ничего не знают о происходящем.
4. `RegistryHub.cs` учитывает участников с ролями `agent`, `window`, `hub`, но запущенные подагенты не регистрируются как дочерние участники.

## 5. Варианты реализации: от MCP-протокола до автоматизации через Хаб

Предлагается трехуровневая архитектура обратной связи:

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                            УРОВНИ ОБРАТНОЙ СВЯЗИ                            │
├─────────────────────────────────────────────────────────────────────────────┤
│ Уровень 1: Протокол MCP (In-Band для ChatGPT / внешнего клиента)             │
│   • Progress Tokens: стриминг текущего шага в плашку вызова инструмента     │
│   • Resources: публикация URI транскрипта spla://subagents/{id}/transcript  │
├─────────────────────────────────────────────────────────────────────────────┤
│ Уровень 2: Домен и Данные (SPLA Core & Service)                             │
│   • Subagent as First-Class Chat (сохранение в ChatRegistry)                │
│   • Трансляция событий (delta, tool.*) в WebSocket ConnectionHub            │
├─────────────────────────────────────────────────────────────────────────────┤
│ Уровень 3: UI и Автоматизация через Хаб                                     │
│   • Авто-открытие вкладки браузера: http://localhost:5050/#/chat/{id}       │
│   • Регистрация в RegistryHub (роль subagent, статус working/waiting)       │
│   • Отображение в системном трее и запуск отдельного окна Avalonia          │
│   • Split-view / Drawer в уже открытом окне SPLA                            │
└─────────────────────────────────────────────────────────────────────────────┘
```

---

### Вариант 1. Минимальный: Поддержка Progress Tokens в MCP-сервере

**Как работает:**
1. `McpStdioServer.HandleAsync` при разборе `tools/call` извлекает `_meta.progressToken`.
2. Если токен передан, создается контекст прогресса.
3. В `McpHost` через существующий `ProgressScope` тики `ProgressTree` и `OnToolProgress` маппятся в вызовы `output.WriteLineAsync(notifications/progress)`.
4. Внешний клиент (ChatGPT, Claude Desktop, Cursor) немедленно начинает отрисовывать статус текущего шага.

**Плюсы:**
- Работает полностью в рамках официальной спецификации MCP.
- Не требует запуска GUI или браузера.
- Минимальный объём изменений.

**Минусы:**
- Показывает только однострочный статус/прогресс, нет доступа к полному диалогу и детальным рассуждениям модели.

---

### Вариант 2. Подагент как полноценный чат (First-Class Chat)

**Как работает:**
1. `SpawnedAgentRunner.RunAsync` генерирует `chatId = "subagent-" + Guid.NewGuid().ToString("N")[..8]`.
2. Чат регистрируется в `ChatManager` / `ChatRegistry` проекта с метаданными (`parentChatId`, `skillId`, `isSubagent: true`).
3. Коллбеки `AgentCallbacks` подагента подключаются к `ConnectionHub.BroadcastToWatchersAsync` (или транслируются через `AgentRuntime.Events`).
4. По завершении чат сохраняется в `.spla/chats/`, история доступна для последующего анализа.

**Плюсы:**
- Полная прозрачность: подагент неотличим от основного чата по уровню наблюдаемости.
- Сохранение истории и возможность ретроспективного аудита.
- Доступно для любого подключенного клиента (Web UI, Avalonia).

### Вариант 3. Автоматизация UI через Хаб и локальный Web-сервер

В новой парадигме инстансов и Хаба ([`ADR_20260819-2`](../adr/ADR_20260819-2_core_agent-instances.md), [`ADR_20260820`](../adr/ADR_20260820_apps_project-hub.md)) Хаб является координатором всех участников и имеет право запускать процессы.

#### Сценарий 3.1: Авто-открытие в браузере (Zero-Config)
- При запуске `spla mcp` или наличии работающего `spla serve` поднят локальный веб-сервер на порту (например, 5050).
- При вызове `agent_spawn` формируется URL: `http://localhost:5050/#/chat/subagent-xyz`.
- При включённой настройке `ui.auto_open_subagents = true` (или аргументе CLI) процесс автоматически вызывает:
  `Process.Start(new ProcessStartInfo(url) { UseShellExecute = true })`.
- Браузер открывает вкладку с живым чатом подагента.
- Дополнительно URL возвращается в первом же `notifications/progress` и в итоговом `ToolResult`.

#### Сценарий 3.2: Управление через Хаб и Трей
- Подагент регистрируется в `RegistryHub` как участник с ролью `ParticipantRoles.Subagent` (или `Agent` с указанием родителя).
- В системном трее (`TrayIconService`) статус проекта переключается на `Working (Subagent: audit-ports)`.
- Клик по уведомлению или пункту меню в трее вызывает `Hub.LaunchProject(...)` / `RequestFocus`, поднимая окно Avalonia или веб-интерфейс, сфокусированный на этом чате.

#### Сценарий 3.3: Боковая панель (Drawer) в активном окне SPLA
- Если у пользователя уже открыто окно SPLA (Web или Avalonia), клиент слушает событие `chat.list.result` или специализированное `subagent.started`.
- В интерфейсе автоматически всплывает боковая панель (или вкладка внизу) с живым стримом подагента.

## 6. Сравнительный анализ и матрица решений

| Параметр | Уровень 1: MCP Progress | Уровень 2: First-Class Chat | Уровень 3: Auto-UI & Хаб |
| :--- | :--- | :--- | :--- |
| **Где виден прогресс** | В окне ChatGPT / внешнего клиента | В окне SPLA / веб-клиенте | В браузере / окне Avalonia / Трее |
| **Степень детализации** | Прогресс-бар и текущий статус | Полный чат, мысли, дерево вызовов | Полноэкранный интерактивный интерфейс |
| **Сложность внедрения** | Низкая (1–2 дня) | Средняя (2–3 дня) | Средняя/Высокая (3–5 дней) |
| **Зависимость от UI** | Нет (чистый headless/stdio) | Нет (хранилище + сокеты) | Требует браузер или Avalonia |
| **Соответствие стандартам** | 100% стандарт MCP | Внутренний протокол SPLA | Внутренняя архитектура Хаба SPLA |

## 7. Дорожная карта и рекомендуемый порядок шагов

Рекомендуется двигаться послойно от базы к интерфейсу:

1. **Этап 1 (База MCP):**
   - Реализовать в `McpStdioServer.cs` разбор `_meta.progressToken`.
   - Подключить генерацию `notifications/progress` из `ProgressScope` / `OnToolProgress`.
   - Добавить поддержку `capabilities.logging` и базовых сообщений `notifications/message`.

2. **Этап 2 (Персистентность и шина событий):**
   - Доработать `SpawnedAgentRunner.cs`: выделять полноценный `chatId`, регистрировать его в `ChatRegistry`.
   - Пробросить стриминг событий оркестратора подагента в `ConnectionHub`.

3. **Этап 3 (Интеграция с Хабом и UI):**
   - Зарегистрировать подагентов в `RegistryHub` как участников.
   - Добавить в настройки флаг авто-открытия интерфейса (`ui.auto_open_subagents`).
   - В Web UI (`web/src`) добавить компонент боковой панели для отображения активных подагентов.
