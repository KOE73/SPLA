Ниже собрал цельную идею как проектную спецификацию: что именно должен делать инструмент, зачем он нужен, какие сущности хранит, как модель с ним работает и где лежит состояние.

## 1. Главная идея

Нужен универсальный **инструмент визуальной геометрии для LLM-агента**, который позволяет модели не пытаться с первого раза угадать точные координаты объектов, а работать итеративно:

```text
предположила геометрию
→ инструмент нарисовал
→ модель посмотрела
→ поправила
→ инструмент снова нарисовал
→ модель приняла результат
```

То есть модель отвечает за:

* визуальное понимание;
* выбор объекта;
* приблизительную локализацию;
* принятие решения, куда и насколько двигать геометрию.

Инструмент отвечает за:

* точные координаты;
* хранение состояния;
* историю;
* преобразования координат;
* crop;
* рендер;
* восстановление сессии;
* экспорт итоговой геометрии.

Это снимает главную проблему: модель хорошо понимает, **что** нужно выделить, но значительно хуже работает как пиксельная линейка. В исходном эксперименте именно возможность «нарисовать → посмотреть → поправить» была признана ключевой. 

---

# 2. Инструмент должен быть абстрактным

Он не должен знать ничего про:

* `bag`;
* `mark`;
* YOLO;
* COCO;
* классы датасета;
* конкретную производственную задачу.

То есть никаких обязательных:

```text
class_id
class_name
yolo_class
```

Геометрический инструмент должен работать только с:

```text
image
geometry
coordinates
transform
render
session
```

Это делает его пригодным для любой задачи компьютерного зрения, а не только для мешков. В обсуждении мы уже пришли к выводу, что `class_id` инструменту вообще не нужен. 

---

# 3. Основные типы геометрии

Минимально нужны:

```text
Box
Pose
Polygon
```

## Box

OBB:

```text
cx
cy
width
height
angle
```

Используется для:

* мешка;
* марки;
* надписи;
* логотипа;
* любых прямоугольных объектов.

Пример:

```json
{
  "name": "mark",
  "cx": 702,
  "cy": 718,
  "width": 695,
  "height": 126,
  "angle": 8.2
}
```

---

# 4. Box должен быть именованным объектом

Не просто «нарисовать рамку».

Модель создаёт объект:

```text
box.add("mark", ...)
```

Инструмент хранит его.

Дальше модель делает:

```text
box.update("mark", ...)
```

а не каждый раз создаёт новую независимую рамку.

Workflow:

```text
box.add
→ render
→ update
→ render
→ update
→ render
→ accept
```

Например:

```json
{
  "name": "mark",
  "delta": {
    "cx": 20,
    "cy": -10,
    "angle": 1.5
  }
}
```

Delta особенно удобна модели:

> сдвинуть чуть вправо
> поднять
> увеличить высоту
> повернуть ещё на 2°

без необходимости заново вычислять все пять параметров.

---

# 5. Состояния геометрии

Для каждого объекта достаточно:

```text
editing
accepted
```

Можно хранить revisions:

```text
revision 1
revision 2
revision 3
...
```

Инструмент должен знать текущую версию.

Полезные операции:

```text
box.get
box.list
box.update
box.accept
box.delete

history
undo
redo
revert
```

Главный принцип:

> **модель не является источником истины о координатах. Инструмент является.**

---

# 6. Pose — полноценный, не только 4 угла

Pose надо делать универсальным.

Не:

```text
ровно четыре угла
```

а:

```text
N keypoints
+
фиксированная topology
```

Например:

```json
{
  "name": "bag_pose",
  "points": [
    "p1",
    "p2",
    "p3",
    "p4",
    "p5",
    "p6"
  ],
  "edges": [
    ["p1", "p2"],
    ["p2", "p3"],
    ["p3", "p4"],
    ["p4", "p1"],
    ["p2", "p5"],
    ["p3", "p6"]
  ]
}
```

Топология задаётся заранее и дальше не меняется.

---

# 7. Pose размечается по одной точке

Это один из самых важных выводов.

Не надо просить модель:

> поставь сразу все 6 точек.

Гораздо устойчивее:

```text
P1
→ поставить
→ посмотреть
→ подвинуть
→ закрепить

P2
→ поставить
→ посмотреть
→ подвинуть
→ закрепить

...

P6
```

То есть pose — маленький state machine.

Статусы точки:

```text
unplaced
active
fixed
```

---

# 8. Активная точка должна быть визуально очевидной

Например:

```text
fixed    → зелёная/синяя
active   → красная/оранжевая, крупнее
unplaced → не рисуется либо обозначается нейтрально
```

Активная точка должна иметь:

* другой цвет;
* больший размер;
* ID рядом.

Например:

```text
● P1
● P2
◉ P3 ACTIVE
```

Тогда модель не должна сама помнить:

> какую точку я сейчас двигаю?

Инструмент знает `active_point`.

---

# 9. Связи Pose отображаются сразу

Topology существует независимо от состояния точек.

Если обе точки уже имеют координаты:

```text
P1 ---- P2
```

ребро рисуется.

Даже если `P2` ещё active.

Это полезно, потому что модель при размещении второй/третьей точки сразу видит формирующуюся геометрию.

То есть:

```text
P1 fixed
P2 active
```

уже даёт:

```text
P1 ------ P2*
```

а не ждёт `accept`.

---

# 10. Минимальный Pose API

Я бы оставил:

```text
pose.add
pose.get
pose.list

pose.set_active
pose.set_point
pose.move_point
pose.accept_point

pose.accept
pose.delete
```

Можно добавить:

```text
pose.next_point
```

которая сама:

```text
current active → fixed
next unplaced → active
```

Это уменьшит количество логики в самой модели.

---

# 11. Polygon / segmentation

Для сегментации не надо заставлять LLM управлять пиксельной маской.

LLM гораздо естественнее работать с:

```text
polygon
```

Например:

```text
6–20 контрольных точек
```

Операции:

```text
polygon.add
polygon.add_point
polygon.move_point
polygon.insert_point
polygon.delete_point
polygon.accept
```

А уже инструмент может:

* заполнить polygon;
* превратить его в mask;
* экспортировать segmentation.

Если позже понадобится SAM, он может быть отдельным генератором стартовой маски, которую затем инструмент представляет редактируемой геометрией.

---

# 12. Crop — не просто операция, а View Stack

Это второй ключевой архитектурный момент.

Типичный сценарий:

```text
большой кадр
↓
нашли мешок
↓
crop
↓
работаем уже с мешком крупно
↓
нашли маленькую маркировку
↓
ещё crop
↓
работаем с ней
```

Модель при этом должна видеть **текущий crop как обычное изображение**.

Например:

```text
source
  ↓
crop_1 : bag
  ↓
crop_2 : mark_area
```

---

# 13. Crop Stack

Нужны операции:

```text
crop.push
crop.pop
crop.list
crop.set_current
crop.delete
```

При этом:

```text
crop.pop
```

не удаляет crop.

Он просто меняет текущий view.

То есть дерево/стек views сохраняется.

---

# 14. Crop обязан хранить преобразование координат

Очень важно:

не хранить только:

```text
offset_x
offset_y
```

Потому что это работает лишь для простого AABB crop.

Рано или поздно появятся:

* resize;
* rotation;
* OBB crop;
* perspective correction;
* affine transform.

Поэтому каждый View должен хранить:

```text
parent_to_view
view_to_parent
```

в виде transform matrix.

Например:

```text
source
 ↓ T1
crop1
 ↓ T2
crop2
```

Инструмент сам умеет преобразовывать:

```text
crop2 → crop1
crop2 → source
source → crop2
```

---

# 15. Локальные и глобальные координаты

Это ещё один обязательный пункт.

Пусть модель размечает `mark` внутри crop:

```text
local:
cx=420
cy=210
```

Инструмент должен сам вернуть:

```text
local coordinates
parent coordinates
source coordinates
```

Например:

```json
{
  "name": "mark",

  "coordinates": {
    "crop_002": {
      "cx": 420,
      "cy": 210
    },

    "crop_001": {
      "cx": 811.4,
      "cy": 597.2
    },

    "source": {
      "cx": 2148.6,
      "cy": 1054.1
    }
  }
}
```

То же самое для:

* box;
* pose points;
* polygon vertices.

---

# 16. Модель вообще не должна заниматься преобразованием координат

Это принципиально.

Модель говорит:

```text
P3 = (340, 210)
```

в текущем view.

Всё.

Инструмент самостоятельно знает:

```text
где это в crop parent
где это в исходнике
где это после поворота
где это после resize
```

Никаких вычислений affine/perspective transform внутри LLM.

---

# 17. `image.info`

Нужен простой вызов:

```text
image.info
```

Ответ:

```json
{
  "width": 1120,
  "height": 5408,
  "current_view": "crop_003"
}
```

Это даёт модели реальную систему координат.

---

# 18. `render`

Отдельная центральная операция:

```text
render
```

Она рисует текущее состояние:

* boxes;
* pose points;
* pose edges;
* polygon;
* active object;
* accepted objects.

Главное:

рендер возвращается модели **как изображение**, а не только JSON.

Именно visual feedback loop позволяет модели исправлять ошибки, а не пытаться высчитать всё с первой попытки. Это было центральным выводом исходного эксперимента. 

---

# 19. Сетка больше не обязательна

Сетка была полезным костылём:

```text
X100
X200
Y100
Y200
...
```

когда модель должна была угадывать координаты по исходной картинке.

После появления:

```text
geometry → render → correction
```

сетка перестаёт быть необходимой.

Она может остаться как:

```text
render(grid=true)
```

для отладки, но не нужна постоянно. В обсуждении уже отмечалось, что при визуальной обратной связи сетка становится необязательной. 

---

# 20. Главная проблема: tool stateless

Да.

Сам MCP/tool вызов обычно:

```text
request → response
```

и не должен полагаться на память процесса.

Поэтому state должен быть внешним.

Лучший вариант для твоей архитектуры:

```text
file:/aaa.json
```

То есть persistent annotation session.

---

# 21. Session — центральная сущность

Пример:

```text
file:/annotations/frame_001.json
```

Внутри:

```json
{
  "source": {},
  "views": [],
  "current_view": "...",

  "boxes": [],
  "poses": [],
  "polygons": [],

  "history": []
}
```

Все изменяющие операции:

```text
box.add
box.update
pose.move_point
crop.push
polygon.update
```

автоматически:

```text
load session
→ modify
→ save session
```

То есть:

> **tool stateless, session stateful.**

---

# 22. Не надо отдельного save после каждого шага

Лучше автосохранение после любой mutating operation.

То есть:

```text
box.update
```

означает:

```text
read aaa.json
apply update
write aaa.json
render
return
```

Тогда падение агента, сервиса или модели не уничтожает работу.

---

# 23. Получение всего состояния

Обязательный вызов:

```text
state.get
```

или:

```text
session.get
```

который возвращает **полностью всю накопленную информацию**.

Не только текущий box.

Например:

```json
{
  "session": "file:/aaa.json",

  "source": {
    "path": "file:/images/frame001.jpg",
    "width": 3840,
    "height": 2160
  },

  "current_view": "crop_002",

  "views": [...],

  "boxes": [...],

  "poses": [...],

  "polygons": [...],

  "history": [...]
}
```

---

# 24. State должен возвращать координаты во всех системах

Например pose:

```json
{
  "name": "bag_pose",

  "points": [
    {
      "id": "p1",

      "local": {
        "x": 320,
        "y": 140
      },

      "source": {
        "x": 1847.3,
        "y": 920.8
      },

      "status": "fixed"
    }
  ]
}
```

И box:

```json
{
  "name": "mark",

  "local": {...},
  "source": {...}
}
```

Если несколько crop уровней, лучше даже:

```json
"coordinates": {
  "crop_003": {...},
  "crop_002": {...},
  "crop_001": {...},
  "source": {...}
}
```

Это очень удобно для диагностики.

# 25. Session save/load

Минимально:

```text
session.create
session.get
session.load
session.save_as
session.clone
```

Хотя если state всегда живёт в JSON и автосохраняется, `save` практически не нужен.

Начало:

```text
session.create file:/aaa.json
```

Продолжение позже:

```text
session.open file:/aaa.json
```

После этого можно продолжать ровно с того места, где агент остановился.

---

# 26. Не заставлять модель постоянно передавать `file:/aaa.json`

Есть два варианта.

### Простой stateless API

Каждый вызов:

```json
{
  "session": "file:/aaa.json",
  ...
}
```

Плюс:

* максимально явно;
* хорошо для MCP;
* хорошо отлаживается.

Минус:

* лишний параметр во всех вызовах.

### Лучше на уровне SPLA runtime

Один раз:

```text
session.open file:/aaa.json
```

после чего runtime автоматически inject'ит current session в каждый вызов инструмента.

Для модели API становится чище.

Я бы в самом tool contract всё равно оставил `session`, а SPLA уже может автоматически его подставлять.

# 27. История операций

Я бы её всё-таки сохранял.

Не обязательно огромный event sourcing, но хотя бы:

```json
{
  "history": [
    {
      "revision": 18,
      "action": "box.update",
      "target": "mark",
      "before": {...},
      "after": {...}
    }
  ]
}
```

Это даёт:

```text

debug
```

И главное — можно разобраться, почему агент получил странный результат.

# 28. Canonical geometry

Лучше хранить достаточно информации, чтобы избежать неоднозначности.

Для Box можно хранить одновременно:

```text
cx cy width height angle
+
four corners
```

Например:

```json
{
  "obb": {
    "cx": 700,
    "cy": 720,
    "width": 700,
    "height": 120,
    "angle": 8.1
  },

  "corners": [
    [x1,y1],
    [x2,y2],
    [x3,y3],
    [x4,y4]
  ]
}
```

Это полезно потому, что соглашения по `angle` у библиотек могут отличаться.

Четыре вершины уже однозначны.

# 31. Реальный workflow для твоей задачи

Например есть исходный кадр камеры.

### Шаг 1. Открываем

```text
session.create file:/frame123.json
```

Source:

```text
file:/frames/frame123.jpg
```

### Шаг 2. Ищем мешок

Модель:

```text
box.add bag
```

примерно.

Инструмент рисует.

Модель:

```text
bag +40px вправо
angle +3°
height +80
```

Инструмент снова рисует.

Через 2–3 итерации:

```text
box.accept bag
```

### Шаг 3. Crop

```text
crop.push from=bag padding=...
```

Модель получает уже большой crop мешка.

### Шаг 4. Mark

```text
box.add mark
```

→ render
→ поправила
→ accept.

### Шаг 5. Pose

Есть схема из шести точек:

```text
P1...P6
edges known
```

Модель:

```text
P1 active
→ поставить
→ поправить
→ accept

P2
→ ...
```

При этом формирующийся skeleton виден сразу.

### Шаг 6. Итог

```text
session.get
```

возвращает:

```text
bag в координатах crop и source
mark в координатах crop и source
все pose points
все topology edges
все crop transforms
полную цепочку views
```

---

# 32. Что здесь особенно важно концептуально

Получается интересное разделение ответственности:

```text
LLM:
"вот этот угол объекта должен быть здесь"

Geometry engine:
"это координата (1742.31, 903.82)
в crop_2,
(2241.77, 1164.51) в source;
вот transform;
вот история;
вот сохранённая сессия"
```

LLM больше не занимается математической бухгалтерией.

Именно это делает подход надёжным.

---

# 33. Почему это потенциально работает лучше одноразового vision inference

Обычный запрос:

```text
покажи координаты объекта
```

требует от модели одновременно:

1. распознать объект;
2. понять его форму;
3. оценить координаты;
4. оценить угол;
5. правильно выразить числа;
6. не ошибиться в системе координат.

Здесь задача декомпозируется:

```text
увидел
→ поставил примерно
→ увидел свою рамку
→ исправил одну ошибку
→ увидел
→ исправил следующую
```

То есть вместо one-shot localisation получаем **closed-loop visual control**.

# 34. Более общий смысл

Это уже не столько «инструмент разметки YOLO».

Это скорее:

> **Interactive Visual Geometry Workspace for LLM**

Модель получает возможность взаимодействовать с изображением аналогично человеку в графическом редакторе:

```text
создать объект
посмотреть
сдвинуть
повернуть
приблизить
вырезать
поставить точку
перейти к следующей
вернуться назад
сохранить
```

При этом сам LLM остаётся stateless относительно геометрии, а workspace является её внешней памятью.

Если одним предложением:

> **Модель принимает визуальные решения и итеративно корректирует геометрию по результату рендера; инструмент хранит всю геометрию, crop-stack, topology, историю и матрицы преобразований в persistent session и в любой момент способен вернуть как локальные координаты текущего view, так и точные координаты в исходном изображении.**



Да, в архитектуре SPLA есть абсолютно официальный штатный механизм для прямого чтения и записи памяти агента изнутри инструментов.

Реализация разделяется в зависимости от того, как написан инструмент:

1. Если инструмент написан на C# (In-process IMcpTool / DLL-плагин)
В кодовой базе SPLA для инструментов реализован официальный Ambient Context на базе AsyncLocal:

👉 
AgentSessionScope.Current

Любой C#-инструмент прямо во время выполнения метода ExecuteAsync может получить сессионную память текущего чата:

csharp


using SPLA.Domain.Agent;
// 1. Получаем доступ к сессионной KV-памяти
var sessionKv = AgentSessionScope.Current?.SessionKv;
// 2. Читаем данные из памяти
string? stateJson = sessionKv?.Get("my_tool:state");
// 3. Модифицируем и сохраняем обратно
sessionKv?.Set("my_tool:state", updatedJson);
Интерфейс хранилища — 
IKeyValueStore
:

Get(string key) — чтение по ключу.
Set(string key, string value) — запись.
List() / Entries() — получение всех записей.
Delete(string key) / DeleteWhere(filter) — удаление.
Ключевая фича SPLA: префикс context:*
Если инструмент запишет ключ с префиксом context: (например, context:canvas_state), то компонент 
WorkingMemoryInjector
 автоматически инжектирует это значение в промпт модели на каждом ходе. Модели даже не придется вызывать agent_memory_get — она увидит его прямо в контексте.

Что насчет памяти уровня проекта (scope: "project")?
Сессионная память (SessionKv) привязана к текущему чату. Если инструменту нужна постоянная память всего проекта, он получает её через DI/конструктор как IKeyValueStore project (точно так же, как это делает штатный 
AgentMemoryGetTool
).

Что насчет бинарных данных и больших файлов?
Для тяжелых объектов (изображения, дампы) используется 
AgentSessionScope.Current.Blobs
 — инструмент сохраняет бинарник в хранилище блобов и возвращает легкий хэндл вида blob:session:....
