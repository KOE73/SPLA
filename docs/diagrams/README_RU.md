# SPLA Semantic Architecture Diagram (MVP)

Интерактивный MVP визуализатора архитектурных диаграмм без использования auto-layout, на основе модели **Semantic Diagram JSON → SVG/HTML Canvas + Draw.io XML Export**.

## 📁 Файлы
1. **[`app/`](app/index.html)** — Собранное приложение визуализатора/редактора, отдаётся `server.go` (`run.cmd`) по адресу `/app/`. Собирается из исходников в [`tools/spla-diagram`](../../tools/spla-diagram); после правки исходников пересобрать командой `npm run build:app` там же.
2. **[`model.json`](model.json)** (и остальные `model-*.json`) — Семантические JSON-модели архитектуры (компоненты, зоны, метаданные, координаты). `catalog.json` определяет, какие из них показаны в боковой панели приложения.
3. **[`README.md`](README.md)** — Английская версия документации.

## 🚀 Что реализовано в MVP:

### 1. Жесткий пространственный контроль (Никакого Auto-layout)
- Каждый компонент и зона имеют фиксированные координаты `x, y, width, height`.
- Изменение текста или метаданных **не ломает** сетку и расположение блоков.

### 2. Семантические прямоугольники (Зоны / Контейнеры)
- **Client Layer**, **Core & Runtime Subsystem**, **Tool Dispatch & MCP Host**, **Storage & Persistence**.
- Зоны — это полноценные семантические объекты с атрибутами `type`, `semanticId`, `tags`, а не просто фоновая графика.

### 3. Поддержка множества схем и динамические кнопки видов
- **Переключатель схем**: Возможность переключаться между разными файлами схем (например, *SPLA System Architecture*, *LLM Pipeline & Context Composition*, *Plugin & Tool Execution*).
- **Кнопки видов формируются из JSON**: Панель кнопок видов (Overview, Runtime Flow, Security и др.) генерируется динамически на основе массива `"views"` внутри загруженного JSON.
- **Загрузка любого JSON**: Возможность открыть локальный JSON файл через кнопку или Drag & Drop.

### 4. Инспектор объекта (Правая панель)
- Клик по любой ноде или зоне открывает детальный инспектор:
  - Название и тип сущности
  - Semantic ID (`zone.core.runtime`, etc.)
  - Ссылки на реальные файлы в кодовой базе (`codeRef`), например `src/SPLA.Core/Runtime/ChatTurnPump.cs`
  - Список зон ответственности (Responsibilities)
  - Теги

### 5. Интерактивная навигация
- Плавный Pan & Zoom (колесико мыши, перетаскивание полотна, кнопки зума и центрирования).

### 6. Двусторонний экспорт и интероперабельность
- **Экспорт в `.drawio`**: формирует валидный XML файл Diagrams.net с сохранением всех геометрий и пользовательских метаданных (`<Object as="data">`). Файл можно сразу открыть в draw.io / Visio и двигать руками.
- **Встроенный редактор модели (JSON)**: позволяет на лету просматривать и редактировать JSON-контракт диаграммы.

## 🧭 Варианты компоновки модели

Одна и та же кодовая база может быть разложена на холсте по-разному. Компоновка — это не оформление, а **выбранная точка зрения**: она решает, какой вопрос схема отвечает. Ниже — каталог вариантов. У каждой модели в `metadata` стоит поле `layout` с именем варианта.

### Вариант A — «Полный смысловой атлас» (`layout: "semantic-atlas"`)

**Отвечает на вопрос:** «как устроена система по смыслу — и всё ли в ней разложено по местам?»

Правила варианта:

1. **Группировка только по смыслу.** Контейнер — это архитектурная роль (LLM Pipeline, Tool Pipeline, Security & Capability, Agent Memory…), а не namespace, не сборка и не папка на диске. Namespace остаётся в `metadata.codeRef` как справка, но не управляет расположением.
2. **Полнота обязательна.** На холсте присутствуют **все** сущности кодовой базы, без исключений и без «прочего». Именно полнота даёт второй смысл схемы: видно, всё ли красиво разложено, или что-то не находит себе роли.
3. **Ровно одно место у сущности.** Один класс — один узел — один контейнер. Появление одного класса в двух местах запрещено: это ломает саму идею схемы и почти всегда означает, что класс делает две несвязанные вещи и его надо разделить в коде.
4. **Вложенные контейнеры.** Крупная роль (`type: "boundary"`) содержит подроли (`type: "component"`), подроль содержит узлы. Глубина ограничена двумя уровнями: дальше схема перестаёт читаться.
5. **Плотная сетка внутри контейнера.** Внутри подроли узлы разложены сеткой по алфавиту — там порядок не несёт смысла, смысл несёт сам факт принадлежности контейнеру.
6. **Контейнеры не пересекаются.** Границы боксов не накладываются друг на друга; узел целиком лежит внутри своего контейнера.

**Диагностическая ценность.** Схема в этом варианте читается как аудит: раздувшийся контейнер = перегруженная подсистема; сущность, которую тяжело отнести к роли = кандидат на переосмысление; класс, тянущийся в две роли = кандидат на разделение.

**Пример:** [`model-core-full.json`](model-core-full.json) — 246 сущностей `src/core`, 13 смысловых границ, 17 вложенных подролей.

### Вариант B — «Маршрут сообщения» (`layout: "message-flow"`)

**Отвечает на вопрос:** «что происходит с одним сообщением от пользователя до ответа?»

Полнота **не** требуется — наоборот, вредна. На холсте только участники маршрута, выстроенные слева направо по ходу движения; всё остальное скрыто. Стрелки нумерованы по шагам. Один и тот же участник может встречаться на пути туда и обратно — здесь это допустимо, потому что узел означает *шаг маршрута*, а не *класс*.

**Пример:** [`model-llm-pipeline.json`](model-llm-pipeline.json).

### Вариант C — «Обзор подсистем» (`layout: "subsystem-overview"`)

**Отвечает на вопрос:** «из каких крупных частей состоит система и кто с кем разговаривает?»

Узел — это подсистема целиком, а не класс. Десятки классов схлопнуты в один бокс. Нужен для разговора с человеком, который видит систему впервые.

**Пример:** [`model.json`](model.json), [`model-core.json`](model-core.json).

## ⚙️ Как атлас поддерживается в актуальном состоянии

Атлас не рисуется руками — он **генерируется** инструментом
[`tools/spla-arch`](../../tools/spla-arch/AGENTS.md) из трёх частей:

```text
  список сущностей         правила точки зрения          json-схема
  (извлекается из кода)  +  (mapping/<вариант>/*.map.json)  +  (model-*.json)
                                    │
                                    ▼
                        детерминированная проверка
                                    │
                 ┌──────────────────┼──────────────────┐
                 ▼                  ▼                  ▼
             сломано             лишнее           не хватает
                 └──────────────────┴──────────────────┘
                                    │
                                    ▼
                    агент правит ПРАВИЛА или СХЕМУ
```

Ключевое разделение: **правила — рукописные и долговечные, координаты —
производные и одноразовые.** Файл правил по сути кэш уже принятых решений о
смысле, чтобы не изобретать классификацию заново на каждом прогоне. Наборы
правил свои на каждую точку зрения: у `semantic-atlas` один набор, у
`message-flow` другой — общего не бывает, потому что группируют они по-разному.

Автоматика разбирает новое сама, пока может:

1. правило по имени → 2. по регулярке → 3. по префиксу пути (побеждает самый
длинный) → 4. **сосед по файлу** (один файл — одна единица смысла) → 5. если
никто не забрал — в оранжевую зону `НЕ РАЗМЕЩЕНО` на холсте.

Оранжевая зона и есть очередь работы для агента. Плюс lock-файл
`<id>.known.json` хранит снимок прошлого прогона, поэтому инструмент отличает
«новое, никто не забрал» от «новое, правило забрало — проверь, туда ли».

```bash
go run . build --mapping ../../docs/diagrams/mapping/semantic-atlas/core.map.json --repo ../..
```

```bash
go run . verify --dir ../../docs/diagrams --repo ../..
```

`verify` ничего не пишет — он только отвечает, сходятся ли код, правила и
схема. Полноту он требует **только** от `semantic-atlas`: у `message-flow`
неполнота — замысел, а не дефект.

### Антивариант — «Сетка по namespace» ⛔

Раскладка, где контейнер = namespace, а узлы внутри разложены по алфавиту. Выглядит как полная карта, но **не отвечает ни на один архитектурный вопрос**: она пересказывает дерево каталогов, которое и так видно в IDE. Отдельно опасна попытка совместить её с осмысленной раскладкой в одном файле — тогда часть классов лежит в namespace-сетке, часть выдернута в смысловые зоны, и читатель не может понять, полная перед ним карта или срез.

Если нужен и смысл, и структура по коду — это **два разных файла**, а не два слоя в одном.
