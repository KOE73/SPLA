# Проекты архитектурной модели SPLA

Здесь лежат **проекты**: наборы сущностей, связей, типов связей, контейнеров,
текстов и видов. Контракт — **v3**, принят
[`ADR_20260831_diagrams_text-provenance-and-view-axes`](../../adr/ADR_20260831_diagrams_text-provenance-and-view-axes.md).

Этот файл — про **работу**: кто во что пишет, в каком порядке, где ловушки и
чего пока нет. Нормативные формы полей — в
[`CONTRACT.md`](../../../tools/spla-diagram/docs/CONTRACT.md); все «почему» — в ADR.
Примеры здесь приведены для удобства; при расхождении прав контракт. Что писать
**внутри** значений `description` и `doc` — в [`TEXT-GUIDE.md`](../TEXT-GUIDE.md).

---

## 1. Раскладка

```
docs/diagrams/projects/<project-id>/
  project.json          манифест                [человек]
  entities.json         сущности                [утилита, когда появится]
  relations.json        связи                   [утилита: origin=code; редактор: origin=authored]
  relation-types.json   словарь типов связей    [человек]
  containers.json       контейнеры              [человек]
  text.<lang>.json      тексты с происхождением [редактор / агент]
  views/
    <view-id>.view.json вид                     [пишет ТОЛЬКО редактор]
```

Базового языка **нет**. `text.ru.json` и `text.en.json` равноправны: направление
перевода записано на каждом значении отдельно, а не объявлено на язык целиком.

Стили общие на проект и лежат выше: [`docs/diagrams/styles.json`](../styles.json).

## 2. Кто во что пишет

| Файл | Утилита | Редактор | Человек в текстовом виде |
|---|---|---|---|
| `project.json` | читает | читает | да |
| `entities.json` | **пишет** | дописывает новые блоки, `origin: authored` | переименования |
| `relations.json` | пишет `origin: code` | *не пишет, см. §5* | **да, только так** |
| `relation-types.json` | не касается | читает | **да, только так** |
| `containers.json` | читает | *не читает, см. §5* | да |
| `text.*.json` | не касается | пишет | да |
| `views/*.view.json` | **никогда** | **пишет** | по своему усмотрению |

Одна граница: утилита не пишет в `views/` ни при каких условиях. Ручная раскладка
живёт только там и машиной не затирается по построению.

Сохранение из редактора трогает **четыре** файла: вид, `entities.json` (если на
холсте появился блок, которого не было в реестре), и каталоги текстов — где
изменённые человеком значения переставляются в `authored`, а нетронутые
сохраняют своё происхождение, так что пустое сохранение даёт пустой diff.

## 3. Формы файлов

### `project.json`

```json
{
  "id": "core",
  "title": "Core Layer (src/core)",
  "subtitle": "Domain, MCP, Security, Host",
  "contractVersion": 3,
  "defaultView": "v_semantic_atlas",
  "defaultAxis": "axis_subsystem",
  "languages": ["ru"],
  "views": ["v_semantic_atlas"],
  "sources": {
    "include": ["src/core", "src/agent/SPLA.Agent/Guards"]
  },
  "styles": "../../styles.json"
}
```

- `baseLanguage` **отменён** — поля больше нет, писать его не нужно.
- `languages` — какие каталоги текстов грузить. Первый язык списка редактор берёт
  основным для показа; привилегии в данных это не даёт.
- `defaultAxis` — ось, которую принять для вида, не объявившего свою. Существует
  ради видов, порождаемых утилитой: генератору незачем знать про оси.
- `views` — перечень видов проекта. Сегодня редактор его **не читает**: вид
  открывается записью в [`catalog.json`](../catalog.json), одна запись на вид.
  Проекту с четырьмя осями нужны четыре записи каталога.

Пути — от корня репозитория. Решение (`SPLA.slnx`) здесь **не указывается**
намеренно: утилита перечисляет `*.csproj` под этими путями и открывает их
поштучно, не полагаясь на поддержку формата `.slnx` в `MSBuildWorkspace`.

### `entities.json`

```json
{
  "entities": [
    {
      "id": "e_repetitionguardmiddleware",
      "name": "RepetitionGuardMiddleware",
      "kind": "class",
      "origin": "code",
      "status": "present",
      "namespace": "SPLA.Agent.Guards",
      "codeRef": "src/agent/SPLA.Agent/Guards/RepetitionGuardMiddleware.cs",
      "members": [
        { "name": "InvokeAsync", "memberKind": "method",
          "signature": "Task<LlmTurnResult> InvokeAsync(LlmTurnContext, LlmMiddlewareDelegate, CancellationToken)" }
      ]
    },
    {
      "id": "e_lmstudio_api",
      "name": "LM Studio HTTP API",
      "kind": "external",
      "origin": "authored",
      "status": "present"
    }
  ]
}
```

- `id` выдаётся **один раз и не меняется никогда**, включая переименование типа.
- `name` — каноническое имя типа. **Не переводится**, в `text.*.json` его нет.
- `kind` — открытая строка. Из кода приходят `class`, `interface`, `record`,
  `struct`, `enum`; рукописные сущности берут что угодно (`external`, `app`,
  `assembly`, `database`). Проверки «такого вида не бывает» нет.
- `origin`: `code` | `authored`. **v2-шное `manual` переименовано в `authored`** —
  во всех файлах, не только здесь.
- `status`: `present` | `missing` | `planned`. Записи не удаляются: ушедшая
  сущность сохраняет id для всего, что на него ссылается.
- `codeRef` — путь от корня репозитория. Врать здесь дороже, чем не писать
  вовсе: по нему сверяются и человек, и будущая утилита.

**Переименование класса** делается правкой `name` при неизменном `id`. Ни один
другой файл при этом не меняется.

### `relations.json`

```json
{
  "contractVersion": 3,
  "relations": [
    { "id": "r_repetitionguardmiddleware_illmmiddleware_implements",
      "from": "e_repetitionguardmiddleware", "to": "e_illmmiddleware",
      "type": "implements", "origin": "code", "status": "present" },

    { "id": "r_gateway_repguard",
      "from": "e_illmgateway", "to": "e_repetitionguardmiddleware",
      "type": "data-flow", "origin": "authored", "status": "present",
      "evidence": [
        { "codeRef": "src/core/SPLA.Domain/Llm/LlmGateway.cs", "symbol": "SendAsync" }
      ] }
  ]
}
```

- **`label` отсюда убран.** Весь текст связи живёт в `text.*.json` под её же id,
  фолбэка на структуру нет. Связь без текста рисуется без подписи — это видно, и
  так и задумано.
- `type` — ссылка в `relation-types.json`. Формально это открытая строка, но тип,
  которого нет в словаре, не имеет ни имени, ни описания и потому бесполезен.
- `id` выводится из **id сущностей**, не из имён:
  `r_<from>_<to>_<type>` без префиксов `e_`. Рукописная связь может иметь свой
  короткий id.
- `evidence` проверяемо: если файл или символ исчезли, сверка сообщает. Так
  логические связи гниют громко, а не молча.

### `relation-types.json`

Новый в v3. Чисто авторский словарь — утилита в него не пишет.

```json
{
  "contractVersion": 3,
  "relationTypes": [
    { "id": "implements", "origin": "code" },
    { "id": "composes",   "origin": "code" },
    { "id": "call",       "origin": "authored" },
    { "id": "data-flow",  "origin": "authored" },
    { "id": "security",   "origin": "authored", "styleId": "edge.security" }
  ]
}
```

Имя и описание типа — в текстовых каталогах по ключу **`rt_<id>`**. Описание типа
— не украшение: пока не записано, чем `call` отличается от `data-flow`, разные
авторы будут ставить их по вкусу, и множество типов перестанет что-либо значить.

Почему отдельный файл, а не запись в `entities.json`: тот каталог частично
порождается из кода, и десяток авторских строк утонул бы в шуме регенерации.

### `containers.json`

```json
{
  "contractVersion": 3,
  "containers": [
    { "id": "c_llm", "parent": null, "theme": "green" },
    { "id": "c_llm_middleware", "parent": "c_llm",
      "match": {
        "name": ["ILlmMiddleware", "LlmPipelineBlueprint", "RepetitionGuardMiddleware"],
        "path": ["src/core/SPLA.Domain/Llm/Middleware/"]
      } }
  ],
  "overrides": {
    "e_repetitionguardmiddleware": "c_llm_middleware"
  }
}
```

- Порядок разрешения: `match.name` → `match.nameRegex` → `match.path`
  (длиннейший префикс) → сосед по файлу.
- `overrides` — явное назначение человеком. **Всегда бьёт правило.**
- Одна сущность может состоять в нескольких контейнерах. Это не ошибка: на
  разных осях она законно попадает в разные рамки.
- Имя контейнера — в `text.*.json` под ключом `c_*`.

**Ось контейнера.** Контракт объявляет ось на **виде**, а не на контейнере, и
поля `axis` у контейнера в контракте нет. Проект `spla_system` тем не менее
проставляет его как подсказку человеку — по одному набору контейнеров на ось.
Это соглашение проекта, а не формат; ничем не читается и ни на что не влияет.

### `text.<lang>.json`

Переписан в v3 целиком. **Каждое переводимое поле — объект, а не строка.**

```json
{
  "contractVersion": 3,
  "language": "ru",
  "entries": {
    "e_repetitionguardmiddleware": {
      "description": { "v": "Стадия Output: замечает вырождение генерации.",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" },
      "doc":         { "v": "Против цикла работают две защиты, и обе слепы поодиночке…",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" }
    },
    "c_llm_middleware": {
      "name": { "v": "Цепочка middleware", "at": "…", "origin": "authored" }
    },
    "rt_security": {
      "name":        { "v": "допуск", "at": "…", "origin": "authored" },
      "description": { "v": "Единственный род связи, который вправе отказать.",
                       "at": "…", "origin": "authored" }
    },
    "r_gateway_repguard": { "name": { "v": "LlmTurnContext ↓", "at": "…", "origin": "authored" } },
    "v_semantic_atlas":   { "name": { "v": "Семантический атлас", "at": "…", "origin": "authored" } }
  }
}
```

Переведённое значение вместо `origin: "authored"` несёт:

```json
{ "v": "…", "at": "…", "origin": "translated", "from": "ru", "fromHash": "a3f19c" }
```

#### Ключи — всё именуемое, не только сущности

| Префикс | Объект |
|---|---|
| `e_` | сущность (только `description` / `doc` — имя не переводится) |
| `c_` | контейнер |
| `rt_` | тип связи |
| `r_` | связь |
| `v_` | вид |

#### Поля

Разрешены четыре: `name`, `title`, `description`, `doc`.

- `description` — что это, одна-две строки. Тултип, читается всегда.
- `doc` — длинный текст: **причины, инварианты, что сломается при нарушении**,
  ссылка на ADR. Читается по требованию. Именно ради этого поля вся конструкция
  и затевалась: схема без причин не сокращает разговор словами.

#### Правила, которые легко нарушить по привычке

1. **Фолбэка нет.** Отсутствие ключа в языке — недостача, а не норма. Пусть дыра
   выглядит как дыра.
2. **`at` — ISO-8601 UTC с `Z`.** Локальные даты и даты без времени запрещены.
3. **Хэш решает, дата информирует.** Порядок по времени в проверках не
   участвует: часы врут, коммиты переставляются.
4. **Гранулярность — поле.** Правка `name` не протухляет `doc`.
5. **Правка человеком делает значение `authored`** и снимает `from`/`fromHash`.
   Редактор так и поступает; вручную — не забыть.
6. `fromHash` — хэш **нормализованного** текста источника (схлопнутые пробелы,
   нормализованные переносы), иначе переформатирование даёт ложные срабатывания.

#### Три состояния

| Состояние | Условие | Действие |
|---|---|---|
| свежий | `fromHash` == хэш текущего значения `from` | ничего |
| протух | `fromHash` != хэш текущего значения `from` | перевести заново |
| разошлись | оба `authored`, ни одно не ссылается на другое | конфликт, решает человек |

**Считать эти состояния сегодня нечем** — см. §5.

### `views/<view-id>.view.json`

```json
{
  "id": "v_semantic_atlas",
  "project": "core",
  "axis": "axis_subsystem",

  "relations": { "default": "visible", "except": ["r_gateway_repguard"] },

  "zones": [
    { "id": "z_llm", "container": "c_llm", "parent": null,
      "x": -1950, "y": 1380, "width": 2852, "height": 1290, "styleId": "domain.llm" },
    { "id": "z_llm_middleware", "container": "c_llm_middleware", "parent": "z_llm",
      "x": -1120, "y": 1480, "width": 900, "height": 1040, "styleId": "zone.green" }
  ],

  "nodes": [
    { "entity": "e_repetitionguardmiddleware", "zone": "z_llm_middleware",
      "x": -750, "y": 1650, "width": 220, "height": 90 }
  ]
}
```

#### `axis` — главное новшество v3

**Обязательное поле.** Оно объявляет, что классифицирует вложенность блока в
рамку на этом виде: `axis_layer`, `axis_subsystem`, `axis_security_zone`,
`axis_process`, `axis_turn`… — множество открытое, имена задаёт проект.

Без него узел внутри прямоугольника нечитаем: «живёт в этой сборке», «работает в
этом процессе» и «подвинут, чтобы стрелки не пересекались» выглядят одинаково.

- Вид без `axis` наследует `project.defaultAxis`.
- Нет ни того, ни другого — схема **всё равно открывается**, но редактор
  показывает баннер, а вложенность в ней не утверждает ничего и не проверяется.
  Отказ открывать был бы хуже: устаревший файл делал бы проект недоступным.
- Два вида на **разных** осях вправе класть один узел в разные контейнеры. Два
  вида на **одной** оси — нет, это противоречие.

#### Правила размещения

1. **Вид — выборка.** Сущность попадает сюда только вытаскиванием из реестра.
   Ничего не появляется само; неразмещённое живёт в реестре. Зоны `НЕ РАЗМЕЩЕНО`
   не существует.
2. **Размещение свободно.** `zone: null` — элемент вне любой рамки. Законно, даже
   если по реестру он куда-то принадлежит.
3. **Принадлежность записана явно**, из геометрии не выводится.
4. **Вложенность зон** — поле `parent`. Может отличаться от иерархии в
   `containers.json`: вид волен уплощать и перегруппировывать.
5. **Зона может не ссылаться на контейнер** (`container: null`) и иметь
   собственное имя в текстах — чтобы декоративная рамка не засоряла реестр.

#### Ловушки, известные по коду загрузчика

- **Имя зоны ищется по её собственному id, а при промахе — по `c_` + хвост
  `z_`.** То есть зона `z_llm_middleware` подхватит текст контейнера
  `c_llm_middleware`. Соглашение об именах здесь несущее, а не косметическое.
- **`edges: []` означает «рёбер нет».** Чтобы вид показывал все связи проекта,
  ключ `edges` надо **опустить**, а не оставить пустым массивом.
- Приняты оба написания: `nodes` и `placements`, `entity` и `id`, `zone` и
  `container`. Писать стоит `nodes` / `entity` / `zone` — редактор сохраняет так.
- Подпись связи на холсте берётся из `name` (или `title`) её текстовой записи.
  Одно `description` даст связь без подписи: проза — в `description`, короткая
  подпись — в `name`.

#### Видимость связей

Три механизма, по убыванию дешевизны:

1. **Правило обоих концов** — ничего не хранит. Связь видна, только если на виде
   есть **обе** её сущности. Следствие, не настройка; съедает основную массу.
2. **`relations.default`** — что делать со связью, по которой решения ещё не
   принимали. `visible` для рабочих видов, `hidden` для обзорных.
3. **`relations.except`** — поимённые решения, противоположные умолчанию. Всегда
   меньшая сторона.

Политики по типу связи **нет** и не будет: типы — открытое множество, новый тип
при такой политике оказался бы в неопределённом состоянии.

---

## 4. Как завести новый проект

1. `project.json` с `contractVersion: 3` и `defaultAxis`.
2. `entities.json` — `codeRef` **проверить на существование файла**, иначе схема
   с первого дня врёт.
3. `relation-types.json` — сначала словарь, потом связи.
4. `relations.json`.
5. `text.ru.json` — на каждую сущность `description` и `doc`; на контейнеры,
   типы связей и виды — `name`.
6. `views/*.view.json` — по виду на ось, каждый с `axis`.
7. Запись в [`catalog.json`](../catalog.json) — **по одной на каждый вид**, иначе
   вид не открыть.

Черновая геометрия, чтобы вид просто открылся, допустима и заведомо одноразова:
раскладку делает владелец (§6).

## 5. Чего сегодня нет

Записано, чтобы никто не строил планы на несуществующее.

- **`spla-atlas` — пустая папка.** Ни `sync`, ни `convert` не написаны;
  в [`tools/spla-atlas/`](../../../tools/spla-atlas/) лежат README и задание.
  Всё, что здесь сказано про «утилиту», — описание её будущего поведения.
  Сейчас `entities.json` и `relations.json` пишутся руками или разовым скриптом.
- **Проверка протухания переводов не реализована.** Формат её выражает, хэши
  никто не считает: редактор намеренно не переводит, а переводящей утилиты нет.
  Три состояния из §3 сегодня различает только человек.
- **`containers.json` редактор не читает.** Он не запрашивает этот файл вовсе;
  связь зоны с контейнером держится на соглашении об именах `z_`/`c_`. Файл ведут
  для будущей утилиты и для человека.
- **Переключателя видов в редакторе нет.** Отсюда «одна запись каталога на вид».
- **Связи из редактора не сохраняются.** Сохранение пишет вид, `entities.json` и
  тексты; `relations.json` и `relation-types.json` правятся только текстом.
- **Сохранение кладёт подпись блока в `name` его текстовой записи** — то есть
  ровно туда, где имени сущности по контракту быть не должно (§3, `entities.json`),
  а описание блока — в `doc`, мимо `description`. Пока это так, после правки
  блоков на холсте каталог текстов стоит просматривать глазами.
- Переезд с v1/v2 **состоялся**: `model-*.json` удалены. Остатки в

## 6. Правило, которое не обсуждается

**Координаты правит только владелец руками в редакторе.** Ни агент, ни утилита,
ни скрипт «для восстановления». Если файл вида выглядит сломанным — сообщить
человеку, а не чинить. Однажды ручную раскладку уже потеряли откатом файла к
`git HEAD`; вся эта конструкция существует ради того, чтобы такое перестало быть
возможным.
