# Архитектурные диаграммы: Визуализация и взаимодействие с агентом

Этот документ обобщает подход к созданию, визуализации и редактированию архитектурных диаграмм в системе, где агент выступает помощником, а пользователь — главным архитектором, для которого пространственное расположение элементов имеет семантический смысл.

## 1. Проблема: Ограничения Mermaid и Auto-layout
Mermaid и подобные инструменты (Graphviz, PlantUML) отлично подходят для простых схем (A → B → C), но неприменимы для сложной архитектуры из-за непредсказуемого глобального авто-лейаута (auto-layout). Любое незначительное изменение текста или связей может полностью перестроить схему, разрушая визуальную ментальную модель пользователя.

## 2. Целевая модель: Семантический холст (Draw.io / HTML+SVG)
Оптимальный подход — использование форматов с жесткой фиксацией координат и возможностью ручного редактирования, таких как **draw.io / diagrams.net XML** или связка **Diagram JSON → HTML+SVG**.

### Архитектура конвейера генерации
LLM не должна генерировать низкоуровневый SVG напрямую. Вместо этого агент формирует структурированную JSON-модель диаграммы с базовыми координатами:

```text
                    Agent
                      │
                      ▼
              Diagram Model JSON
                      │
         ┌────────────┼────────────┐
         ▼            ▼            ▼
       SVG          draw.io       HTML
      renderer       export       viewer
```

Модель схемы включает богатую семантику:
*   **NODE**: component, service, class, database, external-system
*   **EDGE**: call, data-flow, event, dependency
*   **LAYER**: UI, Runtime, Infrastructure, Storage
*   **GROUP**: boundary, subsystem, process
*   **VIEW**: overview, runtime, deployment

## 3. Ключевые принципы и правила для Агента

Пространство на схеме — это часть архитектуры. Пользовательский layout неприкосновенен.

*   **Никакого глобального auto-layout:** Существующие координаты не меняются без явной команды.
*   **Сохранение контейнеров:** Размеры, позиции контейнеров и группировка через ограничивающие прямоугольники (enclosing rectangles) сохраняются.
*   **Визуальная разметка:** Фон, границы (border), толщина линий, цветовые зоны считаются пользовательской семантической разметкой, а не просто стилем, который агент может "улучшить".
*   **Добавление новых элементов:** Новые объекты размещаются внутри подходящей существующей зоны или рядом с логически связанными объектами. Если места нет, объект кладется рядом и помечается как `unplaced`, перестроение всей карты запрещено.
*   **Локальный auto-layout:** Разрешен только для новых, еще не разложенных человеком локальных фрагментов схемы.

## 4. Семантика контейнеров и метаданные

Визуальные прямоугольники, используемые для выделения зон (subsystem, process-boundary, deployment-node), должны быть семантическими объектами, а не просто фоном.

*   **Разделение понятий:**
    *   *Semantic containment*: объект логически принадлежит подсистеме.
    *   *Visual containment*: объект физически лежит внутри прямоугольника на схеме.
*   **Метаданные (Custom Properties):** В draw.io прямоугольник хранится как объект с метаданными (например, `type=security-zone`, `semanticId=zone.runtime`, `tags=runtime,core`). Агент читает эти свойства, понимая смысл зоны без анализа цвета или координат. Происходит четкое разделение: визуальные свойства (фон, координаты) — это presentation, custom properties — semantic metadata.

## 5. UI/UX и развитие (LOD)

*   **Панель свойств:** Для удобства работы с метаданными (чтобы не править XML руками) в UI системы (HTML/SVG viewer) реализуется боковая панель: при выборе объекта отображаются его Type, Semantic ID, Tags, Code reference.
*   **Уровни детализации (LOD - Level of Detail):** Идея на будущее. Штатно draw.io поддерживает zoom/pan и слои. Реализация логики (например, "при zoom < 30% показывать только подсистемы, при zoom > 70% классы") делается на уровне JS-обертки (viewer) поверх базового холста. Элементы размечаются тегами (`lod-system`, `lod-class`), а страница включает/выключает группы в зависимости от масштаба. Первоначально достаточно стандартного зума и ручных фильтров.
