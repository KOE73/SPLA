# ADR_20260814_core — монтирования: папки вне корня как названные зоны

Статус: **принято**

Опирается на [`ADR_20260811_core_security-zones`](ADR_20260811_core_security-zones.md) — зоны, рёбра,
гранты. Здесь вводится ещё один вид зоны и адресация к ней.

> В контексте **проекта, которому нужны файлы вне его корня**, столкнувшись с тем, что
> **относительный путь наружу не имеет базы, а абсолютный непереносим и невыразим на сервере**, мы
> решили **объявлять такие папки в манифесте как именованные монтирования под зарезервированным
> корнем `mnt/`**, чтобы **получить устойчивый адрес, переносимость и возможность включить границу
> проекта**, приняв **один поставщик вместо расширяемой абстракции и зарезервированное имя в корне
> проекта**.

---

## 1. Контекст

Разбор начался с бытового: есть папка с эталонными настройками Linux и несколько проектов-экспериментов,
которые эти настройки разворачивают. Папка одна, проектов много, физически она лежит рядом — `../AAA`.
Требуется обращаться к ней из инструкций.

Что выяснилось при разборе.

**У относительного пути в инструкции нет базы.** `../AAA` — относительно чего? Рабочего каталога
процесса, корня проекта или файла инструкции, лежащего в `agents/features/foo/prompt.md`? Три разных
ответа. Причём `chdir` делают только CLI и Avalonia (`CliBootstrap.cs:45`, `App.axaml.cs:97`), а
`SPLA.Service` не делает вовсе — то есть база зависит ещё и от того, как запущено.

**Абсолютный путь непереносим.** `C:\Linux\etc` в инструкции, которая едет в git, ломается на второй
машине и невыразим на сервере, где зоны `Машина` нет по построению.

**Без объявления выходов граница не включается.** `BoundaryMode.Shadow` существует потому, что список
законных выходов за корень нельзя угадать, его можно только собрать (`LocalWorkspace.cs:80`). `../AAA` —
ровно такой выход. Пока их нечем объявить, выбор из двух: держать теневой режим вечно либо сломать
настоящую работу.

**SSH-плагин строит свою границу.** `LocalTarget.Resolve` создаёт `new PathBoundary(rootPath)` на каждый
вызов (`LocalTarget.cs:50`) — без вырезов, без монтирований, со своим представлением о побеге. Это одна
из тех четырёх независимых реализаций, ради сведения которых `PathBoundary` и появился. А выгрузка по
SFTP — первый по важности сценарий для монтирований.

## 2. Принятые решения

| Решение | Обоснование |
|---|---|
| Монтирование объявляется в манифесте `.spla` | Имя едет в git и живёт в промпте; цель — свойство машины |
| Адресация под зарезервированным корнем `mnt/` | Защищать одно имя, а не каждое монтирование; в промпте читается как внешнее |
| Монтирование — отдельная зона, а не часть зоны «Проект» | Иначе фича пробивает дыру в модели, которую `ADR_20260811` закрывал |
| Названный остров ⇒ доверен по умолчанию | Флаг недоверия поднимает только неназванный источник; настройка для типичного случая не нужна |
| `access: read` — пол на узле, тот же механизм, что `allow_write` у SSH | Свойство узла, а не пары; арность та же, что у существующего механизма |
| `description:` обязателен и уезжает в системный промпт | Без строки «зачем эта папка» модель лезет в неё наугад |
| Канонический адрес — `mnt/<имя>/...`, хостовый путь — необязательная проекция | Хостовый путь в сохранённом состоянии убивает переносимость; чинится потом только миграцией |
| `MapPathToHost` вправе вернуть `null` | Уже в контракте `IWorkspace`; на сервере это штатный ответ, а не пробел |
| Один поставщик — `file-system`; поле `type` в схеме есть | Второй поставщик меняет контракт, а не реализацию (см. §6) |
| Граница — объект проекта, а не поле воркспейса | Иначе SFTP-выгрузка мимо неё, а это главный сценарий |
| Разрешение внутри `PathBoundary.TryResolve`, не в инструментах | Десять из двенадцати инструментов зовут `ws.FileExists`/`ws.ReadAll*` напрямую |

Формат:

```yaml
mounts:
  - name: AAA
    type: file-system
    path: ../AAA          # относительно каталога манифеста, абсолютится при резолве
    access: read          # read | write
    trust: trusted        # trusted (умолчание) | untrusted
    description: фиксированные настройки Linux, эталон — не править
```

Обращение из инструкции и из инструмента: `mnt/AAA/nginx/nginx.conf`.

## 3. Почему `mnt/`, а не имя как есть

Сначала было записано обратное — голое имя `AAA/...` плюс проверка коллизии при загрузке проекта.
Отвергнуто по разбору отказа: проверка при загрузке срабатывает в момент, который владелец проекта не
контролирует. Приходит `git pull`, в корне появляется папка `AAA` — и проект перестаёт открываться.
Отказ загружаться из-за чужого коммита — неприемлемая цена за красоту адреса.

Зарезервированный сегмент переносит проверку в единственную точку и делает её стабильной: реальной
папки `mnt` в корне проекта быть не должно, и это одно условие на весь срок жизни проекта, независимо
от числа монтирований. Добавление монтирования перестаёт требовать переаудита дерева.

Побочная польза, которая на практике окажется главной: `mnt/AAA/...` в промпте видно как внешнее.
Модель не спутает эталон с исходниками проекта и с меньшей вероятностью полезет туда писать.

## 4. Доверие и пол

По модели зон монтирование — **названный остров**: оператор внёс его в манифест и указал цель, как
вносят SSH-хост или соединение с базой. Значит `trusted` по умолчанию, и случай «этой папке я доверяю
на сто процентов» не требует ни одной настройки.

`trust: untrusted` остаётся ровно для одного сценария: папка, куда кладут файлы не вы — общий сброс,
чужая выгрузка, каталог загрузок. Навязывать его нельзя: строить периметр вокруг собственной
инфраструктуры — та самая паранойя, после которой продуктом перестают пользоваться.

Отдельно про общую папку развёртывания, в которую пишут несколько проектов. Монтирование её не чинит,
оно её **называет**: блокировок не появляется, последний записавший выигрывает. Это осознанно
оставлено как есть — либо владелец записи назначается один, остальным `access: read`, либо
last-writer-wins принимается явно.

Недоступное монтирование (цели нет на этой машине) — это отдельный диагноз, а не «файл не найден».
Отказ называет монтирование, потому что реакция на «папка не подключена» и на «файла нет» разная.

## 5. Что это ломает и чинит в существующем коде

**Чинит.**

- Дублирующая граница в SSH исчезает: `LocalTarget.Resolve` принимает границу проекта вместо
  `string rootPath`. Запрет модели называть абсолютный путь при этом сохраняется — `mnt/AAA/x`
  абсолютным не является.
- Четвёртая по счёту реализация «внутри корня» сводится к общей.
- Появляется механизм, которым набирается список законных выходов за корень — то, ради чего заведён
  теневой режим.

**Ломает (осознанно).**

- Имя `mnt` в корне проекта становится зарезервированным. Существующая папка с таким именем требует
  переименования один раз.
- Всё, что сохраняет пути между сессиями — KV, история чата, гранты, записи об ошибках — обязано
  хранить каноническую форму. Места, где сегодня оседает хостовый путь, придётся найти.

## 6. Долг: транспорт ходит мимо `IWorkspace`

Записано здесь, чтобы через полгода не возвращаться с вопросом «а почему SSH открывает файлы сам».

Правильный адресат для «дай поток» — `IWorkspace`. Сегодня он не может ответить:

| Нужно транспорту | Есть в контракте | Где |
|---|---|---|
| отложенный поток на чтение | нет | `UploadSource.cs:157` |
| поток на запись + замена через temp | нет, только `WriteAllTextAsync` | `SftpTransfer.cs:262` |
| перечисление с метаданными (размер, mtime, тип) | нет, `GetFiles` отдаёт строки | `UploadSource.cs:126,153` |
| распознать junction/symlink | нет | `UploadSource.cs:131` |
| **перематываемый** поток, открываемый многократно | нет | `TarContainer.cs:55,78,144` |

Последняя строка — не «дайте поток», а «дайте поток с seek, открывать буду сколько нужно»: у tar нет
индекса, поэтому архив сканируется заново на каждую запись. Виртуальное хранилище такого может не уметь
вовсе. Либо контракт объявляет перематываемость явно, либо `TarContainer` переписывается в один
потоковый проход — чего его собственный `NAIVE`-комментарий и просит. Атомарная замена из той же
породы: `Move`/`Replace` в контракте нет, а на не-файловом хранилище такой операции может не
существовать.

**Для монтирований этот переезд не нужен.** Монтирование типа `file-system` разрешается в настоящий
путь; `FileStream` поверх него работает так же, как поверх пути внутри проекта. Поэтому работа делится:

1. **сейчас** — монтирования и общая граница; SSH продолжает открывать `FileStream`, но по пути,
   выданному общей границей. Сценарий выгрузки работает, дублирующая граница исчезает;
2. **когда появится не-файловый поставщик или серверное развёртывание** — расширение `IWorkspace`
   потоками и метаданными, переезд транспорта, и тогда же честный ответ про seek и атомарность.

Отвечать на эти вопросы сейчас значит проектировать под гипотетического потребителя.

## 7. Чего это не обещает

- **Shell не участвует.** `system_run_shell`, `roslyn_script_run`, git, компиляторы берут путь от
  модели и уходят мимо `IWorkspace`. Для них есть `MapPathToHost`, и в промпте прямо сказано, что
  `mnt/` — адрес для файловых инструментов. Не-файловые монтирования из shell не заработают никогда;
  это следствие, а не недоделка.
- **Монтирование не изолирует.** Как и всё остальное в модели зон, оно держится до первой команды в
  шелле — см. оговорку в `ADR_20260811` про `PLAN_20260807_host_sandbox`.
- **Общая папка не становится согласованной.** Параллельная запись из двух проектов остаётся гонкой.
- **Метки на файлах не держатся.** Недоверенное, записанное в монтирование одним чатом и прочитанное
  другим, метку теряет — тот же предел, что и у файловой системы вообще.

## 8. Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Голое имя `AAA/...` + проверка коллизии при загрузке | Проверка срабатывает в неконтролируемый момент: чужой коммит с папкой `AAA` роняет открытие проекта |
| Префикс-символ (`@AAA/`, `~AAA/`) | Решает коллизию, но ломает естественность в промпте — ровно то, ради чего фича заводится. `mnt/` даёт то же за меньшую цену |
| Монтирование как часть зоны «Проект» | Тогда это просто второй разрешённый корень, то есть дыра в модели, которую `ADR_20260811` закрывал |
| Второй корень вместо монтирования (вернуть `workspace:` в другом виде) | Второе определение корня уже было и уже убито: путь клался как есть и никогда не абсолютился (`ConfigLoader.cs:362`) |
| Поставщик SSH | `file-system` — переписывание пути: без состояния, без частичных отказов. SSH — сетевая ФС: задержки, кэш, отсутствие атомарной записи, `ReadAllBytesAsync` на гигабайты. Это не монтирование, а распределённая ФС под тем же интерфейсом, и она сломает контракт молча. Явные SFTP-инструменты уже делают эту работу честно |
| Интерфейс поставщиков сразу, «раз это дёшево» | Дёшево не значит нужно. Поле `type` в схеме стоит одно слово и снимает вопрос совместимости; абстракция без второго потребителя — угадывание |
| Разрешение монтирований в `MapPathToHost` | Покрыло бы два вызова из двенадцати: остальные инструменты зовут `FileExists`/`ReadAll*` напрямую |
| Разрешение монтирований в каждом инструменте | Пятая независимая реализация границы, при том что сводим четыре |
| Хранить хостовый путь в состоянии, а канонический считать удобством | Проект перестаёт быть переносимым; на сервере хостового пути нет вовсе |
| Сразу перевести SSH-транспорт на `IWorkspace` | Работа крупнее самих монтирований и для них не требуется; ответы про seek и атомарность пришлось бы выдумывать под несуществующего потребителя |
| `trust: untrusted` по умолчанию | Монтирование — названный оператором остров, как SSH-хост. Недоверие по умолчанию сожгло бы бюджет вопросов на собственной инфраструктуре |

## 9. Последствия

**Что получаем.**

- Адрес, читающийся одинаково из любой глубины инструкций, из любого хоста и при любом способе запуска.
- Переносимость: имя в git, цель на машине.
- Возможность двигать корень проекта к `BoundaryMode.Enforce` — законные выходы становятся объявляемыми.
- Единственная граница вместо четырёх; SSH перестаёт быть исключением.

**Чем платим.**

- Зарезервированное имя `mnt` в корне проекта.
- Ещё один вид зоны в модели безопасности и в интерфейсе карты зон.
- Обратный маппинг обязателен везде, где печатается путь: поиск, листинги, отказы, диагностика. Без
  него модель получает хостовый путь и скармливает его обратно.
- Цель монтирования надо прогонять через `ResolveLinks` тем же порядком, что и корень; монтирование,
  ведущее внутрь корня, отклоняется как вырожденное.

**Что теперь нельзя.**

- Нельзя обращаться наружу проекта необъявленным относительным путём — это станет отказом, когда
  граница выйдет из теневого режима.
- Нельзя класть хостовый путь в сохраняемое состояние.
- Нельзя заводить поставщика монтирований, не ответив на вопросы из §6.
