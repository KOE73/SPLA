# ADR_20260824_core — интерактивный shell: команда, которая спросила, и её никто не услышал

Статус: **принято**

Касается seam'а хостовой абстракции, заложенного
[`PLAN_20260701_core_host-abstraction`](../plans/PLAN_20260701_core_host-abstraction.md):
`ISandbox.Shell` / `IShell` / `LocalShell`.

> В контексте **инструмента `system_run_shell`, который повис навсегда на `ffmpeg`, спросившем
> «Overwrite? [y/N]»**, столкнувшись с тем, что **`ShellResult` — терминальный тип, а `RunAsync`
> отдаёт вывод только после смерти процесса, поэтому состояние «жив, но ждёт ответа» невыразимо и
> невидимо: модель не получает ни текста вопроса, ни возможности на него ответить**, мы решили
> **сделать `IShell` сессионным — возвращать управление не только по завершении, но и по простою, с
> накопленным выводом, статусом и идентификатором сессии, оставив stdin открытым для ответа**,
> чтобы **любая команда, что-либо спросившая, становилась для модели обычным ветвлением
> «ответить / подождать / убить», а не вечным зависанием**, приняв **эвристичность детектора
> (простой + форма хвоста вместо настоящего «процесс читает stdin») и слепоту к программам, которые
> при пайпе уходят в полную буферизацию вывода**.

---

## 1. Контекст

Живой случай. Модель вызвала:

```
ffmpeg.exe -v error -t 1 -i "Video\202_02\output_0821_153412.ts" -map 0:v:0 -ss 30 \
           -frames:v 1 -q:v 2 "Video2ShortVideo2Images\sample_202_02_30s.jpg"
```

Выходной `.jpg` уже существовал, ключа `-y` не было. ffmpeg напечатал
`File '...' already exists. Overwrite? [y/N]` и стал ждать ввода. Инструмент показал
«Выполняется…» и не завершился никогда.

Соблазн назвать это ошибкой вызова («забыли `-y`») неверен: **проблема класса, а не команды.**
Спросить может что угодно — `git` про credentials, `npm` про перезапись, `apt` про «Do you want to
continue?», `dotnet` про доверие сертификату, любой интерактивный установщик. Ключ `-y` лечит один
случай из бесконечного списка.

Причина ровно в двух местах.

**Вывод физически недоступен до смерти процесса.** `LocalShell.RunAsync` делает
`ReadToEndAsync` + `WaitForExitAsync`: текст вопроса лежит в пайпе, читать его начнут только после
EOF, то есть после завершения — которого не будет.

**В контракте нет канала ответа и нет способа описать «ждёт».** `RedirectStandardInput` не
выставлен, так что дочерний процесс наследует stdin родителя. А `ShellResult(ExitCode, Out, Err)` —
терминальный тип: пока `IShell` умеет возвращать только его, никакая правка внутри `LocalShell` не
поможет — «вот что успело выйти, процесс жив, похоже ждёт ответа» в этом типе не выражается.

---

## 2. Принятые решения

| Решение | Обоснование |
|---|---|
| **`ShellResult` перестаёт быть терминальным**: добавляются `Status` (`Exited` / `WaitingForInput` / `Running`) и `SessionId` | Это и есть недостающее состояние. Всё остальное — следствие; пока тип терминальный, чинить нечего |
| **`RunAsync` возвращает управление по простою**, а не только по выходу | Единственный способ показать модели текст, который процесс уже напечатал, но ещё не завершился |
| **Два порога простоя**, а не один: `PromptIdle` (2 с) при хвосте **без** перевода строки, `SilentIdle` (120 с) в остальных случаях | Промпт узнаётся по форме: `Overwrite? [y/N] ` печатается без `\n`, потому что курсор остаётся на строке. Один общий порог заставил бы выбирать между «дёргать долгую тихую сборку» и «висеть на вопросе две минуты» |
| **stdin редиректится и остаётся открытым**, а не глушится в NUL | NUL тоже снимает зависание (программа получает EOF и падает), но ценой невозможности ответить. Требование — «модель видит вопрос **и** отвечает», а не «не висим» |
| Чтение stdout/stderr — **инкрементальное**, в буфер с отметкой времени последнего байта | `ReadToEndAsync` по определению не может отдать частичный вывод. Отметка времени — то, на чём стоит детектор простоя |
| Продолжение и убийство сессии — **отдельные инструменты** `system_resume_shell` / `system_kill_shell`, а не режимы `system_run_shell` | У `system_run_shell` обязательный `command`; «продолжить сессию» команды не имеет. Смешение дало бы инструмент, где половина аргументов всегда пустая |
| Ответ и ожидание — **один инструмент** `system_resume_shell` с необязательным `input` | Для модели это одно действие «верни мне управление снова»; наличие текста — деталь. Два инструмента, отличающиеся только тем, пишем ли мы в stdin, — лишняя развилка |
| **Сессии живут в экземпляре `IShell`**, а не в статике | Экземпляр `LocalShell` создаётся вместе с `ISandbox`, а тот резолвится под текущий чат — значит сессии изолируются по чатам тем же механизмом, что и всё остальное, без второго понятия «владелец сессии» |
| **Осиротевшие сессии убиваются**: лимит числа живых + `IDisposable` на shell, убивающий дерево процессов | Процесс, которого модель бросила, иначе живёт до перезапуска SPLA. Это утечка на хосте, а не косметика |
| `DotnetBuildTool` / `DotnetTestTool` передают `SilentIdle = infinite`, оставляя детектор промптов включённым | Сборка и тесты законно молчат минутами, но не спрашивают. Им нужна защита от вопроса, не от тишины |
| **`ConPTY` не берётся** — транспорт остаётся пайпами | Псевдоконсоль решает класс целиком (см. §3), но это отдельная работа со своим P/Invoke, чисткой ANSI и веткой под не-Windows. Контракт после этого ADR её примет без изменений |

### Форма результата для модели

```
ExitCode: -1
Status: waiting_for_input          ← процесс жив и, судя по хвосту, спрашивает
Session: sh_3
Output:
File 'Video2ShortVideo2Images\sample_202_02_30s.jpg' already exists. Overwrite? [y/N]
```

Дальше модель выбирает: `system_resume_shell {session: "sh_3", input: "y"}`,
`system_resume_shell {session: "sh_3"}` (просто подождать ещё) или
`system_kill_shell {session: "sh_3"}`.

## 3. Отвергнуто

**Добавить `-y` в промпт / в шаблон команды.** Лечит ffmpeg и ровно ffmpeg. `git`, `npm`, `apt`,
установщики и любой скрипт с `Read-Host` спрашивают по-своему; список ключей «не спрашивай» не
закрывается никогда.

**Закрыть stdin (перенаправить в NUL).** Дёшево и снимает зависание: программа получает EOF и
обычно выбирает безопасный ответ или падает. Но это прямо противоречит требованию — вопрос
по-прежнему остаётся без ответа, просто теперь молча. Отвергнуто как решение не той задачи.

**Только таймаут с падением.** Тоже снимает зависание и даже показывает накопленный вывод, но
превращает каждый вопрос в неудачу с перезапуском команды заново — а перезапуск бывает дорогим
(перекодирование, установка, миграция).

**`ConPTY` как V1.** Технически это правильный ответ: дочерний процесс считает, что он в консоли,
переходит на построчную буферизацию, промпты долетают всегда, работают даже TUI. Но: Windows-only
API через P/Invoke, отдельная ветка под Linux (`forkpty`), обязательная чистка ANSI-escape из
вывода, и заметно больший объём. Взято поведение, а не транспорт: `IShell` после этого ADR
описывает интерактивную сессию, и подмена пайпов на ConPTY — замена реализации за тем же
интерфейсом. Единственное, что при этом останется невиданным до ConPTY: программы, которые при
пайпе (не консоли) уходят в полную буферизацию и не флашат промпт — `python` без `-u` и подобные.

**Настоящий детект «поток читает stdin»** (через `NtQueryInformationThread` и wait reason). Точнее
эвристики, но это недокументированный ABI ядра, Windows-only и хрупкий при обновлениях. Цена
ошибки эвристики — один лишний возврат управления модели, что несопоставимо дешевле.

**Глобальный статический реестр сессий.** Дал бы второе понятие владельца рядом с уже существующим
«сандбокс резолвится под текущий чат» — и, как следствие, вопрос «чья это сессия `sh_3`», на который
контракт отвечать не должен.

## 4. Открытые вопросы (не решаются этим ADR)

1. **Сессии в серверном сценарии.** `PassthroughSandbox.Default` — процессный фолбэк, и его
   `LocalShell` общий. Пока чаты получают свой сандбокс, изоляция есть; при мульти-юзерном сервере
   (см. `server-multi-user-identity`) надо будет убедиться, что фолбэк не становится общей
   раздевалкой.
2. **Живая сессия через перезапуск.** Сейчас сессия умирает вместе с процессом SPLA. Переживание
   рестарта потребовало бы отвязать процесс от родителя — отдельная работа с отдельными рисками.
3. **Прогресс в живую.** Накопленный вывод отдаётся только по возврату управления. Показ хвоста в
   статус-баре по ходу — задача для `ProgressScope` (см. `progress-tree`), здесь не решается.
4. **ConPTY** — см. §3, целиком впереди.
5. **Порог `PromptIdle = 2 с` угадан, а не измерен.** Программа, печатающая прогресс без `\n` и
   застрявшая на 2 секунды, будет объявлена ждущей ввода. Ложное срабатывание стоит одного возврата
   управления, поэтому порог принят без замера — но он кандидат на настройку по факту.

---

## 5. Последствия

- Ни одна команда, задавшая вопрос, больше не висит бесконечно — худший случай стал «модель увидела
  текст и решает, что делать».
- `IShell` вырос с одного метода до трёх (`RunAsync` / `ResumeAsync` / `KillAsync`); реализации
  сандбоксов, запрещающих исполнение, не затронуты — они по-прежнему отдают `Shell = null`.
- `ShellCommand` и `ShellResult` пополнились полями со значениями по умолчанию, поэтому существующие
  места вызова (`DotnetBuildTool`, `DotnetTestTool`) компилируются без правок; правка им нужна
  только ради `SilentIdle = infinite`.
- У `core.shell` появляется prompt-фрагмент: до сих пор фича была tools-only, но семантику «статус
  `waiting_for_input` — это к тебе вопрос» модель обязана знать до первой встречи с ней.
