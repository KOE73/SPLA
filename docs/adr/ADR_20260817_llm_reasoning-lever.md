# ADR: рычаг рассуждения — то, что объявил провайдер, а не то, что придумали мы

**Дата:** 2026-08-17
**Статус:** принято
**Соседи:** [ADR_20260731_llm_pipeline.md](ADR_20260731_llm_pipeline.md), [ADR_20260814_llm_output-stage.md](ADR_20260814_llm_output-stage.md)

---

## 1. Что случилось

В строке состояния чата не было ни температуры, ни глубины рассуждения. Ядро их знало
(`LLMSettings.Temperature`, `LLMSettings.ReasoningLevel`, слои defaults → project → chat), CLI умел
`--temp` и `--reasoning`, а UI — нет: до сервиса эти ручки были в Avalonia-окне и при переезде на
веб-клиент не доехали.

Вопрос, из-за которого это не «вернуть два поля»: **стандартизован ли уровень рассуждения?**
Ответ, полученный не из документации, а замерами по живым провайдерам 2026-08-17.

### Что показал обход

**LM Studio, нативный `/api/v1/models`** — единственный локальный рантайм, который вообще что-то
говорит. Даёт `capabilities.reasoning: { allowed_options, default }`, и список у каждой модели свой:

| модель | allowed_options | default |
|---|---|---|
| `qwen/qwen3.8-27b` | `["off","low","medium","xhigh","on"]` | `xhigh` |
| `google/gemma-4-e4b`, `gemma-4-26b-a4b-qat`, `glm-4.7-flash`, `qwen3.6-*` | `["off","on"]` | `on` |
| `openai/gpt-oss-20b` | `["low","medium","high"]` | `low` |
| `meta/muse-glimmer` | `["low","medium","high","xhigh"]` | `high` |
| `mistralai/ministral-3-14b-reasoning` | `["on"]` | `on` |
| `qwen3-coder-*`, `deepseek-coder-*`, `qwen3-vl-4b` | — (ключа нет) | — |

Три вывода сразу. Список у Qwen3.8 — **одновременно выключатель и шкала**, и в нём нет `high`, зато
есть `xhigh`. У Ministral нет `off` — модель думает всегда. У кодовых моделей блока нет вовсе.

**Сервер LM Studio при этом говорит на своём словаре, а не на модельном.** `reasoning_effort: "off"`
→ 400: `Supported values: none, minimal, low, medium, high, xhigh`. То есть модельное «off» на
проводе называется `none`. Замер по одному и тому же вопросу к Qwen3.8:

| запрос | reasoning_tokens |
|---|---|
| ничего не передано | 60 |
| `reasoning_effort: none` | **0** |
| `reasoning_effort: minimal` | 32 |
| `reasoning_effort: medium` | 40 |
| `reasoning_effort: xhigh` | 57 |

А `chat_template_kwargs: { enable_thinking: false }` — то, что этот код слал до сих пор для `off`, —
**игнорируется**: модель продолжила думать (23 токена). Работал он ровно потому, что ничего не делал.

**OpenRouter** публикует самый богатый дескриптор — и все три оси сразу:

```json
"reasoning": { "mandatory": false, "default_enabled": true, "supports_max_tokens": true,
               "supported_efforts": ["high","medium"], "default_effort": "high" }
```

**LocalAI** не говорит ничего — и принимает всё. Отправка `reasoning_effort: "none"` его Gemma-4 не
выключила рассуждение, а **сломала генерацию**: вместо одного слова пришло 600 токенов
`0.5-0.5-0.5-0.5…`. Поле принято, до шаблона не дошло, модель поехала.

За пределами стенда картина та же: у Anthropic это `thinking.budget_tokens` (число, не слово), у
Gemini `thinkingConfig.thinkingBudget` (0 = выкл, −1 = динамически), у DeepSeek-R1 ручки нет вообще.

## 2. Решение

**Никакой единой шкалы. Варианты приходят снизу, от провайдера, и показываются его же словами.**

### 2.1 Три оси, а не один «вид»

`ReasoningCapability` (`SPLA.Domain/Models`) несёт оси **рядом**, а не выбирает между ними:

* `Mandatory` / `DefaultEnabled` — выключатель;
* `Efforts` (+ `DefaultEffort`) — шкала, **словарём провайдера и в его порядке**;
* `SupportsTokenBudget` (+ границы) — бюджет токенов.

Модель может иметь несколько осей сразу — Qwen3.8 имеет две. Закрытый `enum kind` пришлось бы
ломать на каждой второй модели, а закрытый `enum` уровней — выбрасывать `xhigh` или выдумывать
`high`, которого у модели нет. Форма списана с дескриптора OpenRouter как с самого полного из
существующих, поэтому Anthropic и Gemini лягут в неё без переделки DTO.

### 2.2 «Не сказали» — это не «нельзя»

Отдельное поле `Known`. Три состояния вместо двух:

| состояние | что значит | что делает UI |
|---|---|---|
| `Known && Supported` | провайдер описал канал | полный рычаг его словами |
| `!Known` | никто ничего не сказал | рычаг **виден, но заблокирован**, с объяснением |
| `Known && !Supported` | провайдер сказал «канала нет» | рычага нет |

Различие несёт нагрузку в обе стороны. Наверх — человек видит разницу между «модель не думает» и
«мы не знаем». Вниз — **рычаг, который никто не объявлял, не дёргается**: `LLMSettings.ModelReasoning`
гейтит маппинг на провод, и именно это спасает от истории с LocalAI выше.

Чтобы «не сказали» не было приговором, у записи модели в `.spla` появилось ручное объявление —
`reasoning_options` / `reasoning_default`, ровно по образцу и с приоритетом `context_length`:
объявленное побеждает объявленное провайдером. Это ответ для vLLM и любого голого
OpenAI-совместимого сервера, чей владелец знает, что тот принимает.

### 2.3 Выбор — один скаляр с открытой грамматикой

`reasoning_level` остаётся **одним значением**, потому что слоится (defaults → project → chat) тем же
механизмом, что температура; вложенный объект потребовал бы правил слияния, которых никто не хочет
писать. Грамматика (`ReasoningChoice`): `""` | `off` | `on` | *слово-усилие* | `budget:N`.

Открытый конец — не небрежность: **неизвестное слово считается словом-усилием и едет как есть**.
Провайдер, который завтра введёт `ultra`, поедет без единой правки кода.

### 2.4 Перевод на провод — дело провайдера

Маппинг ушёл из общего клиента в `IOpenAiCompatProfile.ShapeReasoning`:

* по умолчанию (`OpenAiReasoningDialect`) — `reasoning_effort`, с переводом модельного `off` в
  серверное `none`. Человек, выбирающий вариант, не обязан знать два словаря;
* OpenRouter — свой блок `reasoning: { enabled | effort | max_tokens }`, единственный, куда
  выражается бюджет;
* бюджет в OpenAI-диалекте **не выражается и не подменяется** усилием: `SupportsTokenBudget`
  честно `false`, UI такого варианта не покажет.

### 2.5 Откуда берётся описание

Тем же порядком, что и окно контекста (`AgentRuntime.GetContextLengthAsync`), и рядом с ним:
объявление в конфиге → `IReasoningCatalog` провайдера (OpenRouter) → нативная management-поверхность
(LM Studio, `ModelInfo.Reasoning`) → `Unknown`. Кэш на 10 минут — дольше, чем у окна контекста:
окно меняется при перезагрузке модели, а способности канала — свойство самой модели.

По проводу это **запрос** (`chat.reasoning.get`), а не поле в `chat.opened`: ответ идёт по сети, и
открытие чата не должно ждать живости провайдера.

## 3. Что отвергнуто

**Нормализовать всё в `low/medium/high`.** Пришлось бы врать в обе стороны: `xhigh` Qwen3.8 не
ложится, `high` для неё не существует, а бюджет Anthropic в три слова не сжимается без выдумывания
чисел.

**Прятать рычаг, когда провайдер молчит.** Тогда LM Studio получает ручку, а OpenAI-совместимый
сервер — нет, и человек не понимает, почему. Заблокированный контрол с объяснением сообщает факт.

**Слать `chat_template_kwargs` «на всякий случай» рядом с `reasoning_effort`.** Замерено: LM Studio
его игнорирует, а строгий OpenAI отвергает тело с незнакомым полем. Ноль пользы, ненулевой риск.

**Разрешить дёргать рычаг у неописанной модели.** Соблазнительно («вдруг сервер поймёт»), но именно
это ломает LocalAI. Путь для знающего владельца — объявить опции в `.spla`, то есть взять
ответственность явно.

## 4. Чем проверено

`tests/SPLA.Tests/ReasoningLeverTests.cs` — 33 теста, все фикстуры сняты с живых провайдеров
2026-08-17. Плюс сквозная проверка через сервис на шести записях моделей: Qwen3.8 (смешанный
список), gpt-oss (шкала без `off`), qwen3-coder (канала нет), Nemotron через OpenRouter (шкала +
бюджет), LocalAI (молчит), LocalAI с объявлением в конфиге. В одном чате на одной модели:
`off` → 0 символов рассуждения, `xhigh` → 96; на LocalAI при выставленном `budget:4096` на провод не
ушло ничего и ответ пришёл нормальный.
