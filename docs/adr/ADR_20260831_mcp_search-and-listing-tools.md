# ADR_20260831_mcp — поисковый и листинговый инструменты: закрыть разрыв до grep-паритета плюс дерево каталогов

Статус: **принято**

> В контексте **двух эпизодов навигации по большому корпусу файлов в одной сессии — модель обошла
> `system_search_text` стороной на 32-тысячестраничном справочнике, а другая модель раз за разом
> дёргала листинг по одному каталогу за вызов, спускаясь по дереву вручную** — и обнаружив при
> разборе, что `system_search_text` реально уступает базовому grep (нет контекстных строк, нет
> multiline, нет режимов вывода, полное сканирование до применения `max_results`, сломанный
> игнор-глоб, проглатываемый stderr, резолв бинарника через PATH), а листинг каталогов вообще не
> умеет рекурсии, мы решили **разделить движки по подложке, а не по доступности бинарника; довести
> `system_search_text` до паритета с обычным grep; поставлять `rg` в комплекте и резолвить его по
> явному пути; свести семантику движков через `RegexOptions.NonBacktracking`; и добавить рекурсию
> с деревом в существующий `system_list_files`, не заводя новый инструмент**, чтобы **и поиск, и
> ориентация в структуре проекта схлопывали цепочку из N вызовов в один, как того требует
> доктрина**, приняв **что каждая возможность реализуется дважды — флагами `rg` и руками поверх
> `IWorkspace`, — и это ограничивает аппетит по возможностям сильнее, чем то, что умеет `rg`**.

---

## 1. Контекст

### Инцидент 1 — поиск обойдён стороной

Агент со слабой моделью работал со смонтированным справочником SolidWorks API (32 215 страниц,
29 пакетов). Имея на руках точный искомый символ (`AddCustomProperty`), он пошёл через
`by-symbol.md` (нужен нормализованный ключ) и `system_find_files` (поиск по имени файла) — и не
тронул `system_search_text`, который нашёл бы все страницы с этим текстом одним вызовом без
нормализации. Собственная проверка на `docs/` этого репозитория повторила тот же паттерн: поиск
велся через `Glob`+`Read`, `system_search_text` не привлекался, пока не попросили явно.

### Инцидент 2 — ручной обход дерева

Отдельно замечено: слабые модели при ориентации в незнакомом проекте выпускают серию
`system_list_files` — один вызов на каталог, затем по очереди на каждый подкаталог. Инструмента,
возвращающего дерево целиком за один вызов, не существует.

### Что показал разбор реализации

Все факты — из `src/agent/SPLA.MCP.BasicTools/FileSystem/`.

**`system_search_text`** (`FsSearchTextTool.cs` + `Search/*.cs`):

- Полностью последовательно на всех трёх путях исполнения — ripgrep-обёртка, .NET fallback,
  workspace fallback. Ни одного `Parallel.ForEach`/`Task.WhenAll` нигде в цепочке.
- `RipgrepSearchEngine.cs:67` — самодельный игнор-глоб на `.git`/`bin`/`obj`/`node_modules`
  содержит лишний пробел: `!**/ {ignore}/**`. Ripgrep такой глоб не матчит осмысленно — это дохлый
  код, а не рабочий фильтр.
- `RipgrepSearchEngine.cs:79` — `RedirectStandardError = true`, но stderr нигде не читается и не
  логируется. При падении ripgrep причина падения теряется молча, инструмент просто уходит в
  .NET fallback без объяснения.
- Нет флагов контекста (`-A`/`-B`/`-C`), нет `--multiline`, нет режимов вывода
  (`--count`/`--files-with-matches`) — всегда построчный контент через `--json`.
- `SearchRanking.RankAndFilter` (`SearchRanking.cs`) дедуплицирует и ранжирует **после** полного
  сбора совпадений по всему дереву, `.Take(maxResults)` — последний шаг. `max_results` не
  ограничивает объём работы движка, только объём ответа.
- Короткое описание (`FsSearchTextTool.cs:83`) рассказывает про устройство («Ripgrep with .NET
  fallback, relevance ranking») — ни слова о том, когда его выбрать вместо перебора файлов вручную.
  Длинное `DetailsText` (строки 22–74) даёт примеры только по `.cs`-коду — ни одного примера про
  поиск по документации или произвольному тексту.

**`system_list_files`** (`FsListTool.cs`): один уровень одного каталога за вызов, плоский текстовый
ответ (`[DIR]`/`[FILE]`), нет параметра глубины/рекурсии, нет вывода через blob.

**`system_find_files`** (`FsFindFilesTool.cs`): рекурсивен, но возвращает плоский список путей по
глобу — не структуру дерева. Ближайший аналог к дереву, но им не является.

Ни один ADR или план в `docs/` не описывает проектирование этих двух инструментов — решение ниже
на пустом месте, реконсилировать не с чем.

---

## 2. Решение

### 2.0 Ось разделения движков — подложка, а не доступность бинарника

Это решение переопределяет наивную рамку «`rg`, а если его нет — свой движок». Правильная ось —
**на чём лежат файлы**:

| Подложка | Движок | Почему |
|---|---|---|
| диск (`MapPathToHost` вернул путь) | `rg` | быстрее на порядок, `.gitignore`/кодировки/бинарники даром |
| виртуальный workspace (`MapPathToHost` вернул `null`) | движок поверх `IWorkspace` | `rg` физически неприменим — файлов на диске нет |

Виртуальная подложка — **не запасной путь, а вторая полноценная**. Она не исчезнет никогда, сколько
бы `rg` мы ни поставляли.

Отсюда прямое следствие: **`DotnetSearchEngine` упраздняется**. Он был третьим движком «диск без
`rg`», то есть дублировал логику `WorkspaceSearchEngine` ради прямого файлового ввода-вывода.
Дисковый workspace — это тоже `IWorkspace`, поэтому падение `rg` уходит в тот же самый движок, что
обслуживает виртуальную подложку. Три реализации → две, разделённые по существу, а не по случайности
окружения.

Второе следствие — **ограничение на аппетит**: каждая возможность (контекстные строки, multiline,
режимы вывода, дерево, `per_dir_limit`, сортировки) пишется дважды — как флаги `rg` и как код поверх
`IWorkspace`. Набор возможностей ограничен не тем, что умеет `rg`, а тем, что мы готовы поддерживать
во второй реализации. Это естественный тормоз против расползания параметров, и он намеренный.

### 2.1 Описание `system_search_text` — переписать без завязки на конкретные инструменты

Текущее описание объясняет *как устроено* (ripgrep, .NET fallback, ranking), а не *когда выбрать*.
Первая версия правки называла конкретные конкурирующие инструменты по имени (`find_files`,
`by-symbol`) — отклонено: это одноразовая привязка к формату одного смонтированного корпуса
(`by-symbol.md` — файл конкретно того справочника SolidWorks, не общее понятие SPLA). Верная
формулировка — через **общее свойство задачи**, а не через имя другого инструмента:

- явное указание в начале описания: полнотекстовый поиск по содержимому файлов — сюда, если нет
  точного имени файла или точного ключа/символа;
- минимум один пример поиска не по коду (документация/markdown), чтобы не сузивать инструмент в
  голове модели до «инструмент для `.cs`»;
- явная фраза-триггер вида «search file **contents** here» рядом с явным контрастом «not file
  names — that's a different axis», без называния конкретного другого tool-name.

### 2.2 Довести до grep-паритета

Добавить к `ISearchEngine`/ripgrep-вызову:

- контекстные строки вокруг совпадения (аналог `-A`/`-B`/`-C`), с полями `before`/`after` в
  `SearchMatch`;
- режим `--multiline`, пробрасываемый в ripgrep-путь и поддержанный построчными fallback-путями
  через посегментное чтение вместо `ReadAllLines`;
- режимы вывода: `content` (как сейчас), `files_with_matches`, `count` — с ранним выходом движка
  на `files_with_matches`/`count`, а не постфактум-агрегацией того же полного скана.

### 2.2a Свести семантику регулярок: `RegexOptions.NonBacktracking`

Rust-движок `rg` — конечно-автоматный, без бэктрекинга, и потому **не поддерживает** обратные ссылки
и lookaround. .NET `Regex` по умолчанию бэктрекинговый и поддерживает и то и другое. Один запрос —
разное поведение на разных подложках, о чём модель знать не может.

Решение: движок поверх `IWorkspace` компилирует пользовательскую регулярку с
**`RegexOptions.NonBacktracking`**. Этот режим сам отказывается от бэктрекинга, lookaround и
обратных ссылок — то есть даёт почти ровно тот же набор возможностей, что Rust-движок, — и попутно
исключает катастрофический бэктрекинг от кривой регулярки, присланной моделью. Одним движением
закрыты и расхождение семантики, и класс отказа по времени.

Остаточные мелкие расхождения (синтаксис именованных групп `(?P<n>…)` против `(?<n>…)`, именование
юникод-классов) закрываются валидацией запроса на входе, а не разным поведением на выходе.

### 2.3 Починить найденные баги

- Игнор-глоб `!**/ {ignore}/**` → убрать лишний пробел, проверить, что `.git`/`bin`/`obj`/
  `node_modules` реально исключаются в ripgrep-пути (сейчас, вероятно, нет).
- Прочитать stderr при падении ripgrep-процесса перед уходом в fallback — сейчас причина падения
  теряется молча.

### 2.3a Поставка `rg` и явный путь вместо PATH

`FileName = "rg"` — резолв через PATH, то есть вектор перехвата: кто положит свой `rg` раньше в
PATH, исполняется внутри агента. Для инструмента, декларированного как `ToolEffect.Read`, это
неприятный сюрприз — и отдельно неприятно, что чтение вообще спавнит процесс, а спавн процесса по
модели зон ([`ADR_20260811_core_security-zones`](ADR_20260811_core_security-zones.md)) — это
execute-класс.

Решение — резолв по явному пути, в порядке:

1. явное указание пути (переменная окружения / настройка) — высший приоритет;
2. каталог инструментов рядом с бинарником SPLA — **штатная поставка**;
3. каталог инструментов в глобальных настройках SPLA (`~/.spla/tools/`);
4. PATH — **только при явном разрешении**, по умолчанию выключен.

Поставка `rg` в комплекте не противоречит «единому типизированному бинарнику» из доктрины: та
формулировка — про отсутствие venv-зоопарка и рантайм-зависимостей, а не про запрет положить рядом
один статический exe (~5 МБ, лицензия MIT/Unlicense).

### 2.3b Одноразовая заметка о деградации

Сейчас отсутствие или падение `rg` не видно вообще ниоткуда: инструмент молча становится
медленнее и теряет `.gitignore`-осведомлённость. Решение: **при первом поиске в чате**, если
рабочим оказался движок поверх `IWorkspace` на дисковой подложке (то есть `rg` не нашёлся или упал),
к результату добавляется одна строка в терминах последствия, а не имени бинарника:

```
note: fast search backend unavailable — using built-in fallback (slower, no .gitignore awareness)
```

Дальше в этом чате — молчание. Состояние per-chat, вне KV: заметка не должна засорять рабочую
память, которую модель листает.

### 2.4 Параллелизация — решение отложено до данных, не «да» и не «нет»

Ripgrep **уже сам многопоточный внутри** — обходит дерево и матчит через собственный пул потоков,
по умолчанию равный числу ядер (управляется `-j`/`--threads`, сейчас не передаётся — значит уже
используется дефолт). Добавлять параллелизм в C#-обёртке вокруг ripgrep-вызова — дублирование, не
ускорение: сам процесс уже параллелен, наша обёртка вокруг него — просто ждёт один subprocess.

Наивно-последовательны именно **fallback-движки** (`DotnetSearchEngine`, `WorkspaceSearchEngine`) —
они читают файлы по одному через `File.ReadAllLinesAsync`/`_ws.ReadAllLinesAsync` в `foreach`.
Но эти пути срабатывают только когда `rg` недоступен в PATH или workspace виртуальный
(не на диске) — то есть на практике редко. Решение: **сначала измерить**, как часто в проде вообще
идут в fallback (счётчик/лог), и только если это не единичные случаи — заводить ограниченный
`Parallel.ForEachAsync` с потолком степени параллелизма по файлам fallback-пути. Строить
параллелизм в редко исполняемый код вслепую — цена (сложность, конкурентный доступ к
результирующему списку) может не окупиться на объёме использования, который никто не измерил.

### 2.5 Рекурсивный листинг — параметр к существующему инструменту, не новый инструмент

Отдельный `tree_list_files` **не заводится**. Причина: в эту нишу уже смотрят два инструмента —
`system_list_files` (один уровень) и `system_find_files` (рекурсивно, но плоским списком путей).
Третий не помог бы слабой модели, которая уже не выбрала верный из двух: доктрина прямо называет
рвом курирование, а не количество. Ось глубины добавляется туда, чья работа и есть «покажи, что
здесь» — в `system_list_files`.

**Формат — отступы, как в Unix `tree`.** Псевдографика (`├── └──`) избыточна: лишние токены ради
красоты для человека. Отступ плюс `/` у каталогов однозначен и для модели, и для человека:

```
src/
  agent/
    SPLA.MCP.BasicTools/
      FileSystem/
        FsListTool.cs
```

Это же решает расход контекста: префикс пути не повторяется на каждой строке — он выражен отступом.
Плоский список полных путей — самый дорогой из возможных форматов.

**Параметры** (все опциональны, умолчания безопасны сами по себе):

| Параметр | Зачем |
|---|---|
| `max_depth` | глубина; главный предохранитель от взрыва |
| `pattern` | фильтр вида `**/*.html` |
| `per_dir_limit` | сколько записей показывать в каждой папке |
| `sort` | `name` / `size` / `modified` |
| `desc` | направление — «топ-3 самых больших» против «самых маленьких» |
| `total_limit` | общий потолок на весь ответ |

Голый вызов без единого параметра обязан давать разумный результат: глубина ограничена, общий
потолок включён по умолчанию.

**Обрезка обязана быть честной** — `… and 47 more in this directory`. Молча усечённое дерево модель
примет за полное и построит на нём неверный вывод; это хуже, чем отказ.

**Blob здесь — не тот рычаг.** Blob по своей идее
([`PLAN_20260625_core_data-channel`](../plans/PLAN_20260625_core_data-channel.md)) нужен, когда
объём идёт от инструмента к инструменту **мимо контекста модели**. А дерево запрашивают именно для
того, чтобы модель его прочитала — в этом вся задача ориентации; отправить его в blob значит не
решить исходную задачу. Правильный ответ на объём здесь — честная обрезка (`total_limit` + маркер
остатка), а blob остаётся редкой опцией для «сохранить список в файл». У `system_search_text`
ситуация обратная — там выгрузка результатов осмысленна, и blob уже есть.

### 2.6 `rg --files` как общий backend листинга

У `rg` есть режим `--files`: выдаёт список файлов, которые он **стал бы** искать, ничего не ища
внутри — с учётом `.gitignore`, глобов и детекта бинарников. Это готовый быстрый file lister.

Сверх скорости это даёт **согласованность**: сейчас листинг ходит через `ws.GetFiles`/
`GetDirectories`, а поиск — через `rg`, и два инструмента могут по-разному отвечать на вопрос
«какие тут вообще файлы» (один покажет содержимое `bin/`, другой отфильтрует). Один backend на оба —
и расхождение исчезает как класс.

Оговорки, чтобы не выглядело бесплатным:

- `--files` даёт плоский список — дерево с отступами строится нами поверх, это дёшево;
- размеров файлов он не даёт — сортировка по размеру требует своего `stat` по отобранным путям;
- собственный `--sort` у `rg` **отключает параллельный обход**, поэтому не используется: берём
  быструю несортированную выдачу и сортируем у себя;
- для виртуальной подложки — снова своя реализация, см. 2.0.

## 3. Последствия

**Получаем:**
- поиск текста реально не хуже базового grep — контекст, multiline, режимы вывода;
- три движка вместо трёх → два, разделённые по существу (подложка), а не по случайности окружения;
- одна семантика регулярок на обеих подложках плюс исчезнувший класс отказа по времени;
- меньше молчаливых провалов — видимая причина ухода в fallback, реально работающий игнор-глоб,
  заметка о деградации вместо тишины;
- бинарник не подхватывается из PATH — вектор перехвата закрыт;
- один вызов вместо серии для ориентации в структуре проекта — прямая экономия ходов слабой модели;
- листинг и поиск отвечают одинаково на вопрос «какие тут файлы»;
- описание инструмента учит модель *когда* его выбрать, а не только что он умеет внутри.

**Чем платим:**
- **каждая возможность пишется дважды** — флагами `rg` и руками поверх `IWorkspace`; это главная
  постоянная цена решения и одновременно тормоз против расползания параметров;
- `NonBacktracking` отнимает у пользователя виртуальной подложки lookaround и обратные ссылки,
  которых на дисковой подложке и так не было — выравнивание вниз, сознательное;
- `DetailsText` `system_search_text` вырастет — держать в рамках, не превращать в трактат
  (`agents/sys_prompt_rules.md`);
- шесть опциональных параметров на листинге — близко к порогу, за которым слабая модель начинает
  ошибаться; удержано только тем, что умолчания безопасны и голый вызов осмыслен;
- поставка `rg` добавляет в дистрибутив внешний бинарник со своим циклом обновления;
- параллелизация fallback-движка осознанно не решена этим ADR — если измерение покажет, что он
  используется часто, это отдельное решение, не тихая дописка;
- ранний выход движка на `files_with_matches`/`count` меняет внутреннее поведение сбора
  результатов — переписывать аккуратно, чтобы не сломать ранжирование режима `content`.

---

## 4. Отвергнутые варианты

- **Своя реализация поиска как основной путь.** Это переписывание `rg` силами проекта с совсем
  другой целью: SIMD-поиск литералов, конечно-автоматные регулярки, `.gitignore`, кодировки, циклы
  симлинков — десятки закрытых крайних случаев, которые пришлось бы закрывать заново. Свой движок
  остаётся, но по необходимости подложки, а не как замена.
- **Отдельный инструмент `tree_list_files`.** Третий инструмент в нишу, где уже два; модель,
  не выбравшая верный из двух, из трёх не выберет лучше. Ось глубины — параметром к тому, чья это
  работа.
- **Blob как основной ответ на объём дерева.** Не решает задачу: дерево запрашивают, чтобы модель
  его прочитала. Ответ — честная обрезка.
- **Псевдографика `├── └──` в дереве.** Лишние токены ради вида; отступ однозначен.
- **`rg --sort` для сортировки листинга.** Отключает параллельный обход — теряем ровно то, ради
  чего берём `rg`. Сортируем у себя.
- **Семантический/embedding-поиск по смыслу задачи.** Противоречит доктрине «тонкий
  детерминированный инструмент, не непредсказуемый general-purpose поиск» — тот же довод, что уже
  закрыл [`IDEA_20260813-2_core_digest-tool`](../ideas/IDEA_20260813-2_core_digest-tool.md).
- **Стандарт тегов/ссылок для навигации по `docs/`.** Отдельная задача (граф документов, не
  граф файловой системы) — вне области этого ADR.
- **Называть конкретные конкурирующие инструменты в описании `system_search_text`.** Отклонено —
  формулировка верна только для одного корпуса с файлом `by-symbol.md`; в общем случае это привязка
  к формату конкретного смонтированного справочника, а не общее свойство задачи поиска.
