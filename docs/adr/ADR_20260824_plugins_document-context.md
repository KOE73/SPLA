# ADR_20260824_plugins — семантика документа: контекст против артефакта, и кто её достаёт

Статус: **принято**

Опирается на [`IDEA_20260824_plugins_document-context`](../ideas/IDEA_20260824_plugins_document-context.md)
(разбор вариантов и лицензий) и на уже построенное в
[`PLAN_20260820_core_unified-uri-resources`](../plans/PLAN_20260820_core_unified-uri-resources.md):
`IFormatConverter` + `FormatConverterRegistry` в ядре.

> В контексте **практической задачи «прочитать DOCX → понять → положить строки в Excel»**,
> столкнувшись с тем, что **соблазн решить её одним инструментом `docx → markdown` встраивает в
> фундамент случайный промежуточный формат и смешивает два несовместимых класса работы с
> документом**, мы решили **разделить работу с документом на «содержание» (Context/Data) и
> «артефакт» (Artifact/Layout), реализовать в V1 только первый класс, а извлечение оформить как
> обычный плагин SPLA, регистрирующий пары преобразований в уже существующий
> `FormatConverterRegistry`**, чтобы **ядро не узнало ни одного формата документа, а бэкенды
> (native / pandoc / коммерческие) заменялись без правки ядра**, приняв **отказ от единого дерева
> ContextDocument в ядре, от композиции преобразований и от сохранения оформления в V1**.

---

## 1. Контекст

Бытовая задача: из служебного `.docx` вытащить смысл и дописать строку в реестр `.xlsx`. Прямое
решение — инструмент «конвертируй docx в markdown» — плохо ровно в двух местах.

**Markdown — не абстракция, а один из выводов.** Если фундаментом сделать `docx → md`, то JSON,
plain text, чанки для эмбеддингов и построчная выборка таблиц будут получаться разбором markdown,
то есть разбором уже потерявшего структуру текста.

**«Работа с документом» — это два разных класса.** Прочитать заявку (нужны заголовки, абзацы,
списки, таблицы; не нужны шрифты и координаты) и отредактировать шаблон, сохранив оформление,
формулы и объединения — задачи с разными контрактами. Общий API для них — это API, где половина
аргументов всегда пустая.

**Фундамент под преобразования в ядре уже есть.** `IFormatConverter` (одна пара source→target, один
хоп, без композиции) и `FormatConverterRegistry` (встреча хоста и плагина через
`ResolvedSettings.SharedServices`) написаны и покрыты тестами; `resource_read` умеет `as: <mime>`.
Ничего нового в ядре для этой задачи заводить не требуется — требуется поставщик пар.

## 2. Принятые решения

| Решение | Обоснование |
|---|---|
| **Два класса разведены явно**: `Context/Data` (смысл) и `Artifact/Layout` (файл как оформление). V1 делает только первый | Смешение — это API, у которого нет честного описания: «прочитай смысл» и «сохрани печатную область» не разделяют ни аргументы, ни риски, ни цену ошибки |
| Контракт преобразования — **существующий `IFormatConverter`**, новых контрактов в ядре нет | Пара `application/vnd...wordprocessingml.document → text/markdown` — обычная строка реестра. Второй контракт рядом означал бы два места, где написано «что во что превращается» |
| **Динамическая загрузка = штатный механизм плагинов** (каталог + `meta.yaml` + свой `AssemblyLoadContext`), а не второй сканер «dll преобразований» | Механизм уже делает ровно требуемое: изоляцию зависимостей (OpenXML/ClosedXML не встречаются с хостом), обнаружение по каталогу, включение/выключение в `.spla`. Второй сканер — второй жизненный цикл, второй список ошибок загрузки и второе место, где чинить |
| Один бэкенд — **один плагин**: `documents` (native, V1), позже `documents_pandoc`, `documents_aspose` | Ровно то, что в идее названо «монолитный plugin»: SPLA видит имя, внутренности (OpenXML, ClosedXML, pandoc.exe) — деталь бэкенда |
| **Семантическая модель `ContextDocument` живёт вне ядра** — в `SPLA.Documents.Model`, который бэкенды подключают ссылкой | Ядро читает ярлык (MIME), а не содержимое; это записано в `IResourceProvider`/`ResourceContent`. Дерево блоков в `SPLA.Domain` втащило бы туда знание про заголовки Word |
| Между плагином и ядром **пересекают границу только байты + MIME**, тип `ContextDocument` не пересекает ALC никогда | Поэтому модель НЕ нужно вносить в `PluginLoadContext.SharedAssemblies`: у каждого бэкенда своя копия, и это безопасно ровно потому, что экземпляр никому не передаётся |
| Рендереры (`markdown`, `plain`, `json`) — часть модели, а не бэкенда | Иначе два бэкенда дадут два разных markdown из одного и того же дерева, и «сменить провайдера» перестанет быть безболезненным |
| Плагин отдаёт **и пары в реестр, и собственные инструменты** | Пары включают `resource_read as=...`, но он под флагом `agent.unified_resources` (по умолчанию выключен). Инструмент работает всегда — задача не должна зависеть от экспериментального переключателя |
| Работа с таблицей — **по заголовкам колонок** (`spreadsheet_*`), не по адресам ячеек | Модель оперирует «Дата/Организация/Сумма», а не `B27`. Это и есть тот перенос рассуждения в инструмент, ради которого инструменты здесь пишутся |
| Запись в `.xlsx` (ClosedXML) и в `.csv` (нативно) — **один инструмент, два хранилища**, различаемые по расширению | Для модели это одна операция «дописать строки»; выбор формата — свойство файла, а не отдельный навык |
| Домены имён — `document_*` и `spreadsheet_*`, а не `documents_*` по id плагина | `agents/plugins.md`: префикс — функциональный домен, а не папка плагина |
| Библиотека V1: **Open XML SDK** (MIT) для DOCX, **ClosedXML** (MIT) для XLSX | Обе in-process, кроссплатформенные, коммерчески пригодные; PDF/PPTX отложены осознанно, не забыты |

## 3. Отвергнуто

**`ConvertToMarkdown` как фундамент.** Превращает случайно выбранный промежуточный формат в
контракт: любой другой вывод (JSON, чанки, строки таблицы) пришлось бы получать разбором markdown.

**`ContextDocument` в `SPLA.Domain`.** Ядро тогда обязано знать, что бывает заголовок уровня 3 и
объединённая ячейка. Граница «ядро читает ярлык, не содержимое» — то единственное, что не пускает
в фундамент половину распаковщика OOXML.

**Свой сканер каталога `formats/` с загрузкой dll.** Дал бы второй механизм с той же семантикой,
что и плагины, но со своим списком ошибок, своим включением/выключением и своей изоляцией.
Экономия при этом нулевая: плагинный загрузчик уже умеет всё требуемое.

**Pandoc как V1.** Семантика у него лучше готовой, но: GPL-2.0-or-later, внешний exe, PDF на вход
не читает, Excel не его задача. Как отдельный провайдер — уместен; как единственный вход в фичу —
нет.

**Apache Tika как V1.** Покрытие форматов лучшее в классе, но требует внешнего Java-рантайма;
это другой класс поставки, а не более крупная версия текущей.

**Aspose / Syncfusion как обязательная зависимость.** Коммерческая лицензия (и лимит выручки у
Community-варианта Syncfusion) — не то, что можно зашить в фундамент продукта, у которого могут
появиться крупные потребители. Как заменяемый провайдер — нормально.

**Композиция преобразований (`docx → html → md`).** Запрещена самим `IFormatConverter`, и запрет
здесь не ослабляется: цепочка, если понадобится, пишется отдельным конвертером и регистрируется
своей парой.

**Сохранение оформления в V1** (шрифты, цвета, объединения, печатные области). Это класс
`Artifact/Layout`; для него понадобится свой набор инструментов и, возможно, прямой OpenXML.

## 4. Открытые вопросы (не решаются этим ADR)

1. **Два провайдера на одну пару.** `FormatConverterRegistry.Register` бросает при разных
   реализациях на одной паре — это защита от зависимости ответа от порядка загрузки. Установленные
   рядом `documents` и `documents_aspose` дадут падение на старте. Нужна политика предпочтения
   (список приоритетов в `.spla` либо явное отключение плагина). До появления второго бэкенда
   решать вслепую нечего.
2. **Плагин без инструментов.** `PluginManager.LoadEnabledPlugin` считает «не отдал ни одного
   инструмента» ошибкой загрузки, так что пакет, регистрирующий только конвертеры, будет помечен
   как сломанный. Сегодня не мешает (плагин отдаёт инструменты), но это ровно та форма, в которой
   захочется поставлять чистый пакет преобразований.
3. **PDF.** `PdfPig` даёт координаты, а не структуру; восстановление заголовков и таблиц —
   эвристика. Отдельная работа со своей ценой, не довесок к DOCX.
4. **`Artifact/Layout` API** — целиком впереди.

---

## 5. Последствия

- В ядре не меняется ничего. Появление плагина не влияет на проект, где он не установлен.
- При включённом `agent.unified_resources` в системном промпте автоматически появляется строка
  «docx → markdown» — её рисует существующий `ResourceSchemesContributor` по карточкам реестра.
- Смена бэкенда (native → pandoc → aspose) — операция уровня «положить другой каталог в
  `plugins/`», без правки ядра и без изменения имён инструментов.
