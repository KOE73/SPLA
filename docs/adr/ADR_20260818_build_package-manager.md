# ADR_20260818_build — пакетный менеджер: остаёмся на npm, pnpm отклонён по замеру

Статус: **принято**

> В контексте **шести отдельных npm-проектов в одном чекауте и многоагентной работы через
> `git worktree`**, столкнувшись с тем, что **записанное в доктрину решение перейти на pnpm не было
> выполнено ни в одном месте сборки**, мы решили **остаться на npm и зафиксировать отказ вместе с
> замером**, чтобы **вопрос не всплывал в третий раз как смутное «надо бы»**, приняв **дублирование
> `node_modules` между worktree'ами как осознанную плату**.

---

## 1. Контекст

Обнаружено при настройке GitHub Actions: workflow надо было написать под конкретный пакетный
менеджер, и `agents/structure.md` утверждал —

> Package manager is `pnpm` (not `npm`) — its content-addressable store dedupes `node_modules`
> across the worktrees the multi-agent workflow above produces.

Утверждение в настоящем времени, как о состоявшемся факте. Проверка показала, что в реальности
pnpm не используется **нигде**:

| Где | Что на самом деле |
|---|---|
| Лок-файлы | 6 × `package-lock.json`, ни одного `pnpm-lock.yaml` |
| `PublishAll.ps1` | `npm --prefix web install` / `run build` |
| `SPLA.Service.csproj` | `Exec` → `npm install`, `npm run build` |
| `SPLA.Editor.Schema.csproj` | 4 × `Exec` → `npm install` / `npm run build` (два веб-дерева) |
| Машина владельца | `pnpm` не установлен вообще |

Шесть npm-проектов: `web/`, `src/editor/SPLA.Editor.Schema/web/` и `.../web-text/`, плюс веб-части
плагинов OneC, Sql, Ssh.

Исходный аргумент за pnpm верен по механике. npm кладёт в `node_modules` каждого проекта
**физические копии** пакетов; pnpm держит один склад на машине и раскладывает **хардлинки**, поэтому
второй worktree стоит почти ноль вместо ещё одного полного дерева. В этом репозитории аргумент даже
сильнее, чем в исходной формулировке: дублирование идёт не только между worktree'ами, но и между
шестью деревьями **внутри одного** чекаута — 28 из 77 пакетов `web/` встречаются ещё и в дереве
редактора.

Вопрос был не «правда ли pnpm экономит», а «стоит ли эта экономия своей цены». Это решается
замером, а не рассуждением.

---

## 2. Замер

Машина владельца, 2026-08-18. Скопированы `package.json` и `package-lock.json` из `web/` во
временную папку на `C:` — это ровно сценарий «появился новый worktree».

| Что мерили | Результат |
|---|---|
| Кэш npm | есть: `C:\Users\koe\AppData\Local\npm-cache`, 1.6 ГБ |
| `npm ci` из тёплого кэша | **3.4 с**, 131 пакет, 124 МБ на диске |
| `npm ci --offline` (сеть запрещена принудительно) | **5.3 с** — отработало, значит установка идёт из кэша, а не из сети |
| Три установленных дерева суммарно | 272 МБ (134 + 76 + 62) |

Ключевое здесь — вторая и третья строки. Кэш npm общий на машину и уже прогрет, поэтому новый
worktree не качает ничего; он распаковывает локальное. Полный чистый чекаут — это примерно двадцать
секунд на все шесть деревьев.

---

## 3. Принятые решения

| Решение | Обоснование |
|---|---|
| Пакетный менеджер — `npm`, во всех шести проектах | Уже так; менять не на что ради трёх секунд |
| Лок-файлы `package-lock.json` коммитятся, CI ставит через `npm ci` | `ci` уважает лок-файл буквально, в отличие от `install` |
| pnpm отклонён, отказ записан здесь | Идея верная по механике и проигравшая по цене — такое обязано быть записано, иначе вернётся |
| `agents/structure.md` говорит про npm и ссылается сюда | Доктрина описывает состояние, а не намерение (см. §6) |

---

## 4. Последствия

**Что получаем.**

- Ноль новых обязательных зависимостей: собрать проект по-прежнему достаточно .NET SDK и Node.
- Плоский `node_modules`, к которому весь стек привык, — никаких сюрпризов от строгой раскладки.
- Шесть лок-файлов остаются как есть; ни один не пересоздаётся, ни одна версия не сдвигается.
- CI пишется один раз и не переписывается.

**Чем платим.**

- Каждый worktree несёт свои полные `node_modules` — порядка 272 МБ при трёх установленных деревьях.
- Дублирование внутри чекаута сохраняется: 28 из 77 пакетов `web/` лежат вторым экземпляром у
  редактора.
- Экономия pnpm остаётся невзятой; если worktree'ов однажды станет много, платить придётся линейно.

**Что теперь нельзя.**

- Нельзя вводить pnpm в одном месте: он либо во всех шести проектах, `PublishAll.ps1`, обоих
  `csproj` и обоих workflow, либо нигде. Половинчатый переезд даст два несовместимых лок-формата.
- Нельзя записывать в доктрину намерение формулировкой настоящего времени (см. §6).

---

## 5. Чего это не обещает

- **Это не «pnpm плохой».** Механика pnpm делает ровно то, что заявлено; отклонён размен, а не
  инструмент.
- **Решение не вечное.** Оно опирается на замер при одном worktree и прогретом кэше. Условие
  пересмотра названо явно в §7.
- **Не говорит ничего про CI.** Там выигрыша от pnpm нет в любом случае: раннер каждый раз чистый, а
  `actions/setup-node` кеширует загрузки сам.
- **Не отменяет дублирования.** 272 МБ никуда не делись — они признаны терпимыми, а не устранены.

---

## 6. Почему запись понадобилась: намерение, записанное как факт

Дефект здесь не в выборе менеджера, а в том, как решение попало в документацию.

Фраза «Package manager is `pnpm` (not `npm`)» написана в настоящем времени, с обоснованием и с
уточнением в скобках — то есть **выглядит как описание состояния**. Ни одной пометки «планируется»,
«не внедрено», «ветка такая-то». Проверить её никто не догадался, потому что описания состояния не
проверяют, их читают.

Так план становится фантомным фактом. Дальше он опасен ровно тем, что на него опираются: следующий,
кто настраивает сборку, напишет `pnpm install` — и обнаружит, что лок-файла нет, а в `csproj` зашит
`npm`. Здесь это едва не случилось при настройке CI, и заметили только потому, что понадобилось
выбрать конкретную команду для workflow.

Правило, которое дороже самого выбора менеджера: **`agents/` описывает то, что есть.** Намерение
живёт в `docs/ideas` или `docs/plans` — там настоящее время читается как замысел, а не как
инвентаризация. Это тот же класс ошибки, что и в
[`ADR_20260813_build_branch-stamp`](ADR_20260813_build_branch-stamp.md) §7, только там решение
потеряло обоснование, а здесь — необоснованно обрело статус выполненного.

---

## 7. Когда вернуться к вопросу

Не «когда надоест», а по признаку:

- держится **три и больше worktree одновременно** как обычный режим, а не разовая ситуация, **и**
- переустановка деревьев в новом worktree начинает ощущаться как задержка, а не как пауза, **или**
- появляется общий монорепо-инструмент (workspaces), где pnpm решает уже не дисковое место, а
  связность проектов между собой.

Первый признак — единственный, который делает нынешний замер неактуальным: 3.4 с × 6 деревьев × N
worktree растёт линейно, а 272 МБ × N растёт быстрее терпения. До тех пор ответ — npm.

---

## 8. Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Перейти на pnpm сейчас | Цена немедленная и фиксированная (новая зависимость на каждой машине, 6 пересозданных лок-файлов, 6 `Exec` в двух `csproj`, оба workflow), выгода — секунды и мегабайты при одном worktree |
| Оставить в доктрине «pnpm», доделать переезд потом | Это и есть исходная ошибка: запись, которая описывает несуществующее состояние, вводит в заблуждение ровно до тех пор, пока переезд не сделан |
| Просто заменить `pnpm` на `npm` в `structure.md` и забыть | Стирает чужое решение молча. Через полгода идея всплывёт снова — без замера и без причины отказа |
| pnpm только для `web/`, остальные на npm | Два лок-формата в одном репозитории; худшее из обоих миров |
| Убрать дубли, объединив шесть проектов в npm workspaces | Отдельное решение про структуру проектов, а не про менеджер; здесь не рассматривалось и этой записью не закрывается |
