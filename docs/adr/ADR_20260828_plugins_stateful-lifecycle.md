# ADR_20260828_plugins — плагины с состоянием и события жизненного цикла чата

Статус: **ОТКРЫТ (обсуждение)**  
Дата: 2026-08-28  
Связано: `windows-com-core` plugin (IDispatch-automation), `[[service-event-bus]]` (существующий механизм событий)

---

## 1. Контекст

### 1.1. Текущее состояние: плагины stateless

Все плагины в SPLA.Plugins сегодня **stateless** — ответили на tool_call, забыли, приватное состояние не держат. Это работает для большинства tool-плагинов (cmd, powershell, файловые операции).

### 1.2. Проблема: ресурсы требуют явного очищения

**windows-com-core** (и любой будущий плагин, работающий с системными ресурсами) должен иметь явный жизненный цикл:

- **Создание:** первый `com_connect(ProgID)` → регистрация объекта в таблице хоста
- **Жизнь:** хэндл `com:XXX` живёт в памяти хоста между tool_call'ами
- **Смерть:** когда чат закрывается → **ОБЯЗАТЕЛЬНО** вызвать `Release()` на каждом COM-объекте

**Без явного cleanup** → утечка ресурсов:
- SOLIDWORKS-процесс остаётся с висящими ссылками
- Счётчик AddRef не упадёт до нуля
- Процесс не завершится чистым способом
- При долгом лупе (~10+ туров) таблица разбухает

### 1.3. Почему это не решается на уровне тула

Плагин **не может** знать, когда чат закрывается — нет входного события:

```
Chat lifecycle:  Open → [Agent running] → Closed
                    ↓
Плагин:         tool_call → stateless response
                              ↑ ничего нет здесь
```

Плагин слышит только `tool_call`, не слышит lifecycle-событий самого чата.

## 2. Предложенное решение

### 2.1. Добавить ChatLifecycleEvent в сервис-шину

Параллель с существующим **ServiceEventBus** (для appearance-событий):

```csharp
public enum ChatLifecycleEventType
{
    Open,           // Чат создан, агент начинает первый тур
    Close,          // Чат завершен, ресурсы об омимаютс всеми плагинами
    Suspend,        // (будущее) чат заморожен, например на переключение окна
    Resume,         // (будущее) чат разморожен
}

public class ChatLifecycleEvent
{
    public string ChatId { get; set; }
    public ChatLifecycleEventType Type { get; set; }
    public DateTime Timestamp { get; set; }
}
```

### 2.2. Плагин подписывается на события

```csharp
public interface IStatefulPlugin : IPlugin
{
    void OnChatLifecycleEvent(ChatLifecycleEvent evt);
}

// Реализация в windows-com-core
public class ComCorePlugin : IStatefulPlugin
{
    private Dictionary<string, ComSession> _chatSessions = new();

    public void OnChatLifecycleEvent(ChatLifecycleEvent evt)
    {
        switch (evt.Type)
        {
            case ChatLifecycleEventType.Open:
                // Инициализировать пул хэндлов для этого чата
                _chatSessions[evt.ChatId] = new ComSession();
                break;

            case ChatLifecycleEventType.Close:
                // ОБЯЗАТЕЛЬНО очистить все ручки этого чата
                if (_chatSessions.TryGetValue(evt.ChatId, out var session))
                {
                    session.ReleaseAll(); // Перебрать все com:XXX → Release()
                    _chatSessions.Remove(evt.ChatId);
                }
                break;
        }
    }
}

// ComSession держит таблицу per-chat хэндлов
public class ComSession
{
    private Dictionary<string, IComHandle> _handles = new();

    public void ReleaseAll()
    {
        foreach (var (handleId, handle) in _handles)
        {
            handle.Release();  // DisposeComObject, DecRef, и т.д.
        }
        _handles.Clear();
    }
}
```

### 2.3. Жизненный цикл хэндла из перспективы плагина

```
com_connect("SldWorks.Application")
    ↓
[CreateInstance в SOLDIWORKS]
    ↓
Плагин регистрирует в _chatSessions[chatId]["com:swapp"] = ISldWorks*
    ↓
[несколько туров, tool_call'ы используют com:swapp]
    ↓
OnChatLifecycleEvent(Close, chatId)
    ↓
Плагин вызывает Release() на com:swapp
    ↓
[Счётчик AddRef SOLIDWORKS упал на 1]
    ↓
SOLIDWORKS завершает документ чисто
```

## 3. Открытые вопросы

### 3.1. Когда стрелять OnChatOpen?

**Вариант A:** сразу при `ChatRuntime.Create` (до первого tool_call)
- **Плюс:** плагин может заранее инициализировать ресурсы
- **Минус:** если чат не вызовет плагин, впустую инициализировали

**Вариант B:** лениво — при первом tool_call для этого плагина
- **Плюс:** no waste инициализации
- **Минус:** плагин не может заранее подготовиться, логика сложнее

**Предварительно:** кажется, A проще и правильнее. Плагин сам решает в `OnChatOpen`, инициализировать ли (для stateless плагинов это no-op).

### 3.2. OnChatClose синхронна или асинхронна?

**Вариант A:** синхронна (плагин отработает до того, как чат удалится из памяти)
- **Плюс:** гарантия, что resource очищен перед `ChatRuntime.Dispose`
- **Минус:** блокирует закрытие чата, если плагин долго чистится

**Вариант B:** асинхронна (запустить cleanup фоном)
- **Плюс:** быстрое закрытие UI
- **Минус:** resource может остаться висеть, если процесс упадёт

**Предварительно:** A (синхронна). COM cleanup обычно быстрая (Release это просто DecRef), а гарантия критична.

### 3.3. Трансляция события кому?

**Вариант A:** только IStatefulPlugin'ам (которые реализуют интерфейс)
- **Плюс:** ясная контрактность
- **Минус:** нужен регистр плагинов, которые это поддерживают

**Вариант B:** broadcast всем плагинам через ServiceEventBus (как appearance-события)
- **Плюс:** один механизм для всех событий
- **Минус:** stateless плагины будут получать события, которые их не касаются (но могут игнорировать)

**Предварительно:** B (broadcast). ServiceEventBus уже есть, ему всё равно, что подписывается. Плагины фильтруют сами через if-проверку.

### 3.4. Жизненный цикл в multi-user (server mode)?

В режиме сервера за `spla serve` может быть несколько пользователей, каждый со своим чатом.

**Вопрос:** должны ли перекрываться com-сессии между пользователями или полностью разделены?

**Контекст:** SOLIDWORKS это GUI-приложение, обычно одно на машину (STA). Если два юзера одновременно пытаются рисовать кубики → конфликт.

**Предварительно:** это вопрос для режима сервера. В desktop mode (один юзер) — нет проблемы. На этапе планирования документировать ограничение: «windows-com-core работает только в exclusive режиме или требует per-user SOLIDWORKS instance».

## 4. Архитектурный эффект

### 4.1. На плагины

```
Было:              tool_call → tool_response (stateless)

Становится:        OnChatOpen (инициализация)
                        ↓
                   [несколько tool_call'ов]
                        ↓
                   OnChatClose (cleanup)
```

Плагин может теперь:
- Держать состояние per-chat (таблица ручек, конфигурация, рабочая папка)
- Гарантировать cleanup в конце
- Откатываться к `OnChatClose` если вдруг перезагрузился хост

### 4.2. На сервис-шину

ServiceEventBus расширяется ещё одним типом события (`ChatLifecycleEvent`). Остальное не меняется.

### 4.3. На инструменты

Инструменты вроде `com_invoke`, `com_release` **НЕ меняются**. Они по-прежнему работают как tool_call'ы. Просто теперь плагин знает, когда надо вычистить за собой.

## 6. Риски и ловушки

### 6.1. Deadlock в OnChatClose

Если инструмент `com_release` будет вызван ещё из плагина ВО ВРЕМЯ OnChatClose, а сам tool_call попробует дождаться ответа от ChatRuntime, который удаляется, может быть deadlock.

**Смитигация:** в Фазе 1 написать гарант, что `OnChatLifecycleEvent` вызывается **вне основного цикла хода** (после всех tool_call'ов завершены).

### 6.2. Обвал при исключении в OnChatClose

Если плагин выбросит исключение в `OnChatClose`, другие плагины не получат событие.

**Смитигация:** ServiceEventBus оборачивает handler'ы в try-catch, логирует и продолжает.

### 6.3. Ресурс не освободится, если плагин упадёт

Если плагин зарегистрировался для OnChatClose, но сам процесс упадёт до вызова, ресурс оставит висеть.

**Это нормально?** Зависит. Если SOLIDWORKS живёт отдельным процессом, он сам очистится при перезагрузке. Если это in-proc — проблема.

**Решение:** документировать, что stateful плагины **должны быть готовы к dirty shutdown** (например, используя файл lock'ов для восстановления состояния при перезагрузке).

## 7. Альтернативы (рассмотрены и отклонены)

### 7.A. Плагин сам следит за временем жизни через таймер

**Идея:** `com_connect` запускает таймер, и после N минут отсутствия tool_call'ов автоматически Release'ит.

**Почему нет:** 
- Есть вероятность ложного cleanup (юзер думает, ещё работает)
- Не решает случай, когда чат закрывается сразу
- Усложняет логику плагина

### 7.B. Плагины регистрируют финализаторы через GC

**Идея:** `com_connect` регистрирует finalizer, который вызовет Release при GC.

**Почему нет:**
- GC недетерминирован (может быть задержка)
- Не гарантирует cleanup до shutdown приложения
- Оставляет ресурсы висящими неопределённое время
