# ADR_20260909_core — у картинки есть имя

Статус: **принято и реализовано** (2026-09-09). Ветка: `work`.

Смежное: [`README_CLI.ru.md`](../README_CLI.ru.md) (`chat run --image`, `--image-name`).

---

## 1. Что случилось

В `spla chat run` появился `--image`: несколько картинок на один ход, задаются путями. Первый же
замер на живой модели (`qwen3.8-27b`) дал странное:

```
Вопрос:  Сколько картинок приложено? Опиши каждую одной строкой, по порядку.
Ответ:   Приложена 1 картинка.
```

Картинок было две. На диск в `chat-images/` легли обе, в `image_bytes` — ровно сумма двух файлов,
в массиве `content` — два блока `image_url`. То есть отправлено было две, а модель отвечала как про
одну и описывала слитый образ.

Сначала это списали на провайдера: «сервер склеивает вложения». Проверка документации Anthropic по
vision показала, что дело не в провайдере, а в том, чего мы не отправили.

## 2. Почему так вышло

**У картинки нет имени ни в одном API.** Ни в `image_url`-частях, на которых говорим мы, ни в
`image`-блоках Anthropic: там едут байты и media type, и всё. Имя файла не передаётся никогда — даже
через Files API, где `file_id` это непрозрачный идентификатор, а не подпись. Метаданные самой
картинки тоже не читаются («does not parse or receive any metadata from images»).

Значит, при нескольких картинках в сообщении **единственное, что их различает, — порядок**. На двух
это ещё держится, на десяти кадрах одной камеры — нет: модели нечем сказать «третий», а нам нечем
проверить, про какой она ответила.

Anthropic решает это не полем в протоколе, а формой сообщения — и говорит об этом прямо:

> When sending several images, introduce each one with a short text label (`Image 1:`, `Image 2:`,
> and so on) so you can refer to them by name in your prompt and in follow-up turns.

То есть подпись пишется **отдельным текстовым куском прямо перед картинкой**. Другого способа нет
ни у кого — ни у Anthropic, ни в OpenAI-совместимом мире. Это не обходной путь, это интерфейс.

## 3. Решение

**Имя — свойство вложения, а не украшение вызова.**

```csharp
public sealed record ImageAttachment(string Url, string? Label = null);
```

`ChatMessage.Images` из `List<string>` стал `List<ImageAttachment>`. Из этого следует остальное:

1. **На проводе** (`OpenAiCompatibleClient.BuildMultimodalContent`) сообщение раскладывается как
   `имя → картинка → имя → картинка → … → текст промпта`. Текст ушёл в конец: картинка перед
   вопросом читается моделью лучше, чем после (та же дока), а без имён порядок частей ровно тот же,
   что был, — старое поведение не изменилось.
2. **В файле чата** имя лежит рядом с файлом-сайдкаром. Формат вырос формой, а не заменился:
   безымянная картинка — это по-прежнему `- name.png`, именованная — `- {file: name.png, label: …}`
   (`ChatSessionImageConverter`). Ни один существующий чат не переписывается.
3. **При переоткрытии** картинки поднимаются с диска обратно в сообщение как data URL — не как
   `/chat-image/…`, который для провайдера ничего не значит. До этого переоткрытый чат просто терял
   картинки для модели; теперь он продолжается так, будто его не закрывали, и «Image 2» из ответа
   не теряет своего референта.
4. **Кто чем называет.** CLI — именем файла (`--image-name` переопределяет, всё или ничего);
   окно — именем брошенного файла (вставленный из буфера скриншот остаётся безымянным, называть
   `image.png` нечем); инструмент — своим именем и номером, если вернул несколько картинок.

## 4. Чем проверено

Тот же вопрос той же модели после правки:

```
Приложено 2 картинки:
1. ChatGPT_64x64.png — …
2. Gemini_64x64.png — …
```

Провайдер был ни при чём. `ImageAttachmentTests` держат обе границы: форму частей на проводе
(именованную и безымянную) и round-trip обоих форматов YAML, включая то, что старая форма
возвращается на диск старой.

## 5. Что осталось открытым

- **Наверху нет способа назвать вставленную картинку.** Окно берёт имя из файла или не берёт
  ничего; поля «как назвать» в композере нет. Появится, когда кто-то реально будет собирать партию
  кадров из окна, а не из CLI.
- **`spla chat fork` не копирует сайдкар-картинки** — это `ChatManager.DuplicateChat`, отдельный
  путь мимо `ChatRegistry.Fork`, который их копирует. Дефект старый, вскрылся при проверке
  совместимости; к именам отношения не имеет.
