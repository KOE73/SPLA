# ADR_20260908-2_core — размер результата инструмента: экран вместо ленты и бюджет на выходе

Статус: **принято и реализовано** (2026-09-08). Ветка: `work`.

Смежное: [`ADR_20260824-3_core_tool-call-pipeline`](ADR_20260824-3_core_tool-call-pipeline.md)
(ступень `Post` объявлена там и до сих пор пустовала),
[`ADR_20260715_plugins_ssh-live-session`](ADR_20260715_plugins_ssh-live-session.md),
[`PLAN_20260625_core_data-channel`](../plans/PLAN_20260625_core_data-channel.md).

---

## 1. Что случилось

`ssh_session_wait` с `timeout_seconds: 600` над `docker pull` девяти образов вернул **460 600
символов**. Ход собрался, ушёл на эндпойнт и был отклонён:

```
request (396067 tokens) exceeds the available context size (98304 tokens)
```

Ход умер. Модель результата не увидела; десять минут работы пропали; провайдер сообщил нам то, что
мы могли сказать себе сами.

Полезной информации в этих 460k — около двадцати строк. Всё остальное — один и тот же экран,
перерисованный тысячи раз.

## 2. Два разных дефекта под одним симптомом

Их нельзя чинить одним средством, и это главное наблюдение решения.

**Первый — врал источник.** `SshLiveSession` копил **поток байт** и вырезал из него ANSI
(`AnsiRx`). Но поток pty — это не стенограмма, а последовательность инструкций для рисования одного
прямоугольника. `docker pull` перерисовывает свой блок через `\r` и `ESC[nA`. Вырезая escape-коды,
мы удаляли ровно те инструкции, которые говорили «это заменяет то», и оставляли полезную нагрузку
каждого кадра. Отсюда в выводе `103.8MB/113.2MB48dd761b6bfe: Downloading` — два кадра, склеенных
без разделителя, потому что разделителем был управляющий код.

То есть чистка была **хуже, чем её отсутствие**: структура разрушена, объём не изменился.

**Второй — некому было решить.** Ни у кого в конвейере не было ни права, ни данных, чтобы сказать
«столько не влезет». Инструмент знает свой размер и не знает модели. Ход знает модель и не знает,
что происходит внутри вызова. Ошибка была обнаружена только провайдером — самым дорогим из
возможных наблюдателей.

## 3. Решение

| Решение | Основание |
|---|---|
| **Агентская ветка сессии читает ЭКРАН, а не ленту.** Введён `TerminalScreen` — частичный vt100: курсор, стирание, прокрутка, перенос строк | Escape-коды нужно **исполнять**, а не удалять. Тысяча перерисовок двадцати строк — это двадцать строк. Проверено тестом: миллион символов сырого потока даёт экран короче 200 символов |
| **Зрители остаются на сыром потоке.** Эмулятор стоит только на агентской ветке, `Distribute` не тронут | У человека на том конце настоящий терминал, который делает эту работу лучше. Второй эмулятор в пути мог бы только потерять точность — мышь, alt-screen, 24-битный цвет, всё, что наш класс спокойно игнорирует |
| **Строка «осела» не по `\n`, а когда ушла с экрана.** Только осевшие строки двигают курсор читателя; живой кадр отдаётся заново каждый раз | Это единственный момент, когда строка перестаёт меняться, — то есть единственное честное определение «нового вывода». Повтор живого кадра не дублирование: строка жива именно потому, что ещё меняется |
| **Буферы ограничены:** 4000 строк отката на прогон, 8 КБ сырого окна на поиск маркера | Прежний `run.Raw` рос без границ — полмегабайта на сессию за десять минут. Маркер конца ищется по сырому окну, а не по экрану: маркер, затёртый перерисовкой, — это прогон, который никогда не завершится |
| **`until` матчится по экрану и только при новом выводе** | Шаблон, который видит человек, — тот, который должен срабатывать. Прежде каждые 100 мс пересобиралась и просматривалась вся накопленная строка: на длинной задаче — растущая копия 600 раз в минуту, плюс реальный риск `RegexMatchTimeoutException`, который ловился общим `catch` и превращался в «session error» |
| **Обрезка результата — на ступени `Post` (650), не в инструменте** | Инструмент не может это решить **по существу**, а не по неудобству: он не знает ни модели, ни окна, ни занятости, и один и тот же инструмент обслуживает чат на 8k и чат на 200k. Лимит в символах, назначенный внутри инструмента, — число, придуманное не в том месте: мал — выбрасывает поместившиеся ответы, велик — не предотвращает отказ |
| **Бюджет — способность чата (`IContextBudgetHost`), рядом с `Background` и `Correspondence`** | Тот же приём, что уже принят: `ChatRuntime` реализует интерфейс сам и кладёт себя в `AgentSession`. У прогона без чата (CLI, подагент, тест) способности нет — и это правильный ответ, а не пробел |
| **Режем ВСЕГДА по стоячему потолку (`CeilingChars`); бюджет может только опустить его, никогда поднять** | См. §3.1 — это решение заменило первоначальное «решает бюджет», и заменило по двум независимым причинам |
| **Обе цифры бюджета измеренные, не оценённые:** окно от провайдера, занятость — `prompt_tokens` предыдущего вызова | Оценка, которая **ужесточает**, допустима; оценка, которая **ослабляет**, — нет. Поэтому бюджет и работает только в одну сторону |
| **Не влезло → хвост остаётся, целое уходит в блоб, модели сказано и то и другое — БЕЗ заказа** | Флаг `output='blob'` тут не помогает принципиально: к моменту, когда стало известно, что вывод велик, вызов, который нёс бы флаг, уже состоялся. Курица и яйцо |
| **Хвост, а не голова: 80% оставленного — с конца** | Вывод инструмента хронологичен, вывод — внизу: код возврата, ошибка, итоговая строка. Голова нужна только чтобы сказать, что делали |
| **Блоб — по требованию, кроме случая «не влезло»** | Всегда писать полный вывод в блоб — платить диском за мусор, который в 99% случаев никто не откроет. Прецедент уже есть: `WebFetchTool` кладёт 8000 символов и приписку «use output='blob'» |
| **`blob_grep` — не украшение, а вторая половина решения** | Обрезка говорит модели «остальное в blob:…». Это утверждение истинно, только если до остального можно добраться. `blob_peek` умеет окно в 2 КБ по смещению — чтобы найти строку в полумегабайтном логе, читателю пришлось бы угадать её место 250 раз. **Хранилище, которое читается только вслепую, — могила**, а обрезка с могилой на конце — вежливый способ выбросить данные |
| **Обрезка не меняет исход вызова** | Что случилось с вызовом и что случилось с его текстом — разные факты. Успешный вызов с длинным выводом остаётся успешным |
| **Результат, уже ушедший в канал данных (несёт `ToolResource`), не трогаем** | Инструмент сам договорился. Обрезать здесь значило бы обрезать сводку |

### 3.1. Почему потолок, а не расчёт — и почему это переписано

Первая редакция этого решения была обратной: всё решал бюджет, а неизвестный бюджет означал «отдаём
как есть и молимся». Её убили два независимых возражения, оба заданные вопросом, а не найденные
тестом.

**Первое: результат в круге не один.** Модель может объявить несколько `tool_calls` в ОДНОМ ответе
([`ConversationOrchestrator`](../../src/agent/SPLA.Agent/ConversationOrchestrator.cs) — `foreach (var
tc in response.ToolCalls)`), а ящик фоновых задач отдаёт накопившиеся результаты пачкой на границе
хода. Занятость же обновляется только по ответу модели. Значит все результаты пачки мерились об один
и тот же устаревший остаток, и каждому выдавалась доля от него: при пяти вызовах разрешено две с
половиной оставшихся ёмкости.

Это нельзя было починить учётом внутри звена, потому что лимит был **по своему устройству**
пер-результатным. Стоячий потолок такого режима отказа не имеет вовсе: ему всё равно, сколько было
результатов. Дыра закрылась не заплаткой, а тем, что её больше нет.

**Второе: «неизвестно» — это норма, а не край.** Прогон из CLI, подагент, первый ход любого чата —
везде бюджета нет. То есть безопасный на вид дефолт оказывался самым частым путём.

Отсюда перевёрнутая формулировка: **правило решает, бюджет только ужесточает.** Потолок — это
утверждение о том, сколько текста имеет смысл читать, а не о том, сколько случайно поместится;
поэтому он и не нуждается в знании модели. Ошибка «обрезали то, что влезло бы» стоит одного
`blob_grep`; ошибка «не обрезали» стоит хода.

### Числа и почему именно они

- `CharsPerToken = 2.0` — сознательно пессимистично. На английской прозе ближе к 4, но вывод
  инструментов — не проза: пути, hex-идентификаторы, JSON и кириллица токенизируются намного хуже,
  а тот самый docker-лог весил около 1.2. Две ошибки несимметричны: занизив, изредка обрежем то,
  что влезло бы; завысив — оставим ровно тот отказ, ради которого всё делается.
- `ShareOfRemaining = 0.5` — результат не единственное, что поедет в следующем запросе: там же
  ответ модели, остальные вызовы того же круга и место под то, что она напишет. Результат,
  занявший весь остаток, лишает модель возможности о нём высказаться.
- `CeilingChars = 60000` — **стоячее правило**, работает всегда. Примерно разворот книги: хватает на
  стек-трейс, на секцию ошибок в логе сборки, на листинг каталога — и это уже за той чертой, где
  дополнительный текст перестаёт отвечать на дополнительные вопросы. Не влезшее не потеряно, оно в
  одном `blob_grep`.
- `FloorChars = 4000` — пол для случая, когда бюджет опускает потолок: почти исчерпанное окно иначе
  свело бы результаты к нулю, а модель, которой ничего не показали, не поймёт даже, что пора
  уплотняться.
- `MaxAnswerChars = 20000` у `blob_grep` — поиск, способный вернуть весь блоб, это тот же потоп через
  другую дверь.

## 4. Отвергнуто

**Просто перестать вырезать ANSI.** Тогда в контекст поедет сырой поток с управляющими кодами —
объём тот же, читаемость хуже. Проблема не в чистке, а в том, что коды не исполняются.

**Жёсткий лимит символов внутри `ssh_session_wait`.** Чинит один инструмент из полусотни и ставит
число туда, где неизвестна ни одна из величин, от которых оно зависит. Ровно то, что ADR ступени
`Post` уже отверг фразой «фон не должен заводить свой порог размера рядом».

**Всегда писать полный вывод в блоб.** Дёшево реализуется — и это единственный аргумент за
(см. [[feedback-cheap-not-need]]). Логи docker-пула не нужны ни в каком виде; ценность появляется
только в другом кейсе — упавшая сборка, по которой нужен греп, — и её закрывает флаг.

**Отказывать в ходе, если результат распирает окно.** Рассматривалось как поведение ядра при
патологии. Оставлено на будущее и не сделано: пока обрезка справляется, отказ — это ход, потерянный
намеренно вместо хода, потерянного случайно. Разница невелика.

**Считать токены настоящим токенайзером вместо `chars/token`.** Точнее — и требует знать
токенайзер каждого провайдера, включая локальные модели, где он меняется с загруженной моделью.
Цена точности здесь выше пользы: решение бинарное («влезет / не влезет с запасом»), а не
арифметическое.

**Эмулятор на общей ветке, до `Distribute`.** Сломал бы зрителей, ради которых сырой поток и
существует.

## 5. Последствия

- Ступень `Post` перестала быть пустой. Первое звено на ней — `ResultBudgetStage`; правило «звено
  объявляет отношение к трём точкам» выполнено определением ступени, а не заново.
- У `IAgentSession` появилась четвёртая способность-с-возможным-`null`. Это уже узнаваемая форма
  (`Background`, `Correspondence`, теперь `ContextBudget`) — и повод при следующей проверить, не
  пора ли назвать эту форму явно.
- `ChatRuntime` теперь оборачивает `OnLlmTurn` хоста, чтобы записать занятость. Одна из немногих
  точек, где рантайм вмешивается в колбэки хоста; вмешательство прозрачное — хостовый обработчик
  вызывается следом.
- Вывод `ssh_session_wait` изменился наблюдаемо, и описание инструмента переписано под это: теперь
  он обещает «что показывает терминал», а не «весь новый вывод». Последний экран между вызовами
  выглядит знакомо — это те же строки с новыми числами, и модели про это сказано прямо.
- `TerminalScreen` намеренно неполон. `htop` через него отрисуется правдоподобно, но не верно. Это
  принятая граница: агенту незачем водить htop.

## 6. Открытые вопросы

1. **Порог `CharsPerToken` не измерен на живых провайдерах.** Взят с запасом по здравому смыслу.
   По правилу [[feedback-verify-against-live-providers]] — документация врала трижды подряд — это
   долг: нужен замер на реальных ответах, а не рассуждение.
2. ~~Занятость обновляется по ответу модели, а не по ходу вызовов.~~ **Снято** переходом к стоячему
   потолку — см. §3.1. Занятость по-прежнему устаревает внутри круга, но теперь она может только
   ужесточать, поэтому устаревание безвредно: худшее, что оно делает, — не ужесточает там, где могло
   бы.
3. **Обрезанное целое живёт в блобе до конца чата.** `BlobStore` in-memory и транзиентный. Для
   полумегабайтных логов это может оказаться заметным; выселение на диск в интерфейсе предусмотрено,
   реализации нет. С автоматической обрезкой блобов станет ощутимо больше, чем было, — это первый
   кандидат на проверку под нагрузкой.
5. **`blob_peek` не пересмотрен.** Окно 2 КБ по смещению остаётся; `blob_grep` покрыл главный
   сценарий, но «покажи хвост» до сих пор требует знать длину и считать смещение руками.
4. **Плагинам ступень `Post` так и не открыта.** ADR_20260824-3 обещал открыть её вместе с первой
   реализацией и обернуть плагинное звено защитой. Сделано ядровое звено; `UseFromPlugin` не
   написан — заказчика по-прежнему нет, а дверь без коридора этот проект уже один раз завёл.
