# ADR_20260805_agent — учёт филиалов: имя объявляется, доверие выдаётся

Статус: **принято**

Уточняет [ADR_20260804_agent](ADR_20260804_agent_skills-library.md) в трёх местах: приоритет списка
источников, перекрытие по id и `trust` как поле записи. Библиотечная модель в целом не пересматривается.

---

## Контекст

Библиотека получила фонд, каталог и библиотекаря, но **учёт филиалов** остался тем же, каким был до
метафоры: плоский список путей в `skills.sources`.

Проверка боем нашлась сразу — владелец захотел добавить в работающий проект ещё одну папку со
скилами. Оказалось, что для этого надо переписать весь список: `skills.sources` — единственная
настройка в репозитории, которая **заменяется целиком**, а не мержится. Соседи по тому же файлу
ведут себя иначе: `connections` мержатся по id, `toolsets` по ключу, `skills.items` по id.

Причина аномалии не в резолвере. У соединения есть имя, а у источника имени нет: id выводится из
пути постфактум в [`DirectorySkillSourceFactory.Describe()`](../../src/core/SPLA.Library/Sources/SkillSourceRegistry.cs)
— `skills/` значит `repo`, `.spla/skills` значит `local`. Мержить по ключу, которого не существует до
резолва пути, нечем; замена целиком — честное следствие этого, а не выбор. Комментарий «merging would
make an inherited source impossible to drop» описывает симптом как причину.

Из того же корня растут ещё три вещи, которые по отдельности выглядели мелочами.

**Перекрытие по id.** `SkillLibrary.Rebuild()` отдаёт id первому источнику, остальные помечает
`Superseded`. Для файлов в `/etc` над `/usr/share` это правильно, для библиотеки — нет. Две книги с
одинаковым названием от разных авторов есть нормальное состояние фонда; читатель смотрит на автора,
а не выбрасывает второе издание. Индустрия пришла к тому же через дорогую аварию: **dependency
confusion** возможна ровно потому, что пакет с одинаковым именем из двух фидов разрешался по
приоритету источника, а не по адресу.

**Доверие объявляет тот, кому доверяют.** `trust: trusted` может написать любой слой, включая
закоммиченный `.spla`. Сценарий целиком укладывается в один абзац: клонируем чужой репозиторий → его
`.spla` добавляет источник, указывающий на папку внутри этого же репозитория → и там же объявляет её
доверенной → тексты из чужого репозитория попадают в системный промпт. Метафора шкафа с книгами в
парке из прошлого ADR описывала риск верно, но механизм позволял шкафу самому повесить на себя
табличку «проверено библиотекой».

**Добавить папку негде.** Список живёт только в файлах настроек. Панель `Settings → Skills`
показывает источники и правит тумблеры отдельных скилов, но завести источник не может — а это и есть
самое частое действие. Секреты этот вопрос уже решили: у них есть хранилище, которое правится из UI и
не коммитится. У источников такого места нет.

---

## Решение

**Идентичность объявляется, а не выводится из местоположения; доверие выдаётся снаружи, а не
объявляется изнутри.**

Одной фразой по шаблону: в контексте растущего числа филиалов, столкнувшись с тем, что источник не
имеет имени и сам себе выдаёт аккредитацию, мы делаем источник именованной сущностью с внешним
грантом доверия, чтобы список можно было дополнять, а не переписывать, и чтобы чужой репозиторий не
мог назначить себя доверенным, приняв в уплату явное разрешение неоднозначных имён и второе место
хранения.

Всё остальное — следствия.

### Филиал получает имя

У записи появляется `id` — короткое слово, уникальное в пределах всей библиотеки. Путь перестаёт быть
идентичностью и становится обычным полем: `Describe()` остаётся, но только как фолбэк для записей без
`id`.

Как только у записи есть ключ, слои мержатся по нему — так же, как это делают `connections`,
`toolsets` и `skills.items`. Аномалия исчезает вместе с породившей её причиной, и три операции
получают очевидную форму:

| Операция | Как выражается | Почему так |
|---|---|---|
| **добавить** | новая запись в любом слое | ничего переписывать не надо — это и есть исходная задача |
| **удалить** | `enabled: false` | унаследованное **не удаляется**: выключенный филиал виден в панели, удалённый просто исчезает, и никто не помнит, был ли он |
| **очистить** | `skills.inherit_defaults: false` | явный флаг, а не побочный эффект того, что вы написали свой список |

`inherit_defaults` нужен не для удобства, а для развёртывания: администратору нужен белый список
(«только то, что я перечислил»), а не надежда, что он не забыл выключить лишнее.

Конвенциональные папки перестают быть отдельным механизмом. `repo`, `local`, `machine`, `builtin` —
просто встроенные записи с объявленными именами, каждая выключаемая поштучно. Специальная приписка
установочной папки в `SkillSourceRegistry.Build()` уходит: она существовала затем, чтобы проект,
переопределивший список, не потерял её молча, а при мерже по имени потерять молча уже нельзя — только
выключить явно.

Плагинные источники по-прежнему добавляются сами и в конфиге не описываются: их выключатель — тумблер
плагина, и второго быть не должно. Доверие им отдельно не выдаётся по той же причине — включив
плагин, вы уже доверили ему исполняемый код, что строго больше, чем его тексты.

### Адрес книги — филиал плюс номер

Перекрытие по id отменяется. Полный адрес скила — `источник:id`, оба издания живут в фонде
одновременно, `SkillState.Superseded` и механизм `claimed` удаляются.

Короткое имя продолжает работать, пока однозначно. При совпадении — **ошибка с перечислением
кандидатов**, а не молчаливый выбор: библиотекарь, который сам решает, какое из двух изданий вы имели
в виду, ошибётся однажды и незаметно.

Порядок списка при этом не исчезает, но меняет смысл: он больше не приоритет, а порядок отображения и
tie-break в ранжировании `skill_find`. Иерархия филиалов и МБА из прошлого ADR не затрагивается — она
про то, у кого спрашивать книгу, а не про то, чьё имя побеждает.

Трюк «положи файл с тем же id к себе — и почини поставочный скил» пропадает, и это осознанно. Замена
у него уже есть и она явная: `skills.items` с полным адресом, `builtin:foo → enabled: false`, рядом
своя книга под своим именем. Одно место, которое можно грепнуть, вместо правила разрешения, которое
надо знать.

### Доверие — грант, и он записывается там, где получатель писать не может

Два независимых правила.

**Потолок по слою.** Источник, объявленный в менее привилегированном слое, не может подняться выше
`untrusted` собственными силами. Порядок привилегий — по тому, кто может подменить содержимое слоя:

| Слой | Кто им владеет | Максимум, который он может объявить сам |
|---|---|---|
| проектный `.spla` | приезжает вместе с чужим репозиторием | `untrusted` |
| пользовательский / машинный | человек за машиной | `trusted` |
| политика развёртывания | администратор сервера | `trusted`, и он же задаёт потолок остальным |

**Грант хранится отдельно и адресуется путём.** Поднять источник до `trusted` может только запись в
пользовательском хранилище — та самая, которую делает подтверждение в UI. Ключ гранта — разрешённый
путь, а не `id`: переименовали папку — грант не поехал следом, и это правильное поведение, а не
неудобство.

Ровно этот принцип в проекте уже сформулирован, для другого объекта: *«ACL живёт рядом с хранилищем,
никогда внутри него»* ([`SecretAcl`](../../src/core/SPLA.Domain/Secrets/SecretAcl.cs)). Тот же
аргумент, другая сущность.

**`level` под потолок не попадает.** Две оси разделены до конца: уровень — про экономию контекста,
доверие — про безопасность. Поэтому уровень объявляет тот, кто владеет фондом, а доверие выдаёт тот,
кто рискует. Проект вправе сказать «мои скилы показывать только по запросу»; сказать «мои скилы
проверены» он не вправе.

### Два хранилища, одна модель

Резать надо не по «UI против сервера», а по **источнику полномочий**:

| | Предписанные | Выданные |
|---|---|---|
| Где | слои конфигурации (`defaults.yaml`, `.spla`) | пользовательское хранилище, по образцу `FileSecretStore` |
| Кому принадлежат | проекту, развёртыванию | человеку |
| Коммитятся | да | никогда |
| Правятся из UI | нет | да, это их работа |
| Меняются на ходу | нет | да |

Это **одна модель и два хранилища**, а не два механизма: у записи просто есть поле origin. Эффективный
набор — объединение, смерженное по `id`, где выданные идут последним (самым специфичным) слоем.
Панель показывает оба списка одним списком, помечая предписанные как нередактируемые — человеку важно
видеть весь фонд, а не ту его половину, которой он владеет.

### Сервер — та же модель, другой потолок

Пользовательский список на сервере не становится read-only. Есть `IIdentity` и персональные файловые
области; человек, добавляющий филиал в свою область, действует у себя.

Различается не право писать, а **потолок доверия**: на сервере выданное пользователем по умолчанию
`untrusted`, поднять выше может только политика администратора; локально человек сам себе
администратор, и подтверждения при добавлении достаточно. Плюс путь на сервере — серверный, поэтому
добавление проходит через тот же `ICapabilityGate`, что и любой другой доступ к файлам.

Зрелый образец этой раскладки — управляемый Chrome: `ExtensionInstallForcelist` ставит принудительно
и снять нельзя, личные расширения остаются личными, `ExtensionInstallBlocklist` даёт админу право
запретить и личное. Три списка, одна модель, разные полномочия.

### Схема конфига

```yaml
skills:
  inherit_defaults: true        # false = только объявленное здесь
  sources:
    - id: ops                   # имя объявлено; путь — просто поле
      type: directory
      path: D:\shared\ops-skills
      level: findable           # объявляет владелец фонда
      trust: untrusted          # проектный слой выше не поднимет
    - id: local
      enabled: false            # выключить унаследованное, не переписывая список
```

## Последствия

**Что получили**

- Папка добавляется одной записью в любом слое. Исходная задача закрыта, и закрыта не частным
  случаем.
- Список источников перестаёт быть аномалией: все именованные коллекции в настройках мержатся
  одинаково, и объяснять исключение больше не нужно.
- Потерять унаследованный филиал молча стало нельзя — только выключить, и это видно в панели.
- Чужой репозиторий не может назначить себя доверенным. Дыра закрыта правилом, а не бдительностью.
- Ошибки формы dependency confusion становятся невыразимыми: имя без филиала либо однозначно, либо
  это ошибка.
- Появляется место, куда UI пишет, не трогая коммитируемые файлы проекта.
- Один и тот же код обслуживает локальный запуск и сервер; расходится только политика потолка.

**Чем платим**

- **Неоднозначность вылезает наружу.** Раньше совпадение id разрешалось само (и неправильно), теперь
  это ошибка, которую видит человек. Сообщение обязано перечислять кандидатов, иначе цена
  превращается в раздражение.
- **Второе место хранения** — ещё один файл, ещё одна миграция, ещё один источник расхождения между
  тем, что показано, и тем, что применено.
- **Подтверждение при добавлении** — новый диалог на пути, который раньше был мгновенным. Это та же
  цена, которую платит VS Code Workspace Trust, и платит осознанно.
- **Переписывание, а не доработка**: `SplaSkillSourceSection`, `ApplySkills`,
  `SkillSourceRegistry.Build`, `SkillLibrary.Rebuild`, `SkillCard`, протокол панели,
  `agents/skills.md`, `docs/readme_skills_ru.md`. Совместимость по-прежнему не ограничивает —
  внешних клиентов и опубликованных контрактов нет.

**Что теперь нельзя**

- Нельзя считать, что скил однозначно определяется своим `id`. Он определяется адресом.
- Нельзя объявить источник доверенным из слоя, который сам может приехать из чужих рук.
- Нельзя удалить унаследованный филиал — только выключить.
- Нельзя писать источники в проектный файл из UI: у UI своё хранилище, и смешивать их — значит
  вернуть коммит чужого решения в репозиторий.

## Отвергнутые варианты

**Патч-язык для списков** (`sources.add` / `sources.remove` / `sources.clear`, в духе RFC 6902 или
`$patch: delete` из Kustomize). Отвергнуто: это DSL поверх настроек, который надо документировать,
тестировать и объяснять человеку, а покрывает он ровно то же, что мерж по ключу — при условии, что
ключ есть. Ключ дешевле языка.

**Числовой `order:` у записи** (в духе `NN-name.conf` у systemd и udev). Отвергнуто как
преждевременное: после отмены перекрытия порядок влияет только на отображение и ранжирование. Вернуть
поле, когда порядок снова станет что-то решать, дешевле, чем сейчас объяснять, зачем оно.

**Оставить перекрытие по id, но сделать его явным** (`overrides: true` у источника или
`replaces: builtin:foo` во фронтматтере). Отвергнуто: сохраняет понятие «одно и то же имя из разных
мест — конфликт», ради удобства, которое уже выражается через `enabled: false` плюс своя книга.
Библиотека, где второе издание вытесняет первое, — не библиотека.

**Сервер: пользовательский список только для чтения.** Отвергнуто — резали не по той оси. Право
писать в свою область не является риском; риском является уровень доверия, который эта запись себе
назначает. Различать надо потолок, а не доступ.

**Доверие во фронтматтере скила или в файле-маркере внутри папки** (`.skills-trusted`). Отвергнуто:
самоподписанное доверие не является доверием. Ровно так же `git` отказывается читать конфиг из
репозитория, принадлежащего другому пользователю, а `apt` держит ключи репозиториев в keyring,
которым распоряжается root, а не сам репозиторий.

**Один список без разделения на предписанные и выданные.** Отвергнуто: тогда «добавить папку из UI»
означает запись в коммитируемый файл проекта — то есть личное решение одного человека уезжает в
репозиторий и приезжает всем остальным. Ровно та ошибка, от которой отдельное хранилище секретов
защищает уже сегодня.

**Грант доверия по `id`, а не по пути.** Отвергнуто: тогда переименование записи в конфиге
унаследовало бы чужой грант, а переименование папки — сохранило бы его для новой. Доверяют
содержимому, а содержимое лежит по пути.

## Почитать

- Alex Birsan, *Dependency Confusion* (2021) — как приоритет источника вместо адреса превращается в
  цепочку компрометаций у десятков компаний сразу.
- [VS Code Workspace Trust](https://code.visualstudio.com/docs/editing/workspaces/workspace-trust) —
  эталон гранта, хранимого вне того, кому его выдают: ответ «доверяю авторам этой папки» лежит в
  профиле пользователя и адресуется путём.
- `apt-secure(8)` — доверие к репозиторию как подпись ключом из keyring, которым репозиторий не
  распоряжается.
- Chrome Enterprise, `ExtensionInstallForcelist` / `ExtensionInstallBlocklist` — предписанное,
  личное и запрещённое как три списка одной модели.
- RFC 7386 (JSON Merge Patch) и RFC 6902 (JSON Patch) — два полюса того, от чего мы отказались в
  пользу ключа.
