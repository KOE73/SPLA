# ADR_20260827-2_core — роли: деятель, поручение и переписка

Статус: **принято**

Опирается на [`ADR_20260811_core_security-zones`](ADR_20260811_core_security-zones.md) (корень =
каталог манифеста, гранты на ребро), [`ADR_20260819_core_project-entry`](ADR_20260819_core_project-entry.md)
(профили запуска, отсутствие подъёма по дереву), [`ADR_20260819-2_core_agent-instances`](ADR_20260819-2_core_agent-instances.md)
(один писатель, аренда, окно как вид) и [`ADR_20260825_core_chat-turn-pump`](ADR_20260825_core_chat-turn-pump.md)
(ход рождается из ящика).

> В контексте **работы нескольких специализированных агентов над одним проектом**, столкнувшись с тем,
> что **системный промпт задаёт, кем агент себя считает, но не задаёт, кем он является — модель,
> которой сказано «не чини сам», может починить**, мы решили **сделать роль общим типом настроек
> деятеля, первым экземпляром которого становится `agent:` самого манифеста, и дать ролям два разных
> способа взаимодействия — поручение и переписку**, чтобы **граница роли держалась гейтом
> возможностей, а не уговором в промпте**, приняв **отказ от нескольких манифестов в одном каталоге и
> отказ от иерархии внутри переписки**.

---

## 1. Контекст

**Промпт не является границей.** Роли вида «ревьюер: ищи ошибки, не реализуй исправления» —
распространённый приём, и в чистом виде он держится на послушании модели. Реальную границу задаёт
конфигурация рантайма: включённые возможности (`agent.capabilities`, `SplaSections.cs:65`), режим и
гранты на рёбра. Промпт объясняет **зачем**, гейт обеспечивает **что**.

**Роль по форме почти совпадает с настройкой проекта.** Режим, набор инструментов, выбранная модель,
свои коннекты — это то же, что уже описано в манифесте. Совпадение формы — не дублирование, которое
надо вычищать, а признак, что тип один.

**Отдельный «оркестратор» как вид агента не нужен.** Внешнее подтверждение: Kilo Code, вводивший
Orchestrator отдельным режимом, объявил его устаревшим — обычные режимы сами умеют порождать
суб-агентов. У нас `agent_spawn`/`agent_spawn_batch` доступны обычному агенту с самого начала, и
менять это незачем.

**У спавна была потеряна курируемость.** Отмена обязательного скилла в `agent_spawn` дала свободный
промпт: внешняя голова стала дешевле, но перестала быть управляемой. Роль возвращает управляемость,
не возвращая обязательности скилла.

**Дерево чатов уже не помещается в список.** Несколько деятелей в одном проекте, у каждого несколько
чатов — линейный список перестаёт показывать, что происходит.

## 2. Принятые решения

### 2.1 Роль как тип

| Решение | Обоснование |
|---|---|
| **Роль — общий тип «настройки деятеля»**; `agent:` манифеста становится его первым экземпляром (роль по умолчанию) | Форма совпадает; отдельный формат для роли пришлось бы мигрировать в общий тип при первом же расхождении |
| **Роль не является подмножеством прав проекта.** Потолок — корень каталога и гранты владельца, а не набор возможностей манифеста | Требование «объединение всех ролей ⊆ проект» сделало бы проект максимально привилегированной сущностью — ровно та беда, что описана в `ADR_20260819` про безпроектный режим |
| **Проект объявляет, что существует; роль выбирает, чем пользуется** | Единственный работающий критерий «что общее»: пул коннектов, плагинов, островов — свойство места; выбор модели, режима, видимых островов — свойство деятеля. Заодно сохраняется «прочитал манифест — знаю, куда проект дотягивается» |
| **Роль не самоназначается**: определения пишет владелец, агент не может ни сочинить роль, ни взять невыданную | Единственный настоящий инвариант. Всё остальное — вопрос грантов |
| **Файл в каталоге ≠ активная роль**: манифест перечисляет роли поимённо | Иначе роль, приехавшая чужим PR, становится новым деятелем с доступом к базе. Та же логика, что «нет подъёма по дереву»: не действует то, чего никто не назвал |
| Роль **выбирает режим и сужает внутри него**, а не встаёт второй осью прав рядом с режимами | Две перекрывающиеся системы разрешений немедленно рождают вопрос «кто кого перебивает» |
| Тело роли — `roles/<name>.yaml` рядом с манифестом, едет в git | `.spla/` закрыт целиком (`ADR_20260811`); отдельное расширение вида `*.role.spla` вернуло бы в каталог многозначность, которую `FindProjectFile` объявил ошибкой |

### 2.2 Взаимодействие: два механизма

| Решение | Обоснование |
|---|---|
| **Поручение и переписка — оба, и это разные механизмы**, а не один с настройкой | Под ними лежит разный код: изолированный прогон с возвратом значения против ящика с пробуждением |
| Критерий выбора: **в поручении ответ — возвращаемое значение, в переписке ответ — поступок** | В спавне возвращается последнее сообщение ассистента механически, потому что прогон кончился; в переписке роль сама решает, что и когда сказать, после произвольного числа собственных ходов и вызовов |
| Поручение = `agent_spawn` с параметром роли; существующий `mode` остаётся для безымянного ad-hoc | Слот «кем будет порождённый» уже есть, роль его обобщает; старые вызовы смысла не меняют |
| Переписка = существующий `ChatInbox` + памп; адрес `проект / роль / чат` | Транспорт построен и не запитан: ветка `InboxItemKind.Human` заведена с пометкой «Nothing produces Human yet» |
| **Диалог не заканчивается — затихает.** Терминального состояния нет, есть отсутствие входящих | Сценарий-контрпример: собеседник запустил фоновую задачу, ответил «подожди», проснулся от `TaskResult`, ещё подумал, сделал ещё вызов и только потом решил, что вывод стоит сообщить. Протокол завершения такое не описывает |
| Чат собеседника создаётся **по требованию** | У роли может быть несколько открытых чатов; автоматический выбор одного из них невозможен |
| Собеседники — **множество**, а не ссылка на породившего | Ревьюеру нужны и архитектор, и писатель |
| **Свести два чата может человек из UI** | Тот же механизм с другим входом; отдельного кода не требует. Ожидаемая частота использования низкая, ценность — наблюдательская |
| **Иерархии внутри переписки нет.** «Кто главный» выражается поручением | Реплика — добровольный поступок, подчинение в ней выразить нечем. Кем себя считает участник, задаёт его роль, а не пара |
| Обращение роли к роли — **ребро источник→приёмник**, гранты те же | Реплика есть канал выноса данных из зоны; отдельная подсистема прав не нужна |
| Переписка помнит **своего инициатора** | Из этого одного поля вырастает вся структура «собрания»: кто кого позвал, и чьё приглашение породило ветку. Отдельной сущности для группы не требуется |
| **Специального удержания прогона нет.** Инициатор закончил и закрыл чат — переписка просто затихает | Мягкие ссылки уже дают нужное поведение: отвечать некому, ссылка не разрешается, запись вычёркивается. Собрание без начальника — это не сбой, а нормальный конец собрания |

### 2.3 Виртуальные инструменты ответа

| Решение | Обоснование |
|---|---|
| **Имя инструмента есть адрес**: `reply_<роль>[_<тема>]`, единственный параметр — текст | Идентификатор чата не попадает в контекст модели вообще: нечего забыть при сжатии, нечего перепутать. Список переписок в промпте становится не нужен — его роль играют имена и описания инструментов |
| Тема входит в имя, когда собеседников одной роли несколько; строка «зачем открыта» **обязательна** и нормализуется в идентификатор | Двух архитекторов иначе не различить. Строка перестаёт быть удобством для человека и получает механическое назначение |
| Имя стабильно на время жизни переписки | Переименование разошлось бы с уже сделанными вызовами в истории |
| Инструмент возвращает **квитанцию о доставке, а не ответ** | Ожидание реплики схлопнуло бы переписку обратно в поручение, причём в худшем виде: ход заблокирован, а собеседник имеет право думать ещё несколько ходов |
| Виртуальные инструменты живут в `ChatRuntime` и подмешиваются в выдачу определений, а не регистрируются в `McpHost` | Поверхность инструментов обязана различаться **по чатам**; шов для этого уже прорезан — `GetToolDefinitionsFor(ToolExposure)` (`McpHost.cs:165`). Как следствие, `UnregisterTool` для этой задачи не нужен вовсе |
| Входящая реплика — **новый `InboxItemKind.Peer`**, не `Human` | `Human` описан как «wakes immediately and always (it is a person's own words)»; безусловное пробуждение двух собеседников даёт петлю. `Peer` будится по политике — и это же готовое место для регулятора |

### 2.4 Жизнь, смерть и затухание

| Решение | Обоснование |
|---|---|
| **Мягкие ссылки вместо взаимных подписок**: живость спрашивается у `ChatRegistry` при сборке поверхности хода | `GetOrOpen` (`ChatRegistry.cs:48`) отвечает на всё одним вызовом и попутно будит спящего — поведение, нужное и при доставке |
| Подписки с рассылкой «я умер» отвергнуты | `RuntimeClosed` (`ChatRegistry.cs:45`) срабатывает и на `Delete`, и на `Archive`, и на обычное закрытие рантайма: «рантайм закрылся» ≠ «чат умер». Подписки рвали бы переписки со всего лишь заснувшими, а падение процесса не разошлёт ничего |
| Мёртвая запись вычёркивается лениво, на том же проходе | Отдельный сборщик не нужен |
| Исчезновение собеседника объявляется в чат через `InboxItemKind.Notice` | Инструмент, исчезнувший между ходами, иначе выглядит как галлюцинация. `Notice` подходит буквально: «never itself a wake trigger» — умерший собеседник не повод поднимать ход |
| **Затухание переписки живёт в пампе, а не в промпте** | Модель не переобучить и уговаривать бессмысленно: языковые модели обучены отвечать, их «коэффициент собеседника» по умолчанию высок. Но решение, состоится ли ход у адресата, принимает код |
| Три опоры затухания: молчание — законный исход хода; будит памп, а не модель; с ростом глубины обмена растёт дебаунс, за порогом ход ради реплики не поднимается — **но реплика не выбрасывается**, она ждёт хода, который случится по другой причине | Обмен не обрывается, а замедляется до темпа внешних событий. Наблюдение владельца: при произведении коэффициентов около единицы разговор тянется и глохнет — здесь то же, только гаснет он от отсутствия поводов проснуться, а не от потери интереса |
| `Peer` — внутренняя циркуляция, `Human` и `TaskResult` — внешняя энергия, сбрасывающая затухание | Разговор должен оживать от новости, а не от вежливости. Расщепление видов ящика получило второе, независимое обоснование |
| Жёсткий предел глубины остаётся **аварийным** | Срабатывать не должен никогда; сработал — дефект регулятора, а не нормальная работа |

### 2.5 Представление

| Решение | Обоснование |
|---|---|
| Список чатов становится деревом **роль → чат** | Единственное место, где видно, что происходит между деятелями |
| «Открыть в отдельном окне» — **фильтр на виде**, не второй инстанс | Окно уже определено как «a view onto a project. Holds nothing» (`RegistryProtocol.cs:46`); инстанс на роль воскресил бы нескольких писателей манифеста |
| Реплика рендерится как речь («→ архитектору», «← от архитектора»), квитанция скрывается, формат вызова на проводе не меняется | Свёрнутый вызов уместен для служебного действия; реплика — содержание разговора. Входящая приезжает обычным `user`-сообщением и иначе неотличима от слов человека |
| Удержание контекста для реплики — `Persistent` | Это содержание разговора, а не служебный результат |
| **Собрание — производный вид, а не сущность рантайма**: граф строится из переписок и их инициаторов | «Собрание» есть связное поддерево переписок с корнем в том, кто позвал первым; «подсобрание» — та же ветка ниже. Владелец = инициатор, членство = наличие ребра, конец = смерть корня. Заводить объект со списком участников и жизненным циклом значит платить рантаймом за картинку |
| Граф показывает, **кто с кем говорит и сколько наговорил** | Объём считается по репликам и токенам на переписку — учёт токенов уже ведётся ядром. Это первый вид, на котором видно перекос: роль, которая только говорит, и роль, которую никто не слушает |

## 3. Отвергнуто

**Несколько `*.spla` в одном каталоге (роль = отдельный проект).** Ломает сразу четыре вещи:
`FindProjectFile` объявляет два манифеста в каталоге ошибкой, а не жребием (`ConfigLoader.cs:382`);
`.spla/` один на каталог, и чаты, KV, логи, `token-usage.json` разных «проектов» легли бы вперемешку;
«один serve = один проект = один cwd» перестаёт быть правдой; аренда и реестр рассчитаны на одного
писателя манифеста. Плюс межагентное общение пришлось бы изобретать заново вместо готового ящика.

**`*.role.spla` рядом с манифестом.** Возвращает в каталог ту же многозначность по расширению и
заставляет объяснять, почему один вид файла уникален, а другой нет.

**«Роль только сужает права проекта».** Формулировка первой итерации. Отвергнута: заставляет манифест
держать объединение прав всех ролей, то есть делает сам проект всесильным.

**Отдельный тип агента «оркестратор».** Порождение суб-агентов доступно любому агенту; специальный
тип добавляет сущность, ничего не добавляя к возможностям.

**Ожидание ответа в инструменте реплики.** Превращает переписку в поручение, теряя единственное, ради
чего она заводилась.

**Список открытых переписок в системном промпте с идентификаторами чатов.** Вытесняется именами
виртуальных инструментов; идентификаторы вообще не должны попадать в контекст модели.

**Собрание как сущность рантайма** — с владельцем, списком участников и общей видимостью реплик.
Приносит три вопроса, каждый из которых дороже полученного: видит ли участник то, что сказано не ему
(а если да, контекст каждого растёт на всё сказанное всеми — и это же усилитель петли); что
происходит с собранием при смерти владельца; чем членство отличается от наличия переписки. Всё, ради
чего собрание заводилось, — иерархия, владение и картинка — выводится из переписок и их инициаторов.

**Слово `role` для нового понятия в файле сессии.** В одном YAML оказались бы `role:` уровня сессии
(архитектор) и `role:` внутри каждого сообщения (`user`/`assistant`) — файл истории читается глазами
именно тогда, когда что-то сломалось.

---

## 4. Не решено

**Конкретная форма регулятора затухания.** Пороги, шаг роста дебаунса, что именно считать «внешней
энергией» помимо `Human` и `TaskResult`. Требует замера на живом прогоне.

**Ответ всем сразу.** Без сущности собрания «все» означает «все мои собеседники», а не «участники
одной встречи». Одна реплика будит N чатов, каждый из которых может ответить всем. Если делать, то
сразу под общим счётчиком глубины.

## 5. Последствия

- Появляется общий тип настроек деятеля; `agent:` манифеста читается как роль по умолчанию.
  Существующие манифесты смысла не меняют — роль ноль это ровно то, что там уже написано.
- Поверхность инструментов перестаёт быть глобальной и считается на чат. Это же снимает вопрос
  `PLAN_20260819_core_dynamic-tool-registration`: переключение возможностей требовало перезапуска
  именно потому, что поверхность считалась один раз при старте. Регистрация после старта, вопреки
  формулировке того плана, уже работает (`SettingsOps.cs:396`); не работало снятие.
- `ChatInbox` получает третий вид элемента и вместе с ним — место для регулятора затухания.
- `ChatRegistry` должен различать «удалён» и «в архиве»: сейчас оба дают «не найден», а для текста
  уведомления это разные новости.
- Переименования: `ParticipantRoles` → `ParticipantKind` (участник бывает видом, а не ролью; на
  проводе читать `kind` с откатом на `role`); в файле сессии роль записывается как `as:`;
  `ChatRole` внутри сообщений не трогается — это зеркало протокола провайдера.
- Первый слом формата файла сессии (`as:`) становится поводом обкатать
  [`ADR_20260827_core_config-versioning`](ADR_20260827_core_config-versioning.md) на чём-то мелком.
