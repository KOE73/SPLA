# ADR_20260909-2_core — модель по умолчанию — это флаг на записи, не позиция в списке

Статус: **предложено**

Опирается на [`ADR_20260904_core_connection-scopes`](ADR_20260904_core_connection-scopes.md)
(соединения живут в трёх слоях: shared / user / project, слой побеждает целиком, не по полям).

> В контексте **человека, у которого настроено несколько соединений сразу в двух слоях —
> личном и проектном**, столкнувшись с тем, что **и `chat run`, и разрешение настроек при
> открытии нового чата выбирают модель по правилу «первая в объединённом списке»**, — то есть
> невидимо и завязано на порядок объявления, — мы решили **дать записи модели необязательный
> флаг `default: true`, который резолвер сводит в один `DefaultModelId` по тем же правилам
> слоёв, что и сами соединения**, чтобы **выбор модели по умолчанию был фактом настройки,
> который видно и можно перенести между проектами, а не побочным эффектом порядка строк в
> YAML**, приняв **что флаг стоит на модели, а не на соединении (одно решает оба вопроса,
> второе поле было бы дублирующим), и что несколько отмеченных записей в одном слое — это
> ошибка конфигурации, а не первая по порядку побеждает молча**.

---

## 1. Контекст

Сегодня «умолчание» для модели — это `Models.FirstOrDefault()` /
`Models.Take(1)`, применяемое в двух не связанных друг с другом местах:

- [`SettingsResolver.ToLLMSettings()`](../../src/core/SPLA.Domain/Settings/SettingsResolver.cs:369)
  — модель для нового чата;
- [`ChatRunCommand.cs:187`](../../src/apps/SPLA.CLI/Batch/ChatRunCommand.cs) — модель для
  `spla chat run` без `--model`.

`Models` — плоский список, собранный слиянием shared → user → project
(`ADR_20260904` §2.3). «Первая» в нём — случайность порядка объявления слоёв и записей внутри
слоя, а не решение. У человека с личным LM Studio (слой `user`) и проектным облачным ключом
(слой `project`) это означает: какая модель окажется первой, не выбирает никто, а меняется
это только переписыванием файла настроек руками, из чата это никак не видно и не управляется.

Отдельно от этого: сама идея «модель по умолчанию» и «соединение по умолчанию» — разные
вопросы только на первый взгляд. Соединение без выбранной модели резолверу не пригодится (ему
всё равно нужен конкретный `ResolvedModelEntry` — endpoint, ключ, контекст все берутся оттуда).
Значит, отметить достаточно модель; связанное с ней соединение выбирается автоматически, вторая
отметка была бы полем, которое обязано не разойтись с первым.

Вопрос: где хранить эту отметку и как её сводить, если несколько слоёв её проставили
по-разному.

## 2. Решение

**2.1. Флаг на записи модели.** `SplaModelSection` получает `public bool Default { get; set; }`.
Живёт рядом с `Id`/`Name` в том же блоке `models:`, в том же файле, где уже лежит модель — новых
файлов и новых мест хранения ADR не заводит.

```yaml
connections:
  - id: openrouter
    models:
      - id: qwen3.8-27b
        default: true
```

**2.2. Резолвер сводит слои так же, как соединения.** Новое свойство
`ResolvedSettings.DefaultModelId` считается в `Resolve()` в порядке
`shared → user(defaults.yaml) → connections.yaml → манифест проекта` — том самом, которым
`ADR_20260904` §2.3 уже сводит сами соединения. Каждый слой, где нашлась хотя бы одна запись с
`default: true`, **целиком заменяет** кандидата от предыдущего слоя — не «первая увиденная за
всё время», а «последний слой, который вообще высказался». Это то же правило, каким запись
соединения одного `id` вытесняет прежнюю по слоям целиком, а не по полям.

**2.3. Несколько `default: true` в одном слое — отказ, не тихий выбор первой.** Если внутри
одного файла (одного слоя) отмечены две и более модели, это ошибка конфигурации: резолвер
обязан сообщить о ней тем же путём, каким сегодня сообщает о прочих противоречиях в настройках
(смотреть, как это сделано для дублирующихся `id` соединений), а не выбирать «первую по
порядку» — это как раз то поведение, от которого уходим.

**2.4. Ничего не отмечено нигде — старое поведение, без изменений.** `DefaultModelId == null` →
и `SettingsResolver.ToLLMSettings()`, и `ChatRunCommand` продолжают брать
`Models.FirstOrDefault()` / `.Take(1)`, ровно как сегодня. Синтетическое соединение `"default"`
(`SettingsResolver.cs:619-629`, когда во всём дереве настроек нет ни одной записи) этот флаг не
получает и не должно: оно и так единственное.

**2.5. `FindModel` учится второй форме адреса.** Сегодня `--model` в CLI и резолвер понимают
только точный `Id` записи. Добавляем: `FindModel` также принимает строку вида
`"<DisplayName соединения> · <DisplayName модели>"` (тот же формат и разделитель, что уже
выводит `ResolvedModelEntry.DisplayName`, `SettingsResolver.cs:414`) как альтернативный ключ
поиска — **не новый формат**, а признание того, что уже показывается в интерфейсе, годным
аргументом командной строки. Это закрывает четвёртый пункт запроса пользователя: «скопировать
правильное название» — копируется ровно то, что видно в списке моделей, и оно же подаётся в
`--model`.

**2.6. Кнопка копирования в вебе копирует этот же `DisplayName`.** Рядом с селектором модели
(`StatusBar.vue`) — компонент `CopyButton.vue`, уже существующий и используемый в других местах
интерфейса, копирует `modelLabel(selected)` — строку, которую человек и так видит. Никакого
третьего формата идентификатора не вводится.

**2.7. Постоянно видимая метка соединения.** Сейчас закрытый `<select>` в `StatusBar.vue`
показывает только имя модели (`modelLabel()`, `StatusBar.vue:341`), а имя соединения видно
только в раскрытом списке (`optgroup`) или в отдельном всплывающем окне `ProviderInfoPopup.vue`
по клику на «i». Меняем `modelLabel()`: строка выбранного значения всегда включает имя
соединения — `"{connectionName} | {modelName}"` (модель без имени/значка отдельно не
переусложняем: если имя модели и так совпадает с именем записи, показываем его один раз, как
`DisplayName` делает сегодня через «·» — здесь только разделитель другой, потому что того
требует пространство статус-бара, а не смысл). Изменение декоративное и не трогает `value`
`<option>` (там остаётся `m.id`).

## 3. Последствия

- Выбор модели по умолчанию становится фактом настройки: виден в файле слоя, переносится между
  проектами вместе с личным `connections.yaml`, не меняется от перестановки строк.
- `chat run` без `--model` и разрешение настроек при открытии чата используют один и тот же
  `DefaultModelId` — вместо двух копий одного и того же `FirstOrDefault()`.
- Отдельного «соединения по умолчанию» не заводится — оно избыточно поверх модели по умолчанию
  и было бы вторым полем, которое обязано не разойтись с первым.
- `FindModel` от одного `Id` переходит к двум формам ключа — небольшое расширение контракта,
  которое стоит проверить на то, что `DisplayName` не совпадает по случайности с чьим-то чужим
  `Id` (маловероятно, но резолвер обязан не спутать одно с другим при поиске).
- UI для `default: true` (галочка в карточке соединения/модели) в это решение не входит —
  ADR фиксирует хранение и резолюцию; редактор — отдельная волна плана.
