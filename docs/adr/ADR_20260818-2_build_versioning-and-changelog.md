# ADR_20260818-2_build — версия из трёх частей и changelog, который пишут, а не генерируют

Статус: **принято**

> В контексте **появления CI/CD, где релиз собирается автоматически и в непредсказуемый момент**,
> столкнувшись с тем, что **номер релиза частично назначался вручную и частично машиной, а описание
> релиза сводилось к одной строке**, мы решили **свести версию к `0.<minor>.<build>` и писать
> описание руками в трёх файлах под `CHANGELOGS/`**, чтобы **релиз опознавался одним числом, а его
> описание не зависело от того, вспомнил ли кто-то что-то перед сборкой**, приняв **ручной труд над
> сводкой и ручное замораживание файлов после релиза**.

---

## 1. Контекст

До этого решения версия была `0.2.<patch>.<build>`: `patch` владелец двигал рукой «иногда», `build`
инкрементировался автоматически при каждом прогоне.

На практике это означало, что релизы выходили как `0.2.0.1`, `0.2.0.4`, `0.2.0.10` — с реальными
изменениями между ними и **одинаковым `patch`**. То есть опознавал релиз только `build`, а `patch`
не нёс никакого решения: от того, изменился он или нет, не зависело ничего.

Обнаружилось это не из рассуждений, а из практического вопроса: **как назвать файл changelog**.
Любая схема «файл на версию» упиралась в то, что непонятно, что считать версией. Формально по semver
четвёртая часть — build metadata, которая **игнорируется при сравнении**; то есть стандарт считал
`0.2.0.1` и `0.2.0.4` одной версией, собранной дважды, тогда как в них было разное содержимое.

Второй вопрос всплыл одновременно. GitHub умеет генерировать описание релиза сам — из **смёрженных
pull request'ов** между тегами. Но принятая в этом репозитории модель ветвления (`work → main`
одним squash-мержем на релиз) даёт ровно **один PR между тегами**. Автоматическое описание релиза,
покрывающего два месяца работы и 181 коммит, выродилось бы в одну строку.

---

## 2. Принятые решения

### 2.1 Версия

| Решение | Обоснование |
|---|---|
| Три части: `0.<minor>.<build>` | Последняя часть всегда разная, значит опознаёт релиз однозначно и в одиночку |
| `minor` — рукой, редко | Сохраняет за владельцем жест «началась новая глава», который он и так делал через `patch` |
| `build` — номер прогона `release.yml`, никогда не рукой | Единственный компонент, который обязан меняться на каждом релизе, — значит его должна назначать машина |
| Четвёртой части нет | Компонент, не несущий решения, — шум в каждом месте, где версию печатают, произносят и набирают |
| `AssemblyVersion`/`FileVersion` дополняются нулём до четырёх | Четырёхчастная версия — родная для .NET; дополнить честнее, чем выдумать значение |

Локальная сборка получает `build = 0`, то есть все локальные сборки сообщают одну версию. Это
сознательно: номер имеет смысл только для пакета, вышедшего из CI.

### 2.2 Changelog

Три рабочих файла под `CHANGELOGS/`, и у каждого свой режим письма:

| Файл | Что | Когда пишется |
|---|---|---|
| `current-log.md` | подробная запись, по датам | дописывается по ходу работы |
| `current-list.md` | строка на изменение, без дат | **выводится** из жирных заголовков лога |
| `current-summary.md` | проза по темам | **переписывается целиком перед каждым пушем** |

| Решение | Обоснование |
|---|---|
| Записи заслуживает то, что заметно снаружи | Время не ось: часовой фикс с видимым эффектом важнее двухдневного рефактора без него |
| Тип коммита становится несущим | От `feat`/`fix` теперь зависит попадание в changelog, а не только опрятность лога |
| Список выводится из лога, а не пишется отдельно | Два независимо написанных файла разъезжаются; выведенный не может |
| Сводка переписывается **перед пушем** | Пуш — граница, за которой релиз становится возможен: до него выстрелить нечем, после — можно в любой момент |
| Отметка `<!-- covers: ДАТА -->` в сводке | Позволяет машине отличить свежую сводку от устаревшей, не спрашивая человека |
| Устаревшая сводка **не публикуется вовсе** | Уверенное описание несуществующего состояния хуже отсутствия описания |
| Публикуемое содержимое начинается после первого `---` | Преамбула объясняет, как устроен сам файл, и читателю релиза не нужна |
| В тело релиза едут сводка и список, лог — ссылкой | Полный лог релиза такого масштаба — сотни строк, это не тело релиза |
| Замораживание файлов делает человек в сессии, не CI | CI намеренно не пишет в `work`; бот в рабочей ветке — цена выше выгоды |
| Проверка «пора ли замораживать» — механическая | Тег без соответствующего `CHANGELOGS/<version>.md`; сравнение, а не память |

---

## 3. Почему сводка не переписывается на каждую запись

Первоначально предлагалось именно это — ради свойства «всегда готово к релизу, который может
случиться в любой момент». Замер показал цену:

| | объём | ~токенов |
|---|---|---|
| Запись в лог | 25 слов | ~40 |
| Сводка (за цикл 0.2) | 1400 слов | ~2100 |

**Соотношение около 55:1.** При десяти записях за цикл непрерывное переписывание стоит примерно
вшестеро дороже разового — но дело не в деньгах, они здесь копеечные. Дело в том, что **девять
переписываний из десяти не имеет читателя**: сводка существует ровно для того, чтобы попасть в тело
релиза, и промежуточные её версии не читает никто.

Отметка `covers:` даёт то же свойство дешевле и **строже**: непрерывное переписывание лишь снижало
вероятность устаревания, а отметка делает публикацию устаревшего невозможной по построению.

## 4. Последствия

**Что получаем.**

- Релиз опознаётся одним числом, которое назначает машина; человек не выбирает номер вообще.
- Описание релиза читаемо человеком и не зависит от формата коммитов.
- Готовность к релизу поддерживается непрерывно и не памятью владельца — значит момент сборки
  может быть любым.
- Локальная сборка не изменилась: `PublishAll.cmd` вызывается без аргументов, как и раньше.

**Чем платим.**

- Сводку и лог пишет человек (на практике — агент в сессии). Это единственная ручная работа в
  конвейере, и она осознанная.
- Замораживание после релиза — тоже ручное действие, и оно может отстать от релиза на какое-то
  время.
- Три файла вместо одного: больше объектов, хотя список и выведен.

**Что теперь нельзя.**

- Нельзя назначать `build` рукой — он обязан приходить из прогона.
- Нельзя публиковать сводку, не обновив `covers:`; иначе она либо соврёт, либо будет отброшена.
- Нельзя писать список отдельно от лога — только выводить.

---

## 5. Чего это не обещает

- **Не делает описание автоматическим.** Автоматизирован номер и сборка, но не смысл; смысл пишется.
- **Не защищает от забытого замораживания** — только обнаруживает его при следующей сессии.
- **Не решает вопрос нескольких разработчиков полностью.** Параллельные дописывания в один файл
  остаются обычными merge-конфликтами; группировка по датам их лишь разрежает.
- **Не привязывает версию к смыслу изменений.** `build` растёт от прогонов, а не от того, что
  изменилось; «крупность» релиза выражается сводкой, а не номером.

---

## 6. Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Оставить четыре части | Третья часть не несла решения, но её приходилось читать, чтобы опознать релиз |
| Оставить четыре, но поднимать третью на каждом релизе | Это те же три решения под другими именами, плюс лишний ручной шаг |
| Полный автомат версии по типам коммитов (MinVer, semantic-release) | Оправдан, когда версию потребляет кто-то снаружи и ей верят; пока продукт потребляет автор, добавляет инструмент в сборку без выигрыша. Заодно такие инструменты генерируют changelog **дословно из коммитов** — ровно то, чего здесь не хотят |
| Описание релиза генерировать из `git log` | Знает «что», не знает «зачем»; при squash-мерже вырождается в одно сообщение |
| Описание генерировать LLM прямо в прогоне CI | Кладёт в релизный конвейер ключ провайдера, стоимость и недетерминированность: два прогона на одном коммите дадут разный текст |
| Один файл changelog на всё, новое сверху | Растёт бесконечно; отвергнут владельцем как неудобный |
| Общий накопительный `history.md` рядом с версионными файлами | Та же бесконечность, плюс дублирование содержимого версионных файлов |
| Имя файла назначать заранее, до релиза | Номер билда до сборки не существует, а он и есть опознавательный знак релиза |
| Один файл на релиз с разделами вместо трёх рабочих | Рассматривался и был отвергнут владельцем: три роли пишутся в разных режимах (дописывание / вывод / переписывание), и смешивать их в одном файле неудобно |
| Переписывать сводку на каждую запись лога | ~55 записей лога по цене одной сводки, девять переписываний из десяти без читателя (§3) |
| Замораживание делает CI, коммитя в `work` | Бот, пишущий в рабочую ветку, — постоянная цена ради разового удобства; отвергнуто владельцем |
| Напоминание вместо проверки | Опирается на внимание, которого по условию задачи нет: проектов у владельца несколько |
