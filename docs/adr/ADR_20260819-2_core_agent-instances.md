# ADR_20260819-2_core — инстансы агента: один писатель, аренда и реестр

Статус: **принято**

Опирается на [`ADR_20260819_core_project-entry`](ADR_20260819_core_project-entry.md) (вход в проект) и
на разделение хранилищ из [`ADR_20260811_core_security-zones`](ADR_20260811_core_security-zones.md).

> В контексте **нескольких процессов SPLA, работающих над одними и теми же проектами, в том числе с
> другой машины**, столкнувшись с тем, что **два писателя в один `.spla/` не запрещены ничем, а
> запущенный `serve` невозможно обнаружить снаружи**, мы решили **ввести замок-с-адресом рядом с
> проектом и саморегистрацию инстанса в реестре, адрес которого выдаётся при запуске**, чтобы
> **получить инвариант одного писателя, обнаружение и живые статусы**, приняв **отдельный
> переиспользуемый проект реестра, отказ от `pid` как признака жизни и предварительную переделку
> механизма разрешений**.

---

## 1. Контекст

**Ничто не запрещает второго писателя.** `CliBootstrap` (`CliBootstrap.cs:36`) резолвит проект для
любой команды, а `serve`, `chat run` и `mcp` строят каждый свой `AgentRuntime`. Все трое пишут в один
`.spla/`: чаты, KV, `token-usage.json`. Замка нет нигде.

**Запущенный `serve` не найти.** Embedded-лаунчер берёт эфемерный порт (`EmbeddedServiceLauncher.cs:78`)
и никуда его не публикует, а `spla serve` руками по умолчанию садится на фиксированный 5050
(`ServeCliCommand.cs:11`) — то есть два ручных запуска на разные проекты просто конфликтуют.

**Дочерний процесс убивается вместе с окном** — `Kill(entireProcessTree: true)` в `Dispose`
(`EmbeddedServiceLauncher.cs:227`). «CLI сидит и ждёт автономно» сегодня не выполняется.

**Рантаймы кэшируются навсегда.** `AgentRuntimeRegistry.Open` (`AgentRuntimeRegistry.cs:60`) —
`GetOrAdd` без вытеснения, `Dispose` только при выходе процесса.

**Ожидающие разрешения умирают вместе с соединением.** Запрос уходит только инициировавшему
соединению (`ClientConnection.cs:433`), а при обрыве все `_pendingPermissions` получают `Deny`
(`ClientConnection.cs:172`). Закрытие окна во время работы не оставляет агента работать — оно
доводит ход по отказам.

**CLI может быть удалённым.** `serve` слушает сокет, `EmbeddedServiceLauncher.StartAsync` уже умеет
подключаться к чужому `remoteUrl` вместо запуска ребёнка. Для наблюдателя на другой машине ни
файлового замка, ни `pid` не существует в принципе.

---

## 2. Предусловие

Пока разрешения адресованы соединению, всё остальное в этом документе не работает: инстанс без окна
не может ничего спросить, а состояние «вопрос» непредставимо. Поэтому первым идёт перенос очереди
ожидающих запросов **с соединения на чат/инстанс**: отвечает любой подключившийся клиент, обрыв
означает «сейчас некому», а не «нет».

---

## 3. Принятые решения

### Один писатель

| Решение | Обоснование |
|---|---|
| Один писатель на манифест | Иначе два процесса гоняют одни и те же файлы состояния |
| Замок — `<проект>/.spla/instance.json`, удерживается открытым с deny-write | Живость даёт ОС: хэндл закрывается при любой смерти процесса, включая kill и падение |
| Замок несёт адрес: `instanceId`, `endpoint`, `machineId`, `pid`, `startTime` | «Кому нельзя войти» и «куда подключиться» — один и тот же факт; двум файлам тут делать нечего |
| Отдельного каталога `~/.spla/instances/` нет | Локальный список живых = обойти уже существующий `registry.json` и заглянуть в замок каждого проекта |
| Замок берётся при построении рантайма, а не в конкретной команде | Покрывает `serve`, `chat run` и `mcp` одним местом |
| `chat run` на занятом проекте подключается клиентом к живому инстансу | Убирает гонку и заодно делает прогоны из скриптов видимыми в открытом окне |
| Замок лежит рядом с проектом, а не в домашней папке машины | Проект на сетевой шаре, открытый с двух машин, тоже обязан иметь одного писателя; deny-write работает по SMB |

### Жизненный цикл

| Решение | Обоснование |
|---|---|
| Аренда вместо владения: инстанс живёт, пока есть подключённые клиенты **или** работа в полёте | «Кто породил, тот и владеет» ломается на сценарии «открыл A, открыл B, закрыл окно, вспомнил про B» |
| Состояния: `idle`, `working`, `waiting`, `stalled`, `unreachable` | Один список обслуживает и значки в UI, и правило вытеснения |
| Вытесняется **только** `idle` | Инстанс не хранит уникальных данных: чаты и KV на диске, перезапуск не разрушителен |
| `stalled` (ход не завершён, активности нет) неприкосновенен | Слабая модель встаёт на полдороге, человек возвращается и пинает её дальше; в памяти при этом лежит то, чего нет в логах |
| `--idle-timeout` — не отдельная фича, а значение grace для инстансов, поднятых руками | Grace нужен ради прогрева (плагины, коннекты, скиллы), а не ради сохранности |
| `stop` при `working`/`waiting` отказывает; `--force` отменяет ход через существующий `CancellationToken` | «Выгрузить» не должно означать «потерять полчаса генерации» |
| `Kill(entireProcessTree)` в лаунчере убирается | Решение о смерти принимает инстанс, а не тот, кто отключился |
| Порт по умолчанию — эфемерный, публикуется в замке; `--port` — явный выбор постоянного адреса | Фиксированный 5050 конфликтует у второго проекта |

### Проект — свойство соединения

| Решение | Обоснование |
|---|---|
| Проект фиксируется при установлении соединения и уходит из конвертов сообщений | Сегодня клиент обязан класть `projectId` в каждое сообщение, и забыть его = записать настройки в чужой `.spla` (комментарий в `web/src/state/project.ts`) |
| Локально: одно окно = один проект; переключение = новое соединение | `cwd` у процесса один, `Directory.SetCurrentDirectory` вызывается однократно на старте — переключение внутри процесса было бы полуправдой |
| `cwd` — свойство serve-инстанса; UI его не трогает | Один serve = один проект = один cwd, честно и физически |
| N окон в одном процессе UI допустимы | Инвариант на соединение, а не на процесс |
| На сервере `AgentRuntimeRegistry` остаётся многопроектным и получает вытеснение | N пользователей × M проектов в одном процессе — там это условие выживания, а не удобство |

### Реестр

| Решение | Обоснование |
|---|---|
| Инстанс **сам регистрируется** в точке, адрес которой дан при запуске: `spla serve --registry <url>` | Единственная модель, работающая и для удалённого CLI; `pid` в ней не участвует |
| Живость = наличие канала регистрации; `pid + startTime` — только для `stop` на своей машине | Голый `pid` переиспользуется ОС и признаком жизни быть не может |
| `/health` возвращает `instanceId`, и он сверяется до подключения | Отсекает чужой сервис, занявший тот же порт |
| Без `--registry` — файловый режим за тем же интерфейсом | Zero-config: запустил в папке, и локально всё ещё видно, куда подключаться |
| Код реестра — отдельные проекты: `SPLA.Registry.Contracts` (в `src/core/`, без зависимостей) и `SPLA.Registry` (в `src/service/`) | Сценарий без `SPLA.Server` — не упрощённый сервер, а другой сценарий; код обязан быть один на оба |
| Контракты не тянут ASP.NET | `SPLA.UI.Avalonia` ссылается только на `SPLA.Domain`, `SPLA.Secrets.Dpapi`, `SPLA.Observability` — и должен остаться таким |
| Хаб хостится в CLI (свой endpoint для просмотра и управления) и в `SPLA.Server` | Локальная и серверная топологии отличаются только тем, кто его запустил |
| Avalonia хаб **не хостит никогда**, при локальной работе поднимает дочерним процессом | Тот же способ, каким сегодня поднимается `serve`; смерть трея не должна ронять учёт |
| Роль UI: трей, отображение, моргание | Учёт нужен и headless-серверу, и `chat run` без всякого UI |
| Статусы **никогда не лежат в файлах** | Файлы отвечают на вопрос «где», каналы — «что происходит»; значок «вопрос» с поллингом бесполезен |
| У хаба один канал на инстанс, у UI один канал на хаб | Канал и так существует ради регистрации — статусы едут по нему бесплатно |
| Отладочное окно с полной раскладкой состояния реестра — новый `kind` существующей поверхности `debug` | Поверхность и протокол (`debug.request` → `debug.snapshot`) уже есть; это не пользовательский экран, а полный дамп |

### Токены

| Решение | Обоснование |
|---|---|
| Токен реестра — **одна запись** `secret:user:registry`, дефолтное поле | Ролей `register`/`control` не вводим: нужды нет, а лишние записи и поля плодить нельзя |
| Токен `serve` — отдельная запись | Это другой endpoint, а не другая роль того же |
| `--token` принимает **ссылку** (`secret:user:…`), не только литерал | Сегодня литерал светится в командной строке процесса |
| На сервере область — `shared`, а не `user` | DPAPI под конкретным пользователем не откроется сервисной учётке |

## 4. Отвергнуто

**Отдельный exe-менеджер.** Тянет вопросы, на которые нет хороших ответов: кто его стартует, кто
обновляет, что при расхождении версий с CLI. Хаб — режим существующего бинаря.

**Реестр внутри Avalonia.** Headless-сервер без Avalonia учёт всё равно ведёт, `chat run` обязан
уважать замок без всякого UI, а смерть трея не должна ронять учёт.

**Только файловый реестр.** Файлы не умеют push, а значки состояний требуют именно его. Файловый
режим остаётся вырожденным бэкендом, а не единственным.

**`pid` как признак жизни.** ОС переиспользует номера; для удалённого инстанса `pid` не существует.

**Роли `register` / `control` отдельными полями или записями.** Имеющегося токена достаточно;
разделение прав было придумано под несуществующую потребность.

---

## 5. Открытые вопросы

- Статус-канал: новый тип сообщений протокола или расширение `ServiceEvents` (сейчас там только
  `AppearanceChanged` и `SkillsChanged`, оба процессные).
- TLS для удалённой регистрации. Токен ставится сразу, шифрование сознательно отложено.
- Полная трасса хода на диске. Пока её нет, `stalled` не вытесняется в принципе; когда появится,
  ограничение можно снять.
