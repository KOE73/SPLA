# ADR_20260910_plugins_android — плагин управления Android-телефоном

Статус: **принято** (2026-09-10). Реализация: [`PLAN_20260910_plugins_android-device.md`](../plans/PLAN_20260910_plugins_android-device.md).
Спецификация протокола для исполнителей: [`src/plugins/SPLA.Plugins.Android/AGENTS.md`](../../src/plugins/SPLA.Plugins.Android/AGENTS.md).

## 1. Задача

Агент управляет **личным телефоном** пользователя: видит экран и действует на нём как палец.

Приоритеты, в порядке важности:

1. **Экран — почти постоянно и быстро.** Агент смотрит после каждого действия. Снимок за 1–2 секунды
   (`adb exec-out screencap -p`) слишком медленный, чтобы быть основным путём.
2. **Палец:** касание по координатам, долгое нажатие, свайп, **два пальца** (щипок/масштаб), произвольный
   многопальцевый жест.
3. Установка APK.
4. Остальное — «джентльменский набор», бонус: структура экрана с метками, ожидание, клавиши, ввод текста,
   приложения (список/запуск/остановка), push/pull, logcat, shell.

## 2. Почему это вообще нужно

Через `run_shell` агент уже может вызвать `adb shell input tap`. Плагин оправдывают три вещи, которых
через shell нет:

- **картинка доходит до модели** (`ToolImage`), а не остаётся байтами в stdout;
- **многопальцевые жесты:** `adb shell input` умеет только один палец;
- **скорость:** кадр берётся из постоянного видеопотока, а не снимается заново.

Свайп, клавиши и запуск приложения можно было бы делать через shell. Они есть в плагине, потому что
почти бесплатны, когда транспорт уже построен, но проектных решений не определяют.

## 3. Решения

### 3.1. Транспорт — `adb.exe` из своего runtime, не из PATH

`adb.exe` (+ `AdbWinApi.dll`, `AdbWinUsbApi.dll`) — транспорт и служебные операции: список устройств,
USB/TCP-подключение, запуск `scrcpy-server`, push/pull, shell, установка APK, запасной снимок экрана.

- Системный `PATH`, Android SDK и переменные окружения **не используются и не меняются**. Путь к `adb.exe`
  плагин вычисляет сам (§3.6).
- Процесс запускается с `ProcessStartInfo.ArgumentList`, без склейки строк. Текст модели не попадает
  в командную строку хоста без разбора.
- Порт adb-сервера — стандартный 5037. Настройка `adb_server_port` передаёт `ANDROID_ADB_SERVER_PORT`
  **только в окружение дочернего процесса**. Известный конфликт: если на машине работает adb другой
  версии (Android Studio), серверы будут убивать друг друга. Это документируется, не лечится.

Отвергнуто: **AdvancedSharpAdbClient** (протокол adb из .NET). adb-сервер ему всё равно нужен, так что
зависимость от `adb.exe` не исчезает, а добавляется ещё одна.

### 3.2. Экран — постоянный видеопоток scrcpy, «последний кадр»

```
Android ScreenCapture → scrcpy-server → MediaCodec H.264 → video socket → .NET-декодер → LatestFrame
```

- Поток идёт всё время, пока устройство подключено к чату. Потребители (скриншот для модели, ожидание
  стабильного экрана, будущая живая панель) **берут последний кадр** и не просят новый.
- Кадр хранится как **декодированный YUV** (плоскости). В PNG он превращается **только по запросу**:
  когда картинку надо отдать модели или положить в блоб. Каждый кадр в PNG не кодируется.
- `adb exec-out screencap -p` — **запасной путь** (§3.7) и для редких снимков вне сессии.

Отвергнуто: `screencap` как основной путь (1–2 с на снимок и сеть под полный PNG родного разрешения),
`screenrecord` (ограничен 3 минутами, нет управления).

### 3.3. Декодер — FFmpeg из того же релиза scrcpy, через свой узкий P/Invoke

Для H.264 декодер нужен неизбежно: сырых кадров или MJPEG scrcpy-server не отдаёт.

**Решение:** брать `avcodec-*.dll` / `avutil-*.dll` **из того же архива `scrcpy-win64-vX.zip`**,
из которого берётся `scrcpy-server`. Настольный клиент scrcpy декодирует ровно этими библиотеками ровно
этот поток. Значит, пара «сервер + декодер» проверена авторами scrcpy, и отдельного закрепления версии
для FFmpeg не нужно.

Биндинги — **свои**, около десяти функций через `NativeLibrary.Load` + `NativeLibrary.GetExport` +
`delegate* unmanaged[Cdecl]`. Из структур читаются только поля, которые стабильны много мажорных версий
(начало `AVFrame`, начало `AVPacket`; смещения в `AGENTS.md` плагина).

Отвергнуто:
- **FFmpeg.AutoGen / Sdcb.FFmpeg:** жёстко привязаны к мажорной версии FFmpeg (scrcpy 4.1 = FFmpeg 8.1).
  Переход scrcpy на новую мажорную версию ломал бы сборку плагина, а не только одну функцию.
- **Media Foundation (Windows):** raw-vtable COM. Вне рамки `windows-com-core` (только IDispatch), тяжёл
  для исполнителей, отсутствует в N-редакциях Windows.
- **Декодировать в браузере через WebCodecs:** хорошо для живой панели человека, но модели кадр нужен
  на сервере. Это возможное улучшение панели позже, не замена.

### 3.4. Палец — scrcpy control protocol

`adb shell input` даёт tap/swipe/keyevent одним пальцем и с задержкой процесса на каждое действие.
Многопальцевых жестов у него нет вовсе. Поэтому все жесты идут через **control socket scrcpy**:
`INJECT_TOUCH_EVENT` с `pointer_id`, действия DOWN/MOVE/UP. Для щипка два пальца ведутся одновременно.

Единая модель жеста: **набор пальцев, у каждого путь из точек `(x, y, t_ms)`**. Касание, долгое
нажатие, свайп и щипок — это готовые сборщики такого жеста. Общий инструмент `android_gesture`
принимает его как есть. Контракт выведен из того, что такое касание экрана, а не из списка удобных
кнопок.

### 3.5. Версии закреплены URL + SHA-256; «latest» — отдельный канал, а не значение версии

Внутренний протокол scrcpy меняется между версиями. Сервер к тому же проверяет, что версия клиента
**равна** его собственной. Поэтому:

- Закреплённая пара хранится в `runtime-manifest.json` рядом с DLL плагина: **полный URL + SHA-256 +
  версия**. URL из номера версии **не вычисляется**: у Platform Tools формат имени менялся
  (`-windows.zip` / `-win.zip`).
- Кнопка «latest» — **другой канал установки**, а не подстановка в манифест. У ADB latest нет
  контрольной суммы: хеш вычисляется после скачивания и записывается в квитанцию с пометкой
  `verified: false`. У scrcpy latest берётся из GitHub API: `releases/latest`, поле `digest` у asset.
- Протокол реализован под закреплённую версию scrcpy. Другая версия считается **экспериментальной**:
  плагин пробует работать с ней, а в статусе и самопроверке пишет, что версия не проверялась.
- Строка версии, которую клиент передаёт серверу первым аргументом, берётся **из квитанции установки**,
  а не из константы.

Закреплено на момент решения: **Platform Tools 37.0.0**, **scrcpy 4.1** (FFmpeg 8.1.2 внутри).
Первая установка обязана сверить SHA-256. При несовпадении — остановиться и спросить человека.

### 3.6. Где лежит runtime

В настройках плагина у каждого компонента (`adb`, `scrcpy`) есть путь к **папке компонента**:

| Значение | Папка |
|---|---|
| пусто (по умолчанию) | `%LOCALAPPDATA%\SPLA\runtime\android\<component>\`. Общая для пользователя, рядом с `%LOCALAPPDATA%\SPLA\logs\` |
| относительный путь | относительно **каталога файла проекта** (`ResolvedSettings.ProjectFilePath`). Без проекта — ошибка конфигурации, видна в статусе |
| абсолютный путь | как есть. Можно указать папку уже установленного platform-tools |

Кнопки установки на странице плагина ставят компонент **в папку, которую сейчас показывает поле**.
В папке лежит `spla-runtime.json` — квитанция установки: версия, канал, URL, SHA-256, `verified`,
время установки. Установка идёт через временную соседнюю папку, которая подменяет прежнюю только
после проверки. Полупоставленного компонента не бывает.

Правило «относительно проекта» — первая версия. Пользователь пометил, что его, возможно, доработают.

### 3.7. Два исполнителя за одним интерфейсом

Сессия устройства работает через один из двух backend:

| backend | экран | ввод | когда |
|---|---|---|---|
| **scrcpy** | поток + LatestFrame, размер кадра = `max_size` | control socket, многопальцевый ввод | основной |
| **adb** | `screencap -p`, родное разрешение | `input tap/swipe/keyevent/text`, один палец | scrcpy/декодер не установлен или не стартовал |

Модели всегда сообщается **пространство координат**: размер последнего снимка в пикселях. Все
координаты в инструментах даются в этом пространстве. В adb-режиме многопальцевые инструменты
отказывают с понятной причиной.

Такой порядок позволяет сначала построить простой adb-backend и получить работающий, хоть и медленный
продукт, а потом добавить scrcpy, не трогая инструменты.

### 3.8. Устройство — аренда на чат

Устройство одно, пальцев на нём не может быть два хозяина. Реестр сессий общий на процесс и ведётся
по серийному номеру. Чат **арендует** устройство (`android_connect`), а другой чат получает отказ с
именем арендатора. Взять устройство силой можно только явным `take_over: true`.

Уведомления о закрытии чата пока нет (ADR_20260828 открыт). Поэтому аренда снимается ещё и по простою:
`idle_disconnect_minutes`, по умолчанию 15. Если ровно одно авторизованное устройство свободно,
инструменты подключаются к нему сами, без явного `android_connect`.

### 3.9. Безопасность и происхождение

- **Экран личного телефона — неназванный источник.** Модель на нём видит чужие сообщения, уведомления,
  веб-страницы, рекламу. Снимок помечается `DataOrigin` с `OperatorNamed = false`, как снимок браузера,
  и поднимает сомнение чата. В ядро добавляется фабрика `DataOrigin.Device(string serial)` → зона
  `android:<serial>`. Плагин сам зону не выдумывает.
- Честные декларации инструментов (подробная таблица — в плане):
  - снимок и структура экрана — Read/Low;
  - касания, клавиши, текст — Write/Medium: они действуют от имени владельца в его мессенджерах
    и банке;
  - установка APK — Execute/High;
  - `android_shell` — Shell/Execute/High.
- `FLAG_SECURE` (банки, пароли) даёт чёрный кадр. Это ожидаемо, **не обходится**
  (та же граница, что с обходом bot-detection в браузере).
- Ввод текста через буфер обмена (`SET_CLIPBOARD` + paste) **перезаписывает буфер телефона**.
  Поэтому этот способ выбирается только когда в тексте есть не-ASCII, и в результате инструмента
  это прямо сказано.
- Всё, что модель передаёт в **shell устройства** (имена пакетов, пути), проверяется или экранируется.
  Исключение одно — `android_shell`: его смысл и есть свободная команда.

### 3.10. Настройки и страница плагина

Страница плагина — собственный web-бандл (`web_settings_entry`), по образцу ssh/sql. На ней:

- у ADB и у scrcpy — поле пути (подсказка: куда ляжет при пустом), строка статуса (установлено: версия,
  канал, verified, где), кнопки **«Установить <закреплённая версия>»** и **«Установить latest
  (экспериментально)»**;
- параметры потока: `max_size`, `max_fps`, `video_bit_rate`, `stay_awake`, снимок после действия,
  `settle_ms`.

Установка — транзакция по явной кнопке (обратимые преференсы применяются сами, опасное — только кнопкой). Идёт через уже существующий
`ISplaPluginAction` (`plugin.action`), **без изменений хоста**. `invoke` в web-клиенте ограничен
15 секундами, поэтому действие установки **только запускает фоновую задачу** и сразу возвращается,
а панель раз в секунду опрашивает `runtimeStatus` (стадия, байты).

## 4. Чего не делаем (сейчас)

- Linux/macOS runtime: манифест ведётся по платформе `win-x64`, для остальных — Degraded
  «не поддерживается».
- Звук, камера, виртуальные дисплеи, UHID-клавиатура из scrcpy.
- Беспроводное сопряжение (`adb pair` с кодом): код — секрет, отдельный разговор. `adb connect host:port`
  к уже сопряжённому устройству — есть.
- Живая панель для человека: отдельная волна «по желанию», построенная на том же LatestFrame.
- Несколько устройств в одном чате одновременно.

## 5. Открытые вопросы

1. SHA-256 для Platform Tools r37.0.0 получен из разговора, не из первоисточника (Google публикует SHA-1
   в `repository2-*.xml`). Первая установка его сверит. Если не сойдётся — решает человек.
2. Помечать ли экран телефона как неназванный источник (§3.9). Выбран честный вариант, но цена у него
   есть: каждый чат с телефоном будет «в сомнении». Пересмотреть после недели живого использования.
