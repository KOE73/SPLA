# ADR_20260911-2_agent — AGENTS.md: режим на роль и правила по дереву папок

Статус: **принято** (2026-09-11), не реализовано. Ветка: `work`.

План работ: [`PLAN_20260911_agent_roles-agents-md-compact`](../plans/PLAN_20260911_agent_roles-agents-md-compact.md).

Смежное: [`ADR_20260911-3_agent_compaction`](ADR_20260911-3_agent_compaction.md) (сжатие истории —
пометки этого ADR его переживают), [`ADR_20260827-2_core_roles`](ADR_20260827-2_core_roles.md)
(роли), [`agents/composition.md`](../../agents/composition.md) (сборка системного промпта),
модель зон (корень = каталог `.spla`).

---

## 1. Что случилось

Агент SPLA, запущенный в папке рядом со «взрослыми» агентами (Codex, Claude Code, Cursor), тянет их
AGENTS.md к себе. Узкой роли — переводчику, классификатору, задаче чистого рассуждения — эти правила
не нужны: они съедают контекст и сбивают маленькую модель.

Выяснилось, что загружает файл не код. Настройка для файлов инструкций есть — `instructions:` в
манифесте и в роли (`null` = наследовать, `[]` = ничего), и в `spla.spla`, `roles/scout.yaml`,
`roles/planner.yaml` там уже стоит `[]`. Файл приходит через одну строку во фрагменте возможности
`core.workspace` (`src/agent/SPLA.Agent/Features/CoreWorkspace/prompt.md`):

> IMPORTANT: At the start of every session, look for an AGENTS.md file in the working directory
> (and its parents). If found, read it before doing any other work…

Это приказ модели, а не механизм. Его не выключает никакая настройка, и «(and its parents)» уводит
поиск выше корня проекта — вложенный проект внутри репозитория SPLA находит корневой AGENTS.md
чужих агентов. Ровно исходная жалоба.

Вторая половина проблемы — дерево. В реальном репозитории AGENTS.md лежит не один:

```text
repo/AGENTS.md
repo/src/AGENTS.md
repo/src/backend/AGENTS.md
repo/src/frontend/AGENTS.md
```

У современных агентов семантика у такого файла **по папке**: он действует на свой каталог и всё
поддерево, более глубокий главнее родительского, соседние ветки друг о друге не знают. Загрузить все
файлы в начале сессии нельзя: неизвестно, куда агент пойдёт, а склейка всех файлов даёт лишний
контекст и противоречия между соседями.

## 2. Решение

### 2.1. Режим — одна настройка, два значения

```yaml
agent:
  agents_md: inject   # inject | ignore
```

- `inject` — механизм этого ADR работает: корневой файл в промпте, вложенные по мере захода в папки,
  запрет записи до правил (§2.6).
- `ignore` — SPLA не трогает AGENTS.md совсем: ни корень, ни потомков, ни запрета записи. Для задач
  чистого рассуждения, которым файлы не нужны.
- Ключ не указан — значение наследуется по каскаду (машина → проект → роль), как все остальные
  настройки `agent:`. Отдельного значения `inherit` нет: у нас наследование — это отсутствие ключа.
- По умолчанию для основного режима — `inject`: совместимость с Codex/Cursor/Copilot.

Роль задаёт то же поле в своём файле. Для роли настройка обязательна по смыслу (узкие роли —
главные потребители `ignore`), но не по синтаксису: не указала — наследует.

**Никакого `auto`.** Поведение не выводится из имени, размера или «ума» модели: такая семантика
непредсказуема, и её нельзя проверить глазами в манифесте.

### 2.2. AGENTS.md грузится одним механизмом

Корень и потомки идут через `agents_md`, а не через `instructions:`. Без корня нет и потомков: это
одна цепочка, и делить её между двумя настройками значит однажды получить половину.

`instructions:` остаётся, но это **собственный текст роли или воркера**, а не правила проекта: у
`roles/coder.yaml` там `agents/csharp.md`, у demo-воркеров `prompt.md`. Если в список положили
AGENTS.md, при загрузке настроек пишется предупреждение и файл из списка пропускается — иначе он
попал бы в промпт дважды.

Строка «look for an AGENTS.md…» из `core.workspace` удаляется целиком. Всё решает код; в промпте
остаётся только объявление семантики блоков (§2.4), и только при `inject`.

### 2.3. Граница поиска — корень `.spla`

Цепочка строится от каталога `.spla` (корень проекта, тот же, что у модели зон) вниз до папки, в
которую идёт вызов. Выше корня поиск не поднимается никогда — это само по себе лечит исходный случай
вложенного проекта.

Не участвуют:

- **`mnt/`** — у подключённой папки нет общего корня с проектом, а AGENTS.md из папки с
  `trust: untrusted` был бы готовым каналом инъекции: «правила», которые туда положил кто-то чужой;
- **shell** — `git apply`, `sed`, `dotnet format`, `find -exec` трогают произвольный набор файлов,
  статически путь не определить. Это известный обход, тот же, что у зон; записан явно;
- пути вне корня проекта.

### 2.4. Системный промпт: стабильное — вперёд, области — в самый хвост

```text
StableSystemPrompt      ← includes the <agents> semantics declaration, always present under inject
RootAgents              ← <project root>/AGENTS.md
…(the existing dynamic contributors: skills, working memory)…
ResolvedScopedAgents    ← absolute last
```

Объявление семантики — на английском (правило 8 `agents/sys_prompt_rules.md`), при реализации
сверяется с этим файлом, по смыслу:

```text
Project instructions may appear below as <agents> blocks.
Each block is authoritative for its declared scope (a folder and everything under it).
A narrower scope overrides a broader one on conflict.
Sibling scopes are independent: a block for one folder says nothing about another.
```

Три уточнения, без которых порядок стабилен только на бумаге:

1. **Объявление стоит в стабильной части с первого хода** при `inject`, даже если вложенных областей
   ещё нет. Иначе первая же область меняет не только хвост.
2. **`ResolvedScopedAgents` — последний участник сборки**, после `WorkingMemoryContributor`: рабочая
   память `context:` и активные навыки уже меняют промпт посреди сессии, и области не должны
   сдвигать то, что стоит за ними.
3. **Порядок внутри секции детерминированный:** области в порядке первого входа, внутри цепочки —
   от корня вглубь. Одна и та же история всегда даёт один и тот же промпт.

Формат блока:

```text
<agents scope="src/backend" source="src/backend/AGENTS.md">
…file content verbatim…
</agents>
```

Текст файла не режется: обрезанные правила хуже никаких. Выше порога размера (выбирается при
реализации) — предупреждение в журнал.

### 2.5. Пометка области — отдельная запись истории

Вход в новую область отмечается записью в истории чата:

| Поле `ChatMessage` | Значение |
|---|---|
| `MsgId` | `R-<n>` — новый префикс, `Conversation.GenerateMsgId` |
| `ScopeMarker` | `"src/backend"` — путь области от корня проекта, прямые слеши, никогда не корень |
| `CreatedAt` | время вставки |

Больше в записи ничего нет: ни текста файла, ни хэша, ни вызова.

- **В модель не уходит** — `ContextAssembler.ShouldSend` возвращает `false`, как для меток
  (`IsLabel`). Поэтому её можно добавлять в любой момент, в том числе посреди пачки результатов: пару
  `tool_calls`/результаты она не рвёт.
- **Сохраняется в YAML всегда**, независимо от `saveToolCalls` (вызовы инструментов по умолчанию не
  сохраняются вовсе — именно поэтому выводить области из аргументов вызовов было бы нельзя).
- **Пишется один раз** — при первом входе. Проверка при создании: область уже покрыта, если есть
  пометка с тем же путём или с путём глубже внутри него (пометка `src/backend` покрывает `src/` —
  цепочка всё равно строится от корня). Пометок столько, сколько затронуто AGENTS.md, а не вызовов.
- **Что пишется в пометку:** самая глубокая папка на пути вызова, в которой есть AGENTS.md. Вызов в
  `src/backend/x/y.cs`, где AGENTS.md есть только в `src/` и `src/backend/`, даёт пометку
  `src/backend`. Нет ни одного вложенного AGENTS.md на пути — пометки нет.
- **Сборщик на каждой отправке** проходит пометки текущей истории, строит по каждой цепочку от корня
  (корень исключён — он в `RootAgents`), убирает повторы, читает файлы (кэш по пути + mtime) и выводит
  блоки в `ResolvedScopedAgents`. Файл исчез — блок пропускается. Правила всегда актуальны: текста в
  истории нет, и «старая версия в истории, новая после неё» не бывает.

### 2.6. Запрет записи до правил

Вызов, который **пишет** (создать, записать, пропатчить, удалить — `EdgeClassifier` уже различает
чтение и запись), в область, ещё не покрытую пометкой:

1. ставит пометку;
2. **не выполняется** — возвращает отказ: правила для `<scope>` загружены, они в инструкциях со
   следующего шага, прочитай и повтори, если вызов им соответствует;
3. на следующей отправке правила уже в хвосте промпта, отказ — в истории; повтор проходит, потому что
   область покрыта.

Особого состояния «ждём повтора» нет: отказ сам ставит пометку.

Чтение, список, поиск выполняются сразу, пометку ставят попутно: правила придут на следующей отправке
вместе с результатом. Поиск по каталогу даёт цепочку до самого каталога, но не AGENTS.md из тех
подкаталогов, где нашлись совпадения.

### 2.7. Откат, ответвление, сжатие — без единой строки особого кода

- **Откат** (к отметке, к контрольной точке) обрезает историю — пометки после якоря уходят вместе с
  остальным, и на следующей отправке их блоков в промпте нет. Агент «забывает, что лазил в папку».
- **Ответвление** копирует историю до точки — копирует и пометки до неё.
- **Сжатие** ([`ADR_20260911-3`](ADR_20260911-3_agent_compaction.md)) пометки не видит: они не
  уходят в модель, значит, сжимать нечего; они остаются на месте и продолжают работать.
- **Подагент** считает по своей истории; режим наследует от своей роли, дальше по каскаду.

## 3. Цена: кэш префикса

Всё после изменённого места пересчитывается заново, а после системного промпта идёт вся переписка.
Значит, новая область, правка AGENTS.md или откат, убравший пометку, — пересчёт всей истории. На
локальной модели при 30k токенов это десятки секунд.

Принимаем сознательно, потому что:

- событие редкое: новые папки появляются в начале работы, дальше с ними долго работают, так что
  сброс приходится на момент, когда история ещё короткая и пересчёт дешёвый;
- механизм без текста в истории заметно проще любого варианта с ним.

**Условие проверки:** замер на живом LM Studio (время обработки промпта до и после входа в новую
область на длинной истории). Если окажется больно — меняется только место, куда сборщик выводит
текст (§4.1); пометки, их учёт, откат и запрет записи остаются.

## 4. Рассмотренные варианты

### 4.1. Текст правил в истории (запасной)

Блок `<agents>` приклеивается к результату инструмента или отдельной записью с ролью `User` в месте
первого входа. Кэш не страдает: контекст только растёт.

Отклонено как основной, потому что:

- в истории оседает текст файла; при правке AGENTS.md получается «старая версия, потом новая», и
  модели надо объяснять, какая главнее;
- поле на результате инструмента пропадает при сжатии вместе с вызовом и висит на всех инструментах,
  которым оно не нужно;
- запись с ролью `User` надо особо рисовать в интерфейсе, иначе она выглядит репликой человека;
- `System` в середине истории ломает шаблоны многих локальных моделей (Qwen и др.).

Остаётся запасным на случай, если замер из §3 окажется плохим.

### 4.2. Все пути из вызовов в истории, без пометок

Вычислять затронутые области разбором аргументов всех вызовов при каждой отправке. Отклонено:
разбор каждый раз вместо готовых записей, и вызовы инструментов по умолчанию не сохраняются в YAML —
после переоткрытия чата области пропали бы.

### 4.3. Пометка на каждый вызов + порядок по частоте

Писать пометку на каждое обращение и ставить первыми правила самых посещаемых папок («внимание ближе
к краям контекста»). Отклонено:

- счётчики меняются почти на каждом вызове — порядок блоков тоже, а это пересчёт всей истории на
  каждом ходу;
- вся секция и так в начале контекста, перед всей историей; разница позиций внутри неё — десятки
  токенов на фоне десятков тысяч; старшинство задано глубиной и объявлено явно, порядок блоков для
  модели смысла не несёт.

Отложенная идея, если частота когда-нибудь понадобится: считать её рядом (как `EdgeLedger` считает
рёбра), а переставлять только в моменты, когда кэш и так сбрасывается (новая область, сжатие).

### 4.4. Отдельная настройка поверх `instructions:` с тремя значениями `inherit | inject | ignore`

Из исходного абстрактного черновика. `inherit` у нас — отсутствие ключа; третье значение только
дублирует каскад.

### 4.5. `mode: auto` по модели

См. §2.1 — непредсказуемо, непроверяемо.

## 5. Следствия

- Узкие роли (`ignore`) получают промпт без чужих правил — исходная жалоба закрыта.
- Для этого репозитория меняется поведение основного чата: сейчас корневой AGENTS.md модель читает
  сама по приказу промпта, после — он в промпте всегда при `inject`. По содержанию то же, по
  механизму детерминированно.
- Нужны выбор роли при создании чата (web, кнопка «+ Новый» с выпадающим списком ролей) и `--role` в
  `spla chat run` — иначе `ignore` у роли недостижим для узкой задачи. Это входит в тот же план и идёт
  первым.
- Окно отладки промпта показывает блоки областей через манифест сборки — механизм видим.
