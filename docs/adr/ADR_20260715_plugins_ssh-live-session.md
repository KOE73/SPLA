# DESIGN: SSH live-session tools — поток, экран, диалоги

Статус: принято к реализации (2026-07-14). Контекст: обсуждение после инцидентов
«ubuntu upgrade завис на debconf-диалоге, агент молча ждал» и
«`sudo reboot; echo __SPLA_END__` — сентинел не придёт никогда».

## Проблемы, которые решаем

1. `ssh_session_exec` блокируется до сентинела → интерактивный диалог или reboot вешают turn навсегда; человек вынужден вмешиваться руками.
2. Полноэкранные программы (top, debconf, whiptail, меню со стрелками) для агента нечитаемы: он видит сырой поток escape-кодов, а не экран.
3. Большие выводы (55k+ chars) и повторные «скрины» раздувают контекст.

## Ключевые решения и почему

### 1. Не будить агента — возвращать управление (timeout как у Claude Code Bash)

Инструмент, а не планировщик, отвечает за время. `ssh_session_exec` получает
`timeout_s`; по истечении возвращает НЕ ошибку, а `status: running` + новый вывод.
Turn продолжается, модель решает сама: ждать / отвечать в диалог / спросить человека.
Отвергнуто: «будить агента посреди работы инструмента» (ломает модель turn'а),
субагенты (работа последовательная: жди→смотри→решай, параллелизм не нужен).

### 2. Кольцевой буфер + курсоры читателей

pty пишет весь вывод в ring buffer на сервере (~256KB) непрерывно.
У каждого читателя (агент, живой терминал человека, лог) — свой курсор.
`exec` и `wait` — один механизм чтения с курсора; между вызовами ничего не теряется.

### 3. Сентинел + disconnect-as-result

Конец команды в интерактивном шелле определяется сентинелом
(`; echo __SPLA_END_<rand>__$?`). Разрыв соединения — это тоже РЕЗУЛЬТАТ:
read-loop обязан немедленно вернуть «connection closed by remote (вероятно reboot)»,
а не висеть. Это закрывает кейс reboot: дальше модель в цикле wait/reconnect
с нарастающим интервалом.

### 4. Серверный VT-эмулятор экрана

У SSH-соединения экрана нет — экран существует только у интерпретатора потока.
Рядом с ring buffer тот же поток прогоняется через VT100/xterm-парсер,
поддерживающий сетку Cell[rows,cols] (символ + атрибуты: цвет, инверсия, bold).
Библиотека: начать с готовой (кандидат — VtNetCore, MIT, C#); свой парсер «на 80%»
ломается ровно на тех ncurses-диалогах, ради которых всё делается.

Размер — свойство pty, объявляется при открытии и меняется window-change.
Один авторитетный размер на сессию (показывать в списке сессий, напр. `100×80`).

Resize человеком в произвольный момент — штатно:
- resize идёт через ту же очередь событий сессии, эмулятор атомарно пересоздаёт сетку;
- инструменты НИКОГДА не кешируют координаты/экран между вызовами — каждый шаг
  перечитывает состояние, поэтому resize между шагами безвреден;
- каждый кадр аннотирован своим размером; если размер изменился во время
  send_keys/dialog_choose — шаг просто перечитывает экран и продолжает;
- опционально: пока инструмент в settle-окне (~200мс после нажатия), resize
  откладывается до конца окна.

### 5. Набор инструментов (лесенка от дешёвого к точному)

| Tool | Что делает |
|---|---|
| `ssh_session_exec(cmd, timeout_s)` | пишет команду, ждёт сентинел до таймаута; возвращает новый вывод + status running/done/disconnected |
| `ssh_session_wait(timeout_s, until?)` | читает с курсора дальше до regex/сентинела/таймаута/разрыва |
| `ssh_session_screen()` | отрендеренный экран (24 строки текста) с аннотацией фокуса: выделенные (reverse video) регионы помечены `>>Ok<<`; отдаёт «экран не изменился», если кадр тот же |
| `ssh_session_send_keys(keys)` / `send_text` | стрелки/Tab/Enter/Esc в pty; ВСЕГДА возвращает экран после нажатия (settle ~200мс) + краткий diff («фокус: Ok → Cancel») |
| `ssh_dialog_choose(label)` | намерение вместо механики: детерминированный цикл в C# жмёт Tab/Down, по атрибутам находит выделенный регион, сравнивает с label, Enter; лимит шагов, при зацикливании — ошибка + экран |

Баланс «маленькая сеть vs умный инструмент»: модель говорит «выбери Install»,
перебор фокуса делает код без LLM-токенов. `send_keys` — ручной запасной режим.

### 6. Экономия контекста (без обучения модели — руками хоста)

- Кадры экрана помечаются ephemeral/volatile: при появлении нового кадра той же
  сессии старый заменяется в контексте заглушкой `[кадр экрана 14:32, устарел]`.
  В живом контексте — максимум один кадр на сессию. Использует существующий
  механизм IsEphemeral (ChatMessage → ContextAssembler его отфильтровывает).
- exec/wait возвращают только новый хвост (~2KB) + счётчики; полный лог — в файл
  workspace, в результате ссылка.

### 7. Детектор «завис на вопросе»

После N секунд тишины смотреть не на последнюю строку потока (для ncurses это мусор),
а на отрендеренный экран; отдавать его в ProgressScope («похоже, ждёт ввода: …»)
— человек видит в прогресс-карточке чата, модель получит при таймауте exec.

## Дополнение (2026-08-01): маркер, который никогда не напечатается

Завершение команды детектируется ТОЛЬКО по маркеру (`cmd; echo MARKER$?`). Значит любая
ситуация, в которой маркер физически не может напечататься, навсегда заклинивает сессию:
`_run != null`, и каждый следующий `ssh_session_exec` отказывает с «a command is still
running», хотя шелл давно вернул приглашение. Единственным выходом было закрыть сессию.

Найдены и закрыты обе причины. Обе закрыты в коде, а не инструкцией в промпте: правило,
которое надо помнить на каждой команде и каждой моделью, будет забыто.

1. **Пейджер.** `systemctl status` / `journalctl` / `git log` / `man` уходят в `less`,
   который ждёт клавишу. Человек видит мигающий курсор и `lines 1-44`, агент — «команда не
   завершилась» (и он прав). Лечение: `SshLiveSession` при открытии пишет в pty
   `export PAGER=cat SYSTEMD_PAGER=cat GIT_PAGER=cat MANPAGER=cat LESS=FRX`. Строка видна
   человеку в терминале — так же, как эхо маркера: transparency over cosmetics.
   Список утилит с пейджером открытый, поэтому закрываем класс, а не перечисляем случаи.

2. **Ctrl+C снаружи.** По SIGINT bash отбрасывает остаток строки вместе с `; echo MARKER$?`.
   Внутренний путь `interrupt_on_timeout` это знал и добивал run руками, а `ssh_session_send
   ctrl_c` делал голый `Write("\x03")` — и оставлял run висеть. Теперь есть
   `SshLiveSession.InterruptAsync`: прерывает, ПРОВЕРЯЕТ пробой (`echo PROBE$?`), что шелл
   вернулся, и закрывает pending-run. Статусы: `interrupted` / `done` (успела завершиться
   сама) / `still-busy` (терминалом владеет полноэкранная программа — Ctrl+C её не берёт,
   нужен `q`) / `idle` / `disconnected`. Проба различает эхо своей же строки и результат по
   тому же приёму, что и основной маркер: в эхе стоит литерал `$?`, в выводе — цифры.

Сопутствующее, чтобы модель не ходила по кругу:

- `ForceReleaseRun()` + `force=true` у `ssh_session_exec` — escape hatch: сначала вежливо
  (Ctrl+C), не помогло — забыть run и выполнить команду. В ответе честно сказано, что
  брошенная команда может быть жива и её поздний вывод может подмешаться.
- Токены `__SPLA_END_*` / `__SPLA_PROBE_*` вычищаются глобально (`SplaNoiseRx`), а не только
  маркер текущего run: осиротевший после интеррапта маркер не должен всплыть в выводе
  следующей команды и быть прочитан как результат.
- Пассивный watch по таймауту возвращает `quiet`, а не `running` — раньше `ssh_session_wait`
  писал «STILL RUNNING», когда не выполнялось вообще ничего.
- Тексты всех статусов теперь заканчиваются явным списком «pick ONE: …» и прямым запретом
  повторять тот же вызов. Пустой вывод за окно ожидания отдельно помечается как «скорее
  всего ждёт нажатия клавиши».

НЕ проверено на живом хосте — только сборка.

## Дополнение (2026-08-10): размер pty перестал быть фикцией

Пункт 4 плана («resize-политика») ждал VT-эмулятора, но живой xterm в браузере упёрся в это
раньше: `SshTerminalManager.Resize` был честным no-op с комментарием «у SSH.NET нет post-open
resize». Размер оставался тем, с которым pty родился (у агентских сессий — дефолтные 120×30)
навсегда.

Это не косметика. Всё, что рисует шелл, считает от `COLUMNS` НА ТОЙ стороне:

- readline переносит строку и возвращает курсор по своей ширине — стрелки и история наезжают
  на предыдущую строку, курсор «уезжает вверх»;
- полноэкранные программы (far2l, htop, vim) рисуют в прямоугольник размером с момент
  открытия, остальное окно остаётся мёртвым полем.

Ничем, что клиент шлёт как обычный ввод, это не лечится: размер живёт в pty на удалённой
стороне и меняется только запросом канала `window-change`.

SSH.NET такого API не даёт (геометрию фиксирует `CreateShellStream`), но САМ запрос в
библиотеке есть — `IChannelSession.SendWindowChangeRequest`, просто интерфейс internal, а
канал лежит в приватном поле `ShellStream._channel`. `SshLiveSession.Resize` берёт его
рефлексией; если будущий SSH.NET переименует любого из двоих, `SupportsResize` станет false и
resize деградирует до прежнего no-op вместо исключения. Рефлексия молча гниёт при обновлении
пакета, а симптом был бы удалённым и незаметным — поэтому оба члена прибиты тестом
`SshTerminalResizeTests`.

Политика при нескольких зрителях одной сессии: ПОБЕЖДАЕТ ПОСЛЕДНИЙ resize — этого ждёт
человек, который тянет своё окно; остальные зрители перестроятся на своём следующем resize.
Отдельный случай — ПОДКЛЮЧЕНИЕ к чужой сессии (`terminal.open` с `session`): pty всё ещё
чужого размера, поэтому геометрия зрителя применяется сразу при attach, а не ждёт первого
перетаскивания рамки.

Со стороны клиента к этому прилагались две ловушки вёрстки, без которых сервер получал бы
неверные числа: `initialWidth` в dockview применяется к ГРУППЕ, поэтому каждая новая вкладка
терминала сбрасывала ширину колонки, растянутой руками; а `min-width` flex-элемента по
умолчанию `auto`, из-за чего элемент xterm (он округляет ширину вверх до целых знакомест)
становился полом, ниже которого панель не сжималась, и `fit()` читал обратно раздутую ширину.

НЕ проверено на живом хосте — только сборка и типы.
