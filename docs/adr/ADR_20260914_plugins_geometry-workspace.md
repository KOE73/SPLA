# ADR_20260914_plugins_geometry — интерактивный geometry workspace для LLM

Статус: **принято** (2026-09-14) для v1 (Box + Crop Stack). Pose и Polygon — не отвергнуты, но за
рамками этого ADR: решение по ним откладывается до отдельного расширения, когда появится живой
потребитель. План реализации — отдельным документом (`PLAN_` пока не написан).

---

## 1. Задача

Модель плохо работает как пиксельная линейка: угадать координаты/угол/размер объекта с одного взгляда
на изображение получается ненадёжно. При этом модель хорошо **видит** объект и хорошо **решает**, куда
и насколько его подвинуть, глядя на уже нарисованный результат.

Нужен инструмент, который переносит вычисление точных координат с модели на детерминированный код, а
модели оставляет только цикл «предположила → посмотрела на рендер → поправила → приняла»:

```
box.add (примерно)
  → render (картинка с рамкой)
    → модель видит ошибку
      → box.update (уточнение или delta)
        → render
          → … пока не box.accept
```

Ведущий кейс — разметка мешка и маркировки на нём на кадре с камеры (крупный OBB мешка → crop →
мелкий OBB маркировки внутри). Именно этот кейс проверяет архитектуру, но не определяет интерфейс
инструмента: см. §3.1.

## 2. Почему это соответствует доктрине проекта

По `AGENTS.md` (Doctrine): инструмент должен забирать у модели длинную цепочку рассуждений и
оставаться полезным даже с более сильной моделью. Здесь цепочка — «зрительная оценка → перевод в
точные числа → проверка результата» — заменяется на «зрительная оценка → решение о поправке»; перевод
в числа, хранение состояния и рендер уходят в инструмент. Это не костыль для слабой модели: даже
сильная модель не умеет надёжно называть пиксель по одному кадру, а этот инструмент даёт ей закрытый
цикл проверки, которого никакой чат-клиент структурно не предоставляет.

## 3. Решения

### 3.1. Инструмент ничего не знает про домен

Никаких `class_id`, `class_name`, `bag`/`mark` внутри реализации. Объект в сессии идентифицируется
произвольной строкой `name`, которую передаёт вызывающий (модель или skill). Мешки и маркировка —
пример использования, живущий в promt/skill вызывающей стороны, а не в плагине.

Отвергнуто: специализировать инструмент под задачу мешков сразу («быстрее для одного кейса») — тогда
инструмент перестаёт быть тем, что доктрина требует строить: узким переиспользуемым усилителем, а не
разовым скриптом под задачу.

### 3.2. v1 ограничен типом Box (OBB); Pose и Polygon — не в этой версии

Box v1:

```
{ name, cx, cy, width, height, angle }
```

Причина сузить: Box уже проверяет весь цикл (add → render → update/delta → accept) и весь Crop Stack
(§3.3) на реальном кейсе (мешок снаружи, маркировка внутри — оба Box). Pose требует отдельного
конструкта (topology, active point, state machine unplaced/active/fixed — §6 исходной идеи) и
Polygon — своего (add_point/insert_point/delete_point). Делать оба типа сразу в первой версии —
рискует утопить проверку основной идеи (visual feedback loop) в объёме кода, которого никто ещё не
проверил на практике.

Открытый вопрос: топология Pose — часть контракта инструмента (см. исходную идею §6) или должна
задаваться вызывающей стороной динамически. Решается отдельным ADR при реализации Pose.

### 3.3. Crop Stack — в v1, с explicit transform, не только offset

Каждый `view` (source или crop) хранит матрицу перехода `parent_to_view` / `view_to_parent`, не пару
`offset_x/offset_y`. Причина: offset работает только для AABB-crop без поворота; OBB-мешок задаёт
crop под углом, и ADR сразу закладывает affine, чтобы не переделывать формат сессии, когда понадобится
resize/rotation.

Операции v1: `crop.push`, `crop.pop`, `crop.list`, `crop.set_current`. `crop.pop` не удаляет crop —
только переключает текущий view; дерево views остаётся в сессии.

Координаты объекта модель передаёт **в текущем view**; инструмент сам умеет пересчитать в любой другой
view и в `source`, начиная от точки цикла, когда это понадобится (§3.5). Модель не занимается affine-
арифметикой ни в каком виде — ни явно, ни через передаваемые ей формулы.

Отвергнуто на этом шаге: perspective correction — усложняет матрицу с affine до гомографии без
проверенной потребности; можно добавить позже, не меняя контракт (`transform` остаётся непрозрачным
для модели объектом).

### 3.4. Инструмент абсолютно stateless между вызовами; state — в сессии

Каждый вызов инструмента: прочитать сессию → применить операцию → сохранить сессию → рендер →
вернуть результат. Модель не является источником истины о геометрии — источник истины сессия.

### 3.5. Хранение сессии v1 — per-chat blob, не файл

Решение, отличное от исходной идеи (`file:/aaa.json`, персистентно, переживает перезапуск): в v1
сессия живёт в существующем `IBlobStore` ([[data-channel-blob]] в терминах памяти агента) — то есть
**в памяти чата**, не переживает перезапуск процесса/сервиса.

Причина: `IBlobStore` уже есть, per-chat, ничего нового строить не нужно для v1. Это не временная
экономия в ожидании персистентности — задача массовая (разметка потока кадров/датасета), и рабочая
единица одна: один кадр размечается за один ход/чат, принимается (`box.accept`) и отдаётся вызывающей
стороне; следующий кадр начинается с чистой сессии. Восстановление сессии после перезапуска процесса
не нужно **по природе задачи**, а не потому что до него не дошли руки.

Если позже появится сценарий, где одна сессия должна пережить перезапуск (не пакетная разметка, а
разметка одного длинного документа/видео с паузами) — это меняет предпосылку задачи, а не реализацию
v1, и решается отдельным ADR: контракт сессии (JSON-модель) не завязан на `IBlobStore` и переносится
на диск без переделки инструментов Box/Crop.

### 3.6. Рендер возвращается моделью как картинка, не только JSON

`render` — отдельная операция, результат — `ToolImage` (по образцу `BrowserScreenshotTool` /
`android_screenshot`), плюс текстовая сводка (текущий view, размеры, что нарисовано, что active).
Именно видимый результат, а не JSON с координатами, замыкает цикл — это был центральный вывод
исходного эксперимента, зафиксированного в §18 исходной идеи.

Сетка (§19 исходной идеи) — необязательный флаг `render(grid=true)` для отладки, не режим по
умолчанию: она была костылём для one-shot угадывания координат, который сам цикл render→update уже
снимает.

### 3.7. Новый плагин, не расширение существующего

`SPLA.Plugins.Geometry` — отдельный плагин, а не часть `SPLA.Plugins.Browser` или другого
image-плагина. Причина: инструмент общего назначения (работает с любым `image_ref`, не обязательно со
скриншотом сессии браузера/устройства), и его жизненный цикл (сессии разметки) не связан с жизненным
циклом браузерной/device-сессии. Инфраструктура картинка→модель (`ToolImage`, `DataOrigin`) —
переиспользуется, код — нет.

## 4. Границы v1 (что НЕ входит)

- Pose, Polygon — см. §3.2.
- Персистентная сессия на диске — см. §3.5.
- Perspective/гомография в Crop Stack — см. §3.3.
- SAM/автогенерация стартовой геометрии — исходная идея (§11) упоминает это как отдельный будущий
  генератор стартовой маски; в v1 стартовая геометрия — только от модели (`box.add` с грубой оценкой).
- Live-панель для человека (аналог `android.screen`) — не рассматривалась, не нужна: потребитель
  рендера — модель, не оператор.

## 5. Открытые вопросы (для PLAN)

1. Формат имени инструментов: `geometry_*` по конвенции `agents/plugins.md` (`session_open`,
   `box_add`, `box_update`, `crop_push`, `render`, …) — точный список действий и их аргументов
   решается в плане, не в этом ADR.
2. Как модель ссылается на исходное изображение при `session.create` — путь на хосте, `blob:`-хендл
   из другого инструмента, или оба варианта (по аналогии с `system_write_file`, принимающим
   `blob:`-хендл, см. память [[data-channel-blob]]).
3. Формат `delta` в `box.update` (§4 исходной идеи) — отдельный параметр или тот же набор полей, что
   и абсолютное обновление, с флагом `relative: true`.
4. Нужен ли `history`/`undo` уже в v1, или это первое расширение после проверки основного цикла.
