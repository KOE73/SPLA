# ADR_20260731_llm — конвейер, провайдеры, подключения и учёт

Статус: **принято**

Схемы к этому решению: [`ADR_20260731_llm_pipeline-diagrams`](ADR_20260731_llm_pipeline-diagrams.md).
Ход работ и текущее состояние: [`PLAN_20260731_llm_pipeline`](../plans/PLAN_20260731_llm_pipeline.md).
Политика по ключам: [`agents/secrets.md`](../../agents/secrets.md).

Решение о том, как SPLA работает с языковыми моделями: несколько провайдеров вместо одного,
конвейер middleware вместо сквозных `if`, подключения с областями и правами, учёт токенов по
подключению и пользователю.

Legacy нет — система новая, миграций не делаем.

---

## 1. Что есть сейчас

- `ILLMService` — три метода, одна реализация `LMStudioClient` (OpenAI-совместимый провод).
  В продакшене вызывается **только** `SendMessageStreamFullAsync`
  (`ConversationOrchestrator.cs:134`); два других метода живут исключительно в тестовых заглушках.
- Клиент прибит гвоздями: `AgentRuntime.cs:42` объявляет поле конкретным типом, `:91` создаёт через
  `new`. Тот же объект уходит в `SpawnedAgentRunner` (`:117`) и в оркестратор
  (`ChatRuntime.cs:114`).
- Подключения уже есть (`SplaConnectionSection`), мержатся по id между слоями настроек, чат хранит
  `ModelId`. **Поле `provider` объявлено, но нигде не диспетчеризуется** — точка расширения
  прорезана и пуста.
- Управление моделями уже отделено от диалога (`IModelManagementService`) — правильный прецедент.
- Учёт: `ITokenUsageStore` + JSON-файл, три числа (prompt / completion / turns), два экземпляра
  (проект и машина). Разрезов нет никаких.
- Ключ подключения хранится и передаётся открытым текстом — см. `agents/secrets.md` §8.4.

## 2. Принятые решения

| Решение | Обоснование |
|---|---|
| Один метод вместо трёх | Стриминг — это наличие приёмников в контексте, а не отдельный метод. Иначе комбинаторика «3 метода × N провайдеров × M middleware» |
| Конвейер middleware (модель ASP.NET) | Изменчивость лежит вдоль оси «тот же вызов, разные обязательства вокруг него на разных хостах» — это определение сквозной заботы |
| Провайдеры — плагинами | Один механизм расширения вместо двух; LM Studio тоже становится плагином |
| Подключения: области Server / Project / User, доступ через политику | Локально политика разрешает всё, на сервере проверяет роли и группы |
| User-scope подключения на сервере разрешены | Пользователь может завести своё со своим ключом |
| Учёт: справочник типов токенов + лог вызовов + строки токенов | Новый счётчик провайдера = новая строка справочника, без миграции схемы |
| Биллинг отдельно и позже | Лог — факт, деньги — вывод; цены меняются задним числом, факты нет |
| ORM: EF Core, SQLite / PostgreSQL / MSSQL | Путь записи узкий (append-only insert), диалектных различий почти нет |
| **Fallback моделей — нет** | Пользователь выбрал модель и имеет от неё ожидания; молчаливая подмена хуже честного отказа |
| **Удалённые агенты (Antigravity Interactions) — не провайдер** | Это чужой агент, а не LLM. Если понадобится — придёт позже как инструмент плагина |
| **Legacy — нет** | Секция `llm:` и поле `api_key` вырезаются из схемы целиком |

## 3. Контракт хода

```csharp
LlmTurnRequest   // messages, tools, параметры модели, modelId              — что просят
LlmTurnContext   // request + caller + connection + capabilities + приёмники — что знает конвейер
LlmTurnResult    // message, rawUsage{wireName→amount}, modelReported, тайминги, status

interface ILlmGateway { Task<LlmTurnResult> InvokeAsync(LlmTurnContext ctx, CancellationToken ct); }
```

Наружу торчит **только** `ILlmGateway`. `ILlmClient` (провайдерский клиент) не публикуется нигде —
ни оркестратору, ни `SpawnedAgentRunner`, ни плагину. Это единственный способ гарантировать, что
учёт и лимиты не обойдут.

Всё, что меняется от хода к ходу, живёт **в контексте**, никогда в композиции конвейера. Если
возникает желание собрать другой конвейер под конкретный ход — значит, чего-то не хватает в
контексте.

## 4. Конвейер

```csharp
delegate Task<LlmTurnResult> LlmTurnDelegate(LlmTurnContext ctx, CancellationToken ct);

interface ILlmMiddleware {
    Task<LlmTurnResult> InvokeAsync(LlmTurnContext ctx, LlmTurnDelegate next, CancellationToken ct);
}
```

### Канонический порядок

| # | Стадия | Middleware | Зачем именно здесь |
|---|---|---|---|
| 1 | Trace | `Trace` | снаружи всего — отказ по правам тоже должен попасть в трассу |
| 2 | Trace | `ConnectionResolve` | id → дескриптор + провайдер + capabilities; дальше id никто не резолвит |
| 3 | Policy | `Authorize` | можно ли этому caller'у это подключение и эту модель |
| 4 | Policy | `Privacy` | можно ли **этот контент** в **это** подключение |
| 5 | Policy | `Quota` | предпроверка бюджета |
| 6 | Content | `CapabilityGuard` | vision / tools / reasoning против capabilities → ошибка до сети |
| 7 | Content | `ContentPolicy` | даунскейл картинок, лимиты вложений |
| 8 | Retry | `Retry` | только транзиентные, только то же подключение и та же модель |
| 9 | Accounting | `Usage` | `try/finally` вокруг вызова |
| 10 | Transport | `Credentials` | резолв секрета → создание клиента |
| 11 | — | *вызов провайдера* | терминальный шаг |

Три неочевидных решения в этом порядке:

- **`Retry` снаружи `Usage`** — каждая сетевая попытка даёт свою строку лога, потому что каждая
  попытка стоит денег (провайдер может списать prefill даже при обрыве).
- **`Usage` снаружи `Credentials`** — у учёта нет доступа к материалу ключа; плюс при падении резолва
  строка со статусом `credential_error` всё равно запишется.
- **`Privacy` до `Quota`** — запрет по приватности не должен тратить бюджетную квоту.

### Стадии и права на вставку

`Trace | Policy | Content | Retry | Accounting | Transport`

У `Retry` своя стадия именно потому, что порядок задаётся стадией: будь он частью `Transport`, он
оказался бы **внутри** `Accounting`, и три сетевые попытки записались бы одной строкой.

**Плагинам открыты только `Policy` и `Content`. `Accounting` и `Transport` запечатаны хостом.**
Тогда «плагин встал между `Usage` и провайдером и обнулил учёт» невозможно **по построению**, а не по
проверке. Открытые стадии — это и есть слоты под будущие хуки; заранее их назначение не фиксируем.

**Провайдер — не middleware.** Плагин отдаёт дескриптор провайдера в реестр, то есть данные для
терминального шага, а не новый слой.

### Наборы по хостам

| Профиль | Состав | Смысл |
|---|---|---|
| `bare` | Resolve → Credentials → провайдер | без учёта и без зависимостей: не тянется ни EF, ни БД, ни identity |
| `local` | + Trace, CapabilityGuard, Retry, Usage (файл) | CLI, десктоп |
| `worker` | local + Quota (бюджет на прогон / сутки) | воркер крутится без человека, предохранитель обязателен |
| `server` | всё; Usage → БД; Authorize / Privacy / Quota — серверные реализации | |

Профиль выбирает **хост**. Настройка проекта может лишь *попросить* более узкий профиль, а хостовая
политика решает, уважать ли просьбу: локально — да, на сервере — нет. Иначе пользователь отключает
себе учёт правкой своего `.spla`.

Производительность здесь ни при чём: десять переходов по делегатам — наносекунды против секунд
сетевого вызова. Ценность `bare` — в отсутствии зависимостей.

## 5. Сборка и время жизни

В агентном стеке нет DI-контейнера, сборка императивная — ломать это не надо.

1. **Хост, при старте процесса** (`SPLA.CLI/Program.cs`, `SPLA.Server/Program.cs`, воркеры) собирает
   **чертёж** `LlmPipelineBlueprint`: список типов middleware по стадиям + хостовые реализации
   политик (`Permissive…` против `RoleBased…`, файловый ledger против EF). Только здесь хосты
   различаются. Чертёж — данные, не собранный конвейер.

2. **`AgentRuntime`, в конструкторе** печёт конвейер — потому что провайдеры приходят плагинами, а
   плагины включаются по проекту:

   ```
   LoadPlugins()                                  ← сейчас AgentRuntime.cs:100
     → ProviderRegistry.From(plugins)
     → LlmGateway = blueprint.Build(registry, settings)   ← валидация порядка здесь, на старте
     → SpawnedAgentRunner(gateway, …)                     ← сейчас :117
   ```

   Результат — один неизменяемый `ILlmGateway` на рантайм, общий для всех чатов проекта.

3. **На ходе не собирается ничего** — создаётся `LlmTurnContext` и вызывается gateway.

Следствия, которые легко забыть:

- **Не захватывать `ResolvedSettings` в замыкание middleware.** Настройки живые: системный промпт
  пересобирается на каждом ходе, подключения правятся на лету. Читать через аксессор, а не через
  снимок, захваченный при выпечке.
- **Правка подключений не требует пересборки** (резолвятся на ходе). Смена набора плагинов —
  требует, но это и так событие уровня рантайма.
- Загрузка плагинов не отключается даже в `bare` — иначе не будет ни одного провайдера.

## 6. Провайдеры

```csharp
interface ILlmProviderDescriptor {
    string Id { get; }                                        // "lmstudio"|"openai"|"anthropic"|"google"
    LlmCapabilities Capabilities(ConnectionDescriptor c);
    ILlmClient CreateClient(ConnectionDescriptor c, ICredentialAccessor cred);
    IModelCatalog?    Catalog    { get; }                     // опционально
    IModelManagement? Management { get; }                     // опционально — LM Studio
}
```

Capabilities **декларативные** (таблица провайдера + уточнение из метаданных модели там, где API их
отдаёт), а не «попробовать и поймать ошибку».

Провайдеры глупые и терминальные: знают только свой провод. Ни учёта, ни прав, ни политик они не
видят. Новый провайдер добавляется без единой правки в middleware.

**Раскладка проектов:**

- контракты и контент-модель — `SPLA.Domain`;
- `src/llm/SPLA.LLM.OpenAiWire` — общий формат: разбор SSE, схема tools, аккумулятор tool-call'ов.
  На нём говорят три провайдера из четырёх;
- плагины: `SPLA.Plugins.LLM.LMStudio` (тонкий, поверх OpenAiWire + management API), `.OpenAI`,
  `.Google`, `.Anthropic` (единственный самостоятельный — свой провод целиком).

### Что различается между провайдерами на самом деле

| | Провод | Что ломает текущий код |
|---|---|---|
| OpenAI | `/v1/chat/completions`; плюс stateful Responses API | В стриме usage **не приходит** без `stream_options:{include_usage:true}`. LM Studio отдаёт всегда — иначе тихо теряется весь учёт по стримингу |
| Anthropic | `/v1/messages`: `system` отдельным полем, tools через `input_schema`, tool_result блоком в user-сообщении, свои SSE-события, usage с отдельными cache-счётчиками | Другой формат сообщений целиком. Полноценный второй клиент |
| Google | Gemini через OpenAI-шим `…/v1beta/openai/` | Дёшево. Antigravity Interactions — не сюда, см. §2 |

**Trust:** провайдер обязан получить ключ, иначе не подпишет запрос. Значит **плагин-провайдер —
доверенный код уровня хоста**, и никакая изоляция внутри процесса этого не меняет. Либо каталог
провайдеров только first-party, либо явный список доверенных плагинов на сервере.

## 7. Контент: канон и провод

```
ContentPart = TextPart | ImagePart(BlobRef, mime) | ToolUsePart | ToolResultPart | ReasoningPart
```

Домен и весь агент говорят только на этом. У каждого провайдера — свой `IWireSerializer`. `switch`
существует ровно один раз, внутри провайдера, и он по типу части, а не по провайдеру.

**Четыре соглашения:**

1. Домен не знает провод. Никаких `data:image/jpeg;base64,…` в доменных сообщениях — только
   `BlobRef` (`core.blobs` уже есть).
2. Middleware не знает провод.
3. Провайдер не знает политику. Он не решает, можно ли отправить картинку — он умеет её отправить.
4. **Граница:** преобразование, меняющее смысл или стоимость (даунскейл кадра, обрезка истории) —
   политика, значит middleware, и оно обязано быть видимым в логе хода. Преобразование, меняющее
   только представление (base64, порядок полей) — провайдер, и оно невидимо.

Провайдер, не умеющий часть, — это не `if`, а `capability = false` и понятная ошибка на шаге 6.

### Рассуждения и стриминг

Приёмники (`OnDelta`, `OnReasoning`) живут в контексте; терминальный шаг зовёт их прямо из цикла
чтения — так же, как сегодня зовёт делегаты из параметров. **Middleware находится в потоке вызова и
физически отсутствует в потоке данных.** Живой вывод рассуждений не меняется ни на байт.

Правила, охраняющие это:

- приёмники остаются приёмниками — никаких `IAsyncEnumerable`, поднимающихся вверх через слои
  (кто-нибудь сделает `ToListAsync()` «посмотреть результат» — и живой вывод исчезнет);
- обёртка приёмника **пересылает чанк немедленно** и только потом делает с ним что хочет;
- в обёртке — только дешёвая неблокирующая работа: приёмник ожидается внутри цикла чтения сокета.

**`ReasoningPart` несёт две вещи: отображаемый текст и непрозрачную полезную нагрузку провайдера.**
У Anthropic thinking-блоки подписаны и должны возвращаться вербатим в следующем запросе. Хост
показывает первое, сериализатор возвращает второе. Если этого не заложить — облачный reasoning
сломается не на показе, а на следующем ходе.

Побочный эффект: пляска с `reasoningStreamed` в хостах (`VisionAgent/Program.cs:63-86` различает
руками поток рассуждений и инлайновый `<think>`) уезжает в сериализатор провайдера.

## 8. Приватность

Работает только при наличии **провенанса** у контента — заложить сразу, задним числом происхождение
сообщения не восстановить.

- у подключения: `privacy: local | private-cloud | public-cloud` + `vendor`;
- у плагина в `meta.yaml`: класс чувствительности его выводов (`public | internal | secret`);
- `ToolResultPart` помнит, какой инструмент его породил;
- политика проекта или сервера: матрица «класс × privacy → allow | deny | redact».

Проверка до отправки. При запрете — внятная ошибка, **не** тихая подмена.

## 9. Подключения

```csharp
interface IConnectionCatalog      { IReadOnlyList<ConnectionDescriptor> Visible(ICaller c); }
interface IConnectionEditor       { /* CRUD с ConnectionScope */ }
interface IConnectionAccessPolicy {
    bool CanUse(ICaller c, ConnectionDescriptor d);
    bool CanEdit(ICaller c, ConnectionScope scope);
    bool CanCreateOwn(ICaller c);
    bool CanUseModel(ICaller c, ConnectionDescriptor d, string model);
    IReadOnlyList<ConnectionScope> AllowedScopes(ICaller c);   // ← это и рисует UI
}
```

Области: **Server** (админ завёл, ключ на сервере, пользователь только потребляет) · **Project**
(в `.spla`) · **User** (личная область пользователя; на сервере разрешены).

Реализации: `PermissiveConnectionAccessPolicy` — локально и в воркере, разрешает всё, ноль проверок;
`RoleBasedConnectionAccessPolicy` — сервер, роли и группы (`LocalUser` уже несёт `Roles` и `Groups`).
Роль `connections.admin` открывает правку server-scope.

UI не хардкодит области — рисует то, что вернул `AllowedScopes`.

**Обязательная защита: server-scope id непереопределяемы** из project и user. Иначе обход ACL
тривиален — пользователь заводит своё подключение с тем же id.

Ключи — по `agents/secrets.md` §7: поля `api_key` в схеме подключения не существует, есть
`credential: <entry>`; клиент знает только `hasCredential`.

## 10. Учёт

```
token_kind      id, provider, wire_name, direction(in|out|cache_in|cache_out|reasoning),
                billable, display, status(classified|unclassified)

llm_call        id, ts_utc, user_key, connection_id, model_id, provider,
                model_requested, model_reported, chat_id, run_id,
                origin(chat|spawn|worker|diag), attempt_no,
                duration_ms, status(ok|error|canceled|usage_missing), error_kind

llm_call_token  call_id, kind_id, amount
```

`llm_call` и его `llm_call_token` пишутся **одной транзакцией**.

Биллинг позже и отдельно: `price(kind_id|model, valid_from, unit_price, currency)`; стоимость
считается запросом на дату и никогда не записывается в строку хода. Агрегаты (то, что рисует
`UsagePanel`) — вью или запрос, не хранимые поля.

**Четыре правила, без которых учёт врёт:**

1. Неизвестный счётчик из ответа **автозаводится** как `token_kind(status=unclassified)`, а не
   отбрасывается.
2. `model_reported` обязателен: в `vision.spla` стоит `model: auto`, а облака подставляют
   датированную версию. Учёт по запрошенному имени бессмыслен.
3. Отмена пишет строку: токены уже потрачены. `Usage` пишет в `finally` со статусом `canceled`.
   Иначе Stop = бесплатный расход в отчётах.
4. Оценка ≠ факт. Провайдер не отдал usage → статус `usage_missing`, а не нули. Оценки, если
   появятся, — отдельный `token_kind`, никогда не смешивать.

**Хранение.** `IUsageLedger` — в `SPLA.Domain`; реализация на EF Core — в отдельной сборке
`SPLA.Storage.EfCore` (SQLite / Npgsql / SqlServer), чтобы `bare` не тянул EF. Запись — только
append-only insert, без трекинга и навигаций.

**Запись синхронна** в ходе (insert — микросекунды на фоне хода в секунды). Если БД недоступна —
строка уходит в локальный durable-спул, который доигрывается позже. Недоступность БД не роняет
работу и не съедает деньги втихую.

**Контекст caller'а — ambient**, иначе воркеры и субагенты потеряют пользователя. Использовать
существующий паттерн `AgentSessionScope` / `PermissionScope` (AsyncLocal), не заводить второй.

### Может ли учёт остановить работу — это настройка, а не свойство

Здесь легко схлопнуть два независимых вопроса в один. Они разные:

| Что случилось | Кто решает | Варианты |
|---|---|---|
| Превышен бюджет/квота | `Quota` (стадия Policy) | `Block` — стоп; `Warn` — предупредить и продолжить; квоты нет вовсе |
| **Не удалось записать** строку учёта | `Accounting` | `Fail` — ход падает; `Spool` — в локальный спул, работаем дальше; `Ignore` — молча дальше |

«Учёт не вправе остановить работу» — это `Ignore`, и он верен ровно для одного случая: непрерывный
процесс на бесплатной локальной модели. Для платного облака он вреден, потому что там действует
обратное правило: **нельзя тратить деньги, которые невозможно посчитать.** Если ledger лёг, а мы
продолжаем жечь облако — через сутки никто не скажет, сколько ушло и на кого.

Чтобы это не приходилось задавать руками на каждом воркере, **умолчание выводится из класса
стоимости подключения** (`cost: free | paid` — то же поле, что нужно реестру моделей), а явная
настройка всегда перебивает:

- подключение `free` → `Ignore`, квоты нет;
- подключение `paid` → `Fail` + `Block`;
- в `.spla` воркера можно написать что угодно поверх — например `paid` + `Spool`, если процесс важнее
  точности учёта и риск берётся осознанно.

Так «непрерывный техпроцесс на локальной модели» работает без единой настройки, а «воркер в платное
облако» по умолчанию безопасен.

Отсюда набор реализаций `IUsageLedger`, а не одна:

| Реализация | Где | Поведение |
|---|---|---|
| нет вовсе | профиль `bare` | стадия `Accounting` в конвейере отсутствует — накладных расходов ноль |
| `NullUsageLedger` | воркер, которому учёт не нужен | принимает и выбрасывает |
| `InMemoryUsageLedger` | демо и отладка | копит в памяти, печатает итог в консоль, ничего не хранит |
| `FileUsageLedger` | CLI, десктоп | текущий JSON-файл |
| `EfUsageLedger` | сервер | БД, при недоступности — локальный durable-спул с доигрыванием |

## 11. Осознанно принятые ограничения

- **Жёсткий лимит внутри хода недостижим.** Токены известны только в конце стрима — пользователь уже
  увидел текст. Квота **мягкая**: срабатывает на следующем ходе. Потолок внутри хода возможен только
  через `max_tokens` провайдера.
- **Параллельные ходы** одного пользователя (чаты + субагенты) вместе пробивают лимит по той же
  причине. Тоже мягко.
- **Граница, которую нельзя двигать:** gateway оборачивает **один сетевой вызов к одной модели**. Ход
  агента — это N таких вызовов, и цикл агента живёт над gateway. Всё, что рассуждает о ходе целиком,
  — не middleware. Иначе получится второй оркестратор, конкурирующий с настоящим.
