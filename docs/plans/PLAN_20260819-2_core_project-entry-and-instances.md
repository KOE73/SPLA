# PLAN_20260819-2_core — вход в проект и инстансы агента

**Статус: открыт, не начат.**

Реализует [`ADR_20260819_core_project-entry`](../adr/ADR_20260819_core_project-entry.md) и
[`ADR_20260819-2_core_agent-instances`](../adr/ADR_20260819-2_core_agent-instances.md). Решения там,
здесь только порядок и объём.

Порядок неслучаен: этап 0 — предусловие для всего, что касается жизни инстанса без окна; этапы 1–3
дают ценность сами по себе и без реестра; реестр и UI идут последними, потому что опираются на всё
предыдущее.

---

## Этап 0 — разрешения переезжают с соединения на чат

Без этого инстанс, переживший закрытие окна, доводит ход по отказам, а состояние `waiting` нечем
показать.

- Очередь ожидающих запросов живёт на чате/инстансе, а не в `ClientConnection._pendingPermissions`.
- Отвечает любой подключённый клиент; ответ рассылается остальным как «уже отвечено».
- Обрыв соединения больше не означает `Deny` (`ClientConnection.cs:172`) — он означает «сейчас
  некому»; ход ждёт.
- Появляется явный таймаут ожидания ответа и его настройка. Отсутствие человека не должно держать
  ход бесконечно, но и отказывать за него нельзя.

Затрагивает: `ClientConnection.cs:56,152,172,433,508`, протокол `permission.request` / `permission.reply`,
веб-клиент.

## Этап 1 — профили запуска и вход в проект

- Профиль — параметр CLI (`--init[=standard|minimal|inherit]`), дефолт `minimal`. В манифест
  попадает результат (явные `agent.capabilities`), сам профиль там не хранится.
- Одна доменная фабрика создания проекта `Create(dir, name, profile)`. На неё переводятся
  `LocalProjectProvider.Create`, `ConfigLoader.ScaffoldIfNew`, `MainWindow.NewProjectAsync`,
  `ProjectHandlers.Create`.
- Папка без манифеста: UI спрашивает; CLI в интерактиве спрашивает, в неинтерактиве падает с
  сообщением и подсказкой про `--init`.
- Несколько `*.spla` в папке — явная ошибка вместо `files[0]` (`ConfigLoader.cs:342`).
- Диалог «Новый проект»: папка, имя (по умолчанию из папки), профиль, предпросмотр итогового пути,
  предупреждение о существующем манифесте. Один и тот же диалог в Avalonia и в вебе.

## Этап 2 — замок с адресом

- `<проект>/.spla/instance.json`, удерживается открытым с deny-write; содержит `instanceId`,
  `endpoint`, `machineId`, `pid`, `startTime`.
- Берётся при построении `AgentRuntime`, а не в команде — покрывает `serve`, `chat run`, `mcp`.
- Занятый проект: `serve` отказывает и печатает адрес живого инстанса.
- Порт `serve` по умолчанию эфемерный, публикуется в замке; `--port` остаётся явным выбором.
- `--token` принимает ссылку на секрет и резолвится через `ISecretResolver` (литерал продолжает
  работать).

## Этап 3 — `chat run` прицепляется к живому

- Проект занят → не поднимать второй рантайм, а подключиться клиентом по адресу из замка.
- Проект свободен → как сейчас, in-process.
- Тот же путь делает прогоны из скриптов видимыми в открытом окне.

## Этап 4 — аренда и состояния

- Счётчик клиентов + признак работы в полёте; выход по grace только из `idle`.
- Пять состояний из ADR, публикуются наружу.
- `spla ps` и `spla stop` (с `--force` для отмены хода).
- `Kill(entireProcessTree)` из `EmbeddedServiceLauncher.Dispose` убирается; окно отключается, а
  решение принимает инстанс.
- `--idle-timeout` как значение grace.

## Этап 5 — реестр, файловый режим

- `SPLA.Registry.Contracts` в `src/core/`: DTO инстанса, состояния, `IInstanceRegistry`, события
  статуса. Ноль зависимостей.
- `SPLA.Registry` в `src/service/`: `FileInstanceRegistry` (обход `registry.json` + замки).
- Локальный список живых работает без всякого хаба.

## Этап 6 — хаб и удалённая регистрация

- `RegistryHub`: держит каналы инстансов, отдаёт список, рассылает статусы, принимает `stop`.
- `RemoteInstanceRegistry`: клиентская сторона, `spla serve --registry <url>`.
- Хостинг: режим CLI и внутри `SPLA.Server`. Avalonia поднимает хаб дочерним процессом.
- Токен — `secret:user:registry` (на сервере `shared`).
- `/health` отдаёт `instanceId`, сверяется до подключения.

## Этап 7 — UI

- Трей: список инстансов, «открыть окно», «выгрузить», моргание при `waiting`.
- Значки состояний на чате, агрегат на проекте, общий индикатор при свёрнутом списке.
- Отладочная раскладка реестра — новый `kind` поверхности `debug` (`debug.request` → `debug.snapshot`),
  полный дамп, не пользовательский экран.
- Дерево проект/чаты строится из реестра; чаты подгружаются лениво для развёрнутого узла.

## Этап 8 — проект как свойство соединения

- `projectId` уходит из конвертов, фиксируется при установлении соединения.
- `projectEnvelope()` в веб-клиенте исчезает.
- UI перестаёт трогать `cwd` (`App.axaml.cs:96`); `cwd` остаётся только у serve-инстанса.
- На сервере `AgentRuntimeRegistry` получает вытеснение по той же модели состояний.

## Что сознательно не делается

- TLS для удалённой регистрации — только токен.
- Полная трасса хода на диске. Пока её нет, `stalled` не вытесняется вообще.
- Hot-reload набора инструментов — отдельный вопрос,
  см. [`PLAN_20260819_core_dynamic-tool-registration`](PLAN_20260819_core_dynamic-tool-registration.md).
