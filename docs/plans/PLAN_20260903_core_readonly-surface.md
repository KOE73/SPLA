# PLAN_20260903_core — поверхность только для чтения: архив и подагенты

Статус: **сделано целиком** (2026-09-03). Все три этапа закрыты; оба вопроса, которые план обязывал
решить явно, решены и записаны ниже по месту, а не унесены дальше.

Выросло из [`KNOWN_ISSUES.md`](../KNOWN_ISSUES.md) («`chat.open` воскрешает архивированный чат») и
разговора о том же дне про окна подагентов — оба оказались одним и тем же примитивом с разной
механикой начинки, см. [[project-subagent-visibility]] (память, решение про подагентов записано там).

## Зачем один план на два случая

Оба случая — «эта поверхность не принимает ввод» — но по разным причинам, и план держит их вместе
именно чтобы не спутать причины:

| | Архив | Подагент |
|---|---|---|
| Почему нет ввода | Разговора больше нет — это застывший снимок | Разговор идёт, но ведёт его не смотрящий, а инструмент-вызыватель |
| Источник содержимого | Файл, читается один раз | Живой поток событий хода (`progress.node`, `tool.progress`) |
| Можно ли включить обратно | Да — `chat.unarchive`, и тогда это обычный чат | Нет, никогда — решение 2026-09-03, не TODO (см. память) |

Вторая строка — почему это не один и тот же код: read-only для архива — это, по сути, кэш на чтение;
read-only для подагента — это подписка на трансляцию без права ответить в неё.

## Этап 1. Чтение архивного чата без открытия — **сделано**

- [x] **Протокольный вопрос решён в пользу отдельного типа**: `chat.read` → `chat.read.result`, не
      `chat.open` с флагом. Довод, который перевесил, — тот самый, что был записан как «смещение»:
      `chat.opened` сегодня означает «эта сессия смотрибельна и в неё можно слать `chat.send`», и на
      это обещание опирается каждый обработчик, который на него реагирует. Флаг переложил бы память об
      архивном случае на каждый из них по одному, навсегда; отдельный тип избавляет их от случая по
      конструкции. Ответ везёт заметно меньше `chat.opened` (нет режима, модели, температуры,
      рассуждения, скилла, наборов инструментов, `turnActive`, `state`) — и **отсутствия здесь и есть
      содержание**: всё перечисленное описывает следующий ход, которого у архива нет.
- [x] Сервер: `ChatRegistry.ReadArchived(chatId)` — `Locate` + `LoadChat`, симметричная `Peek`
      (та отвечает про живое, не трогая диск; эта — с диска, не будя ничего). Отдаёт `null` для
      активного чата тоже: у активного есть рантайм, и читать его за спиной — значит вернуть то, что
      последний раз сохранилось, а не то, что человек имеет в виду. `ChatHandlers.Read` различает две
      причины отказа так же, как это сделал этап 0 для `Open`.
- [x] Клиент: `ChatList.vue` — у архивной секции свой `onArchivedClick`, шлёт `chat.read`.
- [x] `ChatSurface.vue` — в режиме чтения нет ни `<div id="composer">`, ни `<div id="status">`
      (строка настроек **целиком** про следующий ход), вместо них строка, объясняющая почему. Режим
      берётся из сессии (`readOnly`, поставлен ответом сервера), а не из того, какую кнопку нажали;
      `chat.opened` его снимает, поэтому разархивированный чат сразу становится обычным.
- [x] Watch не регистрируется: `Read` не зовёт `MarkChatOpen`, потому что рантайма нет и событию
      взяться неоткуда — иначе id залип бы в наборе наблюдаемого до `chat.unwatch`, которого клиент
      никогда не пошлёт (он и не подписывался).

Тесты: `ReadOnlySurfaceTests` (4) — читается только архивное, чтение не открывает рантайм,
разархивация меняет местами «читаемое» и «открываемое»; `chatSessions.test.ts` (3) — сессия из
`chat.read.result` помечена read-only и пуста по настройкам, `chat.opened` его снимает, и история
читаемого чата рендерится **ровно так же**, как у открытого (общая `hydrateMessages`, а не вторая
копия, которая разошлась бы).

## Этап 2. Окно подагента — read-only по умолчанию — **сделано**

Решение уже принято и не пересматривается ([[project-subagent-visibility]]): вмешательство в
работающий спавн не нужно, потому что к моменту, когда смотрящий решил бы вмешаться, подагент уже
успел передумать несколько раз. Это про UI, не про то, можно ли технически.

- [x] Клиент: `ChatSurface.vue` берёт `origin === "spawned"` из дерева чатов (`findChat`, новая
      функция в `chatTree.ts` — рядом с `collectSpawned`/`titleOf`, чтобы форма дерева знала одно
      место) и не рисует ни композер, ни строку настроек.
- [x] **Открытый вопрос закрыт: это не фасад.** `ChatHandlers.Send` **уже** отказывает по
      порождённой сессии, пока её прогон идёт (`Origin == "spawned" && Spawn.Outcome is null`) — это
      приехало волной 2 ради гонки «два писателя в один насос» (ADR §2.2), но отвечает и на этот
      вопрос: правило серверное, и CLI или сторонний клиент, ничего не знающий о подагентах, получит
      отказ на тех же условиях. Соответствующий комментарий в `Send` теперь говорит это прямо, чтобы
      следующий читатель не решил, что попал туда случайно.
- [x] Чего сервер сознательно **не** запрещает — окно после конца прогона. Законченная порождённая
      сессия это обычный чат; клиент прячет её композер как вопрос вкуса (окно подагента — чтобы
      читать), а не потому что писать было бы неправильно. Записано явно, потому что план требовал
      сказать, какой из двух это случай, а не подразумевать.

Сообщение об отказе не звучит как баг: «This session was spawned and its run is still in progress —
it cannot take a message yet», симметрично «Chat is archived» из этапа 0.

## Что не входит

Пуш содержимого подагента в постоянный чат-лист человека, поиск по архиву, массовая очистка
архива — не про эту работу. Она только про то, что смотрящий видит и чего не может сделать на двух
уже существующих, но кривых поверхностях.
