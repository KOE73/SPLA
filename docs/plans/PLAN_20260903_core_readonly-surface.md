## Зачем один план на два случая

Оба случая — «эта поверхность не принимает ввод» — но по разным причинам, и план держит их вместе
именно чтобы не спутать причины:

| | Архив | Подагент |
|---|---|---|
| Почему нет ввода | Разговора больше нет — это застывший снимок | Разговор идёт, но ведёт его не смотрящий, а инструмент-вызыватель |
| Источник содержимого | Файл, читается один раз | Живой поток событий хода (`progress.node`, `tool.progress`) |
| Можно ли включить обратно | Да — `chat.unarchive`, и тогда это обычный чат | Нет, никогда — решение 2026-09-03, не TODO (см. память) |

Вторая строка — почему это не один и тот же код: read-only для архива — это, по сути, кэш на чтение;
read-only для подагента — это подписка на трансляцию без права ответить в неё.

## Этап 1. Чтение архивного чата без открытия

- [ ] Протокольный вопрос, который надо решить явно, а не по умолчанию: отдельный тип сообщения
      (`chat.read`?) или тот же `chat.open` с флагом `readOnly` в ответе, если `Locate` вернул
      `Archived`. Смещение в сторону отдельного типа: `chat.open`/`ChatOpenedPayload` сегодня подразумевает
      «эта сессия теперь смотрибельна и в неё можно слать `chat.send`» — переиспользование того же типа
      для чтения потребует, чтобы каждый обработчик, реагирующий на `chat.opened`, сам помнил про
      `readOnly`, а не был избавлен от архивного случая по конструкции.
- [ ] Путь на сервере: `ChatManager.LoadChat` уже находит архивный файл (`FindChatFilePath` ищет
      active-then-archived) — не хватает только вызова, который отдаёт `ChatSession` как данные и **не**
      создаёт `ChatRuntime`. Кандидат: `ChatRegistry.ReadArchived(chatId)` — тонкая обёртка над
      `Locate` + `LoadChat`, симметричная `Peek` (та отдаёт живое без диска, эта — с диска без рантайма).
- [ ] Клиент: `ChatList.vue` — `onChatClick` для архивной секции (`archived` пропс уже есть у
      `ChatListItem`, значит есть чем различить на месте вызова) шлёт новый запрос вместо `chat.open`.
- [ ] `ChatSurface.vue` / `Composer` — режим без `<div id="composer">`, без пунктов меню настроек чата.
      Определяется тем же способом, что различил клик: пришло по read-пути, не по `chat.open`.
- [ ] Разрыв соединения / переоткрытие панели: архивный чат, однажды прочитанный, не должен
      «прилипать» как watched — `chat.watch`/`MarkChatOpen` не вызывается для read-only, потому что
      слать в него события хода нечему (рантайма нет).

Проверить живьём: клик по архивному чату показывает историю; поле ввода отсутствует; `chat.send` в
архивный (если протокол это в принципе допускает по старой памяти клиента) по-прежнему отказывает
через этап 0.

## Этап 2. Окно подагента — read-only по умолчанию

Решение уже принято и не пересматривается ([[project-subagent-visibility]]): вмешательство в
работающий спавн не нужно, потому что к моменту, когда смотрящий решил бы вмешаться, подагент уже
успел передумать несколько раз. Это про UI, не про то, можно ли технически.

- [ ] Клиент: `ChatSummary.origin === "spawned"` уже различает подагента от чата человека (см.
      `web/src/protocol/types.ts:80`) — использовать это в `ChatSurface.vue`, чтобы не рендерить
      `<Composer>` и пункты настроек, когда открытое окно — подагент. Дешёвая часть, делается первой.
- [ ] Открытый вопрос, который этот этап обязан закрыть, а не унести дальше: только ли это фасад?
      Если `chat.send` на `chatId` живого подагента технически проходит (сессия в обычном `_open`,
      `GetOrOpen` её не отличает от простого чата — `Locate` вернёт `Active`), то read-only — это
      декорация в одном клиенте, а не свойство чата. Второй клиент (CLI, будущий сторонний) может
      писать в подагента, о котором ничего не знает. Решить: держит ли `chat.send` то же самое
      `origin == "spawned"` серверной стороной, или это осознанно оставлено как «наш клиент так не
      делает» и не более — записать явно, какой из двух, а не оставить подразумеваемым.
- [ ] Если решение — серверная сторона тоже отказывает: где именно проверять (`ChatHandlers.Send` до
      `GetOrOpen`, или сам `ChatRuntime` знает о своём происхождении) и какое сообщение об ошибке не
      будет звучать как баг («это чат другого инструмента, не человека» — не «Chat not found»,
      симметрично тому, что сделано в этапе 0 для архива).

Проверить живьём: во время реального `agent_spawn` открыть его окно (сейчас это уже работает —
`autoOpenSubagents`/`openInWindow`) и убедиться, что нет поля ввода, но дерево прогресса и
повествование хода по-прежнему приходят.

## Что не входит

Пуш содержимого подагента в постоянный чат-лист человека, поиск по архиву, массовая очистка
архива — не про эту работу. Она только про то, что смотрящий видит и чего не может сделать на двух
уже существующих, но кривых поверхностях.
