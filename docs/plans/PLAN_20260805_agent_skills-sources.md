# PLAN_20260805_agent — учёт филиалов: имя, адрес, грант

**Статус: не начат.** Реализация
[`ADR_20260805_agent_skills-sources`](../adr/ADR_20260805_agent_skills-sources.md), который уточняет
[`ADR_20260804_agent_skills-library`](../adr/ADR_20260804_agent_skills-library.md) в трёх местах.
Библиотечная модель (фонд / каталог / выдача) не пересматривается — переделывается **учёт
источников**.

Цель в одну фразу: **источник получает объявленное имя и внешний грант доверия — список можно
дополнять, а не переписывать, и чужой репозиторий не может назначить себя доверенным.**

Проверка, ради которой всё затевалось, одна и формулируется без терминов: **владелец добавляет папку
со скилами из панели настроек, не трогая ни одного файла в репозитории проекта, и видит её скилы в
чате.** Если этого не произошло — план не выполнен, сколько бы этапов ни было закрыто.

| Этап | Что | Зависит от |
|---|---|---|
| 1 | Филиал получает имя: `id` в записи, слои мержатся по нему | — |
| 2 | Адрес книги `источник:id`, перекрытие отменяется | 1 |
| 3 | Происхождение записи и потолок доверия по слою | 1 |
| 4 | Выданные источники: пользовательское хранилище | 3 |
| 5 | Грант доверия: отдельное хранилище, ключ — путь | 3 |
| 6 | Горячая пересборка источников без рестарта | 4, 5 |
| 7 | Протокол и панель: добавить филиал, подтвердить доверие | 6 |
| 8 | Серверное: потолок, ворота, персональные области | 7 |
| 9 | Документы, промпт, golden-тесты | все |

---

## Что в объём НЕ входит

- **`skills.providers` и `BranchSource`** — Этап 8 предыдущего плана. Этот ADR их не касается;
  остаются открытыми там, где были. Единственная связь: `SkillSourceRegistry.Factories` перестаёт
  быть закрытым массивом — но это делает тот план, не этот.
- **Эмбеддинги, комплектование фонда, разметка `SPLA.Skills` тэгами** — не про источники.
- **Миграции конфигов.** Совместимости нет: внешних клиентов, опубликованного протокола и чужих
  `.spla` не существует. Ключи меняются, старое удаляется.

---

## Решения по объёму (приняты до начала работы)

**1. Порядок этапов задан зависимостью, а не размером.** Имя (1) обязано быть раньше всего: пока у
записи нет ключа, ни мерж, ни происхождение, ни грант выразить нечем. Адрес (2) идёт вторым, потому
что он самый механический и самый широкий — трогает почти каждого потребителя `SkillLibrary`, и
смешивать его с логикой доверия значит получить дифф, который никто не прочитает.

**2. Два хранилища вводятся подряд (4 и 5) и до всякого UI.** Панель — их единственный клиент, и
писать её поверх хранилища, которого нет, значит писать её дважды.

**3. Горячая пересборка (6) — до панели, а не после.** Сегодня `SkillSources` читается один раз в
конструкторе `AgentRuntime`. Кнопка «добавить папку», после которой надо перезапустить сервис, — это
не закрытая исходная задача, а её имитация.

**4. Каждый этап оставляет дерево зелёным и собираемым.** Промежуточных состояний вида «имена уже
новые, а резолвер ещё старый» между коммитами не остаётся.

## Этап 1. Филиал получает имя

Причина аномалии — не резолвер, а отсутствие ключа. Появляется ключ — аномалия исчезает сама.

- [ ] `SplaSkillSourceSection`: поля `id` (объявленное имя) и `enabled` (`bool?`).
      `Describe()` в [`DirectorySkillSourceFactory`](../../src/core/SPLA.Library/Sources/SkillSourceRegistry.cs)
      **остаётся, но только как фолбэк** для записей без `id` — путь перестаёт быть идентичностью и
      становится обычным полем.
- [ ] `SplaSkillsSection.InheritDefaults` (`bool?`, по умолчанию `true`). `false` = «только то, что
      объявлено здесь». Нужен для развёртывания: администратору нужен белый список, а не надежда, что
      он не забыл выключить лишнее.
- [ ] `SettingsResolver.ApplySkills`: источники **мержатся по `id`**, как `connections`, `toolsets` и
      `skills.items`. Порядок — порядок первого появления ключа; более специфичный слой правит поля,
      но не двигает запись в списке (иначе «поменял `label`» означало бы «поменял ранжирование»).
      Комментарий «merging would make an inherited source impossible to drop» удаляется вместе с
      поведением, которое он оправдывал.
- [ ] `ResolvedSettings.SkillSources` перестаёт быть `List<SplaSkillSourceSection>?` и становится
      упорядоченным списком **разрешённых** записей (тип из Этапа 3, где к ним добавится
      происхождение). На этом этапе — просто список без `null`-состояния: «ничего не объявлено»
      выражается встроенным набором, а не отсутствием поля.
- [ ] Конвенциональные папки становятся **встроенными записями с объявленными именами**: `repo`,
      `local`, `machine`, `builtin`. `DefaultSources()` отдаёт все четыре, включая установочную.
- [ ] Специальная приписка установочной папки в `SkillSourceRegistry.Build()` **удаляется**. Она
      существовала затем, чтобы проект, переопределивший список, не потерял её молча; при мерже по
      имени потерять молча уже нельзя — только выключить явно.
- [ ] `Build()` перестаёт отсеивать дубликаты по `seenIds`: после мержа в словаре дубликата нет по
      построению. Проверка остаётся только для плагинных источников, которые приезжают мимо конфига.
- [ ] Три операции получают форму, которую надо проверить тестами порознь:

      | Операция | Как выражается |
      |---|---|
      | добавить | новая запись в любом слое |
      | выключить | `enabled: false` — унаследованное **не удаляется**, а гаснет и остаётся видимым |
      | очистить | `skills.inherit_defaults: false` |

- [ ] `SkillSettingsLayeringTests` переписывается целиком: сегодня он **закрепляет именно то
      поведение, которое отменяется** («Project_sources_replace_the_machine_list_rather_than_extending_it»).
      Новые случаи: добавление не трогает унаследованное; `enabled: false` гасит унаследованное;
      `inherit_defaults: false` очищает; запись без `id` получает его из пути и всё равно мержится.

**Проверка этапа:** запись `- id: ops` + `path:` в проектном `.spla` при непустом машинном списке
даёт **обе** папки, и ни одна строка машинного списка не переписана.

## Этап 2. Адрес книги — филиал плюс номер

Перекрытие по id отменяется: две книги с одинаковым названием от разных авторов есть нормальное
состояние фонда. Ошибки формы dependency confusion становятся невыразимыми — имя без филиала либо
однозначно, либо это ошибка.

- [ ] `SkillState.Superseded` удаляется из перечисления; словарь `claimed` — из `SkillLibrary.Rebuild`.
      Оба издания попадают в `_skills` и оба резолвятся полноценно.
- [ ] `SkillCard.Address => $"{SourceId}:{Id}"`. Поле вычисляемое, не хранимое.
- [ ] `SkillLibrary.Find(id)` заменяется на `Resolve(string address)`, возвращающий явный результат
      трёх видов: найдено / не найдено / **неоднозначно с перечислением кандидатов**. Библиотекарь,
      который сам решает, какое из двух изданий вы имели в виду, ошибётся однажды и незаметно.
      Принимается и короткое имя, и полный адрес; разделитель `:` в id скилов не встречается и
      запрещается нормализатором.
- [ ] Потребители: [`SkillActivateTool`](../../src/core/SPLA.MCP.Core/Tools/SkillActivateTool.cs),
      [`ChatRuntime`](../../src/agent/SPLA.Runtime/ChatRuntime.cs) (выдача на руки),
      [`SpawnedAgentRunner`](../../src/agent/SPLA.Agent/SpawnedAgentRunner.cs), `LoadBody`,
      `ListResources`. Текст ошибки при неоднозначности **обязан** перечислять кандидаты полными
      адресами — иначе цена, которую ADR принял осознанно, превращается в раздражение.
- [ ] **Как имя печатается модели.** Правило одно: *кратчайшее однозначное*. Скил, чей `id`
      встречается в фонде один раз, печатается коротко; встречается дважды — оба печатаются полным
      адресом. Считается группировкой по `id` при сборке `CatalogView`, детерминированно, без
      состояния. Затрагивает полку, `skill_find` и блок `=== ACTIVE SKILL ===`.
- [ ] **`skills.items`: ключ — предикат, а не адрес** (решение владельца, 2026-08-05). Полный адрес
      выбирает одно издание; короткое имя применяется ко **всем** изданиям с этим id и никогда не
      считается неоднозначным. `items` — это утверждение «скил по имени foo мне не нужен», а не
      заявка на выдачу; неоднозначность есть свойство *выдачи*, где нужна ровно одна книга.
      Существующие конфиги продолжают работать без правки. Затрагивает `SkillLibrary.Resolve`,
      `SettingsOps.SaveSkills` и ключ строки в панели.
- [ ] Трюк «положи файл с тем же id к себе — и почини поставочный скил» пропадает. Замена явная:
      `skills.items` с полным адресом `builtin:foo → enabled: false`, рядом своя книга под своим
      именем.
- [ ] UI: `Superseded` уходит из `CapabilityRow.vue`, `SkillsPanel.vue` (`:disabled`, пропуск в
      массовых действиях) и из `types.ts`. Ключ строки — адрес, а не id: два издания в одном списке
      иначе схлопнутся в один DOM-узел.
- [ ] `SkillSourceDto`/`CapabilityDto` получают `address`; `id` остаётся коротким для показа.
- [ ] Тесты: два источника с одинаковым id дают две доступные карточки; активация по короткому имени
      при совпадении отказывает и называет обоих; активация по адресу работает; подсказки в
      `skill_activate` печатают адреса.

**Проверка этапа:** два источника с `foo` — оба скила `Available`, `skill_activate("foo")` отказывает
с перечислением, `skill_activate("builtin:foo")` активирует именно поставочный.

## Этап 3. Происхождение записи и потолок доверия

Первое из двух независимых правил доверия. Источник, объявленный в менее привилегированном слое, не
может подняться выше `untrusted` собственными силами.

- [ ] `SourceOrigin`: `Deployment`, `Machine`, `Project`, `Granted`. Проставляется в
      `SettingsResolver` в момент мержа — только там известно, какой слой сейчас накладывается.
      Запись, правленная двумя слоями, наследует происхождение **менее** привилегированного из них:
      привилегию определяет тот, кто мог подменить содержимое, а не тот, кто написал первым.
- [ ] Потолок:

      | Слой | Кто им владеет | Максимум, объявляемый самостоятельно |
      |---|---|---|
      | проектный `.spla` | приезжает с чужим репозиторием | `untrusted` |
      | пользовательский / машинный | человек за машиной | `trusted` |
      | политика развёртывания | администратор | `trusted`, и задаёт потолок остальным |

- [ ] Клампинг — **с предупреждением в лог**, а не молча: «источник `ops` из проектного слоя
      объявил `trusted`, понижено до `untrusted`». Молчаливое понижение выглядит как «панель врёт».
- [ ] Политика развёртывания: `skills.policy.max_trust`, читается **только** из машинного слоя
      (`~/.spla/defaults.yaml`). Локально это домашняя папка человека и потолок по умолчанию
      `trusted`; на сервере это папка службы, куда пользователь писать не может, и там администратор
      ставит `untrusted`. Отдельного файла политики не заводим — слой уже есть и уже правильный.
- [ ] **`level` под потолок не попадает, и это проверяется тестом.** Две оси разделены до конца:
      уровень — про экономию контекста, доверие — про безопасность. Проект вправе сказать «мои скилы
      показывать только по запросу»; сказать «мои скилы проверены» он не вправе.
- [ ] Тесты: проектный `trusted` → `untrusted`; машинный `trusted` → `trusted`; `max_trust:
      untrusted` в машинном слое понижает и машинные записи; `level: out-of-catalog` из проектного
      слоя доживает до карточки неизменным.

**Проверка этапа:** сценарий из ADR воспроизводится и обрывается — клонированный репозиторий, чей
`.spla` добавляет источник внутрь себя же и объявляет его доверенным, даёт `DisabledByTrust`, а не
тексты в системном промпте.

## Этап 4. Выданные источники: пользовательское хранилище

Резать надо не по «UI против сервера», а по источнику полномочий. Предписанные живут в слоях
конфигурации, выданные — в пользовательском хранилище.

- [ ] `ISkillSourceStore` + `FileSkillSourceStore` по образцу
      [`FileSecretStore`](../../src/core/SPLA.Domain/Secrets/FileSecretStore.cs):
      `~/.spla/skills.yaml`, читается свежим при каждом обращении (кросс-процессная правка не
      требует рестарта), пишется целиком. Никогда не коммитится — потому что лежит вне проекта, а не
      потому что кто-то не забыл про `.gitignore`.
- [ ] Эффективный набор = предписанные слои, смерженные по `id`, плюс выданные **последним** (самым
      специфичным) слоем. Та же операция мержа, что в Этапе 1, — не второй механизм, а четвёртый слой.
- [ ] Из этого следует ответ на кажущееся противоречие ADR («предписанные нередактируемы в панели» ×
      «унаследованное надо уметь выключить»): панель **не правит** предписанную запись, она пишет в
      выданный слой запись с тем же `id` и `enabled: false`. Оверрайд виден как оверрайд, оригинал
      цел, снятие оверрайда возвращает исходное. Записать это в комментарий у хранилища, иначе через
      полгода кто-нибудь «починит» это прямой правкой проектного файла.
- [ ] Происхождение выданных — `Granted`, потолок как у машинного слоя (локально), см. Этап 8 для
      сервера.
- [ ] Тесты: выданная запись добавляет источник; выданная запись с `id` предписанной гасит её;
      удаление выданной записи возвращает предписанную; хранилище отсутствует → поведение ровно как
      сегодня.

**Проверка этапа:** источник, дописанный в `~/.spla/skills.yaml` руками, виден в фонде, а в
проектном `.spla` нет ни строки нового.

## Этап 5. Грант доверия: хранится отдельно, адресуется путём

Второе правило. Поднять источник до `trusted` может **только** запись в пользовательском хранилище —
та самая, которую делает подтверждение в UI.

- [ ] `ISkillTrustStore` + `FileSkillTrustStore` по образцу
      [`FileSecretAclStore`](../../src/core/SPLA.Domain/Secrets/FileSecretAclStore.cs) —
      **отдельный файл** `~/.spla/skills.acl.yaml`, не секция внутри `skills.yaml`. Ровно тот
      же принцип, что уже сформулирован для [`SecretAcl`](../../src/core/SPLA.Domain/Secrets/SecretAcl.cs):
      *«ACL живёт рядом с хранилищем, никогда внутри него»*. Хранилище источников правится как
      данные; грант — это решение о безопасности, и смешивать их в одном документе значит открыть
      способ выдать себе грант правкой соседнего поля.
- [ ] **Ключ гранта — разрешённый путь, а не `id`.** Переименовали папку — грант не поехал следом;
      переименовали запись в конфиге — грант остался у содержимого. Доверяют содержимому, а
      содержимое лежит по пути. Путь нормализуется той же `ResolvePath`, через которую ходит фабрика:
      два написания одного места не должны давать два разных гранта.
- [ ] Запись гранта: `granted_at`, `granted_by` (userKey — пригодится на сервере), и `path` как ключ.
- [ ] Порядок применения при сборке карточки: объявленный `trust` → клампинг по слою (Этап 3) →
      подъём грантом → **повторный** клампинг по политике развёртывания. Последний шаг не
      декоративный: он и есть право администратора запретить личное.
- [ ] Источники, у которых пути нет (плагинные, будущие `git`/`confluence`), грантом не
      обслуживаются. Плагинным доверие отдельно не выдаётся сознательно: включив плагин, вы уже
      доверили ему исполняемый код, что строго больше, чем его тексты.
- [ ] **Поштучный обход доверия удаляется** (решение владельца, 2026-08-05). Сегодня
      `skills.items: { foo: { enabled: true } }` перебивает `DisabledByTrust`; после этого этапа —
      нет. Если весь источник недоверен, произвольно доверенный один скил из него есть противоречие:
      доверяют содержимому, а содержимое приехало целиком. Хотите доверять — проверьте и **скопируйте
      книгу в доверенный источник**; это одно действие, которое видно в `git diff`, вместо флага,
      который надо помнить.
      Следствия: `SkillLibrary.Resolve` теряет ветку `configured?.Enabled != true`; доверие
      становится **свойством источника целиком**, и механизм ровно один — грант. В панели
      переключатель недоверенного скила больше ничего не чинит, чинит кнопка «доверять этой папке» в
      шапке группы (Этап 7). `An_untrusted_sources_skill_stays_off_until_it_is_enabled_by_name` в
      [`SkillAvailabilityTests`](../../tests/SPLA.Tests/SkillAvailabilityTests.cs) закрепляет
      отменяемое поведение и переписывается.
- [ ] Тесты: без гранта `untrusted`; с грантом `trusted`; переименование папки снимает грант;
      грант, вписанный в проектный `.spla`, не действует ни в каком виде; `max_trust: untrusted`
      перебивает грант; `enabled: true` у отдельного скила **не** поднимает недоверенный источник.

**Проверка этапа:** та же папка, тот же конфиг — одна строка в `skills.acl.yaml` переводит её скилы
из `DisabledByTrust` в `Available`, и удаление строки возвращает обратно.

## Этап 6. Горячая пересборка источников

Сегодня `SkillSources` читается один раз в конструкторе `AgentRuntime`, а `SkillLibrary.Add` умеет
только дописывать в конец. Ни то ни другое не переживает «добавить папку из UI».

- [ ] `SkillLibrary.SetSources(IEnumerable<ISkillSource>)`: отписаться от `Changed`, задиспозить
      старые, подписаться на новые, `Rebuild()`. `Add()` остаётся для конструктора и тестов.
- [ ] `AgentRuntime.RebuildSkillSources()` — сборка источников выносится из конструктора в метод,
      конструктор его же и зовёт.
- [ ] Защита: пересборка не выполняется, пока в каком-либо чате идёт скил (механизм уже есть —
      `IsSkillActive`), и откладывается до его завершения. Подменить фонд под работающей процедурой —
      единственный отказ, который человеку не придёт в голову заподозрить.
- [ ] `SkillLibrary.Reloaded` получает наконец подписчика: broadcast `skills.result` всем клиентам.
      Долг из Этапа 9 предыдущего плана — **у события сегодня ноль подписчиков**, и hot reload не
      доходит ни до одного окна.
- [ ] Тест: добавление записи в хранилище → пересборка → новый источник в `Sources`, его скилы в
      `Holdings()`, старые источники задиспожены ровно один раз.

**Проверка этапа:** правка `~/.spla/skills.yaml` на запущенном сервисе доезжает до открытой
панели без рестарта.

## Этап 7. Протокол и панель: добавить филиал

Самое частое действие, которого сегодня нет ни в одной двери. Секреты этот вопрос уже решили — у них
есть хранилище, которое правится из UI и не коммитится; у источников такого места не было.

- [ ] Протокол: `skills.sources.get` / `skills.sources.save` (+ существующий `skills.result` как
      broadcast). Отдельно `skills.source.trust` — выдача и отзыв гранта: это другое действие с
      другой ценой, и складывать его в общий `save` значит потерять подтверждение.
- [ ] `SkillSourceDto` дополняется: `origin`, `enabled`, `editable` (= `origin == Granted` либо
      предписанная, у которой можно завести оверрайд), `trustGranted`, `path`.
- [ ] Панель показывает **оба списка одним списком**, помечая предписанные: человеку важно видеть
      весь фонд, а не ту его половину, которой он владеет. Бейдж происхождения рядом с бейджем уровня.
- [ ] Формы: добавить папку (путь + `id` + `level`), выключить/включить любую запись, удалить свою.
      Удаления предписанной нет — только выключение, и это надо сказать словами в UI, а не молчаливо
      прятать кнопку.
- [ ] **Явный Save, не авто-применение**, и подтверждение на грант доверия. Источник — транзакция и
      решение о безопасности, а не обратимая преференса вроде темы; правило проекта на этот счёт уже
      записано. Диалог по образцу VS Code Workspace Trust: показать путь, сказать, что тексты оттуда
      попадут в системный промпт, и потребовать явного согласия.
- [ ] Кнопка «доверять этой папке» рядом с бейджем `untrusted` — это ровно та точка, где человек
      сегодня упирается и не понимает, что делать. После решения 2 она же **единственная**: у
      отдельного скила из недоверенного источника переключатель ничего не чинит, и панель обязана
      сказать это словами, а не оставить неработающий тумблер.
- [ ] `SettingsOps.SaveSkills` больше не пишет `skills.items` вслепую по короткому id — см. решение
      Этапа 2.

**Проверка этапа:** ✋ **приёмка всего плана.** Владелец добавляет `D:\shared\ops-skills` через
панель, подтверждает доверие, видит скилы в списке и активирует один из них в чате. Ни одного файла в
репозитории проекта при этом не изменилось — проверяется `git status`.

## Этап 8. Серверное: потолок, ворота, персональные области

Пользовательский список на сервере **не** становится read-only — резали бы не по той оси. Право
писать в свою область не является риском; риском является уровень доверия, который эта запись себе
назначает.

- [ ] Хранилища источников и грантов — per-user, в личной файловой области (`users/{userKey}/`), как
      это уже сделано для секретов. `IIdentity` и области существуют.
- [ ] На сервере выданное пользователем по умолчанию `untrusted`; поднять может только политика
      администратора (`skills.policy.max_trust` из машинного слоя, Этап 3). Локально человек сам себе
      администратор, и подтверждения при добавлении достаточно.
- [ ] Путь на сервере — серверный, поэтому добавление источника проходит через тот же
      [`ICapabilityGate`](../../src/core/SPLA.Domain/Host/ICapabilityGate.cs), что и любой другой
      доступ к файлам. Иначе «добавь источник» становится способом читать что угодно.
- [ ] Per-user `machine`-источник в `users/{userKey}/skills`: сегодня `machine` — домашняя папка
      службы, общая для всех. Долг из Этапа 9 предыдущего плана.
- [ ] Разделяемый кэш источника на процесс (N проектов = N `SkillLibrary` = N watcher-наборов на одно
      дерево) — **сознательно откладывается**: оптимизация без наблюдаемой проблемы, и она честнее
      выглядит после того, как источников станет больше одного на человека.

## Решения владельца, принятые до начала работы (2026-08-05)

Оба вопроса ADR не разбирал, оба меняют форму работы, поэтому записаны здесь, а не выясняются по
ходу.

### 1. `skills.items` ключуется предикатом, а не адресом

Полный адрес выбирает одно издание; короткое имя применяется ко всем изданиям с этим id и **никогда**
не считается неоднозначным. `items` — это утверждение «скил по имени foo мне не нужен», а не заявка
на выдачу; ровно одна книга нужна выдаче, и неоднозначность есть её свойство. Пример из ADR
(`builtin:foo → enabled: false`) остаётся выразимым, существующие конфиги остаются рабочими.

### 2. Поштучный обход доверия удаляется

Сегодня `skills.items: { foo: { enabled: true } }` перебивает `DisabledByTrust`. Это отменяется:
источник недоверен целиком, и произвольно доверенный один скил из него — противоречие. Путь наверх
один и он честный: **проверить книгу и скопировать её в доверенный источник.**

Модель от этого упрощается, а не усложняется. Доверие перестаёт иметь два механизма (грант на
источник и флажок на скиле) и получает один; `skills.items` перестаёт быть наполовину настройкой
безопасности и честно отвечает только за вкл/выкл; в панели у недоверенной группы остаётся ровно одно
осмысленное действие — «доверять этой папке».

### 3. Доверие решается местом, а не слоем (решение владельца, 2026-08-05, по ходу Этапа 7)

Потолок по слою смотрел на то, **кто объявил** запись. Этого мало, и дыра нашлась при живом прогоне:
папка `skills/` внутри клонированного репозитория попадала в промпт **вообще без всякого конфига** —
никто ничего не объявлял, значит некого было ловить на самозванстве.

Правило переносится с автора на местоположение: **всё, что лежит внутри рабочей папки, приезжает
вместе с клоном и стартует `untrusted`, пока человек не поставит галочку.** Оно строго сильнее
прежнего и покрывает его: `.spla` чужого репозитория и папка чужого репозитория теперь неразличимы,
потому что риск у них один и тот же.

Следствия, каждое проверено тестом:

- `repo` и `local` при открытии проекта недоверенны. Галочка ставится один раз на папку и живёт в
  `skills.acl.yaml` — ключ путь, так что это «однажды на проект», а не «каждую сессию». Ровно модель
  VS Code Workspace Trust.
- `machine` и `builtin` не затронуты: домашняя папка человека и установочная — не то, куда клон может
  что-то положить.
- Установочная папка исключена, даже когда физически лежит внутри рабочей — а она там лежит всегда,
  когда продукт разрабатывают на нём самом. Вывод сборки не является чужим содержимым.
- Слоевой потолок остаётся: он ловит папку **снаружи** рабочей, на которую указал чужой `.spla`.

### 4. Имена файлов хранилищ

`~/.spla/skills.yaml` (выданные источники) и `~/.spla/skills.acl.yaml` (гранты доверия) — по
конвенции соседей: `secrets.yaml` / `secrets.acl.yaml` / `secrets.shared.acl.yaml`, то есть
`<сущность>.<роль>.yaml` через точку. Первый сегмент общий, поэтому файлы одной подсистемы стоят
рядом в листинге по устройству, а не случайно.

Второе имя — не аналогия, а тот же объект: грант доверия к источнику **и есть** его ACL, вынесенный
наружу по правилу «ACL живёт рядом с хранилищем, никогда внутри него». Называть его `acl` дешевле,
чем каждый раз объяснять, зачем файла два.

## Риски, замеченные при разборе

**1. Молчаливое расхождение показанного и применённого.** Второе место хранения — новая цена,
названная в ADR прямо. Смягчение: панель показывает происхождение каждой записи, а не сводный
результат; клампинг доверия логируется; grant показывается отдельным признаком, а не растворяется в
`trust`.

**2. Пересборка под работающей процедурой.** Механизм защиты есть (`IsSkillActive`), но сегодня он
только *пропускает* реакцию на изменение источника — отложенного применения нет, то есть добавленный
источник может не появиться до следующего события. Этап 6 обязан сделать именно отложенное
применение, а не пропуск.

**3. `skills.items` и адреса разъедутся с UI.** `SettingsOps.SaveSkills` пишет по `dto.Id`; после
Этапа 2 у карточки два имени. Если панель отправит короткое, а резолвер ждёт адрес, получится
«переключатель не работает» без единой ошибки в логе. Тест на круг «панель → yaml → библиотека»
обязателен, а не желателен.

**4. `Enumerate()` читает каждый файл целиком на каждый `Rebuild`.** Долг известный, но этот план
делает `Rebuild` частым: сегодня он раз в жизни процесса, после Этапа 6 — на каждую правку списка. С
одной папкой это незаметно; с четырьмя встроенными и внешним репозиторием на сетевой шаре — уже нет.
Кэш по mtime+size из «мелких долгов» предыдущего плана переходит из «когда-нибудь» в «вероятно,
понадобится в Этапе 6».
