# PLAN_20260804_agent — переписывание скилов под библиотечную модель

**Статус: этапы 1–7 сделаны, 8–9 открыты.** Реализация
[`ADR_20260804_agent_skills-library`](../adr/ADR_20260804_agent_skills-library.md).

Цель в одну фразу: **скил существует независимо от того, знает ли о нём модель — фонд, каталог и
выдача становятся тремя разными вещами.**

Цель достигнута: скил может быть включён, доступен и при этом невидим модели; каталог перестал расти
вместе с фондом; приложения читаются; человек может выдать скил в чат сам. Что осталось —
**«Открытые вопросы и незакрытые риски»** в конце файла; там же то, что выяснилось по ходу и не
привязано ни к какому этапу. Начинать чтение оттуда, а не сверху.

## Решения по объёму (приняты до начала работы)

**1. Совместимости нет — и мы этим пользуемся.** Внешних клиентов, опубликованного протокола и чужих
`.spla` не существует. Ключи yaml, имена сообщений и раскладка папок меняются свободно, старое
удаляется, а не депрекейтится. Миграций не пишем.

**2. Переименование — отдельным этапом и целиком механическое.** Смешивать его с логикой нельзя:
диффы станут нечитаемыми, а красные тесты — необъяснимыми. Этап 2 не меняет поведения ни в одной
строке.

**3. Ресурсы идут первыми, до всей библиотечной работы.** Они ни от чего не зависят, а без них
`SPLA.Skills` неработоспособен в принципе — то есть проверять остальные этапы будет не на чем.

**4. Библиотекарь-подагент — последним из «умного».** Тэговый отбор закрывает большинство случаев;
подагент имеет смысл только когда есть на чём мерить выигрыш.

## Этап 1. Приложения к книге

Без этого `SPLA.Skills` не работает: `SKILL.md` на шаге 0 требует `references/package-contract.md`, а
механизма прочитать его нет ни одного.

- [x] `ISkillSource`: `ListResources(skillRef)` и `ReadResource(skillRef, relPath)`. Резолв — внутри
      источника, с той же защитой от выхода за корень, что уже в `DirectorySkillSource.Resolve`.
      Оба с дефолтной реализацией в интерфейсе — источник без вложений не пишет ничего. Проверка
      вынесена в `ResolveUnder(baseDir, relative)`, через который теперь ходит и сам `Resolve`, чтобы
      дверь для приложений не разъехалась с дверью для рефа.
- [x] `DirectorySkillSource`: реализация для папочной раскладки (всё рядом с `SKILL.md`, кроме
      самого `SKILL.md`). У голого `name.md` приложений нет и не может быть: его соседи — чужие
      скилы. Исключения те же, что у сканера (`.`-папки, `bin`/`obj`/`node_modules`).
- [x] `PluginSkillSource`: то же для скилов, приезжающих с плагином. Скил плагина — один файл, поэтому
      его приложения лежат в одноимённой папке рядом: `skills/host-audit.md` → `skills/host-audit/`.
      Для `Enumerate` эта папка невидима (он читает только верхнеуровневые `*.md`), так что вложение
      не может стать самостоятельным скилом.
- [x] Инструмент `skill_read_resource`, `ToolScope.Skill`. Доступен **только при активном скиле** и
      **только для его собственных ресурсов** — это формуляр выдачи, а не файловый доступ.
      **Уточнение к плану, решение владельца 2026-08-04:** внутри Skill-скоупа `PermissionManager`
      разделён по `ToolEffect` — read-инструмент даёт `Allow` там, где write даёт `Ask`. Ворота — это
      активация, а не каждая страница: шаг 0 у `capture` читает два файла, вся процедура — больше
      десятка, и подтверждение на каждый приучает прокликивать то подтверждение, которое важно.
      Ничего не расширяет: у инструмента нет параметра «чей скил», а источник не выпускает за папку.
      Research по-прежнему `Deny` на весь скоуп.
- [x] В блок `=== ACTIVE SKILL ===` добавить список доступных приложений. Иначе модель не знает, что
      можно спросить. Только имена, не содержимое.
- [x] Решить явно: приложения снимаются при активации (как тело) или тянутся живой ссылкой на
      источник. Влияет на случай «источник исчез, книга на руках».
      **Решено 2026-08-04, владелец: живая ссылка плюс пиннинг формуляра.** При активации в
      `ISkillSession` пиннится только адрес — `ActiveSourceId`, `ActiveRef` и **список** приложений;
      текст читается из источника в момент вызова `skill_read_resource`.
      *Почему список всё-таки пиннится:* он нужен блоку `ACTIVE SKILL` (спросить то, о чём не знаешь,
      нельзя) и он же отсекает чужой ресурс до того, как кто-либо трогает диск.
      *Почему содержимое — нет:* у `linux-host.capture` тринадцать вложений, а шаг 0 читает два;
      снимок платил бы за одиннадцать лишних всегда, а на сервере превратил бы активацию в дорогую
      сетевую операцию. *Случай «источник исчез»:* формуляр остаётся валидным, тело скила
      припиннинговано и прогон продолжается, а чтение возвращает честную ошибку.
      *Побочное следствие, принятое сознательно:* ресурс, добавленный в папку **после** активации, в
      формуляре не появится до следующей активации — та же форма, что у пиннинга тела.
- [x] Тесты: чтение, выход за корень, чтение чужого ресурса, чтение без активного скила.
      [`SkillResourceTests`](../../tests/SPLA.Tests/SkillResourceTests.cs) — 14 тестов, две половины
      порознь: источник (что вообще принадлежит скилу) и инструмент (кто вправе спрашивать). Плюс
      деактивация возвращает формуляр и «исчезнувший источник не роняет прогон».

**Проверка этапа:** ✅ `linux-host.capture` из `SPLA.Skills` доходит до конца шага 0 — проверено на
настоящем репозитории `C:\GitKOE\SPLA.Skills`: скил `Available`, формуляр содержит все 13 вложений,
`references/package-contract.md` (2241 симв.) и `references/ssh-tools.md` (1719 симв.) читаются через
`skill_read_resource`.

Механически, без изменения поведения. Словарь — в ADR, раздел «Словарь».

- [x] Новый проект `src/core/SPLA.Library/` с раскладкой `Catalog/ Sources/ Format/`; старая папка

## Этап 3. Тэги и уровень источника

- [x] Фронтматтер: `tags: [...]`. Нормализация — нижний регистр, kebab-case, дедупликация.
      Вся нормализация в одной функции `SkillTag.Normalize`, и через неё же идут запросы: два
      нормализатора, согласных сегодня, — это два нормализатора, расходящихся завтра.
      Тэги **не** восстанавливаются щадящим парсером — по тому же правилу, что и `requires`: гадать
      о форме списка хуже, чем считать скил бестэговым.
- [x] `TagVocabulary`: полный словарь фонда, доступен UI и библиотекарю. Строится из набора карточек,
      а не принадлежит библиотеке, — один тип обслуживает и промпт (только доступные), и панель (всё).
- [x] `SourceLevel`: `OutOfCatalog / Findable / InCatalog / OnShelf`, `level:` в `.spla`. По образцу
      [`ToolSetLevel`](../../src/core/SPLA.MCP.Core/ToolSets/ToolSetLevel.cs). Неизвестное значение
      откатывается к `OnShelf`: опечатка не должна прятать скилы молча.
      `Findable` пока для модели неотличим от `OutOfCatalog` — до `skill_find` на Этапе 4.
- [x] `CatalogView`: что уходит модели. Порог `DefaultShelfLimit = 25`.
      **Решение по ходу:** бестэговые скилы **никогда** не сворачиваются. Свернуть скил, которого не
      найти по предмету, значит не сократить его, а потерять. Он остаётся на полке и продолжает
      стоить сколько стоит — цена за нетэгированный фонд остаётся видимой, а не тихо съедается.
- [x] `SkillsContributor` печатает облако тэгов вместо полного списка, когда уровни так говорят.
      Со счётчиками: без них модель не может прикинуть, стоит ли предмет отдельного хода.
      **Уровень перебивает `preloaded`:** скил с `preloaded` из `out-of-catalog`-источника иначе
      вываливал бы в промпт целое тело — самый громкий способ рассказать про источник, о котором
      рассказывать не собирались.
- [x] Фасеты по тэгам в панели настроек. Весь словарь показывается всегда, а не поиском: дрейф,
      который нормализатор не ловит (`ssh` и `ssh-access` — два слова про одно), виден только когда
      слова стоят рядом. Выбор нескольких тэгов **пересекает**, как и у модели.
      Плюс бейдж уровня в шапке группы — ответ на «скил включён, а модель его не берёт».

**Проверка этапа:** ✅ 100 скилов дают каталог меньше 200 токенов — тест
`A_hundred_skills_cost_under_two_hundred_tokens_of_catalog` меряет отрендеренную секцию промпта и
заодно проверяет, что описания действительно исчезли, а не укоротились.

## Этап 4. Библиотекарь по тэгам

- [x] `ITagLibrarian`: отбор по пересечению тэгов плюс текстовое совпадение по описанию. Совпадение по
      тэгу — факт, по тексту — догадка, поэтому факт ранжируется выше. Читает фонд живьём, без кэша:
      библиотекарь, отвечающий по устаревшему индексу, — единственный отказ, который человеку не
      придёт в голову заподозрить. `OutOfCatalog` не возвращается никогда, и его тэги не попадают
      даже в словарь — иначе предметы скрытого источника вычислялись бы по списку слов.
- [x] Инструмент `skill_find` — возвращает **карточки, а не тела**. `Effect = Read`, поэтому не
      спрашивает: задать каталогу вопрос ни к чему не обязывает, воротами остаётся `skill_activate`.
      Пустой результат различает «никто не написал такого скила» и «такого слова тут нет» — второе
      чинится повторным вопросом, первое нет.
- [x] Правило в промпте: связка «облако → `skill_find` → `skill_activate`», с прямым указанием, что
      список предметов — это не «скилов нет», а «имён вам ещё не показали».
- [x] Прогоны на слабой модели (`google/gemma-4-26b-a4b-qat` в LM Studio). Замер, не рассуждение:

      | Обстановка | Запрос | Что сделала модель |
      |---|---|---|
      | только облако, 5 инструментов | бэкап linux по ssh | `skill_find` → `skill_activate` ✅ |
      | только облако | docker-проекты на хосте | `skill_find` → `skill_activate` → `skill_read_resource` ✅ |
      | только облако | dns не резолвится | **угадала id**, получила отказ, металась, потом `skill_find` ⚠ |
      | облако + 90 инструментов плагинов | бэкап linux по ssh | **не позвала вовсе**, ушла в `ssh_list_hosts` ❌ |

      Вывод: сама двухступенчатость слабой модели даётся — в чистом контексте она работает с первого
      раза. Ломает её **конкуренция инструментов**: когда рядом лежит `ssh_list_hosts`, модель берёт
      его и до каталога не доходит. Это ровно тот же отказ, который у `skill_activate` уже был (в
      индексе не зря стоит «правило перебивает инструкцию плагина „начинай сразу“»), а не новый,
      порождённый `skill_find`. Промпт этого пока не закрывает; закрывать — уровнями `ToolSetLevel`
      или отдельным прогоном, но это не Этап 4.

      **Дефект, найденный этими прогонами и исправленный здесь же:** подсказки при неизвестном id в
      `skill_activate` брались из всего `Catalog()` мимо уровня — неверная догадка работала как
      способ перечислить фонд, включая `OutOfCatalog`. Теперь подсказки фильтруются по уровню, а при
      их отсутствии текст ошибки называет `skill_find` вместо тупика.

      Побочное наблюдение, к скилам не относящееся: модель регулярно зовёт несуществующие инструменты
      (`agent_info`, `execute_command`, `network_resolve_host`) при пяти зарегистрированных. Это её
      свойство, а не наше, но оно объясняет часть шума в прогонах.

## Этап 5. Выдача на руки

Закрывает сценарий «средняя модель, малый контекст» полностью и стоит меньше всего.

- [x] Протокол: `chat.skill.activate` — симметрия к существующему `chat.skill.deactivate`.
      Уровень **не** проверяется: человек, выбирающий из списка, который он видит, — это и есть смысл
      `out-of-catalog`. Состояние проверяется: выключенный, недоверенный или без инструментов скил не
      должен просачиваться через другую дверь, чем модельная. Отказ сообщается, а не проглатывается.
      Поднимает те же `SkillDemand`-наборы, что поднял бы `skill_activate`.
- [x] Попап выбора скила в чате — `SkillPickerPopup.vue` по образцу `ModelPickerPopup`: мультитерм по
      id и описанию, клавиатура, плюс кликабельные тэги (пересечение). Кнопка `+ skill` в статус-баре
      показывается, только когда скил не идёт: вторая активация всё равно отклоняется.
- [x] Поиск и фильтр в [`SkillsPanel`](../../web/src/surfaces/Settings/SkillsPanel.vue) плюс массовые
      действия на группе. «All on/off» действует на **видимое**, а не на весь источник: при
      включённом фильтре «всё» означающее не то, на что смотришь, — это способ выключить то, чего
      никогда не видел. `Superseded` пропускаются: их переключатель всё равно ничего не делает.
- [ ] Виртуализация списка — **сознательно не сделана.** Оптимизация без наблюдаемой проблемы:
      панель уже фильтруется тремя способами (текст, тэги, доступность), и до тысяч скилов в одном
      источнике мерить нечего. Вернуться, когда появится на чём.

**Проверка этапа:** ✅ чат с выданным скилом не содержит каталога вообще —
`A_chat_with_a_handed_out_skill_carries_no_catalog_at_all` проверяет, что из промпта исчезли и полка,
и облако, и инструкции про `skill_find`, а осталась только процедура. Живьём: выдал `handout.beta`
через попап на запущенном сервисе — чип появился, попап закрылся, кнопка спряталась; выгрузка вернула
всё обратно.

## Этап 6. Два жанра

**Этап переформулирован при реализации, 2026-08-04.** Планировалось ввести жанры
`kind: procedure | reference`. Отменено вопросом владельца «какой сущности принадлежит `kind`?» —
оказалось, что ни одной, и что второй жанр не нужен вовсе. Разбор в ADR, раздел про жанры.

- [x] `preloaded` удалён **без замены** — из фронтматтера, `SkillEntry`, `SkillCard`,
      `SplaSkillSection`, `CapabilityDto`, `SettingsOps` (чтение и запись), `SkillsContributor`,
      `types.ts` и бейджа в панели. Шесть мест хранения, одно место чтения.
- [x] `ISkillSession` **не меняется**: один скил, как и был. Никакой «одной процедуры плюс N
      справочников» — этой сущности нет.
- [x] Документу, которому нужно быть в промпте всегда, место в `agent.instructions`: у него свой
      ключ настроек и свой contributor, и он не притворяется скилом.
- [x] Golden-тесты промпта перегенерированы осознанно, диффы сверены глазами. Вскрылось, что флаг
      протекал сильнее, чем считалось: preloaded-тело попадало в промпт и тогда, когда в чате **уже
      шёл другой скил**. Закреплено тестом `No_skill_can_reach_the_prompt_without_being_loaded`.

## Этап 7. Библиотекарь-подагент

- [x] `IAgentLibrarian`: полный каталог — в системный промпт библиотекаря, наружу пять карточек.
      **Отклонение от плана: не поверх `agent_spawn`.** Спаун — это полный агентский цикл, и он
      запускает *скил*, которым поиск не является. Библиотекарю нужен ровно один вызов одной модели,
      а `ILlmGateway` это и есть — с учётом токенов и квотами уже в тракте.
      **Ответ модели никогда не считается истиной:** возвращённые id ищутся в фонде, всё
      неразрешившееся молча выбрасывается. Выдуманный id — очевидный способ провалить эту затею, и
      обратный маппинг делает его невозможным, а не маловероятным. `OutOfCatalog` не попадает даже в
      промпт библиотекаря.
- [x] **Отклонение: не отдельный инструмент, а слой внутри `skill_find`.** ADR называет библиотекарей
      слоями, а не конкурентами; прогоны Этапа 4 показали, что слабая модель и один-то инструмент
      зовёт с трудом. Сначала бесплатный тэговый проход, модель — только если он не нашёл ничего.
- [x] Отдельная модель для библиотекаря: `skills.librarian.model`, плюс `enabled` (по умолчанию
      выключено — это вызов LLM до начала работы). Каталог уходит в **его** промпт, поэтому «слабая в
      чате + нормальная у стойки» становится настройкой, а не компромиссом.
- [x] Замер: латентность против качества отбора, на фоне тэгового библиотекаря.

      | Запрос | Только тэги | С библиотекарем |
      |---|---|---|
      | `ssh` (попадание) | 0–3 мс, 2 скила | 0 мс — до модели не дошло |
      | «our outgoing email keeps getting rejected…» | 0 мс, ничего | 2667 мс → `probe.mail` ✅ |
      | «something is wrong with how the machine decides who may talk to it» | 0 мс, ничего | 2087 мс → `probe.firewall` ✅ |
      | «recipe for borscht» | — | 1382 мс → честно ничего ✅ |

      В обоих смысловых запросах не было **ни одного общего слова** с описанием скила. Цена платится
      только на промахе; попадание по тэгу модель не трогает вовсе.

      **Дефект, найденный этим замером и исправленный здесь же.** Текстовый проход `TagLibrarian`
      использовал `Contains`, то есть искал подстроку: `our` сидит внутри `behaviour`, а стоп-слово
      `for` совпадало с половиной описаний. Проход был ложно-успешен почти всегда — он и врал, и не
      давал дойти до библиотекаря за собой. Теперь совпадение по целому слову или по общему префиксу
      (симметрично, от 4 букв, чтобы работали и `rebuild`/`Rebuilds`, и `relays`/`relay`) плюс
      короткий список стоп-слов. Закреплено двумя тестами.

## Мелкие долги, которые чинятся по дороге

- [x] `watcher.Error` не подписан.
      **Формулировка долга была неверной, и это выяснилось при разборе.** Переполнение буфера почти
      всегда самозалечивается: `Rebuild()` перечисляет всё заново, поэтому неважно, какие события
      потерялись — одно уцелевшее чинит каталог целиком. Стареет только хвост пачки.
      Настоящий случай другой: `Error` — единственный сигнал, что watcher **остановился** (каталог
      переименовали, сетевая шара отвалилась, хендл инвалидировался). Пере-вооружение живёт в
      `Fire()`, `Fire()` вызывается только из события, а мёртвый watcher событий не даёт — то есть
      путь восстановления недостижим ровно в той ситуации, ради которой написан.
      Починено: логирование, пере-вооружение и один ребилд, отложенные через тот же debounce-таймер
      (диспозить watcher из его собственного колбэка — способ получить дедлок).
      **Владелец сомневается, что проблема реальна**, и сомнение записано прямо над кодом вместе с
      решением. Ни один из двух отказов в этом репозитории не наблюдался; это рассуждение о контракте
      `FileSystemWatcher`, а не воспроизведение. Тестом не покрыто сознательно: надёжно спровоцировать
      переполнение или смерть хендла дороже, чем стоит сама правка.
- [ ] `Enumerate()` читает каждый файл целиком на каждый `Rebuild`. Нужен кэш по mtime+size и разбор
      только шапки.
- [ ] `SkillLibrary.IsSkillActive` в продакшене никем не присваивается (только в тестах) — либо
      подключить, либо удалить: тело и так пиннится.

## Открытые вопросы и незакрытые риски

Этапы 1–7 закрыты. Здесь то, что выяснилось **по ходу реализации**, ни к какому этапу не относится и
потеряется, если не записать. Порядок — по тому, насколько это мешает делу.

### 1. Конкуренция инструментов бьёт каталог, и промпт этого не закрывает

Главный измеренный отказ, из прогонов Этапа 4. В чистом контексте слабая модель проходит два шага
(`skill_find` → `skill_activate`) с первого раза. Но стоит зарегистрировать девяносто инструментов
плагинов — и она хватает `ssh_list_hosts`, до каталога не доходя вовсе.

Это **не новый** отказ, порождённый `skill_find`: у `skill_activate` он был и раньше, недаром в
индексе стоит «правило перебивает инструкцию плагина „начинай сразу“». Но и не закрытый.

Направления, ни одно не проверено: уровни `ToolSetLevel` (меньше инструментов на виду — меньше
конкуренции); усиление формулировки правила с прогонами как критерием; выдача на руки (Этап 5) как
обход, а не решение. **Мерить, а не рассуждать** — стенд из Этапа 4 воспроизводится за пять минут.

### 2. `ToolModeFilter` и `PermissionManager` расходятся про режим Chat

`PermissionManager` считает, что `Scope.Skill` в Chat — это `Ask`. `ToolModeFilter.IsAllowed`
отфильтровывает в Chat **всё**, кроме `Scope.Agent`. Значит `skill_activate` в Chat модели вообще не
предъявляется, и ветка `Ask` — мёртвый код.

Что из двух верно — решение владельца: либо фильтр пропускает `Scope.Skill` в Chat, либо
`PermissionManager` честно говорит `Deny`. Пока задокументировано как оговорка в
[`agents/security.md`](../../agents/security.md) и сноской под матрицей в
[`agents/skills.md`](../../agents/skills.md), чтобы матрицу не читали как доказательство, что скилы в
Chat работают.

### 3. Настоящий фонд `SPLA.Skills` не размечен тэгами

Вся машинерия Этапа 3 (облако, фасеты, `TagLibrarian`) на реальном корпусе **бездействует**: ни у
`linux-host.capture`, ни у `linux-host.restore` нет `tags:`. Каталог для них сворачиваться не будет —
бестэговые скилы сознательно не демотируются, — а `skill_find` достанет их только текстом.

То есть выигрыш Этапа 3 существует, но пока только в тестах. Нужен проход по `SPLA.Skills` с
расстановкой тэгов; это чужой репозиторий и отдельная задача.

### 4. У библиотекаря-модели нет UI

`skills.librarian` (`enabled`, `model`) правится только руками в `.spla`. Панель настроек его не
показывает и не переключает. Учитывая, что по умолчанию он выключен, включить его сейчас может только
тот, кто прочитал документацию.

### 5. Известные принятые ограничения

Не дефекты — следствия принятых решений, записаны чтобы их не «чинили» по незнанию:

- **Список приложений пиннится при активации.** Ресурс, добавленный в папку скила *после*
  активации, не появится в формуляре до следующей. Та же форма, что у пиннинга тела.
- **`findable` и `out-of-catalog` для модели различаются только через `skill_find`.** Без вызова
  инструмента оба невидимы одинаково.
- **Виртуализация списка скилов не сделана** — оптимизация без наблюдаемой проблемы; панель уже
  фильтруется текстом, тэгами и доступностью. Вернуться, когда в одном источнике будут тысячи.
- **Уровень источника — не UI-переключатель.** Читается из `.spla`, в панели только показывается
  бейджем. Сознательно: это решение развёртывания, а не пользовательская настройка.

### 6. Документы, намеренно не приведённые в соответствие

`docs/ideas/*` и `docs/reviews/*` — исторические записи, они описывают состояние на момент
написания. В них остались упоминания `preloaded`, `SkillManager` и прочего из старого словаря.
Править их — значит переписывать историю; читать их надо с датой в руке.
