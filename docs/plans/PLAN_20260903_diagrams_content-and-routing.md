## 1. Что здесь главное

Схема должна отвечать на архитектурный вопрос, а не украшать его. Поэтому порядок
работ определяется не сложностью, а тем, **на какой стороне лежит пункт**: смысл
(связи, вложенность, комментарии) или образность. Первым делается единственный пункт
на стороне смысла — подписи на концах связей; всё остальное обслуживает восприятие и
идёт после.

Второе, что определяет порядок: **механизм раньше клиентов**. Классы и таблицы с
полями — первые клиенты шаблонов, а не отдельная фича; если сделать их спецрендером
«пока по-быстрому», их придётся переписывать сразу же.

## 2. Потоки работ

### Поток A — подписи на концах связей — **сделано**

Единственный пункт на стороне смысла, самый дешёвый из всех.

1. Два слота в текстовых каталогах: `fromLabel`, `toLabel` по ключу `r_*`, с той же
   формой значения (`v` / `at` / `origin` / `from` / `fromHash`), что и остальные
   тексты. Механизм происхождения не трогается: он не знает, что стоит за ключом.
2. Рендер: якорь от первого и последнего сегмента ребра, перпендикулярный отступ.
3. Инспектор связи: два поля рядом с подписью.
4. У связей с `origin: "code"` слотов нет — как и остального текста
   (`ADR_20260831` §2.13).
5. `CONTRACT.md`: описать слоты; проверка в CI подхватывает их без изменений.

**Готово, когда:** на схеме читается `1` — `0..*`, текст переживает
сохранение-открытие, отчёт CI видит их наравне с прочими текстами.

### Поток B — компилятор шаблонов — **сделано**

Сердце. Делается до любых клиентов.

1. **Парсер**: строки — стек, `|` — колонки, `@Directive(позиционный, имя=значение)`,
   списки в `[…]`. Один разбор аргументов на все директивы.
2. **Дерево в памяти** (`row → [cell]`), наружу не сохраняется никогда.
3. **Устойчивость к ошибке** — приёмочное требование, не пожелание: невалидный текст
   оставляет на холсте последний валидный результат плюс маркер ошибки. Ни исчезнувших
   блоков, ни пустого холста.
4. **Директивы первой очереди**: `@Name`, `@Description`, `@Members`, `@Asset`.
5. **Правила**, без которых язык не заменит спецрендеры: пустое скрывается само;
   `where=` как фильтр; значок из данных, а не из шаблона.

**Готово, когда:** шаблон правится в панели, результат виден на кадре правки, а
намеренно сломанный текст не роняет холст.

### Поток C — реестр шаблонов — **реестр и host API сделаны; панель правки в работе другим агентом**

1. Именованные файлы шаблонов в проекте (не строки внутри `styles.json`).
2. Каскад назначения: размещение → стиль → встроенный дефолт «только заголовок»;
   отсутствие значения = наследовать.
3. Host API: список и чтение по имени.
4. Редактор: выбор из списка с предпросмотром.

**Готово, когда:** один шаблон переиспользуется несколькими стилями, а исключение для
одного узла не требует стиля-однодневки.

### Поток D — класс, интерфейс и таблица — **частично: рендер класса/таблицы сделан**

Первые клиенты механизма, а не отдельная реализация.

1. Уточнить форму `members` в `CONTRACT.md`: `kind`, `name`, `type`, `visibility`,
   `note`. Поле уже объявлено — описывается его содержимое.
2. Шаблоны в поставке: класс/интерфейс (`@Name` + `@Members`) и таблица
   (`@Name` + `@Members(where=kind:field)`).
3. Значки из данных: ключ у PK, замок у `private` — отображение в стиле.
4. Всплывающий слой поверх холста для развёрнутого списка, `doc` и длинного `codeRef`.
   Раскрытие по клику. Высота блока не меняется, в файл вида ничего не пишется.
5. `@Members(collapsed)` — свёрнутое состояние как решение шаблона, с меткой числа
   членов.

Заполнение `members` данными — вне этого плана (см. §5.2).

**Готово, когда:** класс с полями и таблица с колонками рисуются одним движком, а
подробность меняется правкой шаблона, без правки кода.

### Поток E — реестр содержимого — **частично: реестр, санитайзер и вставка сделаны; выбор картинки в UI не сделан**

1. Хранилище именованных ресурсов, адресация по имени (`@Asset(brain)`).
2. **Санитайзер**: белый список элементов и атрибутов, никаких `<script>`,
   обработчиков и внешних ссылок. Делается вместе с реестром, не после.
3. Host API: список (для выпадающего списка с предпросмотром и фильтром) и чтение.
4. Геометрия вставки: `w` / `h` / `align` — общие имена, как у прочих директив.

**Готово, когда:** картинка выбирается из списка, лежит в общем хранилище, а файл вида
не содержит её тела.

### Поток F — фигуры — **сделано**

Механизм готов (`ADR_20260901`): добавление фигуры — регистрация рендерера, ядро не
трогается.

1. `shape` — поле стиля, с override на размещении для исключений.
2. Фигуры: эллипс (порты — пересечение луча из центра с эллипсом), цилиндр,
   шестиугольник, ромб, актор (порты именованные, а не по формуле).
3. Острый UML-прямоугольник: `cornerInset` равен нулю — случай уже предусмотрен ADR.

**Готово, когда:** новая фигура добавляется без единой правки в роутере, распределителе
портов и `DiagramCanvas`.

### Поток G — роутинг — **сделано**

1. Роутер как **чистая функция** от (порты, прямоугольники препятствий). Результат
   нигде не сохраняется. Это свойство закладывается сразу, даже пока режимов два.
2. Режимы: `bezier` (есть), `orthogonal`, `tree-horizontal`, `tree-vertical`.
3. Каскад выбора: ребро → вид → тип связи (edge-стиль в `styles.json`) → дефолт.
   Дефолты по типу настраиваются сразу: наследование — `tree-vertical`, поток — `bezier`.
4. Хранение: режим — в `*.view.json` (ребро, вид) и `styles.json` (тип);
   **вычисленная ломаная — нигде**.
5. Пересчёт только для рёбер, чей габарит задет сдвинутым блоком.

**Готово, когда:** режим переживает сохранение, а `*.view.json` не содержит ни одной
координаты маршрута.

### Поток H — обход коллизий (долг, не в этой волне) — **не начато**

Полный обход препятствий по сетке. Не начинать, пока не сделаны A–G: благодаря чистой
функции из потока G он подключается без миграции файлов и без правки контракта.

Ручные точки перегиба **не делать** — отклонены в ADR §2.8.

## 4. Правила, которые не обсуждаются

1. **Координаты правит только владелец руками.** Роутинг — способ нарисовать линию
   между уже зафиксированными точками; раскладку узлов он не трогает никогда.
2. **Хранится намерение, не результат.** Режим роутинга — в файле; вычисленная
   ломаная — только в памяти.
3. **Источник истины шаблона — текст**, не компилированное дерево.
4. **Сломанный шаблон не роняет холст.**
5. **Каждое пожелание проходит фильтр цены** (ADR §1.3), с уточнением про две
   образности: украшение режется жёстко, читаемость — нет.

## 5. Открытые вопросы

1. **Имя `@Asset`** — переименуемо, пока нет кода.
2. **Кто заполняет `members`.** Руками для сущностей на схемах или ждать извлечения в
   `spla-atlas`. Поток D работает в обоих случаях; вопрос про наполнение, не про
   механизм.
3. **Уровень вида в каскаде шаблонов** — не вводится заранее.
4. **Приоритет потока H** — по живым схемам.
