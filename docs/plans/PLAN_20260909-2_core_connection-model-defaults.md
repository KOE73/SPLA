# PLAN_20260909-2_core — модель по умолчанию и её видимость

Статус: **не начато**.

Реализует [ADR_20260909-2_core_connection-model-defaults.md](../adr/ADR_20260909-2_core_connection-model-defaults.md).
Читать план без него бессмысленно: здесь порядок работ, там причины.

Волна 1 — фундамент, всё остальное на неё опирается. Волны 2, 3 и 4 после неё независимы
и делаются в любом порядке / параллельно.

## Волна 1 — флаг и его резолюция

### 1.1. [`SplaSections.cs`](../../src/core/SPLA.Domain/Settings/SplaSections.cs)

`SplaModelSection` (около строки 484, рядом с `Id`/`Name`) получает:

```csharp
public bool Default { get; set; } = false;
```

YAML-ключ `default:`. Проверить, что запись без этого поля не начинает писать `default: false`
на каждую модель при пересохранении настроек панелью — если сериализатор настроен опускать
дефолтные значения для остальных `bool`-полей секции, этот флаг не должен быть исключением.

### 1.2. [`SettingsResolver.cs`](../../src/core/SPLA.Domain/Settings/SettingsResolver.cs)

Новое свойство на `ResolvedSettings`, рядом с `Models`:

```csharp
public string? DefaultModelId { get; set; }
```

Считается в `Resolve()` **в том же порядке слоёв**, что уже сводит соединения (ADR_20260904
§2.3: shared → user(defaults.yaml) → connections.yaml → манифест проекта). На каждом слое:
если в нём отмечена ровно одна модель — `DefaultModelId` слоя заменяет унаследованный от
предыдущих целиком; если отмечены две и более — ошибка конфигурации (см. 1.3); если ни одной —
слой ничего не меняет, унаследованное остаётся.

Порядок реализации: скорее всего резолвер уже проходит слои последовательно для сборки
`Models`/`Connections` — считать `DefaultModelId` тем же проходом, не заводить отдельный.

### 1.3. Ошибка на несколько отметок в одном слое

Найти, как резолвер сегодня сообщает о противоречиях конфигурации (дублирующийся `id`
соединения — похожий случай), и завести туда же ветку для «в файле N отмечено больше одной
модели как `default: true`». Формулировка ошибки должна называть файл (слой) и оба/все
конфликтующих `id`, не просто «конфликт умолчаний».

### 1.4. Потребители: `ToLLMSettings()` и `chat run`

- [`SettingsResolver.cs:369`](../../src/core/SPLA.Domain/Settings/SettingsResolver.cs) —
  `ToLLMSettings()` без аргумента сегодня берёт `Models.FirstOrDefault()`. Меняем на:
  `FindModel(DefaultModelId) ?? Models.FirstOrDefault()`.
- [`ChatRunCommand.cs:182-187`](../../src/apps/SPLA.CLI/Batch/ChatRunCommand.cs) — ветка
  «`--model` не задан» сегодня `settings.Models.Take(1)`. Меняем на: если `DefaultModelId`
  задан — список из одной этой записи (через `FindModel`), иначе прежнее поведение
  `Take(1)`.

### Приёмка

- ни одна модель не отмечена нигде → поведение не отличается от сегодняшнего ни на бит
  (и `ToLLMSettings()`, и `chat run` берут первую в списке, как раньше);
- одна модель отмечена в `user`-слое → она приходит и в новый чат, и в `chat run` без
  `--model`, независимо от порядка объявления соединений;
- модель отмечена в `user`, другая — в `project` того же чата/проекта → побеждает `project`
  целиком (не «объединение флагов»);
- две модели отмечены в одном файле → внятная ошибка при разрешении настроек, называющая файл
  и оба `id`, а не тихий выбор одной из них;
- `--model <id>` явно заданный по-прежнему имеет приоритет над `DefaultModelId` — эта волна
  трогает только ветку «ничего не задано».

## Волна 2 — второй ключ поиска: `DisplayName` как аргумент

**Требует волну 1 только по месту (тот же `FindModel`), не по датам — можно писать одновременно.**

### 2.1. [`SettingsResolver.cs:362`](../../src/core/SPLA.Domain/Settings/SettingsResolver.cs)

`FindModel(string? modelId)` сегодня ищет только по `Entry.Id`. Добавить вторую попытку: если
точного совпадения по `Id` нет, поискать по `ResolvedModelEntry.DisplayName`
(`"{Connection.DisplayName} · {Entry.DisplayName}"`, строка 414) без учёта регистра. Порядок
попыток: сперва `Id` (короче и однозначнее), затем `DisplayName`.

Если `DisplayName` у двух записей совпал (два разных `id`, одинаковое отображаемое имя) —
трактовать как «не нашли» и дать вызывающему коду ту же ошибку, что при полном отсутствии
совпадения (`ChatRunCommand.cs:189`, «no matching model entries»), не гадать, какая из двух
имелась в виду.

### 2.2. Описание опции CLI

[`ChatRunCommand.cs:27-29`](../../src/apps/SPLA.CLI/Batch/ChatRunCommand.cs) — обновить
`[Description]` у `--model`: теперь принимает либо `id` записи, либо строку вида
`"Соединение · Модель"`, как она показана в интерфейсе (плюс `all`).

### Приёмка

- `--model qwen3.8-27b` (по `id`) работает как раньше;
- `--model "Default · qwen3.8-27b@q4_k_xl"` (скопированное отображаемое имя) резолвится в ту же
  запись;
- неоднозначный или неизвестный `DisplayName` даёт ту же ошибку, что несуществующий `id`, а не
  падение с трассой.

## Волна 3 — постоянная метка соединения в вебе

**Независима от волн 1 и 2** — чисто отображение, серверных данных для неё уже достаточно
(`groups`/`g.connectionName` в `StatusBar.vue` уже есть).

### 3.1. [`StatusBar.vue`](../../web/src/surfaces/StatusBar.vue)

`modelLabel()` (около строки 341) сегодня возвращает `"{name} · {model}"` только когда имя
записи и имя модели различаются, иначе — голое имя. Заменить на: всегда
`"{connectionName} | {modelLabel}"`, где `connectionName` берётся из группы (`g.connectionName`,
уже доступной в `<optgroup>`, строка 21), а `modelLabel` — прежняя логика для самой модели
(имя записи, либо «имя · модель», если они расходятся).

Трогает только видимый текст `<option>`; `value` остаётся `m.id`, `optgroup label` не меняется
(эмодзи + имя соединения там уже стоят и дублирование в самой опции — осознанное: закрытый
`<select>` показывает только текст выбранной `<option>`, группа в свёрнутом виде не видна).

### 3.2. Ширина / перенос

Проверить в браузере (см. `run`/preview), что более длинная строка не разваливает верстку
статус-бара при узком окне — сейчас там и так несколько `<label>` в ряд. Если тесно, разумный
компромисс — сокращать длинные имена соединений в середине (`…`), не в модели: модель — то, что
человек выбирает, соединение — контекст.

### Приёмка

- закрытый селектор модели показывает `"Default | qwen3.8-27b@q4_k_xl"` для записи без
  собственного имени, отличного от модели;
- список при открытии выглядит как сегодня (группировка по `optgroup` не изменилась);
- ничего не съезжает при обычной ширине окна; при очень узком — сокращается имя соединения, не
  модели.

## Волна 4 — кнопка копирования рядом с селектором

**Независима от волн 1–3.** Ссылается на `CopyButton.vue`, уже существующий и используемый в
других поверхностях интерфейса (пузыри чата, composer) — здесь только новое место установки,
не новый компонент.

### 4.1. [`StatusBar.vue`](../../web/src/surfaces/StatusBar.vue)

Рядом с `<select>` модели (после кнопки «i», строка 33) — `CopyButton`, который копирует в
буфer текущее `modelLabel(selected)` (после волны 3 — уже включающее имя соединения). Хвостовая
подсказка (`title`) должна объяснять, что это то же значение, которое принимает `--model` в
`spla chat run` (после волны 2) — иначе кнопка выглядит как случайная мелочь без назначения.

Если `CopyButton.vue` ожидает пропсы в форме, отличной от «строка для копирования» (проверить
по существующим местам использования — `UserBubble.vue`, `Composer.vue`), подогнать вызов под
существующий контракт компонента, не переделывать сам компонент под этот один случай.

### Приёмка

- клик по кнопке кладёт в буфер обмена ровно ту строку, что видно в закрытом селекторе;
- эта строка, вставленная как `--model "..."` в `spla chat run`, резолвится в ту же запись
  (сквозная проверка волны 2 + волны 4 вместе);
- кнопка недоступна/не рисуется, когда модель не выбрана (`!modelId`, тот же признак, что уже
  используется для кнопки «i» строкой выше).

## Отложено (сознательно, не в этом плане)

- ~~**Галочка «сделать умолчанием» в редакторе карточки соединения/модели.**~~ **Сделано.**
  Галочка стоит на строке модели (не на соединении — по ADR §2 флаг живёт на модели), плюс
  «★» в заголовке свёрнутой строки, чтобы не открывать восемь строк ради вопроса «а какая
  сейчас».

  Одно решение по ходу, которого в плане не было: **уникальность держит панель, а не карточка**.
  Слой — это файл, резолвер отказывает файлу с двумя отметками, а модели этого слоя разбросаны по
  всем его соединениям — значит единственное место, которое видит их разом, это
  `ConnectionsPanel`. Карточка только сообщает о желании (`set-default`), гасит соседей панель
  (`setDefaultModel`). Соседние слои не трогаются: каждый называет свой default, а кто победит —
  решает порядок слияния.
- **«Соединение по умолчанию» отдельно от модели.** ADR §2 объясняет, почему второе поле не
  заводится: модель по умолчанию уже несёт своё соединение через `ResolvedModelEntry.Connection`.
- **Наследование `default:` между слоями иначе, чем «слой побеждает целиком».** Не открытый
  вопрос — ADR прямо ссылается на уже принятое правило `ADR_20260904` §2.3 и не вводит новое.
