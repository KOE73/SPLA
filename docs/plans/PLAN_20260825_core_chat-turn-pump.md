# PLAN_20260825_core — насос ходов, Stop = STOP, панель задач

Статус: в работе
Решение: `ADR_20260825_core_chat-turn-pump.md`
Предшественник: `PLAN_20260824-2_core_background-tool-calls.md` (волны 0–1 закрыты, коммит `79156a4`);
эта работа **заменяет его волну 2**.

---

## Что делается и чего НЕ делается

**Делается.** Ход начинает `ChatPump` из ящика, а не соединение из `chat.send`. Реплика человека в
занятый чат встаёт в очередь вместо блокировки поля. Stop гасит ход и все фоновые задачи. Появляется
панель задач.

**Не делается.** Таймерные и внешние поставщики (насос обязан их допускать формой, но ни одного не
вводим). Переживание ящиком перезапуска сервиса. Кросс-чатная панель задач. Консоль фонового шелла.

---

## Порядок и главный риск

Запуск хода — самый горячий путь в системе, и он **сегодня работает**. Инверсия одним движением
ломает все чаты сразу. Поэтому порядок такой: сначала ход учится жить без соединения, потом рядом
появляется насос и берёт себе только фоновые результаты, и лишь последней на насос переезжает
отправка человеком. На каждом рубеже система рабочая.

```
A: ход без соединения ──→ B: насос (только задачи) ──→ C: Stop=STOP ──→ D: человек в очередь ──→ E: панель
   поведение не меняется     закрывает волну 2           видимое        снимает блокировку        видно, что гасишь
```

## Волна A — ход перестаёт принадлежать соединению ✅ (коммит `11ddff9`)

Поведение не изменилось ни на грамм. Чистая перестановка владения.

Разведка перед работой изменила саму волну: `RunTurnAsync` оказался **почти не зависящим от
соединения уже сегодня**. `runtime.Asks.AskPermissionAsync`/`AskClarifyAsync`
(`ClientConnection.cs:424-425`) адресуются чатом, а не сокетом; `BroadcastToWatchersAsync` и так
вещает зрителям чата, а не звонившему. Единственной настоящей привязкой был `_identity.UserKey`
для телеметрии. Поэтому A.1–A.2 свелись к переносу, а A.3–A.4 (перенос CTS внутрь `ChatRuntime`,
распил `SendAsync`) **не понадобились вовсе** — цель волны достигнута без единой правки домена.

- [x] **A.1/A.2. Колбэки и вопросы перестали принадлежать сокету.** `BuildCallbacks` и `TurnContext`
      переехали в новый `ChatTurnDriver` (`src/service/SPLA.Service/Hosting/ChatTurnDriver.cs`).
      Из per-connection в нём был только `_hub`; обработчики вопросов уже были чат-адресными.
- [x] **A.3/A.4. Не потребовались.** `ChatRuntime.SendAsync`, `ConversationOrchestrator`,
      `TurnRegistry`, `_turnGate` — не тронуты. Токен хода по-прежнему создаётся снаружи, только
      теперь драйвером, а не соединением.
- [x] **A.5. `ClientConnection` похудел на ~190 строк** и не содержит логики хода: отдаёт реплику
      и того, кто спрашивает.
- [x] **Драйвер конструируется по месту, а не кэшируется.** Первый заход регистрировал драйверы в
      словаре по `chatId` от `ChatRegistry.RuntimeOpened`; это требовало ленивого запасного пути для
      чатов, открытых раньше подписчика, и вечно держало бы `ChatRuntime` удалённых чатов — у
      `ChatRegistry` нет события закрытия (`Delete`/`Dispose` молчат). Драйвер не имеет изменяемого
      состояния, поэтому кэш убран вместе с обеими бедами.

**Рубеж A пройден:** сборка чистая, 1081/1081, живая проверка в браузере — ход прошёл через новый
драйвер, модель ответила, композитор разблокировался.

**Долг, обнаруженный по пути:** у `ChatRegistry` нет события закрытия чата. Волне B оно, скорее
всего, понадобится — насос обязан умирать вместе с чатом, а подписаться на его смерть сегодня
не на что.

**Не сделано из первоначального замысла A.2:** текст отказа «некому спросить» вместо
«denied by the user» (долг ловушки 3 старого плана). Отложено: пока ход всегда начинает
соединение, спросить есть кого — станет актуально в волне B.

## Волна B — насос, пока только для фоновых результатов ✅

Здесь закрылось то, ради чего затевалась волна 2 старого плана.

- [x] **B.1. Типизированный элемент ящика.** `InboxItemKind` (`Human`/`TaskResult`/`Notice`),
      `Enqueue(message, kind)`, `HasPending`, событие `Enqueued`. `DrainAll()` и
      `ConversationOrchestrator.cs:175` — не тронуты, род нужен только насосу и в разговор не попадает.
- [x] **B.2/B.3. `ChatPump`** (`src/service/SPLA.Service/Hosting/ChatPump.cs`). По одному на чат,
      рождается на `RuntimeOpened` рядом с `WireChatProgress`, умирает на новом `RuntimeClosed`.
      Склейка 500 мс: три задачи, завершившиеся за секунду, дают один ход.
- [x] **B.4. Политика «только если окно открыто»** по умолчанию. Пер-чатного переключателя пока нет —
      см. долг ниже.
- [x] **B.5. Защита от самозапитки** — 3 подряд авто-пробуждения без человека, потом молчание и одна
      заметка зрителям. Сброс по `ChatRuntime.HumanTurnCount` (новое), а не по связи с сервисным слоем.
- [x] **B.6. Гонка «разгребли и разбудили»** закрыта с обеих сторон: пустой ящик → не будить,
      живой ход → перевзвести таймер, а после своего хода — перепроверить сразу, не ожидая окна.

**Сопутствующее, потребовалось по дороге:**
- `ChatRegistry.RuntimeClosed` — долг волны A закрыт, теперь есть на что подписать смерть чата.
- `ChatRuntime.SendAsync` принимает `string? text`: разбуженному ходу нечего добавлять в разговор,
  содержимое даёт слив ящика. При `null` блок пользовательского сообщения пропускается целиком.
- `ConnectionHub.HasWatchers(chatId)`.
- Решение о пробуждении вынесено в чистую `DecideWake(...)` — проверяется без сокета и хаба.

**Рубеж B:** сборка чистая, 1092 теста (1081 + 11 новых `ChatPumpTests`).

**Долги волны B:**
- Пер-чатный переключатель политики пробуждения (B.4) — сейчас политика зашита.
- `userKey: "pump"` для телеметрии авто-хода — строка-заглушка; при многопользовательской работе
  правильнее атрибутировать тому, кто запустил задачу.
- Живьём не прогонялось: доказательство пока только в тестах.
- **Тесты насоса зависят от реального времени.** Окно склейки — константа 500 мс, проверки
  «событие НЕ произошло» ждут по 700 мс. Попытка сделать окно инъектируемым и укоротить ожидания до
  30/120 мс была сделана и **откачена**: в полном прогоне тест склейки начал падать, хотя в
  одиночку проходит за 208 мс — то есть стал чувствительнее к нагрузке, а не устойчивее. Правильная
  починка, судя по всему, не в укорачивании ожиданий, а в подмене самого источника времени
  (`TimeProvider`), чтобы тесты вообще не ждали.

## Волна C — Stop = STOP ✅

- [x] **C.1. `BackgroundTaskRegistry.CancelAll()`** — снимает снимок живых задач, затем гасит:
      снимок-потом-сигнал не даёт гонки с параллельным `Finish()`. Возвращает погашенное
      (id + имя инструмента), упорядоченное как `All`, иначе доклад был бы недетерминированным.
- [x] **C.2. Разоружение насоса живёт на чате, а не в насосе.** Структурное ограничение: `ChatPump`
      создаётся замыканием в `WireRuntimeEvents`, из обработчика `cancel` до него не дотянуться.
      Реестра насосов заводить не стали (та же беда с временем жизни, что у снятого кэша драйверов) —
      вместо этого `ChatRuntime.SuppressAutoWake()`/`AutoWakeSuppressed`, снимается там же, где
      растёт `HumanTurnCount`. Stop и пауза от самозапитки — одно состояние, достигнутое разными
      дорогами, и заканчивает оба одно и то же: человек заговорил.
      В `DecideWake` ветка `Suppressed` стоит **до** `TurnAlreadyRunning`: та перевзводит таймер, а
      разоружённый насос обязан замолчать, а не взводиться вечно.
- [x] **C.3. Доклад** — `Notice` зрителям с перечнем погашенных задач. Только когда задачи реально
      были: голый Stop и так виден клиенту через `TurnComplete{Cancelled=true}`, а «и 0 задач» — шум.
- [x] Ящик не чистится (ADR §2.4).

**Рубеж C:** сборка чистая, 1099 тестов (1092 + 7).

**Почему подавление ставится ДО отмены:** отменённая задача доставляет собственную отмену в ящик, и
каждая такая доставка дёргает насос. В обратном порядке остаётся окно — узкое из-за дебаунса, но
настоящее, — в котором Stop оказывается паузой.

## Живая проверка волн B и C (2026-08-25) — и найденный ею баг

Проверено вживую, на реальной модели:
- **B:** запущена фоновая задача, человек не отправлял **ничего** — чат сам начал ход и доложил
  результат. В диагностике: `enqueued kind=TaskResult` → `decide pending=True running=False
  watchers=True suppressed=False` → `Wake` → после хода `NothingPending`.
- **C:** две задачи по 120 с, нажат Stop. Обе погашены, в чат пришло
  «Stopped the turn and 2 background tasks: bg_2 (system_run_shell), bg_3 (system_run_shell)».
  Обе отменённые задачи доставили свои отмены в ящик, и насос ответил `Suppressed` — то есть без
  разоружения Stop действительно оказался бы паузой. Ровно тот отказ, против которого строилось.

### Баг, который не поймал ни один из 1099 тестов

Насос не создавался **вообще**. `ServeCommand.cs:29` открывает проект по умолчанию, а
`SplaServiceHost.Build` вызывается на строке 44 — то есть `RuntimeCreated` для этого проекта
срабатывал раньше, чем хост на него подписывался, и `entry.Chats.RuntimeOpened` не привязывался
никогда. Под `spla serve` молча не работали **и насос, и живая раздача прогресса**
(`WireChatProgress` висит на том же событии) — последнее с волны 1, и моя тогдашняя отговорка
«у shell-инструментов просто нет вложенных узлов» была неверной.

Тесты этого не видели, потому что все они собирают реестр сами и в правильном порядке.

**Починка:** `AgentRuntimeRegistry.Existing` + `WireRuntimeEvents` проходит по уже открытым проектам
вдобавок к подписке на будущие. Обвязка перестаёт зависеть от порядка построения, вместо того чтобы
требовать правильного порядка от каждого вызывающего.

### Осталось открытым

- **Кнопки Stop нет, когда ход уже кончился, а задачи ещё идут** — а это типичный случай, ради
  которого фон и существует. Композитор показывает Stop только при живом ходе (`Composer.vue:27-28`),
  так что «Stop гасит всё» сейчас недостижим ровно тогда, когда нужен. Закрывается волной E
  (панель задач) — до неё точечная отмена возможна только через `task_cancel` руками.
- Пер-чатный переключатель политики пробуждения (B.4).
- `userKey: "pump"` — заглушка телеметрии.

## Ловушки

1. **Ход без зрителя.** Некому показать и некого спросить. → Не будить, когда окно не открыто (B.4);
   если зритель отвалился посреди хода — отказ вместо вопроса (A.2).
2. **Самозапитка насоса.** Разбуженный ход рождает задачу, задача будит ход. → B.5.
3. **Пустой ход от гонки.** Сигнал пришёл, а слив хода уже всё забрал. → B.6.
4. **`turnActive` из двух источников.** Клиент выставляет его сам при отправке (`Composer.vue:117`);
   с очередью это станет враньём — отправка больше не равна началу хода. → D.2.
5. **Stop гасит чужое.** Отмена глобальна по чату. → Принято осознанно (ADR §4.4), доложить в C.3.
6. **Очередь переживает Stop.** Реплика человека — его намерение, а не работа агента; гасить её
   вместе с ходом значит съесть сказанное. → ADR §2.4.
7. **Порядок доставки.** Реплика человека позади трёх результатов. → Открыто (ADR §4.2).
8. **Двойной `progress.node`.** Уже наступали на это в волне 1, когда подписка стала пер-чатной. При
   переносе callbacks в чат (A.1) проверить, что пер-ходовая подписка не воскресла.
9. **Разгон по токенам.** Авто-ход тратит деньги без просящего. → B.4 + видимость + счётчик B.5.
10. **`_turnGate` против насоса.** Насос обязан брать тот же гейт, иначе два хода в одном чате
    затопчут `_conversation`.
