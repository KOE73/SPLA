## Что делается и чего НЕ делается

Делается: **вызов инструмента может уйти в фон.** Модель получает id задачи сразу, разговор
продолжается, результат приезжает отдельным сообщением на границе следующего хода.

**НЕ делается пробуждение чата на простое** в волнах 0–1: если человек молчит, результат ждёт его
следующего сообщения. Волна 2.

**НЕ делается персистентность задач через рестарт** (ADR §2, последняя строка) и **не делается
консоль фонового шелла для человека** (ADR §4.4).

Волны разделены по одному признаку: **волна 0 не меняет наблюдаемого поведения ничем.** Её можно
влить и забыть; ни один тест, ни один клиент, ни одна модель не заметят разницы. Всё, что меняет
поведение, начинается с волны 1.

## Конструкция

```
модель ──► ToolPipelineBlueprint
             Resolution → Availability → Disclosure → Telemetry → Policy(разрешение здесь)
                                                                     │
                                                            Ambient(scope'ы опубликованы)
                                                                     │
                                                     ┌───── Background(новое звено) ─────┐
                                                     │                                   │
                                              background:false                    background:true
                                                     │                                   │
                                            Progress → Fault → Accounting → инструмент   │
                                                     │                                   │
                                              результат модели                  Task.Run(отсоединение)
                                                                                         │
                                                       ┌─────────────────────────────────┤
                                                       │                                 │
                                          ToolResult.Ok("bg_2 started")      свой ProgressTree (корень)
                                          ─── возврат в тот же ход                       │
                                                                            Progress → Fault → Accounting
                                                                                         │
                                                                        BackgroundTaskRegistry(чат) ◄──┘
                                                                                         │
                                                                                 ChatInbox.Enqueue
                                                                                         │
                                              ConversationOrchestrator: вершина цикла ◄───┘
                                                                                         │
                                                                    синтетическое сообщение role=user
```

Владение: реестр задач, лес прогресса и инбокс — **на `ChatRuntime`**, рядом с `SessionKv`,
`Checkpoint` и `AgentSession`. Ни одна из трёх вещей не статическая и не процессная.

### Соседи по конвейеру

Этот план — не единственный заказчик той же цепочки. Сверено с
[`IDEA_20260824-2_core_tool-policy-middleware`](../ideas/IDEA_20260824-2_core_tool-policy-middleware.md)
(там же разбор со стороны политик):

| Соседняя работа | Ступень | Отношение к фону |
|---|---|---|
| Аргументное PRE (политики) | внутри `Policy` (400), в `PermissionManager` | **Снаружи** отсоединения — вердикт берётся до него. Именно PRE расширяет класс задач, которые можно отпустить в фон без человека |
| POST (обрезка результата, увод в блоб) | новая ступень ~750–800 | **Внутри** отсоединения. Один и тот же код обслуживает синхронный и фоновый результат — см. шаг 1.4 и ловушку 16 |
| Таймаут | новая ступень между `Fault` (700) и `Accounting` (800) | **Внутри** отсоединения. Тем же звеном стережётся и ход, и фоновая задача — см. ловушку 17 |
| Telemetry-span | `Telemetry` (300) | **Снаружи** — и потому у фонового вызова меряет запуск, а не работу. Ловушка 15 |

Правило, из которого всё это выводится: **звено снаружи ступени 550 видит запуск, звено внутри —
работу.** Проверять принадлежность каждой новой заботы к одной из двух половин обязательно, иначе
она молча начнёт мерить не то.

## Ловушки и что с ними делать

1. ✅ **Результат нельзя вернуть в тот же `tool_use`.** Провайдер требует ответ на каждый вызов в том
   же ходе, а второй ответ на тот же id отвергнет. → Синхронный `ToolResult.Ok` с id задачи, а
   результат — отдельным сообщением роли `user`. Сделано (`BackgroundStage`), проверено вживую.

2. ✅ **Вставка в середину пачки рвёт разговор.** `tool_use` без парного `tool_result` — ошибка
   провайдера, не косметика. → Слив инбокса **только** на вершине цикла, до сборки контекста.
   Сделано (0.6), тест `DrainInbox_is_never_called_between_a_tool_calls_batch_and_its_results`.

3. ✅ **`AsyncLocal` перетекает и хорошее, и плохое.** `AgentSessionScope`/`ToolHostScope` унаследовать
   надо; `PermissionScope`/`ClarifyScope` — категорически нельзя: их обработчики указывают на
   соединение хода, который закончится через минуту, и вопрос уйдёт в никуда. → Подменять обе при
   отсоединении на отказ с внятным текстом. Сделано; текст отказа неточен для этого случая
   («denied by the user») — известный, записанный пробел в `BackgroundStage.RefuseAsk`.

4. ✅ **Токен отмены хода — не токен задачи.** Если задача побежит с `ct` хода, кнопка «Стоп» убьёт
   двадцатиминутную сборку. → Свой CTS, связанный с CTS чата; отмена задачи — отдельное действие.
   Сделано и проверено прямым тестом (`Cancelling_the_turns_own_token_does_not_touch_the_detached_task`).

5. ✅ **Смерть чата не убивает задачи.** Наблюдалось. → Волна 0.1 + 0.2 (без пер-чатного `IShell`
   убивать нечего) + отмена всех CTS реестра в `Dispose`. Сделано.

6. ✅ **Гонка за разговором.** `_conversation` и `Save()` защищены гейтом хода; фоновая задача бежит
   вне его. → Задача **никогда** не трогает `_conversation` — только кладёт в инбокс; читает инбокс
   только тот, кто держит гейт. Сделано по построению — `RunDetachedAsync` не видит `Conversation`
   вовсе, только `host.Inbox`.

7. **Прогресс между ходами не доезжает до окон.** Подписка сегодня пер-ходовая. → Разведано в 0.4 и
   сознательно перенесено: нашлась настоящая ловушка на стороне веб-клиента
   (`chatSessions.ts:297` стирает дерево на каждом `llm.turn.start`) — чинить вместе с `Post` и
   реальным вторым деревом, которое есть с волны 1, но подписку уровня чата ещё не переключали.

8. **Гигантский результат портит контекст.** → Порог + `BlobStore` + сводка (1.4). Не сделано —
   ждёт `Post`-звена, как и планировалось.

9. ✅ **Фон в фоне.** Задача, запускающая задачи, даёт неограниченное ветвление. → Внутри отсоединённой
   задачи флаг `background` не раскрывается вовсе (глубина 1), плюс лимит живых задач на чат.
   **Найдено и закрыто в этом же заходе:** первая реализация `BackgroundStage` эту ловушку не
   закрывала фактически — `AgentSessionScope.Current?.Background` внутри отсоединённого прогона
   резолвился как обычно, и вложенный вызов с `background:true` мог уйти в фон повторно. Починено
   `AsyncLocal<bool> _insideDetachedRun`, тест `Background_depth_is_capped_at_one_a_nested_request_runs_in_place`
   поймал бы регресс (стек переполнялся до фикса — тест-хост падал).

10. **Loop-guard и `task_list`.** Модель, опрашивающая задачи в цикле, попадёт под
    `ToolRepeatTracker`. → Не чинить заранее; понаблюдать (ADR §4.6). Если мешает — исключить
    `task_*` из окна повторов.

11. ✅ **Фон наружу через MCP.** У `McpStdioServer` своё дерево на вызов и нет чата, куда доставлять.
    → Флаг не раскрывается чужой голове; вызов с ним исполняется синхронно. Сделано на двух уровнях:
    схема (`GetToolDefinitionsFor` не вызывает инъекцию) и поведение (`host is null` → синхронно).

12. ✅ **Хосты без инбокса** (CLI `spla chat run`, тесты). → Фон — способность хоста: нет инбокса —
    нет флага в схеме. Проверить, что `SpawnedAgentRunner` при этом не ломается. Сделано:
    `IAgentSession.Background` остаётся `null` для суб-агента (`SpawnedAgentRunner` не передаёт
    `background:` в свой `new AgentSession(...)`), `BackgroundStage` деградирует к синхронному
    вызову.

13. ✅ **`StrictSchema`.** Добавленное в схему поле у строгих инструментов обязано быть в `required`
    либо nullable. → Проверить каждого носителя флага (1.3). Сделано и покрыто тестом
    (`A_strict_schema_tool_lists_background_in_required_the_cwd_pattern`).

14. **Устаревший результат.** → Сводка несёт имя инструмента, усечённые аргументы и прошедшее
    время, чтобы модель могла себя восстановить (ADR §4.5).

15. **Telemetry меряет не то.** `TelemetryStage` — ступень 300, то есть **снаружи** отсоединения:
    span фонового вызова закроется через миллисекунды после старта и покажет длительность запуска,
    а не работы. Учёт токенов и конверсия исключений (800/700) внутри и потому корректны — ошибётся
    ровно телеметрия. → Фоновое звено открывает **свою `Activity`** на отсоединённый прогон,
    связанную с родительским span'ом, и кладёт её в запись реестра. Смежно с
    [`IDEA_20260824-3_core_opentelemetry`](../ideas/IDEA_20260824-3_core_opentelemetry.md).

16. **Два порога обрезки вместо одного.** Соблазн реализовать «большой результат → в блоб» внутри
    доставки. Тогда синхронный вызов, вернувший столько же, окно всё равно убьёт, а поведение двух
    путей разъедется. → Обрезка — POST-звено конвейера, доставка им пользуется (шаг 1.4).

17. **Таймаут не встанет куда попало.** Если звено таймаута окажется снаружи `Fault`, истёкший срок
    останется необработанным исключением вместо результата; если внутри `Accounting` — сорванный
    вызов запишется как вернувший результат. → Ступень между `Fault` (700) и `Accounting` (800).
    Узел прогресса падать не учат: `Fault` отдаст `IsError`, `ProgressNodeStage` это уже читает.
    Бонус для этого плана: звено оказывается внутри отсоединённой цепочки, значит одним и тем же
    кодом стережёт и ход, и фоновую задачу, а реестр получает поле «срок» бесплатно.

18. **Фон и таймаут — два ответа на один вопрос.** Инструмент с коротким дефолтным сроком,
    запущенный в фоне, будет убит на второй минуте «по умолчанию». → Решить, откуда берётся срок:
    у инструмента, у вызова, или у обоих с «побеждает меньшее» — и что дефолт фонового запуска
    отличается от синхронного. Решается вместе с ловушкой 17, не после неё.
