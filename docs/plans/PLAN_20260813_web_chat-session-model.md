## 1. Что было сломано и почему это повторялось

Не отдельные ошибки, а отсутствие механизма. Владельцем чата не был никто:

- `ChatSurface` был пустой обёрткой; `ChatLog`, `Composer`, `StatusBar` независимо читали глобальный
  `store.currentChat` и вручную приклеивали `chatId`/`projectId` к каждой команде — больше десятка
  мест, которые могли разойтись.
- Фильтрация входящих по `env.chatId` была обычаем, а не правилом: в `ChatLog` она стояла в 2
  обработчиках из 14. Поток фонового чата рисовался в видимом логе.
- `msgIndex` был уникален только в пределах хода (`TurnContext.NextIndex` начинался с нуля каждый
  раз), поэтому пузыри двух ходов одного чата делили ключ.
- `_openChats` на соединении только пополнялся — снятия наблюдения не существовало вовсе.
- Состояние живого хода жило в компоненте отображения и уничтожалось `clearAll()` при переключении.
- Признака «идёт ход» не было ни в `chat.opened`, ни в списке чатов — композер угадывал по
  событиям, которые случайно застал.

## 2. Решение в одном абзаце

Один владелец и одна точка разбора. `ChatSurface` владеет идентификатором чата и раздаёт его вниз
через provide/inject вместе с готовым `send`, где идентификаторы уже проставлены. Все чат-событийные
кадры разбирает единственный демультиплексор (`state/chatSessions.ts`) и раскладывает по сессиям —
по одной на чат. Компоненты стали видами над сессией и на сокет не подписываются вовсе.

## 3. Серверная часть

| Что | Где |
|---|---|
| `chat.unwatch` — явное снятие наблюдения, инициатор клиент | `Protocol.cs`, `ChatHandlers.Unwatch` |
| `MarkChatClosed` в сессии соединения | `MessageRouter.IClientSession`, `ClientConnection` |
| Индекс пузыря — на чате, монотонный на всю его жизнь | `ChatRuntime.NextBubbleIndex()` |
| `IsTurnRunning` — правда уровня чата (счётчик, а не гейт: ход в очереди тоже занят) | `ChatRuntime` |
| `TurnActive` в `chat.opened` и в элементе списка чатов | `Payloads.cs`, `RuntimeProjections` |
| Список чатов рассылается на старте и на конце хода — видно, где идёт работа | `ClientConnection.RunTurnAsync` |
| Кэш здоровья подключений сразу после рукопожатия | `ClientConnection.HandleHelloAsync` |
| `ChatRegistry.Peek` — спросить о живом состоянии, не поднимая чат с диска | `ChatRegistry` |

**Почему снятие наблюдения не привязано к `chat.open`.** Чат с идущим ходом должен продолжать
вещать в свою фоновую сессию — ради этого всё и затевалось. Наблюдение прекращает не переключение, а
момент, когда клиент выбросил сессию; знает об этом только клиент, он и говорит.

## 4. Клиентская часть

- **`state/chatSessions.ts`** — сессия на чат и единственный разбор входящих. Событие без
  `chatId` отбрасывается с записью в консоль, а не применяется «к текущему»; исключение одно и
  осознанное — `error` без чата показывается там, куда человек смотрит.
- **`state/chatContext.ts`** — `provide/inject` чата: `chatId`, `session`, `send`. Потребителю негде
  назвать чужой чат.
- **Память.** Голова сессии (флаги, счётчики, черновик, вложения) — на каждый чат; лог — только у
  видимого, у работающих и у пары недавних (`LOG_BUDGET` = 4, на слабом клиенте 2 по
  `navigator.deviceMemory`). Выселение лога шлёт `chat.unwatch`. `WeakRef` сознательно не
  используется: момент сборки не определён, кэш на нём то держит всё, то теряет нужное.
- **`AssistantBubble`** переведён на пропсы (текст живёт в сессии) — поэтому пузырь можно
  размонтировать и вернуть без потерь; markdown по-прежнему рендерится с задержкой 70 мс.
- **Прокрутка** следует за потоком только пока читатель внизу. Ушёл вверх — его не дёргают;
  вернулся — слежение включается само.
- **Черновик и вложения** — в сессии чата, а не общие на приложение.
- **`focus.changed`** больше не применяется в главном окне: это широковещательный кадр, любое окно
  могло увести чужой фокус. Окна, которые действительно следуют за фокусом, подписываются сами.
- **Тесты** (`chatSessions.test.ts`, vitest): перемешанные потоки двух чатов, карточки/уведомления/
  расход по своим чатам, `turnActive` на открытии, запрос разрешения только в своём чате, отброс
  кадра без чата, сохранение фонового ответа, снятие пустого пузыря. Для этого у `SplaClient`
  появился шов `receive(env)` — скормить кадр без сокета.

## 5. Разделение статус-баров

**Проектный/серверный бар** (`ProjectBar.vue`, подвал сайдбара, ширина от 170 px): проект +
переключатель, пользователь, точка связи, сводка здоровья подключений (молчит, пока всё живо),
накопленный расход токенов по проекту, ⚙, debug. Не пересоздаётся при смене чата — «скакать» нечему.
`Identity.vue` растворён в нём.

**Чатовый бар** (`StatusBar.vue`): doubt, режим, модель, `i`, пилюля контекста, активный скилл,
наборы инструментов. Точка здоровья осталась рядом с моделью намеренно: здоровье — свойство
подключения, но модель выбирается на чат, и предупреждение должно стоять там, где делается выбор.

## 6. Что осталось

Решением владельца (2026-08-13) — терпит, делается отдельно.

1. **Живой снимок незавершённого хода в `chat.opened`.** Сейчас передаётся только факт «идёт ход»,
   поэтому F5 посреди ответа (и второе окно, подключившееся к работающему чату) подхватывают с
   текущего места, а не с начала ответа. Это последнее место, где «ушёл и вернулся» ещё не бесшовно.
2. **Отпускать base64 локального эха.** После `user.message` сервер уже знает файл; эхо должно
   переключиться на ссылку `/chat-image/...`, а строку отпустить. Сейчас data URL висит в памяти
   вкладки до перезагрузки — скриншот на 2 МБ занимает ~2.7 МБ впустую.
3. **Тест на выселение логов.** `LOG_BUDGET`, порядок недавности и отправка `chat.unwatch` при
   вытеснении написаны и работают по построению, но не покрыты — а это ровно тот механизм, который
   держит память в рамках. Закрыть, пока свежо.

Рядом, но отдельными ветками:

4. Фильтры `show: me/assistant/tools/reasoning` остаются глобальными (классы на `<body>` +
   localStorage), хотя по смыслу это свойство чата. Владелец: «почти не важно, и визуально они на
   своём месте» — оставлено сознательно.
5. Хранилище для крупного и бинарного — `IDEA_20260813_core_binary-storage`.
