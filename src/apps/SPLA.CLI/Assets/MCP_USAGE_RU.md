# Использование этой сборки SPLA как MCP-сервера

`SPLA.CLI.exe` отдаёт тулы этой сборки внешней MCP-голове (Claude Code, Claude
Desktop или любому другому MCP-клиенту). Этот файл существует, чтобы внешняя
голова не переоткрывала нижеследующее методом проб и ошибок.

## Четыре режима, кратко

Есть ровно четыре способа подключиться. Выбирай по строке, дальше — раздел с
нюансами и примерами.

| # | Режим | Команда | Транспорт со стороны клиента | Writer-лиз? | Когда уместен |
|---|------|---------|------------------------------|----------------|----------|
| 1 | **Join-or-start** (по умолчанию) | `spla mcp` | stdio | Нет — этот процесс только проксирует | Обычный случай: один клиент, один проект, без возни |
| 2 | **Standalone** | `spla mcp --standalone` | stdio | Да — держится всё время соединения | CI-джоба / одноразовая песочница, где это единственное, что трогает проект |
| 3 | **Прямой HTTP** | запущен `spla serve`, клиент смотрит на `POST http://127.0.0.1:<port>/mcp` | HTTP (plain или SSE) | Нет — общий с любыми другими клиентами этого инстанса | Несколько MCP-клиентов на одном проекте одновременно, или клиент, который берёт только URL |
| 4 | **Hub (входная дверь)** | запущен `spla hub`, клиент смотрит на `POST http://127.0.0.1:5077/mcp?project=<name>` | HTTP (plain или SSE) | Нет | Несколько *разных* проектов, один фиксированный адрес, или hub и так уже входная дверь машины |

Кратко про компромиссы:

- **1 (join-or-start)** стоит один лишний прокси-хоп и требует, чтобы
  `SPLA.CLI.exe` был доступен сам себе (чтобы поднять дочерний процесс, если
  никто ещё не обслуживает проект). Взамен никогда никого не блокирует от
  открытия того же проекта.
- **2 (standalone)** — самая простая топология процессов: один процесс, без
  ребёнка, без прокси — но забирает единственный writer-лиз проекта на всё
  время, пока открыт stdio-пайп, так что второй `spla mcp`, окно приложения
  или что угодно ещё, трогающее тот же проект, в это время получает отказ.
- **3 (прямой HTTP)** — это же цель прокси из режима 1, только запущенная
  вручную вместо авто-старта: держишь один долгоживущий `spla serve` и
  направляешь на него всех клиентов, так что они делят один writer вместо
  того, чтобы каждый брал свой. Плата — самому следить за этим процессом и
  его портом.
- **4 (hub)** — это режим 3, обобщённый на все проекты машины: один
  фиксированный адрес, `?project=` выбирает какой именно, и ещё не запущенный
  проект поднимется сам. Плата — нужен запущенный `spla hub`, и проект должен
  быть хоть раз уже открыт (чтобы hub о нём знал).

Если запомнить только одно: **режим 1 — это дефолт, и почти всегда он и
нужен.** За режимом 2 идти только когда осознанно нужен writer-лиз и ничего
больше не трогает проект; за 3 или 4 — только когда с одним и тем же
проектом(-ами) работает больше одного клиента одновременно, либо клиенту
вообще нельзя дать команду для запуска.

## Режим 1 — Join-or-start (по умолчанию)

```
spla mcp
```

У проекта ровно один writer. Постройка свежего `AgentRuntime` — то, что эта
команда раньше делала всегда, — забирает этот writer-лиз на всё время жизни
MCP-соединения, что отказывает окну приложения, REPL или второму `spla mcp`
на том же проекте без другой причины, кроме той, что эта команда настояла на
постройке собственного рантайма. `POST /mcp` на `spla serve` существует
ровно для этого вызывающего: он диспетчерит на рантайм, который хост уже
держит открытым, так что любое число MCP-клиентов может делить его точно так
же, как любое число окон браузера уже делят `/ws`.

Поэтому дефолт таков: найти живой инстанс для этого проекта и проксировать
stdio на его маршрут `/mcp`; если никто ещё не обслуживает проект — запустить
такой инстанс самим — дочерний процесс в петле, с idle-таймаутом, который
тихо переживёт это соединение, пока в нём есть нужда. В любом случае этот
процесс никогда не становится writer'ом.

**Сессия держится открытой сокетом, а не вызовами.** `POST /mcp` без
состояния на каждый запрос, так что клиент, замолчавший между вызовами (не
закончивший, просто выжидающий), иначе позволил бы собственному
idle-таймауту инстанса забрать его из-под сессии. Чтобы этого не случилось,
этот процесс также открывает один обычный WebSocket к инстансу и просто
держит его открытым, пока жив stdio-пайп — лиз считает подключённых клиентов,
так что молчащий сокет всё равно говорит «кто-то здесь есть». Потеря этого
удержания (инстанс за токеном, которого у этого процесса нет, и т.п.)
никогда не фатальна — проксирование всё равно работает, просто теряется
защита от idle-таймаута, и об этом пишется в stderr.

**Что будет, если join-or-start сам не смог взлететь** — не к кому
присоединиться, некуда спавнить ребёнка (нет `SPLA.CLI.exe`/`.dll`,
доступного из `AppContext.BaseDirectory`), ребёнок так и не поднялся: это
автоматически деградирует до режима 2 (standalone), со строкой в stderr об
этом. Сломанный join-or-start, превратившийся в «работает, но забирает
writer-лиз», лучше, чем «вообще не работает».

```
[spla-mcp] project: C:\...\your-project-folder
[spla-mcp] joined instance at http://127.0.0.1:54213 — proxying stdio to POST http://127.0.0.1:54213/mcp
```
(`joined` становится `started`, если никто ещё не обслуживал проект.)

## Режим 2 — Standalone

```
spla mcp --standalone
```

Строит `AgentRuntime` прямо в этом процессе и отдаёт его по stdio на всё
время соединения — без прокси, без дочернего процесса, без другого инстанса.
Это исходное, более простое поведение, и оно всё ещё правильный выбор, когда
это действительно единственное, что будет трогать проект (CI-джоба,
одноразовая песочница): один процесс вместо двух, ценой отказа всем, кто
попробует открыть проект, пока он работает.

```
Project file: C:\...\Your-Project.spla
Project: Your-Project
Workspace: C:\...\your-project-folder
Mode:      Edit
[spla-mcp] project: C:\...\your-project-folder
[spla-mcp] offering 35 tools (standalone)
```

Используй это осознанно, не как дефолт — тянись к нему, когда тебе конкретно
нужен writer-лиз (например, точно знаешь, что ничего больше не тронет этот
проект за время сессии), а не просто потому что на бумаге выглядит проще.

## Режим 3 — Прямой HTTP (`spla serve` + `POST /mcp`)

Если ты уже знаешь, что несколько MCP-клиентов одновременно нужны одному
проекту, или хочешь один адрес соединения, переживающий любого отдельного
клиента, — запусти `spla serve` для этого проекта сам и направь каждый
MCP-клиент на его эндпоинт `POST /mcp`:

```
http://127.0.0.1:<port>/mcp
```

(порт из lock-файла инстанса, из `spla ps`, либо фиксированный, заданный
через `mcp.port` — см. [Конфиг](#конфиг-секция-mcp) ниже). Все запросы к
`/mcp` диспетчерятся на один и тот же рантайм, который `serve` уже держит
открытым — так же, как любое число окон браузера уже делят его `/ws` — так
что несколько голов делят один writer вместо того, чтобы каждая забирала
свой лиз. Join-or-start из режима 1 делает это же за тебя автоматически в
обычном случае; делай это руками только когда хочешь контролировать, какой
именно инстанс поднимется, либо когда твоему MCP-клиенту можно дать только
URL, а не команду для запуска (режим 4 — другой случай, которому тоже нужен
URL).

`/mcp` говорит в одной из двух форм, и какую именно ты получишь — целиком
зависит от отправленного запроса, серверу заранее знать не нужно:

- **Plain** (по умолчанию — без специального заголовка) — одна строка
  JSON-RPC на входе, одна на выходе. Вызов, включивший
  `_meta.progressToken`, всё равно *доходит до конца корректно* (медленный
  тул вроде `ssh_run` или долгий `agent_spawn` не обрывается — запрос просто
  остаётся открытым, пока не закончится), просто пушить промежуточные тики
  некуда, поэтому они отбрасываются.
- **SSE** (отправь заголовок `Accept: text/event-stream`) — «streamable
  HTTP»-транспорт MCP. Соединение остаётся открытым, и каждый фрейм
  пушится в момент появления — progress-уведомления по ходу вызова, затем
  финальный ответ — каждое как свой `data: <json-rpc>\n\n` евент. Это
  настоящий сетевой аналог progress-канала stdio: те же живые тики, просто
  по HTTP вместо пайпа.

  ```bash
  curl -N -X POST http://127.0.0.1:<port>/mcp \
    -H "Content-Type: application/json" -H "Accept: text/event-stream" \
    -d '{"jsonrpc":"2.0","id":1,"method":"tools/call",
         "params":{"name":"ssh_run","arguments":{...},
                    "_meta":{"progressToken":"t1"}}}'
  ```

Итого: stdio (режимы 1/2) и SSE-поверх-`/mcp` (режимы 3/4) — два способа,
которыми внешняя MCP-голова видит живой прогресс. **`/ws` — третья, другая
вещь, и вообще не MCP-транспорт** — это собственный протокол SPLA (ходы
чата, рассылка тулов, вопросы на разрешение), на котором говорят только
собственные клиенты SPLA (веб-UI, Avalonia-приложение). Человек может открыть
проект там и наблюдать чат/ход, пока работает MCP-вызов — это наблюдение с
другой стороны, а не то, на что внешняя MCP-голова может подписаться сама.

## Режим 4 — Hub (входная дверь)

Если на машине запущен `spla hub` (см. документацию самого хаба — вкратце:
один процесс на машину, фиксированный порт `5077` по умолчанию, держит индекс
всех инстансов и может поднять инстанс по запросу), он сам отвечает на
`POST /mcp?project=<name>` и проксирует на тот инстанс, который
действительно обслуживает этот проект — сначала подняв его, если такого нет.
Это вариант для случая, когда MCP-клиенту можно дать только фиксированный
URL, а не команду с рабочей директорией, и у тебя есть — или ожидается — не
один проект: адрес хаба не меняется независимо от того, что сейчас
запущено, и именно `?project=` (а не `cwd`) выбирает, на каком проекте ты
окажешься.

```
http://127.0.0.1:5077/mcp?project=YourProjectName
```

`project` сопоставляется с собственным именем проекта (из его манифеста, то
же имя, под которым его перечисляет окно Projects хаба — кликни по плашке
`MCP` рядом с проектом там, чтобы скопировать этот самый адрес), либо
безусловно работает путь до манифеста. Два разных проекта с одинаковым
отображаемым именем делают имя неоднозначным — хаб отвечает `409` с двумя
кандидатами вместо того, чтобы гадать; в этом случае адресуйся по пути до
манифеста. Проект, о котором хаб вообще ничего не знает (никогда не
открывался, не регистрировался), отвечает `404` — открой его один раз.

**Несколько проектов, несколько клиентов: не полагайся на `cwd`, чтобы не
запутаться.** Если жонглируешь несколькими проектами через режим 1, каждый —
отдельная запись `mcpServers` в конфиге клиента, различимая только тем
ключом, который ты этой записи дал (`cwd` выбирает проект, но именно *имя*
— то, что реально видно в списке тулов клиента) — называй их по имени
проекта, а не общим `"spla"`, иначе список тулов превращается в
неразличимый шум, стоит завести хотя бы три записи. Режим 4 обходит это
целиком: одна запись, один адрес, `?project=` в URL однозначен по
построению.

### Обнаружение проектов: собственный MCP-эндпоинт хаба

Все четыре режима выше предполагают, что ты уже знаешь, какой проект нужен.
`POST http://127.0.0.1:5077/hub/mcp` (тот же хост, что у режима 4, но без
`?project=`) — это другая, более простая вещь: MCP-эндпоинт, на который
отвечает сам хаб, а не проксирует. Он отдаёт один инструмент,
`hub_projects_list`, который возвращает все проекты, известные этой машине —
запущенные и нет, с их состоянием, числом окон и тем, доступен ли у них
сейчас MCP-эндпоинт. Это те же данные, что показывает окно Projects хаба,
только их можно вызвать.

Используй его, когда ещё не знаешь имя проекта для `?project=` в режиме 4:
подключись сначала к `/hub/mcp`, вызови `hub_projects_list`, а дальше либо
переключи этого же клиента на режим 4 с найденным именем, либо открой второе
подключение. Он только для чтения: этот эндпоинт не может ничего запустить
или остановить, только сказать, что есть. Чтобы он вообще отвечал, должен
быть запущен `spla hub` — обычный `spla serve` (режим 1) знает только о
себе и этот маршрут не обслуживает.

## Конфиг: секция `mcp:`

Файл `.spla` проекта (или машинный `defaults.yaml`) может нести:

```yaml
mcp:
  enabled: true   # false = spla serve никогда не маппит POST /mcp вообще
  port: 15077     # фиксированный порт вместо обычного эфемерного
```

Также редактируется из веб-UI SPLA, Settings → MCP. Вступает в силу на
**следующем** старте `spla serve` — Kestrel биндит свой листенер один раз,
при старте, так же как флагу включения плагина нужен рестарт, чтобы
загрузиться. Явный `--port` в командной строке `spla serve` всё равно
побеждает `mcp.port`.

`enabled: false` влияет только на уже запущенный инстанс, до которого ты
достучался (ручной `spla serve` из режима 3, или окно приложения). На
join-or-start режима 1 и на hub режима 4 это не влияет никак: оба
запускают дочерний процесс с принудительно включённым MCP независимо от
настройки проекта, потому что запускать ребёнка с единственной целью —
ответить на этот самый маршрут — и получить отказ именно на нём было бы
просто запутывающим провалом с лишними шагами. Настройка только
останавливает маппинг MCP на инстансе, который ты (или окно) запустили
как-то иначе.

## К чему ты подключаешься

SPLA — не мешок с инструментами. Это агентный рантайм, единица всего в
котором — **проект**: файл `*.spla` плюс его папка. Проект решает, какой
LLM-эндпоинт используется, какие плагины и наборы тулов загружены, в каком
режиме работает агент, какие SSH/SQL/прочие соединения существуют и под
какими учётками, и какие скиллы доступны. Два проекта на одной машине дают
два разных списка тулов и два разных набора достижимых хостов. Это дизайн,
а не ограничение: проект — это граница безопасности и конфигурации.

Что это значит для тебя практически:

- **Читай `tools/list` для каждого соединения.** В наборе тулов ничего не
  фиксировано.
- **Тулы уже сконфигурированы.** `ssh_run` на хост, названный в проекте, не
  требует от тебя учётных данных — их держит проект (см. Секреты). Тебе
  выдают предварительно подключённое окружение, а не голый шелл.
- **Ты можешь предлагать работу на уровне проекта пользователю.** Если
  задаче постоянно не хватает хоста, соединения или процедуры, которых ещё
  нет, — обычно чинится не более хитрым вызовом тула, а тем, что пользователь
  добавляет это в проект (соединение, учётку, скилл). Скажи об этом.

### Запуск вообще без проекта

Режимы 1 и 2 оба нормально переносят ситуацию, когда `*.spla` нигде выше по
дереву не нашёлся: настройки резолвятся в машинные дефолты (синтезированное
LM Studio-соединение, `Mode: Edit`, MCP принудительно включён), и сервер
всё равно работает — просто без специфичных для проекта соединений, тулов
или скиллов. Это законный способ получить базовый набор тулов плюс
`agent_spawn`, когда ещё ничего не сконфигурировано, а не только деградация
про запас. Единственное, за чем стоит следить: без манифеста корень
рабочей области — это просто то, чем на момент запуска оказалась рабочая
директория процесса (`Directory.GetCurrentDirectory()`) — для режимов 1/2 это
`cwd`, заданный для этой записи сервера в твоём MCP-клиенте, а некоторые
клиенты подставляют туда что-то неполезное (например, собственную папку
установки), если не задать его самому. Задавай `cwd` явно в конфиге клиента
той папкой, которую действительно хочешь видеть рабочей областью.

**Не работай молча на дефолтах, считая дело сделанным.** Если из
`tools/list` (или из отказа на вызове) видно, что у тебя нет проекта, нет
сконфигурированного соединения, или используется синтезированный
LM Studio-фолбэк, который никто на самом деле не настраивал — скажи об этом
человеку по ту сторону и спроси, чего он хочет, вместо того чтобы гадать:

- Если он уже знает, чего хочет (конкретную папку проекта, конкретный режим,
  конкретное соединение) — просто спроси, какое именно, и сделай по ответу.
- Если он говорит, что не знает, или не отвечает на вопрос, по которому от
  него ожидалось мнение, — не бросай его в тупике: объясни реальные
  варианты простыми словами. Если вопрос в духе *а как я вообще с тобой
  разговариваю* — укажи на [четыре режима подключения](#четыре-режима-кратко)
  выше. Если вопрос в духе *почему у меня нет тула X* — объясни, что
  соединения/режим/скиллы настраиваются **в проекте** (через UI или CLI
  SPLA, а не через тебя). Дай конкретное следующее действие — «открой UI
  SPLA и добавь соединение» лучше, чем «тебе надо настроить проект».
- Не повторяй этот допрос каждый ход, если пользователь уже один раз ответил
  за эту сессию — спроси, получи решение (пусть даже «просто дефолты, мне
  всё равно») и работай дальше.

### Скиллы

**Скилл** — это процедура, написанная владельцем проекта: курируемый,
повторяемый способ сделать одну работу (`linux-host.capture`,
`network.range-audit`). `skill_find` ищет по каталогу, `skill_activate`
закрепляет скилл за сессией. Когда скилл покрывает работу, использовать
его лучше, чем импровизировать: он кодирует именно то, что владелец на самом
деле хочет получить.

Когда в каталоге ничего не подходит — делай работу напрямую. Но если это
работа, которую пользователь явно будет повторять, предложи написать под неё
скилл — так каталог и растёт, и это предложение, которому владелец обычно
рад.

### Режимы агента (не путать с режимами подключения)

`Chat | Research | Inspect | Edit | Agent` — потолок возможностей, не
характер. Не путай это с четырьмя режимами *подключения* выше: это
собственный потолок разрешений агента, ортогональный тому, как ты
подключился. Он решает, какие тулы вообще видны и какие разрешены.
`Research` — примерно только для чтения; `Edit` и `Agent` могут менять
вещи. Проект задаёт дефолт; `agent_spawn` может выбрать более строгий режим
для конкретного суб-агента.

## Запуск сервера

- `mcp` ДОЛЖЕН быть самым первым аргументом (`args[0]`), точно. Это
  проверяется раньше всего остального, потому что stdout принадлежит
  протоколу JSON-RPC с первого байта — даже обычный баннер `=== SPLA CLI ===`
  для этой команды подавлен и перенаправлен в stderr.
- У `mcp` нет `--project` / позиционного аргумента-пути. Файл проекта
  находится так же, как его находит `chat`: поиском вверх от **текущей
  рабочей директории** файла `*.spla`. **Чтобы открыть конкретный проект,
  задай рабочую директорию запускаемого процесса папкой этого проекта** — не
  передавай путь как аргумент, он будет отвергнут как неизвестная команда.

  Пример конфига MCP-клиента (поправь `command` на реальный путь до exe):
  ```json
  {
    "mcpServers": {
      "spla": {
        "command": "C:\\path\\to\\SPLA.CLI.exe",
        "args": ["mcp"],
        "cwd": "C:\\path\\to\\your-project-folder"
      }
    }
  }
  ```
  Если в формате конфига твоего MCP-клиента нет поля `cwd`, оберни exe в
  маленький `.bat`/`.ps1`, который сначала делает `cd` в папку проекта, а
  затем запускает exe. Если проект в рабочей директории не найден, сервер
  откатывается на дефолтные настройки — см.
  [Запуск вообще без проекта](#запуск-вообще-без-проекта) выше.

- Процесс живёт всю сессию: стартует один раз и дальше обслуживает каждый
  `tools/call` через открытый stdin/stdout-пайп, пока пайп не закроется. Он
  не перезапускается на каждый вызов. Что именно он пишет в stderr при
  старте, зависит от того, какой режим сработал — см. примеры по каждому
  режиму выше.

## Секреты и учётные данные

Всё, что требует учётных данных — SSH-хосты, SQL-соединения, API-эндпоинты —
конфигурируется **в проекте, заранее, через UI или CLI SPLA**. Учётки лежат
в хранилище секретов (на Windows — на DPAPI) и на них ссылаются по имени,
например хост с авторизацией `credential 'secret:user:MiHomo 21.2'`.

Следствия для тебя:

- **Тулов для чтения или записи секретов нет — намеренно.** Ты не можешь
  достать пароль и не должен просить пользователя вставить его тебе.
- **Они тебе не нужны.** Вызови `ssh_run` с именем хоста; учётку резолвит
  сам рантайм. Соединения выглядят уже аутентифицированными.
- **Если что-то не сконфигурировано — это шаг пользователя, не твой.**
  Скажи ему добавить хост/соединение и его учётку в UI (или CLI) SPLA, и как
  его назвать. После этого тулы работают без дальнейшего твоего участия.
- Используй `ssh_list_hosts` (и аналогичный листинг для других типов
  соединений), чтобы увидеть, что уже сконфигурировано, прежде чем считать
  что-то отсутствующим.

## Ограничения безголового режима

У этого режима нет окна, так что ничего нельзя спросить у пользователя
посреди вызова:

- Любой тул, чей вердикт по разрешению — «спросить», вместо этого
  отказывает, с говорящим отказом, на который можно среагировать. Это
  дизайн, не баг — передай его пользователю, а не повторяй попытку: повтор
  не может изменить вердикт.
- `agent_clarify` по той же причине возвращает `no_handler`.
- Поэтому: закладывай контекст заранее. Вызов, который спросил бы уточнение,
  просто проваливается.

## Делегирование работы: agent_spawn

`agent_spawn` запускает **суб-агента** — тот же агентный цикл, изолированная
сессия (своя переписка, своя рабочая память, своя скилл-сессия), те же
тулы — и возвращает только его финальное сообщение.

Две формы:

- **Свободная задача** — просто `input`: `{"input": "На хосте MiHomo 21.2
  сообщи имя ОС и версию ядра. Больше ничего."}`. Скилл не нужен.
- **Закреплённая процедура** — добавь `skill`: суб-агент выполнит именно эту
  одну процедуру и ничего больше.

Используй для работы, чью *середину* тебе видеть не нужно: массовое чтение
файлов, широкий поиск, проверка хостов по одному — всё, что иначе залило бы
твой контекст выводом, который ты в итоге просто суммируешь. `agent_spawn_batch`
делает то же самое сразу для многих задач параллельно (ограниченная
конкурентность, по умолчанию 3).

Две вещи, которые важно не упустить:

- **Суб-агент не видит твою переписку.** Всё, что ему нужно, — в `input`.
- **Проси то, что хочешь получить обратно.** Возвращается только последнее
  сообщение ассистента, так что явно скажи «сообщи X», иначе полезное
  останется в сессии суб-агента.

`mode` задаёт потолок суб-агента и может быть строже твоего — read-only
`Research`-суб-агент для обзорной задачи — хорошая привычка. Спавны вложены
до 3 уровней, дальше отказывают.

## Сборка/поиск exe

- Framework-dependent (нужен установленный .NET/ASP.NET Core рантайм): обычный
  `dotnet build` даёт `src\apps\SPLA.CLI\bin\{Debug|Release}\net10.0\SPLA.CLI.exe`.
- Self-contained single file (рантайм на целевой машине не нужен, именно это
  идёт в зип продукта): `.publish\work\SPLA.CLI.exe`, собирается
  `PublishAll.ps1` либо напрямую через:
  ```
  dotnet publish src\apps\SPLA.CLI\SPLA.CLI.csproj -p:PublishProfile=SingleFile -c Release
  ```
  (путь вывода задан внутри `SingleFile.pubxml`, сейчас
  `.publish\SPLA.CLI\win-x64\` для прямой публикации, `.publish\work\` при
  запуске через `PublishAll.ps1`).

## Увидеть этот файл снова

`SPLA.CLI.exe --help-mcp` печатает английский `MCP_USAGE.md` (он встроен в
exe, а не читается с диска, поэтому работает из любой директории). Этот
русский файл при этом не встроен и `--help-mcp` его никогда не возвращает —
он лежит рядом с `SPLA.CLI.exe` и `MCP_USAGE.md` в зипе продукта просто как
файл для людей.
