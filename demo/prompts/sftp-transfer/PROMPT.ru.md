# Промпт — проверка SFTP-инструментов и контейнеров

[English](PROMPT.en.md) · [Подготовка стенда](SETUP.ru.md)

Скопируй агенту в чат текст между линиями целиком. Имена хостов замени на свои: `my-host` — куда
можно писать (`allow_write: true`), `my-readonly-host` — только чтение, его настройки не трогай, он
нужен именно для проверки отказа.

Многие шаги **должны завершиться ошибкой** — это и есть проверка. Агенту сказано об этом прямо,
иначе он начнёт «чинить» и обходить.

---

Протестируй инструменты передачи файлов: `sftp_ls`, `sftp_download`, `sftp_upload`,
`tar_list`, `tar_read`, `tar_write`. Хост для записи — `my-host`, хост только для чтения —
`my-readonly-host`.

ВАЖНО: примерно половина шагов должна ЗАВЕРШИТЬСЯ ОТКАЗОМ. Отказ там, где он ожидается, —
это успех шага. Не пытайся обойти отказ, не подбирай другие пути, не переходи на ssh_run,
чтобы всё-таки перенести файл. Твоя задача — зафиксировать, что именно ответил инструмент.
По каждому шагу пиши: какой инструмент вызвал, с какими аргументами, что вернулось (текст
ошибки приводи дословно, он и есть результат).

Подготовка (на my-host, через ssh_session_exec в одной живой сессии):
  mkdir -p /tmp/spla_sftp/sub
  echo "upper" > /tmp/spla_sftp/README
  echo "lower" > /tmp/spla_sftp/readme
  echo "colon" > /tmp/spla_sftp/'od:d'
  echo "normal" > /tmp/spla_sftp/app.conf
  echo "deep"   > /tmp/spla_sftp/sub/nested.yml
  ln -sf app.conf /tmp/spla_sftp/link.conf
  ls -la /tmp/spla_sftp

Шаг 1. `sftp_ls` по `/tmp/spla_sftp`, recursive=true.
  Ожидание: успех. Видны файлы, каталог sub, и link.conf помечен как link.

Шаг 2. `sftp_ls` по `~`.
  Ожидание: успех, домашний каталог пользователя.

Шаг 3. `sftp_ls` по `/tmp/spla_sftp/*.conf`.
  Ожидание: ОТКАЗ — путь не может содержать подстановочные знаки, велено использовать 'include'.

Шаг 4. `sftp_download`: remote_path=`/tmp/spla_sftp/app.conf`, local_path=`check/app.conf`.
  Ожидание: успех, один файл.

Шаг 5. `sftp_download`: remote_path=`/tmp/spla_sftp`, local_path=`check/plain`, recursive=true.
  Ожидание: ОТКАЗ. Причина должна назвать конкретную проблему: имена, которые Windows не примет
  (`od:d`), и/или коллизию README против readme, и/или символическую ссылку. Приведи текст целиком.

Шаг 6. То же самое, но local_path=`check/set.tar`.
  Ожидание: успех — контейнер принимает всё, что не приняла папка.

Шаг 7. `tar_list` по `check/set.tar`.
  Ожидание: успех. Проверь, что там ОДНОВРЕМЕННО есть `README` и `readme` (разные файлы),
  есть `od:d`, и что `link.conf` показан как symboliclink с целью `-> app.conf`.
  У записей видны права (mode).

Шаг 8. `tar_read`: path=`check/set.tar`, entry=`tmp/spla_sftp/app.conf`.
  Ожидание: успех, содержимое «normal». Если путь записи другой — возьми точный из шага 7.

Шаг 9. `tar_read` тот же, но output=`blob`.
  Ожидание: успех, вернулся blob:<handle>. Запиши handle.

Шаг 10. `tar_write`: в тот же контейнер, entry=`tmp/spla_sftp/app.conf`,
  content — изменённый текст (например «normal + edited»), mode=`600`.
  Ожидание: успех. Затем `tar_read` этой же записи — содержимое изменилось,
  а `tar_list` показывает, что остальные записи на месте и их число не уменьшилось.

Шаг 11. `tar_write` с delete=true по `tmp/spla_sftp/sub/nested.yml`.
  Ожидание: успех, запись удалена; `tar_list` подтверждает, что удалилась только она.

Шаг 12. `tar_write` с delete=true по несуществующей записи `nope.conf`.
  Ожидание: сообщение, что такой записи нет. Не ошибка-исключение, а внятный ответ.

Шаг 13. `sftp_download`: remote_path=`/`, local_path=`check/everything.tar`, recursive=true.
  Ожидание: ОТКАЗ, причём БЫСТРО и до начала передачи — по любому из лимитов: размер отдельного
  файла, суммарный объём или число записей. Отметь, какой лимит сработал, сколько это заняло по
  ощущениям и появился ли файл everything.tar (не должен).

Шаг 14. `sftp_download` с local_path=`../escape.tar`.
  Ожидание: ОТКАЗ — путь выходит за пределы проекта.

Шаг 15. `sftp_download` с local_path=`C:\Temp\escape.tar`.
  Ожидание: ОТКАЗ — нужен путь относительно проекта.

Шаг 16. `sftp_upload` на хост `my-readonly-host`: remote_path=`/tmp/spla_probe.txt`, content=`x`.
  Ожидание: ОТКАЗ — хост только для чтения, требуется allow_write. Не пытайся записать туда
  другим способом.

Шаг 17. `sftp_upload` на `my-host`: remote_path=`/tmp/spla_sftp/uploaded.conf`,
  content — blob-handle из шага 9.
  Ожидание: успех. Проверь через `sftp_ls`, что файл появился и размер совпадает.

Шаг 18. Повтори шаг 17 без overwrite.
  Ожидание: ОТКАЗ — файл уже существует.

Шаг 19. Повтори с overwrite=true.
  Ожидание: успех.

Уборка: удали /tmp/spla_sftp на my-host.

В конце дай таблицу: шаг | ожидалось (успех/отказ) | что вышло | ok/fail.
Заверши словами «готово» или «не готово».

## Что проверяет каждый шаг

| Шаг | Проверяет |
|---|---|
| 1–2 | листинг, распознавание типов, раскрытие `~` без шелла |
| 3 | отсутствие глоббинга объяснено, а не «файл не найден» |
| 4 | одиночный файл, атомарная запись через `.part` |
| 5 | **предполётная проверка**: недопустимые имена, коллизии по регистру, симлинки — отказ ДО передачи |
| 6–7 | ради чего существует контейнер: те же файлы доезжают целиком, ссылки записаны как ссылки |
| 8–9 | чтение записи; выдача через data-channel мимо контекста |
| 10–12 | дозапись с заменой и удаление (полный перечит архива), остальное не потеряно |
| 13 | лимиты срабатывают до первого байта |
| 14–15 | локальный путь не выходит за проект; абсолютные пути Windows запрещены |
| 16 | SFTP минует read-only guard, поэтому запись гейтится `allow_write` — дверь закрыта |
| 17–19 | загрузка из blob, семантика overwrite |

## На что смотреть в ответах агента

- Тексты отказов должны быть самодостаточны: называть виновника (какой файл, какое имя,
  сколько мегабайт) и подсказывать выход («назови назначение .tar»). Если отказ невнятный —
  это дефект промпта или сообщения, а не поведения.
- После шага 5 в `check/plain` не должно остаться частично скачанных файлов.
- После шага 13 не должно остаться `everything.tar` и `everything.tar.part`.
- Если агент после отказа полез в `ssh_run`/`scp` — дефект промпта плагина, зафиксируй.
